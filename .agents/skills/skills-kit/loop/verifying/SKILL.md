# Verifying

Verifying 是测试/验收闭环编排：理解验收规格，生成或选择测试用例，执行最小可信验收，修复失败，再做最小范围重验并回写结果。

## 完成标准

一次 verifying 完成时，应能回答：

1. 本次验收覆盖哪些验收场景、计划任务、用户路径、接口、命令、数据或配置。
2. 每个验收场景对应哪些测试用例、命令、脚本、浏览器路径、接口调用或人工检查。
3. 哪些用例是已有资产，哪些是本轮生成或补齐，为什么它们足够证明对应验收场景。
4. 执行结果是通过、失败、待确认还是阻塞，并有可复查证据。
5. 失败项是否已定位、修复并完成最小范围重验；已通过项无需重复验收，除非修复影响它。
6. 验收文档、计划文档或测试记录中需要更新的状态已经更新；无法更新时已说明原因。

## 输入优先级

按顺序读取事实来源，缺失则跳到下一项：

1. 用户明确指定的验收文档、测试用例、issue、PRD、设计稿或发布说明。
2. 业务 skill 中的验收/测试流程。
3. `to-acceptance` 生成的 `docs/spec/*-acceptance-*.md`，以场景 ID 作为验收单元。
4. `to-plan` 生成的 `docs/plan/*-plan*.md`，以 TaskList 的「验证用例」列关联验收场景。
5. 项目声明的测试入口：最近的 `AGENTS.md`、README、package/build/test 配置、Makefile、CI 配置、脚本目录、测试目录和运行手册。
6. 当前变更文件、调用链、配置、数据模型、入口点和用户提供的复现步骤。

## 闭环流程

按顺序执行，除非用户明确要求跳过某一段：

1. **理解验收规格**：列出要证明的行为结果、场景 ID、前置条件、可观察断言和不做范围。完成标准：每个进入本轮的场景都有明确断言；缺少事实的场景标为待确认。
2. **生成验收矩阵**：把每个场景映射到最小测试用例或验收动作。完成标准：每个场景都有一条可执行验证路径，或有明确阻塞原因。
3. **补齐测试用例**：复用已有测试；缺少覆盖时，按项目约定生成最小用例。前端优先用户可观察 E2E，后端优先公开接口/契约/服务边界测试。完成标准：新增用例与场景 ID 或行为结果能一一解释。
4. **执行验收**：运行项目声明的最窄命令或最小用户路径；没有现成入口时，构造可重复的轻量验证方式。完成标准：每个执行项有命令、输入、环境和结果证据。
5. **定位并修复失败项**：先判断失败来自代码、测试、数据、环境、权限还是外部依赖；只修复授权范围内的问题。完成标准：每个失败项有根因判断和处理结论。
6. **最小范围重验**：修复后只重验失败项及受修复影响的相邻项。完成标准：相关失败项转为通过，或明确阻塞。
7. **回写并报告**：更新验收文档场景状态、计划 TaskList 验证结果或测试记录；结论前置报告通过/失败/阻塞、证据、残余风险和下一步。

## 验收矩阵

根据场景和改动类型组合验证方式：

| 场景/改动类型          | 优先验证                                                                  |
| ---------------------- | ------------------------------------------------------------------------- |
| 纯文档、配置说明、注释 | 格式/链接/示例命令审阅，必要时运行文档示例                                |
| 库函数、算法、纯逻辑   | 单元测试、fixture、属性/边界用例、类型检查                                |
| CLI、脚本、批处理任务  | fixture 输入输出、退出码、错误路径、幂等性和文件副作用检查                |
| 后端接口、服务逻辑     | 单元/集成测试、HTTP/gRPC 请求、契约校验、鉴权/错误路径、数据读写验证      |
| 数据库 schema 或迁移   | 迁移 dry run、回滚策略、读写兼容性、种子数据或快照验证                    |
| 前端 UI 或交互         | 真实浏览器用户路径、组件测试、无障碍/响应式关键断言、网络请求与页面一致性 |
| 构建、打包、发布配置   | 目标包/服务的构建或打包、产物存在性、入口可启动、配置加载验证             |
| 跨模块或混合改动       | 从最外层用户路径或服务调用路径验证，再补充关键单元/契约检查               |

## 用例生成原则

- 测试用例来自验收场景，不来自实现结构；断言必须指向用户价值、公开接口或业务契约。
- 一个用例验证一个行为结果；同一场景需要多层覆盖时，先保留最能证明行为的外层路径，再补关键单元或契约用例。
- 预期值必须来自验收文档、业务规则、固定样例、接口契约或用户确认；不得用被测实现重新计算预期值。
- 新增用例应靠近项目既有测试资产，并遵循项目命名、目录、工具链和数据准备方式。
- 缺少测试基础设施时，先用可重复验收脚本、命令记录或浏览器路径证明行为，再记录后续补齐正式测试的风险。

## 运行与修复原则

- 不默认使用任何特定工具名、包管理器、构建命令、浏览器插件、日志平台、发布环境或流水线。
- 缺少项目事实时，不猜测命令；先读取项目文档和配置。
- 默认只执行验证命令。自动修复、格式化写入、迁移、发布、清理数据、重启服务等有副作用操作，必须有项目约定或用户授权。
- 出现错误时，保留最小复现：命令、输入、工作目录、环境、错误消息、请求/响应、日志片段、截图或 trace 线索。
- 环境或外部依赖失败不得伪装成代码验收失败；记录依赖、缺口、已尝试动作和需要谁处理。

## 专属流程扩展

verifying 不承载专属流程。以下内容由项目文档或额外 skill 补充：

- 特定前端框架、构建工具、包管理器、浏览器插件或端侧调试工具。
- 特定后端语言、RPC 框架、日志平台、trace 系统、错误码体系或数据库工具。
- 特定公司/团队的发布环境、流水线、审批、灰度、回滚和监控平台。
- 特定业务域的账号、权限、数据准备、验收路径、合规要求和报告模板。

当用户明确要求某个专属流程，且对应 skill 可用时，先读取该 skill，再把它作为本轮验收矩阵的一项。
