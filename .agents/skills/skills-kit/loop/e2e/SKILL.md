# E2E

E2E 是 agent-driven browser testing：用 Markdown 维护 Gherkin 场景、真实浏览器步骤和执行证据，由 agent 像用户一样操作页面完成验收。测试资产是文档，不是测试代码。

## 工作流程

1. 确定当前项目根目录、业务上下文、文档标识和 E2E 文档绝对路径。完成标准：文档目录和文件名来自业务 skill、项目约定或用户确认。
2. 如果 E2E 文档已存在，先读取现有内容并增量更新；反之创建文档。完成标准：既有场景 ID、执行记录和结论未被重排或覆盖。
3. 从用户目标、验收文档、设计稿、现有页面和可访问路由中提取前端用户旅程。完成标准：每条旅程都有明确入口、用户动作、可观察断言和不做范围。
4. 为每条旅程编写 Gherkin 场景，并分配稳定 ID，格式为 `E2E-S1`、`E2E-S2`、`E2E-S3`。完成标准：每个场景只验证一个用户可观察结果，插入新场景不改变既有 ID。
5. 将每个 Gherkin 场景展开成 agent 浏览器步骤。完成标准：步骤能由 agent 在真实浏览器中执行，并包含 URL、账号/数据前置、操作、等待条件、断言和证据要求。
6. 执行或准备执行记录。完成标准：已执行的场景记录浏览器、环境、时间、结果和证据；无法执行的场景记录阻塞原因和所需输入。

## 路径选择

- E2E 文档保存路径不唯一，按每个业务的实际文档组织方式存储。
- 如果当前任务命中业务 skill，先读取业务 skill，并遵循其中的 E2E、验收、文档或测试路径约定。
- 如果用户指定路径或项目已有 E2E 文档目录，优先沿用该路径和命名风格。
- 如果业务 skill、用户输入和项目证据都无法确定目录或文件名，先询问用户。

## Gherkin 规则

- 使用官方标准 Gherkin 关键字：`Feature`、`Rule`、`Background`、`Scenario`、`Scenario Outline`、`Examples`、`Given`、`When`、`Then`、`And`、`But`。
- `Given` 只写用户可理解的前置状态、测试数据和权限；`When` 只写用户动作；`Then` 只写页面可观察结果。
- 断言面向用户可见行为，例如页面文本、控件状态、URL、焦点、表单值、列表内容、图表状态、加载/错误提示、下载结果或截图证据。
- 一个场景只验证一个行为结果；独立结果拆成多个场景。
- 预期值来自需求、验收文档、设计稿、业务规则、固定测试数据或用户确认；缺少事实时写入待确认项。

## 浏览器执行规则

- 像真实用户一样操作浏览器：打开页面、点击、输入、选择、拖拽、滚动、上传、下载、返回、刷新和切换视口。
- 执行前先确认环境、入口 URL、账号、权限、测试数据、浏览器状态和会影响结果的外部依赖。
- 每个步骤都写清等待条件，优先等待用户可观察状态稳定，例如文本出现、按钮可用、URL 改变、请求完成后的页面状态或加载提示消失。
- 证据按场景最小保存：结果摘要、关键截图、URL、可见文本、表单状态、网络/控制台异常摘要或下载文件名。
- 登录、MFA、验证码、付费操作、生产写入、删除数据、发送真实通知等高风险动作先停下确认。

## 文档边界

- 维护 Markdown E2E 文档作为测试资产；需要浏览器操作时由 agent 执行文档中的步骤并回写结果。
- 不创建 Playwright、Cypress、Selenium、Vitest、Jest 或其他基于代码的自动化测试用例；如果项目已有这些框架，本 skill 只引用其结果作为旁证，不新增测试代码。
- 不把“页面能打开”“没有报错”作为唯一断言；断言必须指向用户价值、业务流程或界面契约。
- 不把实现细节、私有函数、组件内部状态或 mock 调用次数写成 E2E 断言。

## E2E 文档模板

- 必须包含 `测试矩阵`、`场景`。
- 其余章节基于上下文按需添加，不限定具体格式和内容。
- 保留 `<!--  -->` Tag;
