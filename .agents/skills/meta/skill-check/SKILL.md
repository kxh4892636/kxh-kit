# skill-check

检查 skill 时，目标是找出会降低可触发性、可迁移性和可维护性的具体问题；清理时只移除已证明无效或无行为差异的内容。不要只按关键词删除；先证明引用、格式或规范问题，再改文件。

## 流程

1. **确定范围**

   找到用户指定的 skill、插件或目录。若用户没有指定范围，优先检查当前插件或当前仓库中与请求相关的 skill 目录。若用户要求“先输出”“等确认再改”，只报告问题和建议，不修改文件。

2. **建立事实清单**

   读取目标目录的实际结构：
   - 当前存在的 skill 文件夹和 `SKILL.md`
   - manifest、update registry、AGENTS.md、plugin 配置和实际存在的 agent 配置等入口文件
   - 目标 skill 正文和直接引用文件中提到的 skill 名、插件名、相对路径、绝对路径、URL、脚本、命令、工具名和 frontmatter 字段
   - 与执行相关的 `references/`、`assets/`、`scripts/`、`tests/`、`evals/` 文件

   用实际文件系统和当前工具列表校验引用。对 URL，只有在任务要求清理 URL 或该链接影响执行时才联网验证；否则标记为外部引用，避免把未验证链接当作坏链。

3. **检查引用格式**

   对 Markdown 链接、图片、内联路径和命令中的路径分别检查：
   - skill 内部资源优先使用相对路径；相对路径必须从包含该引用的文件位置出发能解析到目标；跨目录引用要验证 `../` 层级。
   - 示例占位路径要写成明显模板；不要让普通文件名形式的示例被误当成真实依赖。
   - 链接文本、目标文件和触发条件要一致；不要把已改名 skill、旧目录名或历史迁移说明留作运行指引。
   - 当语义是运行、使用、调用或切换到另一个 skill 时，统一写成 `/skill-name`，并校验名称与目标 skill 的 frontmatter `name` 一致。
   - 工具名和子 agent 类型必须能从当前可用工具或项目入口证明；无法证明时标记为 `uncertain`。

4. **检查 skill 规范**

   需要判断 skill 规范、description、入口长度、渐进式披露、信息层级、重复论述或无行为差异内容时，先使用 `/writing-great-skills`，按它的原则做优化检查。本 skill 只负责路由和问题归类，不重复展开具体写作规则。

5. **编辑**

   最小化修改面。优先清理目标 skill 本身；只有入口文件、manifest、registry 或 AGENTS.md 明确引用了过期对象时才同步更新它们。

6. **验证**

   至少完成以下检查：
   - 确认已删除或已改名对象不再残留在目标范围内。
   - 用文件系统验证修改后的相对路径和直接引用文件仍可解析。
   - 逐项核对所有 skill 调用均使用 `/skill-name`，且调用名与目标 skill 的 frontmatter `name` 一致。
   - 校验 `SKILL.md` frontmatter 只有当前运行环境接受的字段。

## 交付结果

- 删除或替换了哪些失效引用。
- 修正了哪些引用格式问题。
- 发现或修复了哪些 skill 规范问题。
- 哪些引用被确认仍有效。
- 哪些引用因证据不足而保留或需要用户确认。
- 已运行的验证命令和结果。
