# 工作流与交接文档

将当前工作或用户参数拆分成**工作流**(tracer bullet 垂直切片方式), 并确认工作流的边界与依赖.

## 1. 探索工作区(可选)

如果尚未探索工作区, 先了解工作区现状. 探索时读取 `CONTEXT.md`(如存在), 使用领域语言辅助工作流的确认; 同时读取所触及区域的 ADR, 使工作流的确认遵循既有架构决策.

## 2. 确认工作流

运行 `/grilling`, 讨论范围仅限于如何拆分当前工作, 各工作流的具体定义, 拆分工作流后各自讨论.

工作流的拆分使用 **tracer bullet** 垂直切片方式:

- 工作流以一项完整业务能力或用户路径作为边界, 能够独立实现和验证.
- 工作流贯穿业务领域的所有层级(例如编程领域的前端, 后端, 数据库, 测试等), 纵向而非层级的横向切片.
- 工作流的执行需要直接依赖的工作流的完成. 直接依赖为 `无` 的工作流可立即执行.

每个工作流包含但不限于:

- 工作流概述: `{ID}-{TITLE}` + 工作区摘要;
- 与其他工作流的边界和直接依赖(`ID`列表或`无`);

向用户展示完整工作流, 询问用户:

1. 拆分方式是否合适?(拆分粒度/边界/垂直切片)
2. 依赖关系是否正确?
3. 是否有需要继续拆分或合并的工作流?

持续迭代, 直至用户确认.

## 3. 明确工作流定义

运行 `/grilling`, 在步骤 2 基础上额外明确各工作流的具体定义,包含但不限于:

1. 工作流的目标;
2. 工作流的实现路径;
3. 工作流的交付物和完成条件;
4. 工作流的验证方法;

当每个工作流的定义都明确, 不包含模糊或不完整的信息时, 本步骤完成.

## 4. 生成交接文档

为整体工作和每个工作流生成一份**交接文档**,保存到 `docs/workstreams/{WORKSTREAM_NAME}` 目录下.

```
├── docs/workstreams/{WORKSTREAM_NAME}/
│   ├── {WORKSTREAM_NAME}.md  # 整体工作的交接文档
│   ├── {ID1}-{TITLE1}.md    # 工作流1的交接文档
│   └── {ID2}-{TITLE2}.md    # 工作流2的交接文档
```

整体工作的交接文档包含但不限于:

- 整体工作的定义;
- 所有工作流的定义;
- 工作流交接文档的索引;
- 相关产物的路径或 URL(如有).

每份工作流的交接文档包含但不限于:

- 该工作流的定义;
- 建议调用的 skill 及调用时机;
- 所需上下文与相关产物的路径或 URL(如有).

交接文档只携带所需的上下文. 不重复 PRD, spec, ADR, commit, diff 等已有产物, 通过路径或 URL 引用. 尚未确认的细节后续在对应工作流中决定.

当每个工作流仅凭其交接文档及引用即可定位完成工作流所需的全部上下文时, 本步骤完成.

## 状态维护

整体交接文档是所有工作流状态的单一事实来源. 状态项只保留当前快照, 变更历史由 Git 保留.

每个工作流使用以下状态: `pending`, `in_progress`, `blocked`, `completed`.
工作流创建后为 `pending`, 直接依赖全部 `completed` 后进入 `in_progress`; 等待直接依赖时不属于 `blocked`,遇到实际障碍时进入 `blocked`, 解除后恢复为进入阻塞前的状态. 完成条件或验证结论失效时, 从 `completed` 重新进入 `pending`.

当前执行者在每次状态变化后立即更新整体交接文档中的对应状态项, 并记录:

- 当前状态和更新时间;
- 进入 `blocked` 时的阻塞原因, 解除条件和解除后恢复的状态;
- 进入 `completed` 时的交付物与验证证据路径或 URL;
- 从 `completed` 重新进入 `pending` 时的原因.

当整体交接文档中的状态与实际情况一致, 且任一工作流的可执行性, 阻塞解除条件和完成证据均可由该文档及其引用判断时, 本次状态维护完成.

## 约束

- 用户参数优先级高于 skill.
