# E2E

验收通过真实系统边界证明消费者可感知的结果. 它使用一条**证据链**: 验收主张 → 真实路径 → 外部观察 → 结论. 用户输入和工作区约定决定工具, 环境, 数据与证据; 本 skill 只固定证据链与结论门禁.

探索代码库或确定验收资产时, 读取 `CONTEXT.md`(如存在), 使验收资产匹配领域语言; 同时读取所触及区域的 ADR 和 Workflow, 使验收资产遵循既有架构决策和工作流.

## 共同入口

1. **确定验收主张**: 从用户目标, 需求或变更范围识别消费者入口和待证明结果. 完成标准: 每个范围内结果都有外部可观察断言, 矛盾与缺失前置已精确记录.
2. **选择主执行路径**: 优先复用已有验收资产; 任务不要求持久资产时, 直接选择可复现路径. 完成标准: 每个断言都映射到一条可复现的消费者路径.

根据任务目标或调用方门禁进入以下一个或两个分支.

## 可组合分支

### 维护验收资产

验收资产是 agent-driven 的 Markdown 验收文档. 验收场景使用 Gherkin 语言, 场景分配稳定 ID(格式 `S1`); 文档用 `<!-- LOOP KIT ACCEPTANCE START -->` 与 `<!-- LOOP KIT ACCEPTANCE END -->` 标签包裹验收内容. 文档结构与承载字段由用户输入, 工作区既有约定和会话上下文决定.

按以下优先级确定 `<acceptance-dir>`:

1. 用户指定路径.
2. 工作区规范或同类模块已有的验收目录与命名风格.
3. 工作区根目录下的 `tests/acceptance/`.

没有用户或既有命名时, 验收资产使用 `<acceptance-dir>/yyyy-mm-dd-xxx.md`, 日期取创建当天本地日期, `xxx` 使用简短 kebab-case 名称.

完成标准: 每个新增或变更的验收主张都有稳定身份, 消费者入口, 前置, 外部动作, 可观察断言和执行方法. 任务只要求资产时, 记录资产位置和 `not_run`, 此分支即完成.

### 跑真实路径

1. **执行**: 通过消费者可用的浏览器, 协议或 CLI 入口执行, 并观察系统边界上的结果. 完成标准: 每个范围内断言都有实际结果或可定位的阻塞前置.
2. **闭合证据链**: 记录执行范围, 环境与版本置信度, 关键断言, 实际结果, 证据以及结论. 完成标准: 每个范围内验收主张都有且只有一个结论及其证据或阻塞原因, 另一执行者能够复现本次路径.

## 结论门禁

- `passed`: 范围内断言均已实际执行并观察到预期结果.
- `failed`: 必要前置已满足, 真实路径产生了与验收主张矛盾的外部结果.
- `blocked`: 必要前置使真实路径无法到达外部观察点; 记录缺失条件和恢复入口.
- `not_run`: 只表示资产分支已完成, 运行态结论留空.
- 验收特定变更或部署时, 确认运行态承载目标版本; 其他运行态检查如实记录版本置信度.
- 断言与证据和验收主张相称; 证据只保留经过脱敏的必要信息.

## 证据反模式

- **旁路路径**: 决定性动作或主要断言直接操作内部实现. 主动作和主要断言穿过消费者入口; 工作区约定的 setup 只准备数据或前置.
- **代理证据**: 用不对应验收主张的内部信号代替消费者结果. 内部日志, HTTP 200 或截图只有在直接支撑外部可观察断言时才构成证据.
- **孤立证据**: 证据无法关联验收主张, 执行时间, 环境与版本或实际结果. 每份证据都回链到一次执行和一个断言.
