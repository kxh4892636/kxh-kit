# Interface Troubleshooting

用于 E2E 或联调中的接口失败定位。它从消费者证据沿请求链向服务端收敛，判断客户端、服务端、契约、环境、权限、数据和依赖责任边界，并给出最早重验阶段。

## 触发场景

- HTTP/RPC 非成功、超时、取消、CORS、重定向、网关或协议错误。
- 传输成功但业务 code/message、schema 或核心数据异常。
- UI、CLI 或下游消费者结果与接口数据不一致。
- 用户提供 logId、traceId、requestId 或等价关联标识要求排查。

## 完成标准

- 已记录请求上下文：协议、endpoint、method、关键参数、传输状态、业务结果、环境、版本、时间和触发路径。
- 已提取可用的 `logId`、`traceId`、`requestId`、`x-tt-logid`、`x-tt-trace-id`、`x-request-id` 或项目等价字段；缺失时已记录检查位置。
- 已使用项目可用的日志、Tracing、APM 或服务诊断能力收集服务端证据，或精确记录权限、保留期、工具和数据缺口。
- 已给出责任分类、证据强度、授权范围内的处置结果，以及修复后最早需要重验的门禁。

## 请求证据

按执行通道选择浏览器网络面板、HTTP/RPC 客户端、网关日志或项目 CLI，保存：

- endpoint、method、关键 query/body/header；凭证与个人数据脱敏。
- HTTP/RPC 状态、业务 code/message、核心 data/schema 异常。
- 请求开始时间、耗时、环境和待验版本。
- 页面/命令/上游操作路径与消费者可见异常。
- response header、body 或日志中的关联标识。

完成标准：证据足以让另一执行者在同一环境定位同一次请求，或重建等价请求。

## 诊断阶梯

1. **消费者**：检查入口、参数序列化、身份上下文、重试/取消、响应解析和展示/消费逻辑。完成标准：请求实际发送内容与消费者契约已对齐。
2. **协议与网关**：检查路由、域名、TLS/CORS、鉴权、状态码、限流、超时与网关转换。完成标准：已确认请求是否到达目标服务及在哪一跳失败。
3. **服务与依赖**：用关联标识查询日志、Trace、APM、配置和依赖调用。完成标准：失败节点、错误类型和上游/下游传播关系有服务端证据。
4. **数据与环境**：检查租户/角色、测试数据、配置版本、灰度/泳道、缓存和外部依赖。完成标准：环境差异与代码缺陷已区分。

优先使用仓库或组织提供的诊断工具。当前环境存在 `/argos` 或 Argos CLI 时，可通过对应入口提交请求上下文和关联标识；记录诊断摘要与 session ID。使用 BITS 判断部署版本时读取 [pipeline-guard.md](pipeline-guard.md)。

## 责任边界

- **客户端/前端**：参数、路由、身份上下文、状态处理、响应消费或 UI/CLI 输出错误。修复后从受影响单元的本地门禁开始，重验失败接口和消费者结果。
- **服务端/后端**：日志、Trace 或代码证明接口实现、数据处理、依赖调用或配置错误。修复后执行受影响服务门禁，部署目标版本，再重验失败接口及消费者入口。
- **契约**：生产者与消费者对 schema、枚举、错误码、兼容窗口或版本理解不一致。先确定权威契约和兼容策略，再同时验证受影响两侧。
- **环境/权限/数据/依赖**：身份、白名单、配置、测试数据、运行环境或外部系统导致。恢复前置后从最早受影响的运行态步骤重验。
- **证据不足**：关联标识、复现路径、日志权限、版本或 owner 信息不足。记录缺口与获取方式，不把推测写成根因。

## 修复与重验

任务授权代码修改且对应仓库可用时：

1. 按仓库规范做与诊断证据对应的最小修改。完成标准：每个改动都能映射到已确认原因。
2. 执行受影响客户端或服务端的本地门禁。完成标准：所有适用检查通过。
3. 需要运行态证据时按项目发布流程部署；BITS/PPE/BOE 路径读取 [pipeline-guard.md](pipeline-guard.md)。完成标准：目标环境与新版本有可核验映射。
4. 回到触发请求的 E2E 步骤，重验传输状态、业务契约、消费者结果和受影响入口。完成标准：原失败消失，且相邻契约未回归。

提交、push、发布和远程重试分别遵循用户授权与项目流程；只读诊断任务停在证据、根因分类和可执行建议。
