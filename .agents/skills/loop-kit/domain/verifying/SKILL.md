# Verifying

验证使用一条证据门禁链：**影响面 → 本地门禁 → 运行态 → E2E → 诊断 → 最小重验**。先从代码、项目规范和已有证据确定哪些阶段适用，再从最早缺少可信证据的阶段进入。

识别影响面和设计门禁链时，读取 `CONTEXT.md`（如存在），使验证项和报告匹配项目领域语言；同时读取所触及区域的 ADR，使验证范围、门禁和运行路径遵循既有架构决策。

## 门禁链

1. **影响面**：识别受影响的仓库、可部署单元、语言/框架、外部契约、消费者和目标环境，并为每个单元列出适用的检查、测试、构建、部署与 E2E。完成标准：所有变更都映射到验证项；每个不适用阶段都有可核验理由。
2. **本地门禁**：按仓库规范对受影响单元执行格式检查、lint、类型检查、单元/集成/契约测试和构建中的适用项。使用能覆盖影响面的最小命令集合。完成标准：所有适用命令通过；失败已携带命令、退出码和最小错误摘要进入第 5 步。
3. **运行态**：仅在验收需要运行态时准备或确认目标环境。沿用项目发布方式；命中 BITS develop/pipeline 或 PPE/BOE 时读取 [pipeline-guard.md](references/pipeline-guard.md)。完成标准：目标入口可访问，并有 commit、制品、镜像、构建号或等价证据证明运行态承载待验版本。
4. **E2E**：运行态系统调用 `/e2e` 的“跑真实路径”分支，库或无独立运行态的组件执行项目声明的集成/契约消费者路径。完成标准：所有受影响场景都有外部断言、证据和 passed / failed / blocked 结论；失败进入第 5 步。
5. **诊断**：把失败归类为前端/客户端、后端/服务端、契约、环境、身份/权限、数据、依赖或测试资产问题；接口问题读取 [backend-troubleshooting.md](references/backend-troubleshooting.md)。任务授权修改时只修复证据指向的原因；只读验证任务记录原因与建议。完成标准：每个失败都有责任边界、处置结果和最早受影响阶段。
6. **最小重验**：从最早受修复或前置变化影响的阶段重走门禁链。完成标准：所有适用阶段通过，或每个剩余项都有 blocked 证据、缺失条件和恢复入口。

## 入口分支

1. **完整交付**：代码已改动且需要交付结论，或前置阶段缺少可信证据时，从第 1 步执行全部适用门禁。完成标准：每个受影响单元的本地门禁和每条外部路径都有最终结论。
2. **仅本地验证**：用户把范围限定为 lint、类型、测试、构建或本地检查时，只执行第 1、2 步。完成标准：结果明确列出已覆盖项以及未覆盖的运行态与 E2E。
3. **从运行态继续**：本地门禁已有可信通过证据，且用户提供部署任务、环境或版本信息时，从第 3 步进入。完成标准：版本对齐后完成所有适用运行态场景。
4. **仅运行态验收**：目标版本已部署且用户要求走查、联调、截图、接口或真实流程时，从第 4 步进入。完成标准：版本事实、场景断言、证据和失败重验范围完整。

## 过程与证据分支

1. **接口排障**：网络、协议、业务响应或消费者结果异常，或用户提供 trace/request ID 时，读取 [backend-troubleshooting.md](references/backend-troubleshooting.md)。完成标准：请求上下文、关联标识、诊断证据、责任边界和重验入口已记录。
2. **Huatuo 覆盖率**：用户要求 Huatuo 前端增量覆盖率、MR/分支覆盖率或插桩行证据时，读取 [huatuo-coverage.md](references/huatuo-coverage.md)。完成标准：查询口径、整体与文件结果、行级分类和不确定项完整；覆盖率暴露交付失败时回到第 1 步。

## 共同契约

- 仓库规范、构建清单和现有 CI 是验证命令的事实源；先读取版本管理器与工具链声明，再执行对应命令。
- 最小命令集合必须覆盖完整影响面：按文件、包、workspace、服务和消费者依赖选择粒度，并记录未执行项的理由。
- 验证命令保持源码只读；任务授权修复时，将代码改动与失败证据对应后再最小重验。
- 阶段证据包含命令与退出状态、环境与版本、场景 ID、关键断言、日志/trace/request ID 和产物位置。
- 最终报告先给结论，再列适用阶段的 passed / failed / blocked、修复动作、重验范围和剩余风险。
