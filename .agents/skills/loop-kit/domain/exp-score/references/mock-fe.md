# Experience Score Frontend Mock

体验分前端接口 Mock 的矩阵、采集、落盘与校验规则。创建、更新或补充体验分接口响应时应用本文件。

## Mock 矩阵

一个文件只表达一个 `流程 × 接口 × 场景` 坐标。先按 [workspace.md](workspace.md) 定位前端仓库；下文 `docs/mock/...` 均相对于该仓库根目录。

```text
# 回归流程
docs/mock/base/{api-key}/{scenario}.json

# 需求流程
docs/mock/{feature-name}/{api-key}/{scenario}.json
```

- 回归流程维护长期稳定的基线，根目录固定为 `docs/mock/base`。
- 需求流程维护当次需求数据，根目录固定为 `docs/mock/{feature-name}`；`feature-name` 使用小写 kebab-case，优先取用户输入，其次取需求中唯一明确的功能名。`base` 只表示回归流程；名称仍不唯一时，写入前向用户确认。
- `api-key` 默认取请求 URL pathname 的最后一个非空片段，忽略域名、query 和 hash。例如 `/governance/shop/experiencescore/getAnalysisScore?time=30` 对应 `getAnalysisScore`。不同 URL 或 method 得到同一个默认键时，写入前由用户指定互不冲突的键。
- `scenario` 优先使用下表的稳定键；其他场景使用用户明确给出的小写 kebab-case 键，缺失时写入前向用户确认。

| 场景     | 文件名           |
| -------- | ---------------- |
| 正式分   | `formal.json`    |
| 成长分   | `grow.json`      |
| 正式无分 | `formal-no.json` |
| 成长无分 | `grow-no.json`   |

“无分”表示页面处于对应分数体系但尚未出分，不表示接口失败、空响应或抓取异常。

## 流程

### 1. 定位矩阵坐标

从用户输入、需求上下文和目标页面确定：

- 回归流程或需求流程；
- 需求流程的 `feature-name`；
- 端型、平台、商家态、页面和采集窗口；
- 目标接口的 URL 或 `api-key`；
- `formal`、`grow`、`formal-no`、`grow-no` 或用户指定的其他场景键。

采集窗口默认是页面进入阶段；用户指定交互后请求时，将对应操作纳入窗口。需要真实页面数据时，先读取 [e2e-common.md](e2e-common.md) 确定体验分路由和覆盖维度，再调用 `/doudian-login` 准备目标商家态。

完成标准：每个目标响应都能映射到唯一的 `{root}/{api-key}/{scenario}.json`，采集窗口和全部矩阵坐标均由用户输入、需求或页面事实确定。

### 2. 获取响应来源

每个目标响应按来源选择分支：

1. 用户提供响应：读取原始 JSON，以及对应 URL/method 或已确认的 `api-key`，保留来源说明。
2. 真实页面采集：使用可复用当前登录态的浏览器，在导航、刷新或目标交互前开启网络监听，执行已确定的采集窗口并收集 `XHR` 和 `Fetch` 响应。

真实页面默认候选项是体验分业务接口和页面直接消费的业务配置接口。静态资源、监控上报、TCC、登录框架和商家后台壳请求记为排除项；用户指定这些接口时再纳入候选项。

对每个候选请求记录 URL、method、HTTP status、业务 code/message 和响应体。错误场景由用户明确指定；只在该分支把 HTTP 或业务失败响应标记为“保存”。

完成标准：采集窗口内的每个候选请求都已标记为“保存”或“排除”，排除项有可复核理由；每个目标接口均已捕获，或已有明确的缺失原因。

### 3. 按接口与场景归组

从 URL 计算或使用已确认的 `api-key`，再确定响应的唯一矩阵坐标。同一坐标出现多次时：

- 响应一致：去重，只保留一份；
- 响应不同：根据请求参数和页面实际消费结果选择目标响应；仍有多个有效语义时，由用户指定新的场景键后再拆分，避免静默覆盖。

完成标准：每个保存项只有一个目标文件；每个目标文件只表达一个流程中一个接口、一个场景的响应。

### 4. 写入 Mock

- 保存完整 JSON 响应 envelope，包括 `data` 之外的业务状态和顶层字段。
- 使用两空格缩进并保留文件末尾换行。
- 仓库文件仅包含响应体；请求头、Cookie、Token 和浏览器会话信息留在仓库外。
- 响应体包含凭证或个人敏感字段时，先脱敏，并在交付记录中列出字段路径和变换；业务契约所需的普通 ID 和数值保持原类型。
- 更新已有文件前先比较内容，只修改当前矩阵坐标，保留其他接口、场景和用户改动。
- 需求流程只写入对应 feature 根目录；只有用户明确要求沉淀回归时才更新 `base`。

完成标准：所有保存项已写入约定路径，工作区中的 Mock 差异与本次矩阵范围完全一致。

### 5. 校验与交付

使用本机 Node 解析本次新增或修改的每个 JSON，并执行：

1. 校验目录符合回归或需求路径形态，且矩阵坐标唯一；
2. 校验文件名与场景映射一致；
3. 校验保存的是完整响应 envelope，包括来源中存在的业务 code/message 和顶层结构；
4. 将文件与经过相同脱敏变换的来源对象做深比较；
5. 复核仓库文件不含请求头、Cookie、Token 或未记录的个人敏感字段；
6. 运行 `git diff --check`，检查 `git status --short` 和本次文件清单。

交付记录包含流程类型、`feature-name`、平台、页面、商家、接口到文件的映射、重复请求处理、排除项和校验结果。

完成标准：本次目标接口无遗漏，所有文件均可解析，除已记录的脱敏外来源比对无差异，且交付记录能解释每个文件为何存在。
