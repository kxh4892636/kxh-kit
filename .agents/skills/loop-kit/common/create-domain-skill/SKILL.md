# Create Domain Skill

为业务模块创建一份稳定、可重查的领域地图。代码仓库是当前事实源，用户是意图与取舍的事实源；外部资料只引用，不复述。先完成考古，再写 skill。

## 1. 确定边界

确认目标业务模块、所在仓库、skill 名称和交付位置。先读取仓库规则；存在 `DOMAIN.md` 时按其规则读取 `CONTEXT.md` 和相关 ADR。使用已有领域术语与决策，但只引用其事实来源，不在目标 skill 中复述。缺失时继续探索，不把缺失本身变成待办。

列出需要查明的业务能力、入口、消费者和所有适用的全栈层次。层次可包括用户界面、客户端状态与接口、服务端入口、应用与领域逻辑、持久化、异步处理、数据任务、外部系统和运行环境；同时检查鉴权、权限、租户、敏感数据、配置和功能开关等横切边界。所有层次以仓库当前实际存在且可验证的事实为准。

完成标准：目标边界清晰，每个适用层次与横切边界均已纳入调查，未适用部分有仓库事实支撑，尚未落地的目标设计没有混入当前事实。

## 2. 仓库考古

遵循仓库规定的检索优先级，从业务入口沿调用与数据流追踪到最终副作用，再反向确认消费者。优先检索代码、契约、配置、构建与生成规则、测试、运行脚本、可观测资产和交付配置；文档用于提供语义与决策，代码和配置用于核对当前事实。文档中的目标设计只有在仓库中已经落地时才作为当前事实。

系统查明：

- 业务职责、术语、边界和明确不负责的事项；
- 各层的职责、稳定入口、关键抽象与数据所有权；
- 层内依赖、跨层契约、外部依赖及依赖方向；
- 模块特有的鉴权、权限、租户、敏感数据、配置和功能开关边界；
- 一次典型变更从契约或数据模型到消费者的开发顺序、生成步骤和联调节点；
- 本地运行、测试分层、数据准备、替身与真实依赖的使用边界；
- 静态门禁、构建、集成、端到端、运行态和人工验收的适用条件；
- 日志、指标、链路、前端异常、任务状态与数据质量等适用的诊断证据；
- 发布、迁移、兼容、回滚、重跑与故障排查等适用的运行闭环。

对每项结论保留事实来源和置信度。外部资料已有的内容只引用；通用工程规则只路由到持有它的 skill。目标领域 skill 不复制代码片段。路径只有在对定位模块至关重要，且其稳定性由仓库约定、模块边界或工具链支撑时才保留；其余实现位置改用业务术语、符号、契约、配置键或其他检索锚点。

完成标准：每个适用层次都能回答“负责什么、依赖谁、如何变更、如何证明正确”，跨层契约的源头、消费者和同步顺序已经闭合。

## 3. 关闭未知项

把未确认内容分为两类：可由仓库证明的事实继续考古；涉及业务意图、历史原因、权衡或仓库无法证明的内容询问用户。一次只问一个会改变 skill 内容的问题，说明已找到的证据与仍缺少的判断，并等待回答后再继续。

用户答案、外部资料与仓库当前实现冲突时，展示冲突并请求裁决；不复制其中一方作为替代。已经明确的领域术语和架构决策保持原义。

完成标准：影响架构、依赖、开发链路或验证方式的未知项均已由仓库证据或用户确认关闭；其余不确定性已由用户明确接受为待核实项。

## 4. 编写领域 skill

按仓库现有 skill 约定创建允许自动调用的目标 skill。为其编写面向模型的 description，使用稳定的业务术语、模块名称和彼此不同的任务分支作为触发条件；Claude 与 OpenAI 均保持隐式调用允许状态。

主文件是一张简洁的任务路由图：连接业务边界、关键全栈关系与固定约束，把外部资料和通用 skill 作为事实来源引用，并把仅由目标 skill 持有的分支知识放入按关注点组织的 reference。仅在分支确实需要时拆分 reference，使每项含义只有一个事实来源。

控制目标 skill 的规模：`SKILL.md` 与它直接或间接引用的 Markdown 文件合计不超过 21 个，每个 Markdown 文件少于 233 行。接近限制时优先删除重复与失效内容、引用已有事实来源或合并过细的分支；仍无法满足时向用户说明阻塞，不牺牲必要信息。

领域 skill 至少覆盖：

- 业务边界与统一术语的事实来源；
- 全栈架构与端到端数据流；
- 内部、跨层和外部依赖关系；
- 契约、数据模型与生成物的所有权；
- 模块特有且当前存在的横切边界；
- 典型变更的开发、生成、联调与数据准备链路；
- 测试策略与测试替身边界；
- 交付门禁、运行态验证与人工验收；
- 可观测性、发布、迁移、回滚、重跑和排障中实际适用的部分。

把每类典型变更映射为“影响层次 → 开发顺序 → 验证证据”，已有开发或验证资料只引用。对不适用项只在它容易被误判为适用时记录边界。描述稳定职责、关系、顺序、定位线索与判定条件；具体实现始终回到当前仓库检索。

当业务边界、跨层契约、依赖方向、开发链路或验证入口变化时，标明目标 skill 需要重新梳理；普通内部重构不触发整体重建。

完成标准：领域 skill 能让不了解模块的执行者正确定位一次变更的影响面，按依赖顺序开发，并为每项交付主张找到足够的验证证据；目标 skill 在 Claude 与 OpenAI 中均允许自动调用；外部资料没有被复述；内容中没有代码片段或缺少稳定性依据的具体路径；受管 Markdown 不超过 21 个且每个文件最多 232 行。

## 5. 推演与确认

用当前仓库事实构造代表性任务，推演单层变更、跨层契约变更、数据或迁移变更、故障诊断或运行态验证。即使某类任务不适用，也要验证领域 skill 能否给出正确边界。每次推演只检查它能否正确路由、识别影响面、给出开发顺序并找到验证依据，不修改业务代码。

检查目标 skill 在 Claude 与 OpenAI 中均允许自动调用，递归枚举 `SKILL.md` 引用的 Markdown 并检查文件数量与逐文件行数，再检查 frontmatter、内部引用、信息单一来源、格式和仓库适用门禁。随后向用户输出完整草案或清晰的文件清单与全文，标明仍被接受的待核实项，并请求确认。

完成标准：四类任务推演均得到正确路由或明确的不适用边界，用户已经看到可审阅的最终草案。确认前保持草案状态，等待用户反馈后再提交、发布或进入后续实现。
