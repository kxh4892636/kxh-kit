# Verifying

交付验证使用一条**证据链**：交付主张 → 适用门禁 → 实际结果 → 结论。门禁失败时进入**最小循环**：失败 → 证据定位 → 最小修复 → 重验。用户输入、仓库规范、变更影响面和已有证据决定门禁、命令、环境、工具与深度。

## 证据链

1. **明确交付主张**：确定本次要证明的变更、受影响单元、外部契约、消费者和目标环境。完成标准：每项交付主张都映射到待验证的影响面，未知与不在范围内的部分已明确。
2. **选择门禁**：从仓库声明的格式检查、静态检查、测试、构建、运行态确认和消费者路径中，选择足以支撑交付主张的最小集合；已有证据仅在目标、版本、配置和前置仍适用时复用。完成标准：每项门禁都有事实来源、执行入口和通过条件。
3. **执行门禁**：按依赖顺序从最早缺少可信证据的门禁开始；需要消费者可见的运行态证据时调用 `/e2e`。完成标准：每项已选门禁都有实际结果、仍适用的可信证据或明确的阻塞前置。
4. **运行最小循环**：门禁失败后，从最早失败门禁取得足够证据，在任务授权范围内做证据指向的最小修复，再从最早受影响门禁重验；仍失败时以新证据进入下一轮。完成标准：每轮失败、修复和重验一一对应，受影响证据链重新通过或形成明确的 blocked 结论。
5. **闭合结论**：先给交付结论，再记录各门禁的结果、关键证据、未验证范围和剩余风险。完成标准：结论不超出证据覆盖范围，另一执行者能够复现失败或阻塞项。

## 结论门禁

- `passed`：范围内适用门禁均已实际通过，或有仍适用于当前目标的可信通过证据；发生修复时，只使用修复后的重验结果。
- `failed`：必要前置已满足，门禁实际结果与交付主张矛盾。
- `blocked`：必要门禁因无法满足的前置而不能得到结果；记录缺失条件和恢复入口。
- 局部门禁通过只支持对应范围的结论；未验证部分保持显式。
