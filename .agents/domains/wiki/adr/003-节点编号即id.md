# 003-节点编号即id

## 背景

初版每个标题一个自动生成的 id：可写 `{#id}` 显式指定，省略时按标题文本生成 slug。真实标题里 118 个含行内代码、14 个含公式、1 个含链接、13 个超 40 字符，slug 剥完这些只剩不可读的碎片；作者也无法在引用时预测 slug 长什么样。用户明确改为「markdown 标题直接使用，例如 `## 1.2 接口`，数字前缀用于维护标题的唯一性」。

## 决策

标题以数字编号开头，编号就是节点 id：`# 1 根`、`## 1.2 接口`、`### 1.2.1 ...`。引用写作 `[接口](#1.2)`。编号与标题之间空格可有可无（正则 `^(\d+(?:\.\d+)*)\s*(\S.*)$`）。编号只要求同图唯一，不要求连续；标题层级不跳级（H2 不能直接挂 H4）；整块恰好一个 H1。

## 后果

- 作者要自己维护编号，重排编号等于重排所有指向它的 `#编号` 引用——这是这套方案的主要成本。
- 缺编号、编号重复、层级跳级、多个 H1、空标题都在 remark 阶段抛错，坏导图让该篇 MDX 编译失败（`build` 与 `start` 一样），报错带文件路径。
- 不再有 `{#id}`、`{/* #id */}` 与 slug 兜底，解析器少一半分支；旧的 `parse-mindmap.ts` 与 `model.ts` 一起删掉。
- 编号仍是人读的层级顺序，所以图上的左右分侧与「1.1.1 属于 1.1」的直觉一致。

## 备选与弃用理由

- **slug 自动生成**（已实现、已弃）：中文与代码/公式标题产出不可读 id，且引用方无法预判。
- **显式 `{#id}`**（已实现、已弃）：作者要维护两套标识（编号 + id），引用还得先查 id。
- **标题全文做 id**：211 处同文件重复标题、20 个跨文件重名 H1，必然撞车。
