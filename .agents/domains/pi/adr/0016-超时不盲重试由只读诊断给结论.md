# 超时不盲重试：先由只读诊断 worker 给结论

超时后“再派一次”曾是最省事的写法，但同一个坑会被原样再踩一遍：任务太大、方向不对、被外部阻塞、或者只是在等一个人回答——这些都不是重派能解决的，而重派还会把已经做完的工作重做一遍，并给编排方多一轮“它又超时了”的噪声。现在改成：代码先把现场打成证据包，交给一个**只读**诊断 worker 给出 `{cause, evidence, suggestion{adjust, retryMessage}, confidence}`，再按建议决定重派（同一条 note 最多 2 次）、转人工（`needs-human`）还是停手（诊断不可解析）。

## Considered Options

- **代码级盲重试（固定次数）**：实现最省，但没有“为什么卡住”的信息，第二次超时的概率与第一次一样高；对“等人回答”这类任务纯属空转。
- **不重试，直接转人工**：安全但把编排方变成人工轮询；大部分超时其实是可修的（范围太大、测试太长、方向错）。
- **让编排方判断要不要重派**：把诊断成本压回编排方（它没有 `read` / `bash`），还要多一轮对话才能恢复，且与“编排方不执行”的边界冲突。
- **代码组装证据 + 只读诊断 worker + 代码按建议重派（选定）**：诊断只需读现成的事实，重派是机械动作，两者各归其位。

## Consequences

- 诊断 worker 是 `depth 1` 的临时会话：只有只读 `orchestrator_read` 与 `orchestrator_report`，没有写工具、没有 `dispatch`；提示词明确“禁止全盘扫描，只准读证据包里给出的路径”。证据包由代码组装（该 worker 最近 N 条账本事件、最后一次 report、note 状态与正文摘要、会话 jsonl 尾部 M 条、`git status` 摘要、命中判据与阈值），所以诊断不依赖模型自己去找现场。
- 账本事件固定为 `timeout` → `timeout.diagnosed` → `retry.scheduled`（幂等键 `(retryKey, attempt)`）或 `retry.exhausted`（`exhausted` / `needs-human` / `no-diagnosis` / `spawn-failed`）；重派是**新开一代会话**（旧会话已作废），`retryMessage` 必须带上次原因与“不要重复已完成的 X”。
- 诊断不可解析按“不重试”处理：宁可转人工，也不做一次没有依据的重派。
- 代价是一次额外会话（几十秒 + 一次 JSON 输出）。它只发生在超时路径上，而超时本身已经是异常，值得多花这一次。
- 诊断和重试都不改 note 状态：那是 worker 与人的决定，代码只负责留现场与派工。
