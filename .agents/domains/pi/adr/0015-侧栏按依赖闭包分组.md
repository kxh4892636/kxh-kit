# 侧栏的组 = 派工种子 + 双向依赖闭包

侧栏原来按 `registry` 里该组的 `notes` 原样分组，结果“同一批工作”被拆成两块：`45` 在 worker 里跑，依赖它的 `46` 掉进「未分组」，看不出它们是一条链。而“组”本来就是**依赖上不能并行的那一批**，不是派工时恰好点到的那些 id。于是组的成员改成 **种子 ∪ 双向传递闭包**（上游：它依赖的；下游：依赖它的），`completed` 的 note 不再展开（它们由「已完成 N 条 ▸」折叠承载）。

## Considered Options

- **只显示 `registry.notes`（原状）**：与句柄键一一对应，但链上的相邻 note 被拆散，`待开工` / `阻塞` 的上下游看不出因果。
- **只展开上游（依赖）**：能看出“为什么还不能开工”，但看不出“做完会解锁谁”，`46` 仍然掉在未分组。
- **双向闭包（选定）**：一个组就是一条可交付的工作链；代价是不同组的闭包会重叠，需要去重规则。
- **全部 note 平铺、不分组**：信息完整但失去 worker 归属，且 live worker 与历史 note 混在一起。

## Consequences

- 闭包不穿过 `completed`：已完成的 note 既不加进组，也不通过它继续扩（它们的下游早已可开工，不属于这条链的“未完成部分”）；种子本身已完成时仍保留，否则「已完成 N 条」的计数会漏。
- 重叠时同一个 note 只出现在**组键排序最前**的组（组键 = 组内 note id 升序连接），行尾加 `↔` 表示它也在别的组的闭包里；宁可在别处标注，也不要同一 note 在两行重复出现。
- 组内按 id 升序、`执行中` 置顶（多个执行中按 id）：正在动的先看到，其余保持稳定顺序便于对照 note 编号。
- 闭包跟着投影/文档的更新走，并按参与计算的数据签名缓存：签名（组 specs + 每个 note 的 `id|status|blocked_by`）不变就复用上次结果，渲染路径完全不 walk note。
- `未分组` 只剩“没有派工、也不在任何闭包里”的 note；abort / 超时之后组不会凭空消失（种子还在 registry 里）。
