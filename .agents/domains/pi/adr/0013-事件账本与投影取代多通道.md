# ADR-0013 事件账本与投影取代多通道

## 背景

编排方的运行态原先散在六条通道里：report 与超时靠 `pi.sendMessage` 注入模型、ack 靠
`queue_update` 与 `agent_start` 近似推断、`pass` 授权放内存集合、崩溃凭据写 `interrupted.json`、
未送达通知排 `reports-pending.json`、worker 清单只在进程内的句柄表里。每条通道都有自己的一套
失败与重试，谁都不完整；更根本的问题是**运行态靠 worker 自觉改 note 状态**——worker 忘了置
`in_progress`，侧栏就把正在跑的活显示成“待开工”（本 note 开工时正是这样被误读的），而把状态
交给人/模型去同步，延迟与漏改都不可控。模块的可靠性远比模型回合可靠。

## 决策

运行态收口成一本 append-only 事件账本（`<agentDir>/orchestrator/events.jsonl`）加一层投影：
代码在 `agent_start` 写 `input.consumed`（FIFO 标最老一条，精确 ack）、定时器扫投影写
`timeout` 并 abort（不依赖模型回合）、退出写 `worker.exit`；`pass` 落成 `note.pass` 事件
（取代内存 `released`，重启靠重放恢复）；report 只落 `report.filed`，编排方按需调
`orchestrator_state` 拉摘要（读一次写 `state.pulled`，未读跨重启成立）；侧栏订阅投影
（同进程 append 后毫秒级刷新，3s 轮询降为跨进程兜底）。账本按 `snapshot` 轮转压缩，旧行
归档到 `events-<日期>.jsonl`；`notes.json` 结构不变，仍是 Plan 业务真相。

## Considered Options

- **继续修补 outbox 重试**：能救单条通知，救不了“模型被推送”这件事本身，且每条通道仍要各自
  持久化与去重。
- **引入 SQLite**：事务与查询更省事，但多一个原生依赖，pi 插件按 TS 直载、不能带构建产物；
  追加一个 jsonl + 定期压缩已经够小。
- **只加投影、不改注入**：模型仍会被 report 打断，ack 与超时仍要靠回合推进，收益只有一半。

## Consequences

- 事件必须小（摘要 ≤120 字、证据条数与长度上限），长内容留在 note 与会话 jsonl 里；主账本超过
  门槛才压缩，压缩时加文件锁（`open(..., "wx")` 做 lockfile，Windows 上也成立）。
- 单写者优先：同进程共享一份账本与投影；跨进程靠 `fs.watch` + 200ms 轮询 `sync`，两个 pi 实例
  同时压缩时由 lockfile 互斥。
- 模型不再收到任何自动注入；“叫醒”只剩 `orchestrator.wakeOnReport` 一个开关，默认关闭。
- 旧的 `interrupted.json` / `reports-pending.json` 在首启迁移时并入初始 `snapshot` 后删除，
  不做向后兼容。
