# 编排方不在会话启动时自动播报

背景：编排方曾把"哪些 Plan 被打断、在等人、可归档"的检查（下称启动对账）挂在 `session_start` 上，模式生效时注入一条 `orchestrator-reconcile` 消息并带上 `triggerTurn`。进入会话常常只是改代码、或用户已经把模式关掉，而多 Plan 并行时全量通报并不对应用户此刻关心哪个 Plan。

决策：**`session_start` 不播报、不读写崩溃凭据、不花模型轮次**。恢复改为按 Plan 的显式查询：`orchestrator_read` 的 `resume <plan>` 既是"选中"也是恢复包，`/orchestrator status` 是全局视图；`interrupted.json` 只在这两处展示后按条目（resume）或整档（status）清除。

理由：自动播报强制消耗一轮模型与一段上下文，而收益（"知道状态"）可以推迟到用户真的要恢复时再取；状态真相本来就在磁盘上（notes 派生 + 崩溃凭据），随时可查，不需要在会话边界上重复搬运。

## Considered Options

- **保留启动播报，只去掉 `triggerTurn`**：消息仍会挤进上下文，且用户在改代码的会话里要读到与当下无关的全量状态。
- **首次编排动作时播报**：需要定义"首次"并给会话加一份易失状态，等于把播报重新做成隐式副作用。
- **引入 `currentPlan` 状态**：多 Plan 并行时它是易失的第二份真相，"选中"由 `resume <plan>` 这个动作本身已经表达。

## Consequences

- `reconcile.ts` / `formatReconcile` / `ReconcileItem` 一并删除，四类分流不再有第二个消费方；措辞复用 `statusLine` / `planStatusOf`。
- 崩溃凭据的粒度必须支持"只移除一个 Plan 的条目"，否则 `resume` 会顺手丢掉其它 Plan 的中断记录。
- 用户在会话里不查询就看不到崩溃记录；凭据会一直留在 `interrupted.json` 直到被显式查询消费。
