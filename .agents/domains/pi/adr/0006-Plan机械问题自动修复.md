# Plan 的机械问题自动修复

`notes.json` 的校验很严：摘要超长、`updated_at` 缺失、`index` 重复或引用不存在的 note 都会让整个文档不可读，而 `nano_flow_write` 需要先加载文档才能写回，于是「坏文档无法用工具修」——之前 `pi/reference/2026-11-07-pi-toolkit插件合并` 就因摘要超过 144 字在 `nano_flow_read plans` 里报错。用户要求 check 发现的问题自动解决，并把这个约束写进插件。

## Decision

- 新增 `src/nano-flow/repair.ts` 的 `repairDocument()`，只修复可机械判定的问题：
  - note 摘要超过 `noteDescriptionMaxChars`：按 Unicode 码点截断，末尾用 `…`
  - `updated_at` 缺失或为空：补当前 ISO 时间
  - `index`：去重、丢弃不存在的 note id、裁剪到 `indexMaxRows`
- `store.openDocument()` 先严格解析；失败时尝试修复，修复后重新校验并原子写回，返回 `{ document, repairs }`。
- `nano_flow_read` / `nano_flow_write` 用 `openDocument` 读取并静默写回修复；`nano_flow_check` 在 plan/workspace 校验前先跑一遍修复，并在输出顶部列出「已自动修复」项。
- 修复范围只到机械问题；正文超限、缺 evidence、依赖错误/环、Markdown 链接、ADR 数量等语义问题仍由校验报告，工具不做猜测。

## Considered Options

- **保持严格失败、人工修**：坏文档无法经 `nano_flow_write` 修复，且 `notes.json` 被 `tool_call` 收口，正常路径下无法自助恢复；拒绝。
- **自动修复所有校验问题**：截断正文、补 evidence、改依赖、补链接都会编造事实；拒绝。
- **只在 `nano_flow_check` 修复**：`nano_flow_read plans` 仍会被坏 Plan 打断，且写入路径也会失败；改为共享 `openDocument`。
- **只在写入时修复**：读路径仍不可用；拒绝。
- **不落盘、只修内存**：下次读取仍然失败；拒绝。

## Consequences

- 读操作也可能写文件（仅机械修复时），这是有意的取舍。
- 修复只做一次并落盘；后续读写看到的是规范化文档。
- 语义问题仍会失败，且错误信息保留；自动修复的项在 `nano_flow_check` 输出可见。
- 摘要截断会丢失超出部分的文字；原文仍可从 git 历史或旧会话找回。
