# worker 会话落盘与按需恢复

背景：worker 会话原本是 `SessionManager.inMemory`，一次 dispatch 结束后上下文只活在句柄表里，pi 一重启（或换一条组）就从零开始调研；同一组 note 分两次派工，第二次的 worker 不知道第一次得出了什么结论，只能重读一遍。

决策：两种 worker 的会话都落盘成 jsonl，会话 id 由**工作键**（`<plan 目录>::<组>` 或 `temp:<id>`）哈希得到，因此"哪个键对应哪个会话文件"不依赖内存；`orchestrator_dispatch` 命中某个键时按 `live → 磁盘恢复 → 新建` 的顺序取会话，启动时不自动挂回任何 worker。被 `abort` 或超时的会话在状态目录里登记作废：临时 id 再派直接报错（id 本身就是地址），Plan/组的键换成"与作废时刻绑定"的下一代会话 id，旧 jsonl 当历史留在盘上。

理由：worker 花在取证上的上下文是最贵的东西，report 之外的细节（读过哪些文件、否定过哪些方案）不该每轮重来一次；而"按需"而不是"自动"恢复，是为了保住 note 13 的定案 —— 启动不自动播报、不自动跑一轮模型，恢复只发生在编排方明确派工的那一刻。

## Considered Options

- **保持内存会话**：最简单，但重启即失忆、同组重派要重做调研；用户明确否决。
- **全自动恢复**：启动时把所有盘上的 worker 会话都挂回来。否决 —— 启动即产生行为，与 note 13「启动不自动动作」冲突，而且大部分旧会话根本不会再被用到。
- **按需恢复（选定）**：只有 `dispatch` 命中同一个键时才读回磁盘。多一层查找，但恢复时机完全由派工决定。

## Consequences

- 续上的会话带着旧结论：上一次的假设、被否掉的方案、可能过期的文件内容都会一起回到上下文。重启续聊前最好在 note 里写清"哪些结论仍然有效"，这也是为什么 `worker.md` 要求把插话与检查点落盘。
- 磁盘会增长：worker 会话与主会话一样只增不删，位置在 pi 的 sessions 目录（pi 会显示它们，用 `worker:` 前缀命名以便区分）。清理方式就是删对应的 jsonl 文件与状态目录里的 `workers.json` 条目；删了不影响正确性（下次派工按新会话处理）。
- 与"每次干净上下文"的取舍：干净上下文的好处是不会把上一轮的错结论当事实；落盘续聊的好处是不用重做调研。现在把选择权交给编排方 —— 想干净就 `abort` 掉那个键再派（换一代会话），想延续就直接派。
- 临时 worker 变回"普通 pi 会话"：它有了自己的 jsonl、能被同 id 寻址，`temp:<id>` 因此成了一个持久的地址，而不只是进程内的计数器。
