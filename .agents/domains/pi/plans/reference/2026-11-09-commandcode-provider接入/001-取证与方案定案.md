# 001-取证与方案定案

## 交付

一条有证据的接入结论：为什么用扩展而不是静态 `models.json`、每条模型走哪个 `api`/`baseUrl`、凭据为什么能走 `/login`、96 条模型的元数据从哪两处拼出来。

## 取证结果

| 事实 | 证据 |
|---|---|
| 三条端点：`/chat/completions`（OpenAI Chat Completions）、`/responses`（OpenAI Responses）、`/messages`（Anthropic Messages） | [provider 文档](https://commandcode.ai/docs/provider) |
| `GET https://api.commandcode.ai/provider/v1/models` 无需鉴权，200，返回 96 条，字段只有 `id`/`name`/`context_length`/`supported_endpoints`/`created`/`owned_by` | 实测 `curl`（带不带 key 都 200） |
| 端点分布：11 条仅 `/messages`（全部 `claude-*`）、72 条支持 `/chat/completions`+`/responses`、13 条仅 `/chat/completions` | 对同一响应按 `supported_endpoints` 分组统计 |
| pi 内置目录没有 commandcode | `https://pi.dev/api/models/providers/commandcode` → 404；`docs/providers.md` 环境变量表无此项 |
| pi 接 provider 只有三条路：`models.json` 自定义 provider、扩展 `registerProvider(id, ProviderConfig)`、扩展 native `createProvider` | `docs/models.md`「Configure a compatible endpoint」、`docs/custom-provider.md`「Choose the smallest integration」 |
| 没有 `apiKey` 的 provider 会自动获得 API key 登录方式，出现在 `/login` 的 API key 列表，凭据落 `~/.pi/agent/auth.json` | `dist/core/provider-composer.js` 的 `composeApiKeyAuth`：`!inherited && rawKey === undefined && oauth` 才跳过，否则 `login` 提示 `Enter API key` |
| Anthropic 的 baseUrl 由 SDK 追加 `/v1/messages`，OpenAI 追加 `/chat/completions` | `pi-ai/dist/api/anthropic-messages.js` 用 `new Anthropic({ baseURL: model.baseUrl })`；内置 `opencode-go` 的 anthropic 模型 baseUrl 是 `https://opencode.ai/inference/go/anthropic`、openai 模型是 `.../go/openai/v1` |
| 价格可从 `https://commandcode.ai/docs/resources/pricing-limits` 页面内嵌 JSON 取 | 页面含 `{"id":...,"name":...,"category":...,"provider":...,"inputCost":...,"outputCost":...,"cacheReadCost":...,"timeOfDay":{...}}` |
| 价格页的 id 与 `/models` 的 id 不同构，条数也不同（95 vs 96） | 价格页是 `kimi-k3.1-pro`，`/models` 是 `moonshotai/Kimi-K3.1-Pro`；需归一化匹配并核出差的那一条 |
| `legend`/`typesafe/jev` 这类决策模型不在这 96 条里，走 `/v1/systemone` | provider 文档的 System One 段 |

## 决定与理由

1. **扩展形态，不用静态 `models.json`**：用户要全量自动生成；静态清单会随上游漂移（96 条、数千行 JSON），而扩展一次注册就能跟随 `/models`。代价是 pi-toolkit 里多一个模块与单测。
2. **不写 `apiKey`，走 `/login`**：用户明确选 `/login` 的 API key 链路；`composeApiKeyAuth` 保证无 `apiKey` 时仍生成登录提示。
3. **Claude 走 `anthropic-messages` + baseUrl `https://api.commandcode.ai/provider`，其余走 `openai-completions` + `https://api.commandcode.ai/provider/v1`**：由 `supported_endpoints` 决定，baseUrl 差异来自两个 SDK 的路径追加语义。
4. **`/responses` 不接**：72 条支持它，但 `/chat/completions` 覆盖全部 85 条非 Claude 模型，起步只留一套路径，减少 `compat` 面。
5. **provider 不做开关**：开关是工具语义（`tools.*`）；provider 注册不激活工具，未登录只表现为不可用。
6. **元数据缺口先取保守默认**：`reasoning: false`、`input: ["text"]`、`maxTokens` 取上下文窗口的保守比例，再用真机探测覆盖（note 003）。

## 落地结果

六条决定全部在 note 002 落地，并用真实网络验过：注册成功、`apiKey` 为空、目录 96 条（11 条 `anthropic-messages` + 85 条 `openai-completions`）、93 条拿到价格。两处计划外的调整（`pi --list-models` 不能用于核对未登录 provider；目录失败且无快照时改为抛错）记在 note 002 的「实现偏差」。

## 缺口（交给 003）

- `reasoning`/thinking 档位对哪些模型有效、`thinkingLevelMap` 该不该给：只能探测。
- `image` 输入能力：价格页只有 category，名称线索仅 `deepseek-v4-flash-vision-exp`、`nvidia/nemotron-3.5-super-vl`；其余按 text。
- `maxTokens` 上游不给：需用一次超长请求或文档确认，暂取保守值。
- 峰谷价：pi 的 `cost` 是静态值，只取非高峰价，峰时成本会低估。
- 价格页缺的那 1 条模型要以 `/models` 为准补 `cost: 0` 并标注。
