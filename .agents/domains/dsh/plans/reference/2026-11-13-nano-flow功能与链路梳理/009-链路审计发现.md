# 009 链路审计发现

只读审计，不改代码。按严重度排序，标「已复现」的两条在临时目录用随包脚本跑过。

## 必须修

### 1. 一条坏 note 会让 Plan 被标成 completed（已复现）

- 证据：`documents/check-domain.mjs:293-305`。spec 状态由「可读到的 note」派生；`readDocument` 对缺 YAML 头/坏头/name 阻塞项的 note 返回 null，该 note 不进列表。
- 复现：一个 `status: completed` 的 note + 一个没有 YAML 头的 note，跑 check → `fixed: "spec 状态按 note 派生改为 completed"`。面板同时跳过坏 note，显示「全部完成」。
- 影响：有未完成/不可读工作的 Plan 被当成做完，后续轮转 seed、dream、迁移到 reference 都按已完成处理。
- 最小修法：只要有 `NNN-*.md` 未能读成文档，就跳过派生并报「note 无法读取，spec 状态不派生」；派生只在「全部 note 都读到」时执行。补一条测试：坏头 + 全 completed。

### 2. 领域根是工作区外的绝对路径时，校验永远失败（已复现）

- 证据：`documents/lib/base.mjs:87-110` 的写入边界只认 `rootDir`（工作区）；`check-domain.mjs` 用 `--domains` 定位领域根，配置允许绝对路径。
- 复现：工作区 `/tmp/ws` + 领域根 `/tmp/ext`，跑 `check-domain.mjs /tmp/ws --domains /tmp/ext` → 四个 `write` 错误「目标不在工作区内，拒绝写入」，`GUIDE.md`、`CONTEXT-MAP.md`、三个 index 都不生成，退出码 1。
- 影响：该配置下 `nano_flow_create` 能写、`nano_flow_check` 永远红；索引与追踪表全缺。
- 最小修法：写入边界改成「工作区 ∪ 解析后的领域根」，或启动时明确拒绝工作区外的绝对领域根。

## 应修

### 3. create 的 `plan` 参数能把 note 写到领域树之外

- 证据：`planning/create.ts:114-140` 用 `join(plans/<lifecycle>, plan)` 后只判 `existsSync`；`L267` 的 `ensureInside` 只保证文件在那个目录里。
- 触发：`nano_flow_create({kind:"note", domain:"dsh", plan:"../../../tmp"})`，目录存在就写入 `/tmp/001-x.md`。
- 修法：`plan` 只允许单段目录名（无 `/`、非 `.`/`..`），或解析后要求父目录是 `plans/<lifecycle>`。

### 4. 两个进程同时跑校验会踩同一个临时文件

- 证据：`documents/lib/base.mjs:110` 临时文件名固定为 `<file>.tmp`。
- 触发：同一仓库开两个会话（或轮转后的 autoCheck 与手工 check 重叠）同时写同一个 `notes_index.md`：先 rename 的把临时文件拿走，后者报 `写入失败: ENOENT`，或把对方的内容 rename 走。
- 修法：临时名带 pid + 随机后缀（设置存储已经这么做）。

### 5. 每次轮转泄漏一个打开的日志句柄（已修，见 [010](./010-修复轨迹句柄泄漏.md)）

- 证据：`planning/plan-log-service.ts:98` 的 `sessions` 只在 `dispose`（L325）清理；旧会话日志被删后 `state.handle` 仍开着。
- 触发：一个宿主跑 N 次轮转 → N 个 `SessionState` + N 个未关闭读句柄；`presets` 同样只增不减。
- 修法：会话被移除（归档/announceRemoved）时 `close()` 句柄并从 Map 删除；`presets` 同批清理。
- 状态：2026-11-13 已按修法实现，见 [010](./010-修复轨迹句柄泄漏.md)。

### 6. 绑定表两处读改写，并发会丢条目

- 证据：`index.ts:104-117`（覆盖写）、`L403-412`（先 prune 再写）、`pending/rotate` 的 `adoptBinding`（读表写表），没有串行化。
- 触发：轮转过继与其他会话 `nano_flow_bind` 同时发生，后写者用旧快照覆盖 → 另一条绑定消失（面板空、轨迹停写）。
- 修法：绑定表用一条 promise 链串行化（照设置存储的写法）。

### 7. 绑定被删后轨迹还在写

- 证据：`planning/plan-log-service.ts:168` 表里没有该会话时直接 return，`state.binding` 保留。
- 触发：绑定条目被另一进程 prune 掉或文件被改 → 面板（每次重读文件）空白，`log.jsonl` 继续追加。
- 修法：条目消失时清 `binding`/`planDirectory`，停止 append。

### 8. 轮转先建会话再发消息，失败留下孤儿

- 证据：`session/rotate.ts` 的 `replacement()` 先 create + adopt + autoCheck，随后 `original()` 发送；发送失败只回落旧会话。
- 触发：新会话发送失败（内容被宿主拒绝等）→ 新会话与它的绑定都留着；下一条消息再建一个。
- 修法：发送失败时删除/归档新会话并撤掉它的绑定条目，再回落。

### 9. 跨进程 prune 会删掉刚建会话的绑定

- 证据：`index.ts:127-162` 的存活性 = 本进程 `persistence.list()` ∪ 本地 `sessions.get`。
- 触发：两个宿主共用 `DSH_HOME`，A 刚建的会话还没落盘日志；B 里一次 bind 触发 prune → A 的绑定被删。
- 修法：只清「确认已死」的条目（例如已不在磁盘、也不在本地 store），或跳过 `boundAt` 很新的条目。

## 可选优化

11. `dream scan` 每次全量解析 `log.jsonl`（`dream/scan.mjs:66`）：日志只追加，扫描成本随文件增长。当前量级没问题。
