# 009-调研Plan写入现状与惰性化取舍

交付：一份可执行的新写入节奏（何时写 note、何时跑 check、面板可滞后到哪一步），落进固定提示词与 skill，并有 ADR/CONTEXT 口径。验收：新口径下每轮 Plan 写入次数与 check 次数可枚举；轮转后新会话仍能只凭 Plan 恢复。

## 取证：现在有五处要求「及时写」

### 1. 固定提示词 `prompts/system.md`

- **第 23 行**：「索引文件是生成物，不要手改；文档本身用普通文件工具读写。**每轮形成新事实后跑一次 `nano_flow_check`**。」
- **第 117 行**：「**状态先行**：新建 note、变更状态或下一步时，先把文件与 YAML 头（`status`、`reason`、`next_step`）落盘，再补正文；Note 看板只读 YAML 头，这样状态变更能第一时间显示。长正文可以随后分次写完。」
- **第 139 行**（轮转段）：「……**每轮结束前必须把检查点写回磁盘**：spec 的当前进度与恢复入口、note 的状态与 next_step。仅凭 Plan 就能判断目标、理由、进度、证据、缺口和下一步，才算可以安全轮转。」
- **第 157–165 行**（维护循环）：每轮形成新事实（用户输入、取证、决策、执行或验证）后 → 更新领域文档 → 对齐 → 跑 `nano_flow_check`。

### 2. `skills/do`

- 「执行、取证、验证与验收后，**实时更新** spec 与 note 的受影响内容和执行检查点。」
- 「完成后同步受影响的 spec 章节与领域文档，**再跑 `nano_flow_check`**。」
- 「**暂停或切换上下文前**更新检查点，恢复时按 spec 的恢复入口继续。」

### 3. `skills/ask`

- 第 3 步修订：「**把结论就地写入**权威文档（spec、note、CONTEXT、ADR、question）」；用户反馈与处理结论也要落盘。
- 第 4 步收敛：「同步进度与恢复入口**并跑 `nano_flow_check`**」。

### 4. `GUIDE.md`（只由 dream 维护）

- 「会话轮转不挂压缩插件……**每轮结束前把检查点写回 spec 与 note**。」

### 5. 历史来源

「状态先行」是 0.5.24 加的，原话与理由在已归档的 [013-note状态先行约束](../../archived/2026-11-08-nano-flow重构与dsh迁移/013-note状态先行约束.md)：当时提示词只有「每轮新事实后跑 check」，没有要求先落状态，写长 note 时正文与状态一起落盘，看板要等整篇写完才变——所以补了「先写 YAML 头」。这条约束的收益是**面板实时**，成本是**每个状态变更一次写入**。

## 取证：代价在哪里

- **面板数据面**：Note 看板默认折叠，展开后客户端每 5s 轮询 `GET /api/toolkit/nano-flow/notes`；快照只读 note 的 YAML（`status` / `description` / `reason` / `next_step`），不读正文、不读 spec。**只有 YAML 头会影响面板**。
- **每次写入 = 一次工具往返**：本会话所有工具都经 `run_code` 包一层（plan log 里 `tools[].name` 一律是 `run_code`），所以「写一次」的最小成本是一轮工具调用 + 参数 + 结果，不是零。
- **`nano_flow_check` 的成本**：起 node 进程跑 `check-domain.mjs`，扫全工作区 14 个域、20+ Plan，再重写各索引与 spec 追踪表；通过时输出很短，失败时最多列 21 行。它本身不贵，贵的是**频率**。
- **不受影响的写**：`<plan>/log.jsonl` 由宿主在轮末自动追加 compact 轨迹，不消耗 agent 工具调用——轨迹这条数据面本来就是惰性的。

## 取证：惰性化的真实风险

1. **轮转丢检查点**：轮转在「用户发消息」时按上下文压力触发（无手动命令），新会话只拿到 seed（当前 Plan 线索 + 上一轮输出 + 本次输入），**Plan 文件是唯一权威**。若进度只在内存里没落盘，新会话会把已完成的工作当成没做，重复执行。
2. **面板滞后**：面板 5s 轮询，若 YAML 只在轮末更新，一轮之内（可能几分钟、几十次工具调用）面板都停在旧状态。
3. **spec 与 note 漂移**：写正文不写状态或反过来，会让 check 报 spec 状态派生不一致（本会话刚撞到过：note 全 completed、spec 仍 in_progress）。

## 待确认（已向用户提问）

- Q1 写入时机：按交付节点写 / 只在轮末批量写 / 只在轮转与结项前写。
- Q2 `nano_flow_check` 频率：与写入同批 / 每轮一次 / 只在结项与索引必须刷新时跑。
- Q3 面板滞后容忍度：完全接受 / 只有 `blocked` 立即写、其余惰性 / 不接受。

## 第 1 轮

#### Q4 — 写入时机

- 问题：Plan 文件什么时候落盘（现状每个状态变更即写）。
- 前置问题：无。
- 下游边界：决定状态先行的存废、check 频率与面板滞后容忍度。
- 推荐答案及理由：按交付节点写——同一节点内合并成一次批量写。
- 修改意见：用户选「轮次开始可以一次，轮末可以一次」，即每轮最多两次批量写。
- 处理结论：**已确认**。轮首一次（本轮目标/方向落盘）、轮末一次（进度、状态、证据、spec）；中途不写。

#### Q5 — check 频率

- 问题：`nano_flow_check` 什么时候跑（现状每轮形成新事实就跑）。
- 前置问题：Q4。
- 下游边界：每轮工具调用次数、索引与 spec 追踪表的新鲜度。
- 推荐答案及理由：与写入同批、一次为限。
- 修改意见：用户选「与写入同批，一次为限」。
- 处理结论：**已确认**。每次批量写完之后跑一次 check，同一批次不再重跑。

#### Q6 — 面板滞后

- 问题：Note 面板（5s 轮询 YAML）允许滞后到什么程度。
- 前置问题：Q4。
- 下游边界：是否保留「状态先行」、`blocked` 是否即时写。
- 推荐答案及理由：`blocked` 立即写、其余惰性。
- 修改意见：用户选「全部接受，随批量写入更新」。
- 处理结论：**已确认**。面板与索引随批量写更新，一轮之内允许停在旧状态；`blocked` 也在批量写里落盘，不即时写。

## 定案

新的写入节奏（替换现行「状态先行 + 每轮新事实跑 check」）：

1. **每轮最多两次批量写**：轮首一次、轮末一次。一次批量写 = 一个程序里写完全部受影响文件（note 的 YAML 与正文、spec、领域文档），不逐条 edit。
2. **每次批量写后跑一次 `nano_flow_check`**，同一批次不重复跑；本批没有文件改动就不跑。
3. **面板与索引允许在一轮内滞后**，随批量写刷新；取消「状态先行」的强制即时更新。
4. **轮末批量写是硬要求**（轮转随时可能触发）：spec 的进度与恢复入口、note 的 `status`/`reason`/`next_step` 必须在轮末落盘，否则新会话会重复已完成的工作。
5. 例外：用户显式要求「现在就落盘」、或本轮要交接给另一个会话/子 agent 时，当场写。
