# 030-轮转时机与种子内容调整

## 用户输入（2026-11-08，ask 第 2 轮）

1. **删除**「自动轮转把触发它的用户原文用 `<rotation-prior-input>` 包住」的机制。
2. **改自动轮转时机**：不在用户输入时判断，改为**本轮结束后**发现超过阈值就轮转。
3. **携带上一轮输出**：轮转（手动与自动都算）时把最后一轮的模型输出用 XML 标签包住，放在携带骨架的最后。

## 现状取证

- 压力判断在 `sessionController.prompt` 包装的 `queue` 分支；`turn/end` 与 `assistant/message` 的 `data.message.content` 结构已在会话日志实测（plan-log 同源），seed 以 inbox splice 注入、可不带用户输入开一轮。
- 上述取证已落到 031/032 的实现与测试；行号随实现漂移，以代码为准。


## 第 1 轮

#### Q4 — 轮转后新会话是否立即自动跑一轮只读恢复？

- 问题：轮末触发时没有待投递的用户消息；是否照 `/rotate` 现状，建会话后立刻投 seed 触发一轮（会产生一次模型调用与一份只读报告）？
- 前置问题：无
- 下游边界：决定"新会话第一轮由谁发起"，也决定旧会话能否立刻退役。
- 推荐答案及理由：**立即投 seed**（与 `/rotate` 一致）。旧会话删掉后用户下一条消息必须落到新会话，种子先投才能保证新会话有上下文；延迟投递还要额外的"等用户输入再投"机制。
- 修改意见：待评价
- 处理结论：待用户确认

#### Q5 — 退役窗口内落向旧会话的用户输入怎么处理？

- 问题：轮末建新会话到删除旧会话之间（含客户端切换延迟），用户可能刚好发出消息给旧会话。选项：a) 包装 `prompt`，把发往已退役会话的消息转发到新会话；b) 直接删除、接受极小概率丢失/报错；c) 延迟固定时长再删。
- 前置问题：无
- 下游边界：决定是否保留 prompt 包装（即使不再读压力）、以及退役时序。
- 推荐答案及理由：**a 转发**。改时机后"用户消息丢失"是新引入的风险，转发逻辑可复用现有 prompt 包装，成本低；且与 D1 不冲突（转发不标注原文）。
- 修改意见：待评价
- 处理结论：待用户确认

#### Q6 — turn/end 的触发条件

- 问题：是否只在本轮正常结束（`reason.kind === "completed"`）时判断压力；aborted / error 轮是否也判断？
- 前置问题：无
- 下游边界：决定轮转在异常结束时是否发生（异常轮后立刻换会话可能丢掉用户正在看的内容）。
- 推荐答案及理由：**只认 completed**（沿用旧实现口径）；压力口径继续用 `projectedTokens ?? pressureTokens`，与界面百分比一致。
- 修改意见：待评价
- 处理结论：待用户确认

#### Q7 — 「最后一轮模型输出」取哪一段？

- 问题：该轮有多次 `assistant/message`（含 reasoning 与 tool-call 块）。取 a) 该轮**最后一条含文本**的 assistant 消息的 text 块；b) 该轮所有 assistant 文本拼接；c) 连 reasoning 一起？
- 前置问题：无
- 下游边界：决定 XML 块体积与新会话上下文占用；也决定是否复用 `buildTurnRecord` 的 assistant 口径。
- 推荐答案及理由：**a**（最终答复）。轮末的价值是"刚才说了什么结论"，中间步骤已由 `log.jsonl` 留存；reasoning 不进（易泄漏推理痕迹且体积大）。
- 修改意见：待评价
- 处理结论：待用户确认

#### Q8 — 输出块的截断与标签

- 问题：单轮输出可能很长。截断上限用多少、保头还是保尾？标签名用什么？
- 前置问题：Q7
- 下游边界：seed 体积与新会话首轮 prompt 预算。
- 推荐答案及理由：**上限 8192 B（复用 `ASSISTANT_LIMIT`）**，超限保**尾部**并加 `…（前 N 字节已截断）` 标记；标签 `<rotation-last-output>`，前置一行说明"以下 XML 块是轮转前会话最后一轮的模型输出"。
- 修改意见：待评价
- 处理结论：待用户确认

#### Q9 — 块放 seed 的哪个位置

- 问题："放在携带骨架的最后"= 三段骨架之后、自动校验结论之前，还是整个 seed 最末？
- 前置问题：无
- 下游边界：只影响阅读顺序与解析习惯。
- 推荐答案及理由：**整个 seed 最末**（校验结论之后再追加），保证"最后一块就是上文输出"，与用户表述一致。
- 修改意见：待评价
- 处理结论：待用户确认

#### Q10 — 自动轮转的客户端跟随与 plan-log 竞态

- 问题：a) 自动轮转没有 `command/executed`，客户端不会切会话——是否复用现有 notes 5s 轮询顺带读 rotation 并在 `rotation.from === 当前会话` 时切换？b) `plan-log` 也由 `turn/end` 驱动 flush，若退役先删日志，最后一轮轨迹会丢——退役前是否等 flush 完成？
- 前置问题：无
- 下游边界：决定客户端改动面与退役时序；不做 a 用户会留在被删会话视图，不做 b 会丢最后一轮日志。
- 推荐答案及理由：**a 复用轮询切换**（零新路由，最长 5s 延迟，可先接受）；**b 退役前 await 一次 plan-log flush**（或至少固定延迟 ≥ 1s 再删）。
- 修改意见：待评价
- 处理结论：待用户确认

## 第 2 轮（2026-11-08，用户修订）

- 用户反馈：**触发时机不变**（仍是用户输入之后）；手动与自动都在 seed 里携带「该轮最后一条含文本的 assistant 消息的 text 块 + 用户输入」。
- 因此作废的结论：Q4（轮末立即跑一轮）、Q5（退役窗口转发）、Q6（只认 completed）、Q10b（plan-log 竞态）都不再适用——不引入轮末触发，现有 prompt 包装与退役时序保持不变。
- 仍然成立：**删除** `wrapPriorInput` 与 `<rotation-prior-input>` 包装（用户第 1 轮决定，未撤销）。
- Q7 已定：取该轮**最后一条含文本**的 assistant 消息的 text 块。
- Q8/Q9 暂按推荐执行（未收到反对即生效）：上限 8192 B、超限保尾部并标注；标签 `<rotation-last-output>`；块放整个 seed 最末（自动校验结论之后）。
- Q10a 客户端跟随：不在本轮改动范围（自动路径的视图切换维持现状）。

#### Q11 — 「用户输入」指哪一份、怎么投递？

- 问题：三种读法互斥：a) 触发轮转的**本次输入**照旧作为普通 user 消息投递（seed 只新增上一轮输出块）；b) seed 内嵌**上一轮 user + assistant** 问答对，本次输入仍作为普通消息；c) 把本次输入**并进 seed**（prompt 只有 seed）。
- 前置问题：无
- 下游边界：决定 `prompt` 的 content 数组结构、手动 `/rotate` 是否出现"无用户输入"的空缺，以及新会话看到的是"独立 user 消息"还是"被包起来的 user 文本"。
- 推荐答案及理由：**a**。与"触发时机不变"一致；用户原文作为真正的 user 消息更自然，也不违背"删除 XML 包装"。
- 修改意见：待评价
- 处理结论：待用户确认


## 第 3 轮（2026-11-08，用户回答 Q11 + 新决定）

- **Q11 处理结论（已确认）**：「用户输入」= **本次触发轮转的用户原文**。因此新会话的 user 消息由两部分组成：seed 骨架（其中含上一轮 assistant 最终文本的 XML 块）+ 本次用户原文；用户原文作为独立文本块随同投递，**不再套 `<rotation-prior-input>` 包装**。
- **新决定（用户）**：删除手动 `/rotate` 机制，轮转**只能自动触发**。

#### Q12 — 删掉 `/rotate` 后，自动轮转的视图切换怎么办？

- 问题：a) 保留 rotation 路由与客户端跟随，改为**notes 轮询**发现 `rotation.from === 当前会话` 时切换；b) 连路由与跟随一起删，完全依赖宿主 UI 自己切（需 live 验证）；c) 保留 `/rotate` 作为隐藏调试入口（与"只能自动触发"冲突）。
- 前置问题：Q11
- 下游边界：决定客户端改动面；不做 a/b 之一，用户会停留在已被物理删除的会话视图上。
- 推荐答案及理由：**a**。自动路径今天就没有视图切换（`followRotation` 只监听 `command/executed`，note 012 已把它列为残余风险）；删命令后必须补一条自动路径的跟随，复用 5s notes 轮询成本最低。

## 第 4 轮（Q12 确认）

- Q12 处理结论（已确认 a）：删除 `/rotate` 后，客户端**复用轮询**切换——读 rotation 路由，`rotation.from === 当前会话` 时隐藏旧行并 `openSession(to)`。

## 定案（2026-11-08）

- **触发**：不变。`queue` 消息进入时读压力，`used = projectedTokens ?? pressureTokens`，达到 `contextWindow × rotateAt` 即轮转。
- **seed 骨架**：三段文字不变；最末追加 `<rotation-last-output>` 块（上一轮最后一条含文本的 assistant 消息的 text；上限 8192 B，保尾并标注；无输出则省略）。
- **用户原文**：删除 `wrapPriorInput` 与 `<rotation-prior-input>`；本次用户原文作为同一条 user 消息的独立文本块跟随 seed 投递。
- **手动触发**：删除。`/rotate` 命令、`RotationEngine.rotate()`、客户端 `command/executed` 跟随、`system.md` 与文档口径一并清理。
- **视图切换**：客户端轮询 rotation 路由（挂在 Nano Flow 会话已有的 5s 轮询里），自动轮转后切到新会话。
- **不在范围**：轮末触发、旧会话退役时序、plan-log 竞态、模型/推理档位继承（轮转仍只传 cwd + 预设）。
