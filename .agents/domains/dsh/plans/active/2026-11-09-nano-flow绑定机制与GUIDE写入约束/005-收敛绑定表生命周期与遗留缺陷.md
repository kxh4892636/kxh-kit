# 005-收敛绑定表生命周期与遗留缺陷

交付：Plan 生命周期迁移、会话消失、cwd 漂移之后绑定表仍能自洽——R3/R4/R6/R7 各有明确处置（修复或删除）并有测试覆盖。验收：`pnpm -C packages/dsh-toolkit test` 与 `check` 通过，四处改动都能在测试里复现原故障。

## 现状

绑定表是 `$DSH_HOME/toolkit/nano-flow-plan-bindings.json`，结构 `Record<sessionId, { planPath, cwd, boundAt }>`；写入口只有 `nano_flow_bind`（[009](../../../adr/009-Plan绑定只经bind工具.md)）。绑定目录只按 `join(cwd, planPath)` 解析两处：[index.ts:440-442](../../../../../../packages/dsh-toolkit/src/index.ts#L440-L442) 与 [plan-log.ts:312](../../../../../../packages/dsh-toolkit/src/nano-flow/plan-log.ts#L312)。

## R3 生命周期迁移后绑定失效

现象：active → reference/archived 移动目录后 `planPath` 指向不存在的目录。`notesOf` 返回 null（看板空）；而 `appendJsonLine` 先 `mkdir(dirname, {recursive:true})`（[plan-log.ts:254-256](../../../../../../packages/dsh-toolkit/src/nano-flow/plan-log.ts#L254-L256)），于是旧路径被重建、留下孤儿 `log.jsonl`。

处置候选：写入前确认目标 Plan 目录（或其中的 `spec.md`）存在，不存在就跳过本条并 warn，不建目录；看板侧对不存在目录直接返回 null。目录缺失的判断可注入，便于测试。

验收：测试模拟「绑定后把 Plan 目录移走再 flush」，断言旧路径下没有新建 `log.jsonl`、且没有 warn 以外的副作用。

## R4 死条目无回收

现象：会话删除或轮转后条目只增不减；`replaceBinding`（[index.ts:100-113](../../../../../../packages/dsh-toolkit/src/index.ts#L100-L113)）只写不删，全仓没有删除路径。

处置候选：在插件 `dispose`（或 `nano_flow_bind` 收尾）做一次轻量 GC——从会话存储取现存会话 id，删掉表里宿主已不存在的条目；宿主不提供列举能力时跳过、保留条目，不报错。

验收：测试构造「表里 3 条、宿主只认 1 条」，断言 GC 后只剩 1 条；宿主能力缺失时条目原样保留。

## R6 cwd 漂移

现象：`notesOf` 用 `binding.cwd` 解析（[index.ts:442](../../../../../../packages/dsh-toolkit/src/index.ts#L442)），`inheritedPlanDirectory` 却用 `join(workspace, binding.planPath)`（[plan-log.ts:303](../../../../../../packages/dsh-toolkit/src/nano-flow/plan-log.ts#L303)）。绝对 `planPath` 在后者下被拼错；工作区换机器或换目录时前者指向旧 cwd。

处置：抽一个 `resolvePlanDirectory(binding, workspace)`——绝对路径直接用；相对路径优先 `binding.cwd` 且该目录存在，否则退回 `workspace`——两处都改用它。

验收：测试覆盖「绝对 planPath」「binding.cwd 已不存在」「工作区迁移」三种组合。

## R7 遗留启发式

现象：`notesForWorkspace`（[notes.ts:113-125](../../../../../../packages/dsh-toolkit/src/nano-flow/notes.ts#L113-L125)）保留「领域根下恰好一个 active Plan」逻辑，生产代码无调用，只有 `notes.test.ts` 引用。

处置：直接删除函数与对应测试。若之后 dream 或客户端仍需要「未绑定时按唯一 active Plan 显示」，另开 note 走显式入口，不要恢复这条启发式。

## 顺序与依赖

先 R3+R6（共用目录解析），再 R4（独立），最后 R7（删除）。若口径变化影响提示词或 README，同步 `src/nano-flow/prompts/system.md` 与 README。

## 评审

按 `/do` 的 review 环节跑了 Spec 与 Standards 两个 subagent，发现的偏差全部处理：

- 判活口径原本只看持久化列表，会误删「还活着但没落盘日志」的会话 → 已并入活会话判断；
- 补上无 `list`、`list` 抛错、空列表三条分支的用例；
- `rebindSession` 的 prune+replace 两处重复 → 抽成一个本地函数；
- `inheritedPlanDirectory` 的 `exists` 默认值由 `() => true` 改为 `existsSync`，避免调用方漏传时回退失效；
- `listActivePlans` 死导出与测试删除；`makeHarness` 由 166 行拆成三个小于 89 行的函数；
- 段头 `cwd` 口径见上。

## 遗留

- 覆盖率门禁：全局分支仍差约 1 个百分点，主要在 undo/archive 与 `rotate.ts`，与本 note 无关，需要单独一轮补测。
- `appendJsonLine` 内部仍会 `mkdir`，存在「检查存在 → 写入」之间目录被移走的毫秒级竞态；概率极低，未额外加锁。
- R4 的回收只在 `nano_flow_bind` 时触发；从不 bind 的 DSH_HOME 不会自发清理死条目。
