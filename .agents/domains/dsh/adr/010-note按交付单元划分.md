# 010-note按交付单元划分

note 的划分从「一条 note 只跟进一个原子化子任务」改为「一条 note = 一个可独立验收的交付单元」。同一交付单元内的返工、补测、修正与验证并入原 note，不新开；只有验收条件或状态需要分别表达（会单独 `blocked`、单独完成验收）时才拆。

## Context

旧口径写着「一条 note 只跟进一个原子化、独立的子任务」（固定提示词 Plan 段），ask skill 里对应的是「拆成 note 垂直切片」。两者都推着 agent 按子任务拆，于是同一功能的连续修正会变成多条 note：本会话的 Note 面板提示就拆成了两条（007 三字段、008 气泡改回深色）。

用户随后要求「note 尽可能少，相同内容合并」，提出按主题聚合。核对后发现按主题聚合会压掉状态粒度：

- Note 面板只显示 `pending / in_progress / blocked`（`contract.ts` 的 `PANEL_STATUSES`），`completed` 不显示；
- 007（三字段交付，已完成）与 008（改回深色，等你验收）若合并成一条，只能留一个 `status`：`completed` 时整条从面板消失，「还有一项待确认」看不见；`blocked` 时面板显示阻塞，但主体其实已交付。

同时，「少 note 省 token」的前提也不成立：写入成本约等于被改文件的字节数（007 是 8 220 字节，008 是 1 492 字节，合并后每次更新要重写约 9.7 KB），真正省 token 的是每轮最多两次批量写（见 [009-调研Plan写入现状与惰性化取舍](../plans/reference/2026-11-09-nano-flow优化迭代/009-调研Plan写入现状与惰性化取舍.md) 的定案）。单条 note 还有 13 KB 上限，按主题聚合更容易撞上限、被迫再拆。

## Decision

按**可独立验收的交付单元**划分 note。判据是一句话：这条 note 会不会单独进入 `blocked`、或单独完成验收？会则拆，不会则是同一个交付单元。

- 同一交付单元内的返工、补测、修正、验证 → 并入原 note；
- 历史 note 不做合并（保留决策链，供 dream 提炼）；
- 尚未开始的 `pending` note 若粒度明显过碎，可以在动工前合并。

## Considered Options

- **按交付单元（选定）**：状态粒度与面板信号保真，返工不制造新 note。
- **按主题聚合**：目录最整洁，但同一主题下「已完成」与「等验收」无法分别表达，面板失真。
- **保持原子化子任务（旧口径）**：定位最细，但同一交付的正常返工也会新开 note，note 数膨胀。

## Consequences

- 007/008 维持两条：008 的验收状态需要单独可见。
- 固定提示词 Plan 段的「原子化子任务」句与 ask skill 的「垂直切片」段同步改写。
- 需要「按主题合并」时，先问自己会不会单独 blocked；不会才是同一条 note。
- 面板滞后与写入节奏不受本决策影响，见 0.5.45 的批量写定案。
