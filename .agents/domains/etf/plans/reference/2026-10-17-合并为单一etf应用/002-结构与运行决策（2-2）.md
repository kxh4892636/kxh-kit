### 第 4 轮

#### Q10 — 数据库接口与 SQLite 实现解耦

- 问题：数据库访问接口与 SQLite 接入实现如何划分边界，才能在将来替换为 MySQL/PostgreSQL？是否需要再抽象一层跨方言 SQL 接口？
- 前置问题：Q9。
- 下游边界：决定端口位置、SQLite schema/迁移归属、repository 目录结构、组合根装配方式与测试替身策略。
- 推荐答案及理由：以 `MarketRepository` 作为数据库访问接口（初版建议放 `market/service/ports.ts`，Q12 修订为放 `market/repository/market-repository.ts`），SQLite 实现放 `market/repository/sqlite/`，连接与迁移放 `libs/sqlite/database.ts`；换库 = 新增同接口实现 + 在 `server.ts` 替换一处装配，handler/service 不变。不再抽象跨方言 SQL 接口：DDL、schema、迁移与查询语法无法被薄接口隐藏，强行抽象会迫使 repository 使用原生 SQL 并丢失 Drizzle 类型。
- 修改意见：2026-10-17 用户「数据库接口和 sqlite 接入实现进行解耦, sqlite 是对接口的实现, 但是可以任意替换为 mysql pg 等数据库接入代码」。
- 处理结论：已确认；接口归属经 Q12 修订为 repository，写入 spec「实施决策」与 02。

#### Q11 — SQLite 接入库

- 问题：SQLite 接入使用什么库实现？
- 前置问题：Q10。
- 下游边界：决定 `libs/sqlite/database.ts` 的驱动、schema 定义方式、迁移生成工具与依赖项。
- 推荐答案及理由：保持 `better-sqlite3` 13.0.3（驱动）+ `drizzle-orm` 0.45.2（schema/查询）+ `drizzle-kit` 0.31.10（迁移生成）。三者已在 pnpm catalog/锁文件固定并在 Node 24/Windows 实测；同步 API 适合现有同步用例与事务；`better-sqlite3` 13 要求 Node >=22 且随包提供 Windows/Linux/macOS 预编译；已核对 drizzle-orm 0.45.2 的驱动目录，有 `better-sqlite3`、`libsql`、`mysql2`、`node-postgres` 等，没有 `node:sqlite`。
- 修改意见：2026-10-17 用户询问「现在 sqlite 数据库接入你准备使用什么库来实现?」。
- 处理结论：已选择沿用现状；若用户指定其他库，再按替代方案重新确认（`node:sqlite` 需升级 Drizzle，`libsql` 面向远程/边缘）。

### 第 5 轮

#### Q12 — 三层职责与框架依赖边界

- 问题：handler/service/repository 各自承担什么职责？数据库接口归哪一层？service 与 repository 是否允许依赖 Hono？错误类型是否携带 HTTP 状态？
- 前置问题：Q9、Q10。
- 下游边界：决定 `MarketRepository`/`TradingDay`/`MarketError` 的位置与内容、HTTP 映射位置、依赖方向、测试分层与验收时的 import 检查。
- 推荐答案及理由：handler 是控制层，负责 Hono 路由、请求校验与错误映射；service 是业务逻辑层；repository 同时承载数据库接口与具体实现。service/repository 与后端服务框架无关，不导入 Hono/AppType/HTTP 状态；只有 handler（含 `app.ts`/`server.ts` 传输装配与入口）依赖 Hono。因此 `MarketRepository` 与 `TradingDay` 放 `repository/market-repository.ts`，SQLite 实现放 `repository/sqlite/`；`MarketError` 只带业务错误码，HTTP 状态映射放 `handler/errors.ts`。
- 修改意见：2026-10-17 用户「handler 是控制层, service 是业务逻辑层, repository 是数据库接口和具体的实现; service 和 repository 与后端服务框架无关, 只有 handler 依赖后端服务框架, 可以参考 kitex 的思路」。
- 处理结论：已确认；框架边界与错误分层写入 spec「实施决策」与 02，验收以 `service`/`repository` 的 import 检查为准。

### 第 6 轮

#### Q13 — Hono RPC 的大型应用组织与类型优化

- 问题：在保持 Hono RPC 的前提下，如何按官方「Using RPC with larger applications」组织路由与类型，避免拆分后类型丢失或 IDE 变慢？
- 前置问题：Q8、Q12。
- 下游边界：决定 `server/app.ts` 的链式组合方式、`AppType` 的导出形态、全局错误类型、客户端成功类型推断、`.onError`/`.notFound` 写法，以及是否引入 `hcWithType`/project references。
- 推荐答案及理由：`server/app.ts` 用单一链式 `routes` 组合 `CORS → 健康检查 → .route("/api", handler) → onError → notFound`，导出 `AppType = ApplyGlobalResponse<typeof routes, GlobalErrorResponses>`；子应用内部同样链式定义。`shared/api.ts` 提供 `ApiErrorBody`/`ApiErrorStatus`，客户端成功响应用 `InferResponseType<..., 200>`，全局错误按状态收窄；404 用 `c.json(..., 404)`，不用 `c.notFound()`；handler 使用 `async/await`，不返回 `.then()` 链；不创建 RoR 式 `Context` 控制器。单一包只保留一个 Hono 版本、共用 `strict: true` 的 tsconfig。引入 `hcWithType` 作为唯一 `hc<AppType>` 实例化点；TypeScript project references/按子应用拆客户端达到规模阈值再升级。
- 修改意见：2026-10-17 用户「hono 使用 rpc 形式对外暴露接口, 并使用大型应用程序的优化」，并给出 https://hono.dev/docs/guides/rpc#using-rpc-with-larger-applications；随后要求「引入 hcWithType」。
- 处理结论：已确认；已核对 Hono 4.13.7 提供 `ApplyGlobalResponse`，并用 tsc 验证「链式 routes + ApplyGlobalResponse + InferResponseType<..., 200>」与「`hcWithType`（`Parameters<typeof hc>` + type-only `AppType`）」均可编译；写入 spec 与 02。

### 第 7 轮

#### Q14 — 成功与失败统一响应结构

- 问题：服务端成功与报错如何共用一套响应结构？`code` 用业务码还是 HTTP 状态，`data`/`message`/`extra` 各承载什么？
- 前置问题：Q8、Q12、Q13。
- 下游边界：决定 `shared/api.ts` 契约、成功 handler 的包装、错误映射、`ApplyGlobalResponse` 的错误类型、前端解包逻辑与测试断言。
- 推荐答案及理由：统一为 `ApiResponse<T> { code: number; message: string; extra: Record<string, any>; data: T }`。成功 `code = 0`、`data = T`、`message = "ok"`、`extra = {}`；失败 `code` 为数字业务码（1001 invalid_argument、1002 not_found、1003 canceled、1004 internal、1005 upstream_unavailable、1006 deadline_exceeded、1007 route_not_found）、`data = null`、`message` 为安全描述，`extra` 为结构化细节（默认 `{}`）。HTTP 状态继续表达传输语义并由 Hono 单独返回，与业务码分离；`shared/api.ts` 提供 `apiCode`、`apiOk`、`apiFail`。前端检查 `response.ok` 与 `body.code === apiCode.ok` 后解包 `data`；全局错误类型用 `ApiResponse<null>`，成功类型取 `InferResponseType<..., 200>["data"]`。
- 修改意见：2026-10-17 用户「服务端成功返回和报错都使用一个接口 code data message extra」，随后明确「code 是 number，message 是 string，extra 是 Record<string,any>，data 是响应数据，code 是业务 code，HTTP 状态码由服务器框架自身返回」。
- 处理结论：已确认；`code` 使用数字业务码（0 成功，1001–1007 错误，1007 表示未匹配路由），HTTP 状态由 Hono 单独返回；`MarketError` 的域内字符串码在 handler 映射到业务码与 HTTP 状态。码表集中在 `shared/api.ts`，可在首次发布前调整编号。
