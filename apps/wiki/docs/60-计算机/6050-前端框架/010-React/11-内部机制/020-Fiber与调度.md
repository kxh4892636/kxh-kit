# Fiber 与调度模型

## Fiber 模型如何帮助理解可调度渲染？

- 工作记录: 可以把 Fiber 理解为 React 为组件和宿主节点组织渲染工作与状态关联的内部记录，不是用户手写的 JSX 元素本身;
- 关联结构: 工作单元之间保留父子与相邻关系，使 React 可以组织遍历和后续工作，而不只依赖一次不可拆分的函数递归;
- 抽象边界: 具体字段与数据布局属于实现细节，应用不应读取或修改它们来完成状态更新;

## 可中断渲染为什么不等于并行执行组件？

- 让出执行: React 可以在适当工作边界让位于紧急更新，再恢复或重做较低优先级工作;
- 主线程限制: 一段耗时很长的组件函数或普通 JavaScript 调用仍会阻塞，Transition 不会自动把它移到 Worker;
- 重做条件: 新输入可能使先前后台计算失效，因此渲染必须纯粹，不能因为已经执行过部分函数就认为它们会提交;

```text
后台结果渲染 ──遇到紧急输入──> 处理输入
      │                         │
      └──── 继续或重新计算 <─────┘
                 ↓
             提交完成结果
```

## current 与 work-in-progress 如何表达两份视图？

- 当前结果: current 可用于理解已提交、用户正在看到的状态关联;
- 工作结果: work-in-progress 表达正在准备的新结果，只有成功提交才成为当前界面;
- 外部一致性: 不应把工作中的可变内容提前泄漏给事件或 DOM，ref 渲染写入问题正与此有关;

## 应用怎样表达更新优先级？

- 公共接口: 用正常状态更新保持输入即时响应，用 Transition 或延迟值表达可让位的工作;
- 不猜内部调度: 不依赖“浏览器空闲时一定执行”或具体内部优先级数字，实际完成时机受工作量和后续更新影响;
- 性能路径: 昂贵同步计算需要拆分、缓存或移到合适执行环境，不能只改变优先级标签;
