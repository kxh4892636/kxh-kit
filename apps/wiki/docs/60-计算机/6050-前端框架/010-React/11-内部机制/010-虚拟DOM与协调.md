# UI 描述与协调

## 虚拟 DOM 这个词通常在描述什么？

- UI 描述: 组件计算出的元素描述表达类型、输入与子结构，React 据此决定宿主环境应该呈现什么;
- 概念区别: React 元素、Fiber 工作记录与浏览器 DOM 节点是不同层次，不把它们统称为同一种对象;
- 使用价值: 理解“先描述结果，再交给框架更新”即可指导大部分应用代码，无需手工维护第二棵 DOM;

## 协调怎样把新描述与旧界面关联？

- 关联工作: React 根据新输出与已有树判断哪些组件和节点可继续使用、哪些需要插入或移除;
- 阶段归属: 这属于渲染计算的一部分，DOM 修改发生在提交阶段，不额外虚构一个位于 render 与 commit 之间的公开生命周期;
- 代价边界: React 使用有约束的匹配策略，不能把“减少必要 DOM 修改”理解成保证数学上的全局最优树编辑序列;

```text
组件输入 → 元素描述
             ↓
       匹配已有组件身份
             ↓
        提交宿主变更
```

## 类型与 key 为什么比对象内容相似更重要？

- 身份规则: 位置、类型与 key 决定哪些 state 可以沿用，详细条件统一见保留与重置 state;
- 数据相似: 两个条目内容一样不代表它们是同一业务实体，两个对象引用不同也不必意味着 DOM 全部替换;
- 列表设计: 让 key 对应实体身份，比试图干预内部比较过程更可靠;

## 为什么重新执行组件不等于页面全部刷新？

- 计算与提交: 组件可以重新计算相同输出，最终不产生 DOM 差异，完整阶段模型见渲染与提交;
- 性能判断: 需要区分计算耗时与 DOM、布局、绘制成本，再决定优化哪一步;
- 实现边界: 不依赖内部比较次数或数据结构维持业务正确性，把正确状态转换交给公共接口;
