# ACID、BASE、CAP 与 PACELC

ACID 和 BASE 保证的对象是什么? CAP 为什么不是“任意选两个”? 网络正常时 PACELC 又要求什么权衡? 怎样把抽象定理转成数据库选择问题?

## ACID

- 原子性（Atomicity）: 事务内操作全部成功或全部回滚;
- 一致性（Consistency）: 事务把数据库从一个满足约束的状态带到另一个满足约束的状态;
- 隔离性（Isolation）: 并发事务的可见效果受控，使其像按某种顺序执行;
- 持久性（Durability）: 已提交结果在系统故障后仍能恢复;
- 适用: 余额、库存、权限等不能接受中间状态或丢失提交的业务事实;

## BASE

- 基本可用（Basic Availability）: 系统大部分时间可响应，即使能力或结果可能降级;
- 软状态（Soft State）: 副本不要求每时每刻同步一致，状态可随异步传播改变;
- 最终一致（Eventual Consistency）: 无新写入时，副本最终收敛到一致结果;
- 代价: 应用必须理解旧读、冲突、幂等、补偿与收敛边界;
- 关系: BASE 不是 ACID 各字母的一一反义，也不是所有 NoSQL 的强制属性;

## CAP

- 一致性 C: 所有客户端同时看到同一最新数据;
- 可用性 A: 每个发给非故障节点的请求都得到响应，但不保证是最新值;
- 分区容忍 P: 节点间消息丢失或网络分区时系统仍按定义运行;
- 正确理解: 真实分布式系统无法消除网络分区; 分区发生时才必须在一致性与可用性之间选择;
- CP: 分区时拒绝无法保证一致的操作，牺牲部分可用性;
- AP: 分区时继续响应，接受旧值或冲突并在之后修复;
- CA: 只在不考虑分区的边界内成立，常见于单节点或同一故障域;

## PACELC

- 表述: `P -> A/C, Else -> L/C`; 分区时选可用性或一致性，无分区时仍需在延迟与一致性间权衡;
- 意义: CAP 只描述故障期选择，PACELC 把占绝大多数时间的正常运行性能纳入模型;
- 示例: 同步等待远端副本能提高一致性，却增加写延迟; 本地快速响应能降延迟，却扩大副本新鲜度窗口;

## 选型问题

- 失败期: 网络分区时宁可拒绝请求，还是返回可能陈旧的数据?
- 正常期: 业务可接受多大读写延迟和多长不一致窗口?
- 数据边界: 哪些实体必须强一致，哪些读模型、搜索或分析结果可最终一致?
- 运维边界: 冲突怎样检测、合并、补偿和审计? 用户会看到什么状态?
