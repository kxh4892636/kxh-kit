# 单体、模块化单体与微服务

单体为什么既简单又会变难? 模块化单体解决什么问题? 微服务边界应按什么划分? 什么是分布式单体? 何时不该采用微服务?

## 单体

- 单体: 以一个部署单元完成完整业务能力的自包含应用;
- 优势: 开发、调试、测试和监控路径短; 进程内通信快; 单库 ACID 事务自然;
- 劣势: 代码与团队增长后耦合、构建和部署影响面扩大; 只能整体扩缩; 单缺陷可能拖垮全局;
- 技术约束: 整体常绑定同一技术栈，每次变更都需重新部署整个应用;

## 模块化单体

- 模块化单体: 保持单一部署，但按业务能力划分独立模块与显式接口;
- 目标: 在不支付分布式系统成本的前提下，降低模块依赖并允许局部演进;
- 成功条件: 模块拥有清晰数据与行为边界，禁止绕过接口访问内部表或实现;
- 演进价值: 若某模块日后确需独立扩缩或团队自治，稳定边界可成为提取服务的起点;

## 微服务

- 微服务: 一组小而自治的服务，每个服务在一个 bounded context 内实现单一业务能力;
- “小”: 指职责聚焦，不是代码行数;
- 自治: 独立代码库、部署、扩缩和数据所有权，团队能端到端负责;
- 优势: 团队并行、独立发布、故障与数据隔离、按服务扩缩、技术选择灵活;
- 代价: 网络延迟与失败、分布式数据一致性、测试、可观测性、部署与运维成本;

## 设计准则

- 按业务领域建模边界，追求高内聚、低耦合;
- 服务通过设计良好的 API 或事件通信，不泄漏实现细节;
- 数据由服务私有，避免共享数据库模式和同步发布;
- API 演进保持向后兼容; 远程调用采用超时、幂等、熔断与隔离;
- 团队拥有服务全生命周期，减少共享代码和中央协调;

## 分布式单体

- 定义: 外形像微服务，实际仍需多个服务同步发布、低延迟互调或共享数据库才能工作;
- 征兆: 服务无法独立扩缩、循环依赖、跨服务事务无处不在、一个服务故障全链路失败;
- 后果: 同时承受单体耦合与分布式运维成本;

## 选择

- 默认起点: 新业务优先模块化单体，先验证领域与团队边界;
- 采用微服务的信号: 团队在共享代码库互相阻塞，局部负载与发布节奏差异明显，独立边界带来可量化业务价值;
- 拒绝理由: “大公司都用”不是需求; 微服务首先解决组织和自治问题，不是技术成熟度徽章;
- 与 SOA: SOA 强调企业范围服务复用与统一标准; 微服务更强调小型自治团队、独立部署和去中心化;
