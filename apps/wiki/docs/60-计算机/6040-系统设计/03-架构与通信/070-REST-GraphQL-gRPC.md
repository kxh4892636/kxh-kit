# REST、GraphQL 与 gRPC

API 为什么是生产者与消费者之间的契约? REST、GraphQL 和 gRPC 的基本抽象分别是什么? 三者如何权衡耦合、往返次数、性能、缓存、工具链与浏览器支持?

## API

- API（Application Programming Interface）: 生产者与消费者约定的操作、数据、错误和兼容规则;
- 设计目标: 先稳定领域语义，再选择传输技术; 一致、可演进的契约比框架能力更重要;

## REST

- 基本抽象: 资源; 用 URI 标识资源，用 HTTP 方法表达操作;
- 约束: 统一接口、客户端与服务器分离、无状态、可缓存、分层系统，以及可选 code-on-demand;
- 方法: `GET` 读取、`HEAD` 只取首部、`POST` 提交、`PUT` 替换、`PATCH` 部分修改、`DELETE` 删除;
- 状态码: `1xx` 信息、`2xx` 成功、`3xx` 重定向、`4xx` 客户端错误、`5xx` 服务端错误;
- 优势: 简单、可移植、HTTP 缓存成熟、客户端与服务器低耦合;
- 代价: 固定资源形状会过取数据，复杂页面可能需要多次往返;

## GraphQL

- 基本抽象: 查询; 客户端声明所需字段，服务端按 schema 与 resolver 返回精确形状;
- schema: 定义可查询类型、字段与操作;
- query / mutation: 分别读取和改变服务端数据;
- resolver: 为字段或操作生成结果的处理函数;
- 优势: 减少过取和多资源往返、强 schema、代码生成、适合图状数据与快速客户端迭代;
- 代价: 缓存和版本策略自定义，复杂度移到服务器，resolver 容易产生 N+1 查询;

## gRPC

- 基本抽象: 远程方法; 用 Protocol Buffers 作为 IDL 和二进制序列化格式;
- 能力: 生成多语言客户端与服务端代码，支持双向流、负载均衡、追踪、健康检查和认证集成;
- 优势: 载荷小、吞吐高、延迟低、契约和代码生成强，适合内部微服务与多语言环境;
- 代价: 浏览器支持受限、人不可直接阅读、学习与调试门槛高，客户端与服务定义耦合更强;

## 选择

| 需求                                 | 倾向    |
| ------------------------------------ | ------- |
| 公共 Web API、HTTP 缓存、广泛兼容    | REST    |
| 多样客户端自选字段、聚合图状数据     | GraphQL |
| 内部服务、高吞吐低延迟、强 IDL、流式 | gRPC    |

- 混合: 对外 REST/GraphQL、对内 gRPC 很常见; 技术边界应服务不同消费者，而非追求统一;
- 版本: REST 常用路径或媒体类型; GraphQL 倾向字段弃用; gRPC 依赖字段编号与向后兼容规则;
- 结论: 没有普遍最优技术，用访问模式、消费者能力、延迟、缓存和演进成本决策;
