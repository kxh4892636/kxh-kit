# 长轮询、WebSocket 与 SSE

服务器如何在没有普通请求触发时把更新推给客户端? 长轮询、WebSocket 与 SSE 的连接和方向有何不同? 怎样根据消息方向、兼容性、连接规模与恢复需求选择?

## 长轮询

- 工作方式: 客户端发请求，服务端保持连接，直到有更新或超时才响应; 客户端收到后立即再次请求;
- 本质: 用一连串延迟响应的 HTTP 请求模拟服务器推送;
- 优势: 实现简单、HTTP 基础设施兼容广，适合小规模或低频更新;
- 代价: 每次响应后重建请求，服务器需维持大量挂起请求; 多请求并发时顺序、取消和超时更复杂;

## WebSocket

- WebSocket: 在一条持久 TCP 连接上提供客户端与服务器全双工消息通信;
- 握手: 客户端发送带 `Upgrade: websocket` 的 HTTP 请求，服务端以 `101 Switching Protocols` 确认;
- 建立后: 双方可随时发送文本或二进制帧，不再按普通 HTTP 请求/响应交互;
- 优势: 双向实时、重复首部开销小，适合聊天、协作、游戏与双向位置更新;
- 代价: 长连接状态、负载均衡、心跳、断线重连、消息补偿与容量规划更复杂;
- 恢复: 协议不替应用自动补齐断线期间消息; 需要游标、序号、重放或重新同步;

## SSE

- SSE（Server-Sent Events）: 客户端建立长期 HTTP 连接，服务器以事件流单向推送文本事件;
- 优势: API 简单、浏览器支持和代理兼容较好，原生重连语义适合通知、进度和行情;
- 限制: 同一连接只能服务器到客户端，不支持二进制; 浏览器与 HTTP 版本可能限制并发连接数;

## 选择

| 场景                     | 选择      |
| ------------------------ | --------- |
| 更新少、兼容旧基础设施   | 长轮询    |
| 服务器单向连续推送       | SSE       |
| 双向低延迟、文本或二进制 | WebSocket |

- 共同问题: 身份续期、心跳、背压、代理超时、连接迁移、顺序、重复与可观测性;
- 扩展原则: 不只计算请求每秒，还要计算并发连接、每连接消息率、缓冲内存与广播 fanout;
