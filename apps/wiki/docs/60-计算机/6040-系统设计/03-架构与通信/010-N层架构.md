# N 层架构

层（layer）与层级部署（tier）有什么区别? 开放层和封闭层怎样控制依赖? 一层、两层与三层架构分别适合什么系统? 物理拆分为什么既提高弹性又增加延迟?

## Layer 与 Tier

- 层（layer）: 逻辑职责与依赖边界; 上层可使用下层服务，下层不反向依赖上层;
- tier: 物理部署边界，运行在不同进程或机器上，可同步调用或异步通信;
- 关系: 一个 layer 不必独占一个 tier; 多个逻辑层可同进程部署，也可把一个逻辑能力分布到多台机器;
- 权衡: 物理拆分能独立扩缩、隔离故障，却增加网络延迟、序列化、部署和安全管理成本;

## 依赖规则

- 封闭层: 只能调用紧邻的下一层; 依赖清晰，但纯转发层会制造无价值跳数;
- 开放层: 可跳过中间层调用更下层; 路径短，但容易绕开策略并形成跨层耦合;
- 设计原则: 默认让依赖方向单向，只有明确性能或能力原因时开放旁路，并把例外写进接口契约;

## 常见形态

- 一层架构: 界面、业务和数据位于同一应用或机器; 部署简单，适合本地工具与小型系统;
- 两层架构: 客户端直接访问数据存储; 适合受控环境，但业务规则易散落客户端，安全和演进困难;
- 三层架构: 展示层处理交互，业务逻辑层执行规则，数据访问层读写数据库;
- N 层扩展: 把网关、领域服务、集成、缓存等继续拆为独立职责，但层数不是设计质量指标;

## 权衡

- 优势: 关注点分离、独立扩缩、团队分工、维护性，以及层间防火墙式安全边界;
- 劣势: 整体复杂度、网络延迟、基础设施成本与跨层排障难度上升;
- 深层陷阱: 每层只转发数据而不隐藏复杂性，会形成“浅模块链”; 合并无独立策略的层通常更简单;
- 验证问题: 每一层隐藏了什么复杂性? 有哪些稳定接口? 是否能独立测试、扩缩或替换?
