# TCP 与 UDP

TCP 和 UDP 的根本差异是什么? TCP 怎样建立可靠字节流? 流量控制与拥塞控制分别保护谁? 实时通信为什么常选 UDP?

## 协议选择

| 维度     | TCP                    | UDP                    |
| -------- | ---------------------- | ---------------------- |
| 连接     | 面向连接               | 无连接                 |
| 数据抽象 | 有序字节流             | 独立数据报             |
| 交付     | 确认、重传、按序交付   | 不保证到达、顺序或重传 |
| 开销     | 连接与可靠性机制较重   | 8 字节首部，状态少     |
| 典型场景 | HTTP、HTTPS、SMTP、FTP | DNS、VoIP、直播、组播  |

- 选择 TCP: 数据完整与顺序比延迟更重要，例如网页、文件和事务请求;
- 选择 UDP: 最低延迟更重要，迟到数据已失去价值，应用能容忍或自行恢复丢包;
- UDP 检验和: 能检测报文损坏，但不能修复或重传;

## TCP 连接与字节流

- 三次握手: 客户端 `SYN(client_isn)`，服务器 `SYN+ACK(client_isn+1, server_isn)`，客户端 `ACK(server_isn+1)`;
- 三次的理由: 双方分别确认自己的发送能力和对方的接收能力，并同步初始序号;
- 四次关闭: 双向字节流可独立结束; 一方 `FIN` 后，对方可能仍需发送未完成数据，因此确认与自身 `FIN` 分开;
- 序号: 标识报文段首字节在字节流中的位置;
- 确认号: 接收方下一步期望的字节序号，属于累计确认;
- 粘包: TCP 没有应用消息边界; 应用必须使用固定长度、长度前缀或分隔符自行成帧;

## 可靠性与控制

- 可靠交付: 校验和检测错误，ACK 确认到达，超时与快速重传恢复丢失，接收窗口保存失序数据;
- 快速重传: 发送方收到 3 个重复 ACK 时，不等待超时就重传缺失报文段;
- 流量控制: 接收方通过 `rwnd` 告知剩余缓冲空间，避免发送速度超过应用读取速度;
- 拥塞控制: 根据网络拥塞调整发送速率，保护共享网络; 与只保护接收端缓冲的流量控制不同;
- 队头阻塞: 前部字节缺失会阻止后续已到达字节交付给应用，造成不可预测抖动;

## 风险

- SYN 洪泛: 攻击者制造大量半开连接耗尽服务器状态;
- SYN cookie: 服务器先把连接信息编码进序号，收到合法 ACK 后才分配完整连接状态;
- 远程调用认知: TCP 可靠不等于服务调用必然成功; 超时后仍可能不知道服务端是否已执行，业务仍需幂等与重试策略;
