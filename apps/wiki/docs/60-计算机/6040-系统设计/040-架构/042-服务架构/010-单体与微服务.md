# 单体与微服务

单体、模块化单体和微服务各有什么特点？微服务最佳实践和陷阱是什么？何时不需要微服务？

## 单体

- 单体: 自包含独立应用，作为单一单元构建部署;
- 优点: 开发调试简单、通信快速可靠、易监控测试、支持 ACID;
- 缺点: 代码增长后维护难、紧耦合、技术栈锁定、整体重新部署、单点故障影响全系统、难以扩展;

## 模块化单体

- 单应用部署，但代码按功能拆成独立模块;
- 优点: 模块间低依赖，可局部增强或修改;

## 微服务

- 微服务: 一组小型自治服务，每个服务实现单一业务能力（有界上下文）;
- 每个服务独立代码库、独立部署、独立数据存储;

### 特征

- 松耦合;
- 小而聚焦;
- 围绕业务能力组织;
- 韧性与容错;
- 高可维护性;

### 优点

- 独立部署;
- 多团队敏捷;
- 故障隔离与数据隔离;
- 独立扩展;
- 技术栈不长期绑定;

### 缺点

- 分布式系统复杂;
- 测试困难;
- 维护成本高;
- 服务间通信挑战;
- 数据一致性与完整性;
- 网络拥塞与延迟;

### 最佳实践

- 按业务域建模;
- 松耦合高内聚;
- 隔离故障，使用熔断;
- 只通过良好设计的 API 通信;
- 数据私有;
- 避免共享库/Schema 和僵化协议;
- 去中心化;
- API 向后兼容;

### 陷阱

- 边界不按业务域;
- 低估分布式难度;
- 共享数据库或依赖;
- 缺乏业务对齐与所有权;
- 缺乏幂等性;
- 强行 ACID;
- 缺乏容错导致级联故障;

## 分布式单体

- 现象: 表面微服务、内部紧耦合;
- 标志: 需要低延迟通信、服务难独立扩展、服务间依赖、共享资源、紧耦合;

## 微服务 vs SOA

- SOA: 通过服务接口最大化组件复用，使用通用通信标准;
- 微服务: 强调最小独立服务单元、团队自治和解耦;

## 何时不需要微服务

- 团队小、共享代码库有效;
- 无明确业务价值;
- 业务不成熟;
- 当前架构未被通信开销限制;
- 建议: 新系统从单体开始，微服务不是银弹;
