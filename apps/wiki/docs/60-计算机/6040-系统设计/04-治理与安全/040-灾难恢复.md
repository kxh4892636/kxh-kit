# 灾难恢复

灾难恢复保护的故障范围是什么? RTO 与 RPO 分别约束停机和数据丢失? 备份、冷站点与热站点如何权衡成本和恢复速度? 为什么“有备份”不等于“能恢复”?

## 概念

- 灾难恢复（DR）: 自然灾害、网络攻击或重大业务中断后，重新获得基础设施、数据和处理能力的过程;
- 原理: 在不同故障域复制数据与计算能力，主站点失效后从未受影响的位置恢复或接管;
- 目标: 减少停机与损害、快速恢复服务、保护客户信任;
- 与高可用: 高可用处理日常组件故障并缩短中断; DR 面向整个站点、区域或组织级灾难;

## RTO 与 RPO

- RTO（Recovery Time Objective）: 从中断到恢复服务的最长可接受时间;
- RPO（Recovery Point Objective）: 最多可接受丢失多少时间范围内的数据;
- 示例: `RTO=1h, RPO=5min` 表示一小时内恢复，恢复点最多落后故障前五分钟;
- 成本规律: RTO 与 RPO 越小，需要越实时的复制、自动化切换和预置容量，成本通常越高;

## 策略

| 策略     | 状态                           | 恢复与成本           |
| -------- | ------------------------------ | -------------------- |
| 异地备份 | 保存数据，无持续计算环境       | 成本最低，恢复最慢   |
| 冷站点   | 预置基础设施，数据与服务需恢复 | 中等成本与 RTO       |
| 热站点   | 持续同步数据并维持可接管系统   | RTO/RPO 小，成本最高 |

## 可恢复性闭环

- 备份隔离: 副本跨账户、区域与权限边界，防止误删和攻击同时破坏主副本;
- 恢复演练: 定期从备份恢复并验证数据、密钥、依赖与流量切换; 未演练的备份只是希望;
- runbook: 明确触发条件、负责人、切换顺序、通信、回切和审计;
- 数据一致性: 恢复多个系统时定义共同恢复点、事件回放和重复处理;
- 容量: 热站点之外的策略也需确认恢复后能承载最低业务流量;
- 验证: 以实际恢复时间和实际数据损失证明 RTO/RPO，而非只检查复制任务成功;
