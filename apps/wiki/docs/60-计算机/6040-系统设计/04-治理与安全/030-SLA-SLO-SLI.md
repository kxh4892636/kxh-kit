# SLA、SLO 与 SLI

SLA、SLO 和 SLI 分别回答什么问题? 怎样从用户体验定义指标? 为什么只有可测量的 SLO 才能指导工程决策? 错误预算如何连接可靠性与发布速度?

## 三层契约

- SLA（Service Level Agreement）: 服务提供方与用户之间的协议，规定承诺、责任与可能的赔偿; 常由业务和法务参与制定;
- SLO（Service Level Objective）: SLA 内部或团队自定的具体服务目标，例如 30 天可用性 `99.9%`;
- SLI（Service Level Indicator）: 实际测得的指标值，用于判断 SLO 是否达成;
- 关系: 用 SLI 测量 SLO，以 SLO 支撑 SLA; 一个 SLA 可包含多个 SLO;

## 从用户体验定义

- 可用性 SLI: 成功请求数 / 有效请求数;
- 延迟 SLI: 在阈值内完成的请求比例，比单一平均值更能描述尾延迟;
- 正确性 SLI: 返回正确结果或满足数据新鲜度的请求比例;
- 耐久性 SLI: 在约定周期内未丢失的对象或提交比例;
- 约束: 指标必须简单、定义明确、可重复计算，并说明窗口、排除项和数据来源;

## 错误预算

- 错误预算: `1 - SLO` 允许的失败比例; `99.9%` SLO 在窗口内允许 `0.1%` 不满足;
- 用途: 预算充足时可承担合理发布风险; 消耗过快时优先可靠性、修复和降风险;
- 价值: 把“永远稳定”和“快速交付”的争论转成共同、可量化的用户承诺;
- 反模式: 把内部 CPU 指标直接当 SLI、只看平均延迟、设置无法测量或成本远超用户价值的 SLO;

## 设计步骤

1. 识别用户真正依赖的关键旅程;
2. 定义成功事件、有效事件和测量位置;
3. 选择统计窗口与目标;
4. 验证遥测是否准确覆盖用户视角;
5. 设定告警与错误预算策略，并定期复盘目标是否仍有价值;
