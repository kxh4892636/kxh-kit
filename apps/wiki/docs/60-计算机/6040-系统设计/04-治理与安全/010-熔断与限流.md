# 熔断与限流

熔断怎样阻止级联故障? closed、open 与 half-open 如何转换? 常见限流算法如何处理突发? 分布式限流为什么会出现不一致与竞态?

## 熔断器

- 熔断器: 监控远程调用失败，在失败达到阈值后停止调用不健康依赖并快速失败;
- 目的: 远程调用可能失败或长时间挂起; 大量等待会耗尽线程、连接和内存，引发级联故障;
- Closed: 正常放行调用并统计失败; 失败率或数量越过阈值后进入 Open;
- Open: 不调用依赖，立即返回错误或降级结果; 冷却时间后进入 Half-open;
- Half-open: 只放行少量探测请求; 成功则恢复 Closed，继续失败则回到 Open;
- 配套: 超时、隔离舱、重试预算、降级、告警和可观测性; 熔断不能替代这些机制;
- 重试风险: 无退避和上限的重试会放大故障; 只对幂等、短暂且可恢复错误重试;

## 限流目标

- 限流: 阻止某操作频率超过定义上限，保护共享服务与资源可用性;
- 用途: 缓解 DoS 与滥用、控制自动扩容成本、平滑大数据入口、落实租户配额;
- 响应: 明确返回拒绝或延迟语义，例如 `429 Too Many Requests` 与 `Retry-After`;

## 算法

| 算法     | 机制                               | 权衡                       |
| -------- | ---------------------------------- | -------------------------- |
| 漏桶     | 请求入队，按固定速率流出，满则丢弃 | 输出平滑，不容忍大突发     |
| 令牌桶   | 按速率补令牌，请求消耗令牌         | 允许桶容量内突发           |
| 固定窗口 | 每个固定时段计数                   | 成本低，窗口边界可双倍突发 |
| 滑动日志 | 保存窗口内每次请求时间             | 精确但存储与计算高         |
| 滑动窗口 | 当前窗口加上前窗加权计数           | 成本与边界平滑的折中       |

## 分布式限流

- 不一致: 各节点本地计数会让用户通过多节点超过全局配额;
- sticky session: 把用户固定到节点可简化计数，但降低容错与扩展弹性;
- 中央计数器: Redis 等提供全局视图，但新增网络延迟、容量与单点风险;
- 竞态: `get → increment → set` 会丢更新; 使用原子递增、Lua 脚本或事务，而非围绕热键加全局锁;
- 一致性选择: 强全局限额昂贵; 可按风险接受近似限流、分片配额或分层本地加全局限流;
