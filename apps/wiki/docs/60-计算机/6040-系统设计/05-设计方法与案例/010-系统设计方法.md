# 系统设计方法

怎样把抽象问题收敛为可评估设计? 功能、非功能和扩展需求如何分层? 量级估算怎样约束架构? 数据、API、组件与瓶颈应按什么顺序推导? 如何避免技术先行?

系统设计是一个范围极广的主题。系统设计面试考察的不是复述某张标准架构图，而是把抽象问题转化为技术方案的能力。它具有双向性：候选人通过提问获取约束，面试官通过回答改变问题边界，设计在来回沟通中逐步收敛。

不同工程级别的期望也不同。经验较少者通常重点证明能设计出正确主路径；经验丰富者还应主动识别容量边界、故障模式、技术权衡和演进路线。因此不存在适合所有人的唯一脚本，下面的步骤是一套防遗漏的推导框架。

## 1. 澄清需求

- 双向过程: 系统设计没有唯一答案; 候选设计必须通过提问与需求方共同收敛;
- 功能需求: 用户必须完成的行为，例如创建内容、读取信息、发送消息;
- 非功能需求: 延迟、可用性、可靠性、安全、可维护性和可扩展性等质量约束;
- 扩展需求: 指标、分析、推荐等可选能力; 明确是否在本轮范围内;
- 边界问题: 谁是用户? 核心旅程是什么? 有哪些异常与权限? 哪些能力明确不做?

典型追问包括：“本轮需要设计哪些功能?”、“是否有必须覆盖的边界情况?”。功能需求是系统必须履行的用户契约；非功能需求也称非行为需求，约束的是实现质量；扩展需求则是可能超出当前范围的“有更好”能力。三者必须分开，否则容易把时间花在分析平台等附属能力上，却没有闭合核心请求路径。

## 2. 估算规模

- 业务量: 日活、每用户操作次数、读写比、对象平均大小和保留期;
- RPS: `每日请求数 / 86400`; 另乘峰值系数估算容量，而非只看日均;
- 带宽: `每秒对象数 × 平均对象大小`，分别计算入口与出口;
- 存储: `每日新增对象数 × 对象大小 × 保留天数 × 副本与索引系数`;
- 缓存: 从热点比例、对象大小和有效期推算，不机械套用 80/20;
- 目的: 估算只需达到能排除错误架构的精度; 所有假设都应显式并可替换;

常用计算关系如下：

```text
平均 RPS = 每日请求数 / 86400
峰值 RPS = 平均 RPS × 峰值系数
带宽 = 每秒对象数 × 平均对象大小
存储 = 每日新增对象数 × 对象大小 × 保留天数
生产容量 = 原始容量 × 副本、索引、编码与增长系数
```

“系统要处理多大规模?”、“读写比是多少?”、“每秒多少请求?”、“需要多少存储?”是原材料强调的四个基本问题。平均值不能代替峰值，原始数据大小也不能代替真实容量。

## 3. 设计数据模型

- 实体: 找出系统必须长期记住的事实;
- 关系: 明确一对一、一对多、多对多与所有权;
- 访问模式: 先写主要读写路径，再决定索引、SQL/NoSQL、复制和分片;
- 一致性: 指定哪些更新必须原子，哪些视图可延迟;
- 生命周期: 创建、更新、过期、删除、归档和合规擦除;

应能明确回答：有哪些实体、实体之间是什么关系、需要多少表或集合，以及 NoSQL 是否真的比 SQL 更适合当前访问模式。尽早画出数据模型，是为了让后续 API 和组件设计围绕真实数据流展开，而不是先画技术组件再寻找用途。

## 4. 设计 API

- API 作用: 把系统能力与调用预期变成显式契约;
- 最小接口: 先覆盖核心需求的操作、参数、返回值和错误，不写实现代码;
- 语义: 明确幂等性、分页、排序、版本、鉴权和重试行为;
- 演进: 扩展需求稍后加入，避免首版契约被次要功能淹没;

此阶段不需要实现代码，一个包含参数和返回类型的简单接口就足够，例如：

```ts
createUser(name: string, email: string): User
```

在基本签名之外，还要补充鉴权、幂等、分页、版本、超时与重试语义，避免相同接口在不同调用方眼中有不同含义。

## 5. 绘制高层组件

- 入口: DNS、负载均衡、API 网关与客户端协议;
- 计算: 按业务职责而非技术名词划分服务;
- 数据: 主存储、缓存、搜索、对象存储和分析管道;
- 异步: 只有在需要削峰、解耦或广播时引入队列与事件;
- 讲解: 沿一条核心用户旅程逐步说明请求、数据和失败路径;

这一阶段要明确单体还是微服务、数据库类型和组件职责。有了第一版图后，从客户端视角走一遍完整路径，让每个组件的存在都能由需求或约束解释。

## 6. 深入关键机制

- 优先级: 选择最影响需求的两三个难点深入，不平均铺开所有组件;
- 权衡: 对每个选择说明替代方案、收益、代价和适用假设;
- 常见主题: 分区键、负载分布、缓存一致性、流量突发、消息交付和故障恢复;
- 态度: 技术没有绝对优劣; “NoSQL 总比 SQL 可扩展”等口号不能替代证据;

先与需求方确认需要深入的组件，不要平均展开全部模块。这里是展示经验的主要位置：列出替代方案，用示例解释收益和代价，并说明结论依赖哪些假设。也可以讨论系统还能支持哪些附加能力，但它们是可选项。

## 7. 识别瓶颈并闭环

- 单点: 网关、主库、协调器、缓存和后台工作器是否有冗余?
- 容量: 哪一层先达到 CPU、连接、带宽、存储或 IOPS 上限?
- 故障: 超时、重试、熔断、降级、数据恢复和消息积压怎样处理?
- 数据: 是否需要副本、分片、一致性哈希或异地恢复?
- 验证: 用最初的功能与非功能需求逐项回查设计，不以“画完组件图”作为完成;

原材料给出的最终追问包括：数据库副本是否足够、是否存在单点、是否需要分片、怎样提高系统健壮性、怎样提高缓存可用性。准备具体公司的面试时，还应阅读其工程博客，了解实际技术栈和重点问题，再把这套通用框架落到具体约束上。
