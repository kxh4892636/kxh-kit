# 系统设计方法

怎样把抽象问题收敛为可评估设计? 功能、非功能和扩展需求如何分层? 量级估算怎样约束架构? 数据、API、组件与瓶颈应按什么顺序推导? 如何避免技术先行?

## 1. 澄清需求

- 双向过程: 系统设计没有唯一答案; 候选设计必须通过提问与需求方共同收敛;
- 功能需求: 用户必须完成的行为，例如创建内容、读取信息、发送消息;
- 非功能需求: 延迟、可用性、可靠性、安全、可维护性和可扩展性等质量约束;
- 扩展需求: 指标、分析、推荐等可选能力; 明确是否在本轮范围内;
- 边界问题: 谁是用户? 核心旅程是什么? 有哪些异常与权限? 哪些能力明确不做?

## 2. 估算规模

- 业务量: 日活、每用户操作次数、读写比、对象平均大小和保留期;
- RPS: `每日请求数 / 86400`; 另乘峰值系数估算容量，而非只看日均;
- 带宽: `每秒对象数 × 平均对象大小`，分别计算入口与出口;
- 存储: `每日新增对象数 × 对象大小 × 保留天数 × 副本与索引系数`;
- 缓存: 从热点比例、对象大小和有效期推算，不机械套用 80/20;
- 目的: 估算只需达到能排除错误架构的精度; 所有假设都应显式并可替换;

## 3. 设计数据模型

- 实体: 找出系统必须长期记住的事实;
- 关系: 明确一对一、一对多、多对多与所有权;
- 访问模式: 先写主要读写路径，再决定索引、SQL/NoSQL、复制和分片;
- 一致性: 指定哪些更新必须原子，哪些视图可延迟;
- 生命周期: 创建、更新、过期、删除、归档和合规擦除;

## 4. 设计 API

- API 作用: 把系统能力与调用预期变成显式契约;
- 最小接口: 先覆盖核心需求的操作、参数、返回值和错误，不写实现代码;
- 语义: 明确幂等性、分页、排序、版本、鉴权和重试行为;
- 演进: 扩展需求稍后加入，避免首版契约被次要功能淹没;

## 5. 绘制高层组件

- 入口: DNS、负载均衡、API 网关与客户端协议;
- 计算: 按业务职责而非技术名词划分服务;
- 数据: 主存储、缓存、搜索、对象存储和分析管道;
- 异步: 只有在需要削峰、解耦或广播时引入队列与事件;
- 讲解: 沿一条核心用户旅程逐步说明请求、数据和失败路径;

## 6. 深入关键机制

- 优先级: 选择最影响需求的两三个难点深入，不平均铺开所有组件;
- 权衡: 对每个选择说明替代方案、收益、代价和适用假设;
- 常见主题: 分区键、负载分布、缓存一致性、流量突发、消息交付和故障恢复;
- 态度: 技术没有绝对优劣; “NoSQL 总比 SQL 可扩展”等口号不能替代证据;

## 7. 识别瓶颈并闭环

- 单点: 网关、主库、协调器、缓存和后台工作器是否有冗余?
- 容量: 哪一层先达到 CPU、连接、带宽、存储或 IOPS 上限?
- 故障: 超时、重试、熔断、降级、数据恢复和消息积压怎样处理?
- 数据: 是否需要副本、分片、一致性哈希或异地恢复?
- 验证: 用最初的功能与非功能需求逐项回查设计，不以“画完组件图”作为完成;
