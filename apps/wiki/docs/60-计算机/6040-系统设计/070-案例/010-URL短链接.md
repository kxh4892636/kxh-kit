# URL 短链接

URL 短链接服务的核心目标是什么？如何估算读写、带宽、存储和缓存？短码生成有哪些方案？高层与详细设计如何做？

## 什么是 URL 短链接

- URL Shortener: 为长 URL 创建别名或短 URL;
- 用户访问短链接时被重定向到原始长 URL;
- 示例: 长 URL `https://karanpratapsingh.com/courses/system-design/url-shortener` → 短 URL `https://bit.ly/3I71d3o`;

## 为什么需要

- 节省分享 URL 时的空间;
- 短 URL 更不容易输错;
- 可针对不同设备优化链接;
- 可跟踪单个链接的点击与指标;

## 需求

### 功能需求

- 给定 URL，生成更短且唯一的别名;
- 用户访问短链接时重定向到原始 URL;
- 链接在默认时间后过期;

### 非功能需求

- 高可用、最小延迟;
- 可扩展、高效;

### 扩展需求

- 防止滥用;
- 记录重定向的分析和指标;

## 估算与约束

假设: 读重系统，读写比 100:1，每月生成 1 亿条链接。

### 流量

- 读: 每月 100 × 1 亿 = 100 亿次重定向;
- 写: 每月 1 亿条新链接;
- 写入 RPS: 1 亿 / (30×24×3600) ≈ 40 URLs/s;
- 读取 RPS: 100 × 40 = 4000 redirections/s;

### 带宽

- 每次请求约 500 bytes;
- 写入入站: 40 × 500B = 20 KB/s;
- 读取出站: 4000 × 500B ≈ 2 MB/s;

### 存储

- 每月 1 亿条记录，保存 10 年;
- 总记录: 1 亿 × 10 × 12 = 120 亿条;
- 每条约 500B，总存储约 6 TB;

### 缓存

- 遵循 Pareto 80/20: 80% 请求访问 20% 数据;
- 日读取: 4000 × 24 × 3600 ≈ 3.5 亿请求/天;
- 缓存 20%: 0.2 × 3.5 亿 × 500B ≈ 35 GB/天;

### 高层估算表

| 类型           | 估算      |
| -------------- | --------- |
| 写入（新 URL） | 40/s      |
| 读取（重定向） | 4K/s      |
| 入站带宽       | 20 KB/s   |
| 出站带宽       | 2 MB/s    |
| 10 年存储      | 6 TB      |
| 缓存内存       | ~35 GB/天 |

## 数据模型设计

初始可用两张表:

### users

- 存储用户信息: `name`、`email`、`createdAt` 等;

### urls

- 存储短 URL 属性: `expiration`、`hash`、`originalURL`、`userID`;
- 可用 `hash` 列作为索引提升查询性能;

### 数据库选型

- 数据关系不强，NoSQL 更合适: DynamoDB、Cassandra、MongoDB;
- 若用 SQL: Azure SQL Database、Amazon RDS;

## API 设计

### 创建 URL

```tsx
createURL(apiKey: string, originalURL: string, expiration?: Date): string
```

- 参数: API Key、原始 URL、可选过期时间;
- 返回: 新短 URL;

### 获取 URL

```tsx
getURL(apiKey: string, shortURL: string): string
```

- 参数: API Key、短 URL;
- 返回: 原始 URL;

### 删除 URL

```tsx
deleteURL(apiKey: string, shortURL: string): boolean
```

- 参数: API Key、短 URL;
- 返回: 是否成功;

### 为什么需要 API Key

- 用于防止滥用;
- 可按用户限制每秒/每分钟请求数;
- 是开发者 API 的常见做法;

## 高层设计

### URL 编码方案

#### Base62

- 字符集: A-Z、a-z、0-9，共 62 个字符;
- 数量公式: 62^N;
- 7 位短码可表示约 3.5 万亿 URL;
- 优点: 最简单;
- 缺点: 不保证不重复、不防碰撞;

#### MD5

- 对原始 URL 做 MD5（128-bit，32 位十六进制），再 Base62 编码取 7 位;
- 问题: 重复和碰撞;
- 可重算直到唯一，但增加系统开销;

#### Counter

- 单服务器维护计数器，每次返回唯一数字并递增;
- 单点故障风险;
- 多实例会产生碰撞;
- 可用 Zookeeper 分配计数范围:
  - Range 1: 1 → 1,000,000
  - Range 2: 1,000,001 → 2,000,000
  - Range 3: 2,000,001 → 3,000,000
- Zookeeper 多实例可消除单点故障;

### Key Generation Service (KGS)

- 独立服务预生成唯一 key，存入独立数据库;
- API Server 使用时向 KGS 取 key，KGS 标记已用;
- 并发处理: 用两张表，key 使用后移动到已用表并加锁; 可在内存缓存一批 key 提升读性能;
- KGS 数据库估算: 6 字符 key 可生成约 568 亿个，存储约 390 GB;
- key 库大小不会像主库那样持续增长;

### 缓存

- 按估算约需 35 GB/天缓存 20% 请求;
- 可用 Redis 或 Memcached;

### 基本设计流程

**创建新 URL**

1. API Server 向 KGS 请求新唯一 key;
2. KGS 提供 key 并标记已用;
3. API Server 将 URL 条目写入数据库和缓存;
4. 返回 HTTP 201 Created;

**访问短 URL**

1. 客户端请求短 URL，进入 API Server;
2. 先查缓存，未命中再查数据库;
3. 命中则返回 HTTP 301 重定向到原始 URL;
4. 数据库也不存在则返回 HTTP 404;

## 详细设计

### 数据分区

- 使用水平分区（Sharding）;
- 可选分区方案: Hash-Based、List-Based、Range-Based、Composite;
- 数据不均可用一致性哈希解决;

### 数据库清理

- 主动清理: 独立 cleanup 服务定期删除过期链接，类似 cron;
- 被动清理: 用户访问过期链接时惰性删除;

### 缓存

- 淘汰策略: LRU（Least Recently Used）;
- 缓存未命中: 直接查数据库并回填缓存;

### 指标与分析

- 扩展需求: 记录访问者国家、平台、浏览次数等;
- 可随 URL 条目一起存储和更新;

### 安全

- 私有 URL 和授权: 单独表存有权限访问某 URL 的 user id;
- 无权限返回 HTTP 401 Unauthorized;
- API Gateway 可提供认证、限流、负载均衡;

## 识别并解决瓶颈

需要思考的问题:

- API Service 或 KGS 崩溃怎么办？
- 流量如何在组件间分发？
- 如何降低数据库负载？
- KGS 的 key 数据库故障怎么办？
- 如何提升缓存可用性？

可采用的韧性措施:

- API Server 和 KGS 多实例;
- 客户端、服务器、数据库、缓存之间引入负载均衡;
- 读重系统使用多个数据库读副本;
- key 数据库使用备用副本;
- 分布式缓存多实例和多副本;
