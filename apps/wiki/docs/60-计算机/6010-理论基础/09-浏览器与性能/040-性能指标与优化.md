# 性能指标与优化

## 五类通用优化方法分别在做什么?

| 类别     | 做法                                                                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 工程化   | 最小化; 混淆; 分块;                                                                                                                                                    |
| html     | 减少 DOM 层级; 响应式图片/视频; 使用 ssr;                                                                                                                              |
| js       | 减少入口文件体积; 减少入口文件执行时间; 使用 preload 和 as 预加载 js; 使用 import() 动态加载; 减少第三方代码; 使用 async 和 defer 异步/延迟加载 js; 放置于 html 底部;  |
| css      | 压缩 css; 使用 preload 和 as 预加载 css; 关键 css 使用内联 css; 合理使用 css 选择器（避免过多选择器、避免使用通配符和属性选择器）; 放置于 html 底部; 使用 js 动态加载; |
| 静态文件 | CDN; 静态资源本地缓存; 开启 gzip;                                                                                                                                      |

## FCP 和 LCP 衡量的是什么?

- FCP: 浏览器呈现第一个 DOM 需要的时间，衡量页面什么时候开始有东西可看;
- LCP: 视口中最大内容元素显示的时间，衡量主体内容什么时候出现;
- FCP 的优化手段: 优化 js、优化 css、优化静态文件、优化字体;
- LCP 的优化手段: 与 FCP 相同;
- 两者的差别: FCP 盯第一个 DOM，LCP 盯视口中最大的内容元素;

## TTI、TBT、SI 分别衡量什么?

| 指标 | 定义                                                |
| ---- | --------------------------------------------------- |
| TTI  | 页面变成完全可交互，需要的时间;                     |
| TBT  | 页面堵塞用户输入的总时间，即 FCP 到 TTI 之间的时间; |
| SI   | 页面加载期间，视觉显示的速度;                       |

- 共同优化手段: 优化 js（最小化、预加载、减少执行时间、减少第三方代码），并最小化主进程工作;
- 三者的分工: TTI 关心什么时候能操作，TBT 关心在这之前被堵住了多久，SI 关心内容填满屏幕的快慢;

## CLS 为什么会发生?

- CLS: DOM 从渲染到隐藏期间的累计布局偏移;
- 成因一: 无尺寸的图片，加载出来后才发现要占位置;
- 成因二: 无尺寸的 iframe，嵌入内容撑开时挤动周围元素;
- 成因三: 动态注入的内容，后插入的元素把已有元素推走;
- 代价: 用户正要点某个按钮，按钮却被推走，点击落到了别处;

## RAIL 对响应、动画、空闲、加载各有什么要求?

| 指标          | 要求                                          |
| ------------- | --------------------------------------------- |
| Response Time | 用户交互的响应时间，要求小于 100ms;           |
| Animation     | 动画在 16ms 内绘制完成;                       |
| Idle          | 页面在没有用户输入和事件触发时的时间，尽量短; |
| Load          | 页面加载时间，尽量短;                         |

## SSR 是什么，值不值得用?

- SSR: 页面在服务器进行渲染;
- 优点一: 首屏加载速度快，服务器预先生成 HTML，客户端在收到响应之前即可显示部分页面;
- 优点二: 支持 SEO;
- 优点三: 用户体验好，因为首屏加载速度快;
- 缺点一: 服务器压力大;
- 缺点二: 开发成本高，需要额外的服务器页面模板与数据获取流程;

## SSR 的落地流程有哪些步骤?

- 配置服务器环境: 客户端搭建 node 环境;
- 应用服务器: 监听 HTTP 请求，返回 HTML 文本;
- 路由: 根据不同路径返回对应 HTML;
- 客户端脚本: HTML 插入客户端脚本，用于交互和数据获取;
- SEO 优化: 添加 `<meta>` 标签;
