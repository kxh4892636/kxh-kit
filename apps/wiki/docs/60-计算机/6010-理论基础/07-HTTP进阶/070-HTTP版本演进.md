# HTTP 版本演进

## HTTP 本身有哪些弊端?

- 一次连接只可发送一次请求: 每个请求都要付出一次建立连接的开销;
- 请求只能从客户端开始: 服务器无法主动把数据推给客户端;
- 首部信息冗余且不压缩: 每次请求都重复发送大量相同的首部字段，白白占用带宽;

## SPDY 试图怎么弥补这些弊端?

- SPDY（已废弃）: 使用 SSL;
- 多路复用流: 单一 TCP 连接承载多个 HTTP 请求;
- 请求优先级: 给请求排出处理次序;
- 强制压缩: 强制压缩首部等信息;
- 服务器推送功能: 服务器可以主动把资源推给客户端;

## WebDAV 给 HTTP 加了哪些方法和状态码?

- WebDAV: 分布式文件系统，客户端直接操作服务器内容;
- 归属: 下列方法和状态码由 HTTP/1.1 添加;

| 方法      | 描述           |
| --------- | -------------- |
| PROPFIND  | 获取属性       |
| PROPPATCH | 修改属性       |
| MKCOL     | 创建集合       |
| COPY      | 复制资源及属性 |
| MOVE      | 移动资源       |
| LOCK      | 资源加锁       |
| UNLOCK    | 资源解锁       |

| 状态码                   | 描述                                             |
| ------------------------ | ------------------------------------------------ |
| 102 Processing           | 可正常处理请求，但目前是处理中状态               |
| 207 Multi-Status         | 存在多种状态                                     |
| 422 Unprocessible Entity | 格式正确，内容有误                               |
| 423 Locked               | 资源已被加锁                                     |
| 424 Failed Dependency    | 处理与某请求关联的请求失败，因此不再维持依赖关系 |
| 507 Insufficient Storage | 保存空间不足                                     |

## HTTP/2.0 带来了哪些新特性?

- 多路复用: 基于二进制帧首部标识字段区分不同请求;
- 服务器推送: SSE;
- 请求优先级: 控制响应优先级;
- 二进制分帧: 提高传输效率;
- 首部压缩: 压缩 http 首部信息;

## HPACK 如何压缩首部?

- HPACK: HTTP/2.0 使用的首部压缩算法，具有静态压缩和动态压缩两种方式;
- 静态压缩: 预先建立称为静态表的字典，将经常使用的首部字段预先编码并存储在静态表中; 传递 HTTP 请求时，仅发送静态表的索引;
- 动态压缩: 基于哈希算法，对 HTTP 首部进行编码，双方维护一张哈希表; 传递 HTTP 请求时，仅发送哈希表索引值;
- 空间管理: 哈希表空间不足时，优先删除最少使用的首部字段;
- 收益: 首部字段从每次原样重发变成只发索引，重复首部的传输量大幅下降;

## HTTP/3.0 为什么改用 UDP?

- HTTP3.0: 使用 UDP 协议传输，基于 UDP 实现 QUIC 协议;
- 前向纠错: 基于 FEC 技术，通过发送冗余数据还原丢包数据; 额外发送一个校验包，其值为所有数据包的异或值;
- 还原条件: 若任一非校验包丢包且只丢失一个包，可通过其他包还原;
- 重传机制: QUIC 具备重传机制;
- 堵塞控制: QUIC 具备堵塞控制;

## HTTP/3.0 的两点优势是什么?

- 一次握手: HTTP3 只需要一次握手，第一个包即可携带请求数据;
- 无队首堵塞: HTTP2 使用的 TCP 和 TLS 均存在队首堵塞，HTTP3 基于 UDP，服务器端无滑动窗口，即无数据包的处理顺序;
- 代价: 前向纠错要额外发送校验包，用冗余数据换丢包还原能力;
