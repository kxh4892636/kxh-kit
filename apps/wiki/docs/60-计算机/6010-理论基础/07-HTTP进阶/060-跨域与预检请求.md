# 跨域与预检请求

## 同源策略限制了什么?

- 同源策略: 限制不同源之间的资源如何交互;
- 同源: 两个 URL 的协议、主机和端口号都相同才算同源，三者有一项不同就是跨域;
- 通俗解释: 浏览器默认不信任别的网站发来的页面，怕一个页面偷偷读走另一个网站的数据;

| 限制内容 | 具体表现                                             |
| -------- | ---------------------------------------------------- |
| 存储读取 | js 无法读取非同源网页的 cookie、storage 和 indexedDB |
| DOM 读取 | js 无法读取非同源网页的 dom                          |
| 请求发送 | ajax 和 fetch 不能发送跨域请求                       |
| iframe   | iframe 无法访问非同源 dom                            |
| 资源加载 | https 和 http 资源无法跨协议加载                     |

## 跨域有哪些可行方案?

- CORS: 通过设置 `Access-Control-Allow-Origin`，设置允许的源;
- 代理: 同源页面发送请求至同源服务器，服务器转发至跨域服务器，再将请求结果返回至同源页面; 跨域这一步由服务器完成，不经过浏览器的同源限制;
- WebSocket: websocket 并非 http 协议，不受同源策略限制，可用它进行客户端和服务器端通信;
- 选择依据: 浏览器端能改代码就用 CORS，只想要结果不想发跨域请求就用代理，本来就长连接通信就用 WebSocket;

## 预检请求在检查什么?

- options 请求: 浏览器发送跨域请求之前，先发送一个 options 请求，用于检查服务器是否允许该跨域请求;
- 谁跳过它: 简单请求忽略该 options 请求，直接发送;
- 代价: 复杂请求比同源请求多一次往返，服务器还要额外处理这个不携带业务数据的请求;

## 哪些请求算简单请求?

- 简单请求: 即使跨域也不会触发预检请求的请求;
- 方法约束: 请求方法必须为 POST、GET 或 HEAD;
- 首部约束: 只使用规定的首部字段 `Accept-*`、`Content-*`;
- Content-Type 约束: 只能是 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`;

## 什么情况下请求会变成复杂请求?

- 复杂请求: 违背简单请求约束的请求均为复杂请求;
- 触发条件一方法: 请求方法不在 POST、GET、HEAD 之内;
- 触发条件二首部字段: 使用了规定之外的首部字段;
- 触发条件三 Content-Type: 使用了三种允许值之外的类型;
- 后果: 复杂请求必须先通过预检，预检通过后才发送真正的请求;

## 预检响应里的关键首部字段有哪些?

| 首部字段                      | 含义                                             |
| ----------------------------- | ------------------------------------------------ |
| `Access-Control-Allow-Method` | 服务器允许的 http 方法                           |
| `Access-Control-Allow-Origin` | 服务器允许的跨域 URL                             |
| `Access-Control-Allow-Header` | 服务器允许的首部字段                             |
| `Access-Control-Max-Age`      | 预检请求缓存时间，缓存时间内不会再次触发预检请求 |

- 首部族命名: 这一组字段都以 `Access-Control-Allow-XXX` 的形式出现，分别对应方法、来源、首部与缓存时长;
- `Max-Age` 的价值: 把预检结果缓存下来，避免每个复杂请求都先来一次 options 往返;
