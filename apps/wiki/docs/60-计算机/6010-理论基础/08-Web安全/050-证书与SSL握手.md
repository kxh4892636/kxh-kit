# 证书与 SSL 握手

## CA 如何签发并验证一份公钥证书?

- CA（数字证书认证机构）: 可信赖的第三方机构，服务器端人员向 CA 申请公开密钥的数字签名;
- 签发: CA 基于自己的私有密钥加密数字签名，生成公开密钥证书;
- 签发细节: 基于明文信息，使用散列算法生成信息摘要，再基于 CA 私钥加密信息摘要，生成证书签名;
- 验证: 客户端基于 CA 的公开密钥对公开密钥证书进行验证;
- 验证细节: CA 的公开密钥事先保存至浏览器中，客户端使用相同散列算法生成信息摘要，基于 CA 公钥解密证书签名，对比证书签名和信息摘要，两者一致则合法;

## 自签名证书是怎么来的?

- OpenSSL: 基于 OpenSSL 构建私有认证机构，即自认证机构;
- 自签名证书: 该机构颁发的证书称为自签名证书;
- 代价: 它不在浏览器内置的可信 CA 之列，只能在自己的信任范围内使用;

## 安全通信机制由哪四条构成?

- 身份验证与密钥传递: 使用非对称加密进行身份验证和传递对称加密密钥;
- 数据加密: 使用对称加密进行数据加密;
- 完整性校验: 使用哈希算法验证数据完整性;
- 服务器真实性: 使用 HTTPS 证书保证服务器端的真实性;

## 一次 HTTPS 通信的简要步骤是什么?

- 客户端发送链接请求;
- 服务器发送公钥证书;
- 客户端验证公钥证书;
- 客户端生成随机密钥，使用服务器公钥加密随机密钥;
- 服务器使用私钥解密随机密钥;
- 对方使用随机密钥进行通信（对称加密）;

## SSL 四次握手的报文顺序是怎样的?

| 握手   | 方向            | 报文                | 内容                                                                   |
| ------ | --------------- | ------------------- | ---------------------------------------------------------------------- |
| 第一次 | 客户端 → 服务器 | Client Hello        | 随机数 1; 支持的加密算法; 支持的协议版本;                              |
| 第一次 | 服务器 → 客户端 | Server Hello        | 随机数 2; 选择的加密算法; 选择的协议版本;                              |
| 第一次 | 服务器 → 客户端 | Certificate         | 公钥证书;                                                              |
| 第一次 | 服务器 → 客户端 | Server Hello Done   | 第一次 SSL 握手结束;                                                   |
| 第二次 | 客户端 → 服务器 | Client Key Exchange | 随机数 3; 基于随机数 1、2、3 构造 pre-master secret，使用公钥加密发送; |
| 第二次 | 客户端 → 服务器 | Change Cipher Spec  | 表明之后通信使用 Pre-master secret 校验;                               |
| 第二次 | 客户端 → 服务器 | Finished            | 客户端侧握手完成;                                                      |
| 第二次 | 服务器 → 客户端 | Change Cipher Spec  | 表明之后通信使用 Pre-master secret 校验;                               |
| 第二次 | 服务器 → 客户端 | Finished            | 服务器侧握手完成;                                                      |
| 第三次 | 客户端 → 服务器 | HTTP 请求           | 开始传输应用数据;                                                      |
| 第三次 | 服务器 → 客户端 | HTTP 响应           | 返回应用数据;                                                          |
| 第四次 | 客户端 → 服务器 | close_notify        | 断开 SSL 连接，之后发送 TCP FIN 报文;                                  |

- 为什么分成四次: 前两次交换密钥材料，第三次开始传业务数据，第四次负责关闭;
- 关闭顺序: SSL 建立在 TCP 之上，先关 SSL 再关 TCP，所以 `close_notify` 先于 FIN 发出;

![HTTPS 通信时序](../images/2024-01-17-17-18-21.png)

## 已经握过手的连接怎么恢复?

- 基础: SSL 建立在 TCP 之上，SSL 断开时 TCP 依旧保持连接;
- 恢复方式: 使用重新握手建立 SSL 连接，在前两次握手的基础之上移除 Change Cipher Spec 报文;
- 收尾: 客户端发送到 Finished 报文后，使用 Pre-master secret 再次发送一个 Finished 报文;

## 为什么要用三个随机数?

- 增加解密难度: 随机数让每次握手的密钥材料都不同，攻击者无法用固定材料推算;
- 确保每个会话使用不同的密钥: 同一对客户端与服务器反复通信，每个会话的对称密钥也互不相同;

## 证书的两个作用是什么?

- 验证服务器身份: 确认正在通信的对方确实是证书上的那一方;
- 传递服务器公钥: 把服务器公钥交给客户端，用于加密通信使用的对称加密密钥;
