# 传输与序列化协议

一次 RPC 为什么需要“序列化、消息、传输”三层？Thrift 默认主线怎么组合？Kitex Protobuf 和 gRPC 有什么区别？选协议时该比什么？

## 一句话理解

- 序列化协议: 把结构体变成 payload 字节（如 Thrift Binary、Protobuf、Hessian2）;
- 消息协议: 在 payload 外写上“调用哪个方法、是请求还是响应、怎么关联、错误怎么表达”;
- 传输协议: 规定消息边界和连接承载（如 Framed、TTHeader、HTTP/2）;
- 类比: 序列化是“把货物装箱”，消息协议是“贴快递单”，传输协议是“选公路还是铁路”;

## 分层为什么必要

- 对象要过网络，必须变成字节: 这是序列化层;
- 接收方要知道“这段字节属于哪个方法、哪次请求”: 这是消息层;
- 接收方要知道“一条消息从哪里开始、到哪里结束”: 这是传输层;
- 分层让每一层可独立替换，例如同一套 Thrift 消息可以配 Framed 或 TTHeader;

## Thrift 主线

- Binary: Thrift 默认二进制序列化;
- Framed: payload 前加 4-byte 长度; Kitex v0.13.0 起为默认 Thrift transport;
- TTHeader: 在 payload 外携带 service、method、metainfo 等 header;
- TTHeaderFramed: TTHeader 与 Framed 组合;
- PurePayload: 无额外 transport header 的 payload;

```go
cli, err := userservice.NewClient(
	"user",
	client.WithHostPorts("127.0.0.1:8888"),
	client.WithTransportProtocol(transport.TTHeaderFramed),
)
if err != nil {
	return fmt.Errorf("create client: %w", err)
}
```

## Protobuf 与 gRPC

- Kitex Protobuf: 高性能 unary 协议; 不是标准 gRPC wire protocol;
- gRPC: Protobuf payload + HTTP/2 transport; 支持互通与 streaming;
- 自动选择: proto IDL 包含 stream method 时使用 gRPC;
- 显式选择: unary 也要求 gRPC 时配置 `transport.GRPC`;
- Server: 支持协议探测; Client 必须选择正确协议;

## 协议对比速查

| 维度               | Thrift                                                        | Kitex Protobuf                                          | gRPC                                                               |
| ------------------ | ------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------ |
| RPC 信封           | method、MessageType、SeqID、Args/Result/Exception             | Magic、MessageType、method、SeqID、Protobuf body        | HTTP/2 Headers、length-prefixed messages、Trailers                 |
| 业务体编码         | Thrift Binary                                                 | Protobuf                                                | 通常为 Protobuf                                                    |
| 方法与请求关联     | method + SeqID                                                | method + SeqID                                          | `:path=/Service/Method` + HTTP/2 Stream ID                         |
| 错误表达           | Result 或 Thrift Exception                                    | 自定义 Protobuf Error                                   | Trailers 中的 `grpc-status`、`grpc-message`                        |
| 外层承载           | Framed、TTHeader、TTHeaderFramed                              | Framed、TTHeader、TTHeaderFramed                        | HTTP/2                                                             |
| 交互模型           | PingPong、Oneway; streaming 需 TTHeader Streaming 或 gRPC     | unary PingPong                                          | unary、client streaming、server streaming、bidirectional streaming |
| wire compatibility | Buffered/Framed 可与兼容的 Apache Thrift 实现互通             | 仅与理解 Kitex 自定义信封的对端互通                     | 可与标准 gRPC 实现互通                                             |
| 优势               | 信封简单; 支持 Exception 与 Oneway; Kitex Thrift 路径成熟     | Protobuf 编码 + 轻量原生信封; 适合纯 Kitex 内部 unary   | 标准互通; 原生 streaming; HTTP/2 多路复用、流控与 Header/Trailer   |
| 限制               | 经典消息协议无 streaming; Binary 对部分数据可能比 Protobuf 大 | 自定义 wire protocol; 不兼容标准 gRPC; 不支持 streaming | 协议栈最复杂; 小型 unary 有更多 header、状态机与流控开销           |

## 常见误区

- 误区: 把“序列化协议”和“传输协议”混为一谈; 选型时要分别确认;
- 误区: 以为 Kitex Protobuf 就是 gRPC; 标准互通必须选 gRPC;
- 误区: Client 和 Server 协议不一致; 先确认服务端实际监听协议再配 Client;
