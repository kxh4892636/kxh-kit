# 传输与序列化协议

## 分层

- IDL: 定义数据与方法;
- serialization protocol: 将结构体编码为 payload; Thrift Binary、Protobuf、Hessian2;
- transport protocol: 规定消息边界、header 与连接承载; Framed、TTHeader、HTTP/2;
- message type: PingPong、Oneway、Streaming; 不等同于 transport;

## Thrift 主线

- Binary: Thrift 默认二进制序列化;
- Framed: payload 前加 4-byte 长度; Kitex v0.13.0 起为默认 Thrift transport;
- TTHeader: 在 payload 外携带 service、method、metainfo 等 header;
- TTHeaderFramed: TTHeader 与 Framed 组合;
- PurePayload: 无额外 transport header 的 payload;

```go
cli, err := userservice.NewClient(
	"user",
	client.WithHostPorts("127.0.0.1:8888"),
	client.WithTransportProtocol(transport.TTHeaderFramed),
)
if err != nil {
	return fmt.Errorf("create client: %w", err)
}
```

## Protobuf 与 gRPC

- Kitex Protobuf: 高性能 unary 协议; 不与 gRPC wire protocol 等价;
- gRPC: Protobuf payload + HTTP/2 transport; 支持互通与 streaming;
- 自动选择: proto IDL 包含 stream method 时使用 gRPC;
- 显式选择: unary 也要求 gRPC 时配置 `transport.GRPC`;
- Server: 支持协议探测; Client 必须选择正确协议;

## 特定互通

- Hessian2: 通过扩展 Codec 与 Dubbo 互通; 不属于 Kitex 核心序列化路径;
- Thrift streaming: Thrift IDL 配合 HTTP/2 承载流式方法;
- TTHeader: 需要 Kitex 元信息透传、服务标识或多 Service 路由时采用;

## 决策顺序

- 第一步: 先由互通对象决定 Thrift 或 Protobuf;
- 第二步: 再由 unary/streaming 决定消息模型;
- 第三步: 最后选择 Framed、TTHeader 或 gRPC transport;
- 第四步: Client 与 Server 进行兼容性测试，不凭名称猜测 wire compatibility;
