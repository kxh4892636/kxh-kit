# 消息类型与连接

Kitex 支持哪几种消息交互？PingPong、Oneway、Streaming 分别适用什么？连接模型有哪些？连接池参数怎么调？为什么 Client 要复用？

## 一句话理解

- 消息类型: 一次 RPC 调用里“请求和响应怎么交互”;
- 连接模型: Client 和 Server 之间如何复用底层连接;
- 类比: PingPong 像“一问一答”，Oneway 像“只寄信不等回信”，Streaming 像“打开语音通话持续说话”;

## 消息类型

| 类型      | 交互                   | 适用场景         | 约束                          |
| --------- | ---------------------- | ---------------- | ----------------------------- |
| PingPong  | 一次请求、一次响应     | 常规 RPC         | 默认选择                      |
| Oneway    | 只发送、不等待业务响应 | 可丢失通知       | 仅 Thrift; 不推荐承担可靠业务 |
| Streaming | 一个调用内多次收发     | 推送、上传、对话 | 处理 EOF、半关闭与取消        |

- Thrift: 支持 PingPong、Oneway，以及基于 HTTP/2 的 streaming;
- Kitex Protobuf: 支持 unary PingPong，不支持 streaming;
- gRPC: 支持 unary、client streaming、server streaming、bidirectional streaming;

## 连接模型

- 短连接: 每次请求建连; 成本高，只在实例数量或连接约束要求时使用;
- 长连接池: Kitex 默认模型; 每个 address 维护可复用连接;
- gRPC: HTTP/2 原生多路复用，一条连接可承载多个并发 stream;
- netpollmux: 旧 Thrift/Kitex Protobuf 多路复用实现已停止维护，新项目不要用;

## 连接池参数

- `MaxIdlePerAddress`: 每个目标保留的空闲连接数;
- `MaxIdleTimeout`: 空闲回收时间; 默认 30s，最小 3s;
- `MaxIdleGlobal`: 全局空闲连接上限; 过小会降低复用率;
- 调整依据: 下游实例数、并发、请求耗时、突发流量与文件描述符预算;
- 经验: 先观察 active/idle 和复用率，再调参数，不要拍脑袋;

## 选择规则

- unary 服务: 长连接池 + PingPong;
- 长时双向通信: StreamX/gRPC streaming;
- 大量下游实例: 控制每实例连接数，避免连接总数乘法膨胀;
- 首请求敏感: 使用 Client warming up 初始化发现与连接;
- 连接异常: 先区分建连失败、池无可用连接、对端关闭与传输超时;

## 监控

- 连接数: 按目标实例观察 active、idle 与建连失败;
- 复用率: 过低通常意味着池过大、idle timeout 过短或 Client 未复用;
- 延迟: 分离 discovery、connect、write、server 与 read 阶段;
- 状态报告: 可实现连接池 `Reporter` 接口接入监控;

## 常见误区

- 误区: Oneway 当可靠消息用; Oneway 不等待响应，失败难感知;
- 误区: 每个请求新建连接; 会放大握手开销和 fd 占用;
- 误区: Streaming 场景仍用 PingPong 轮询; 应评估长连接推送模型;
