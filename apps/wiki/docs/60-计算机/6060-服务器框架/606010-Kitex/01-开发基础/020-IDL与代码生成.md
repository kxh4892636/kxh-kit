# IDL 与代码生成

Thrift IDL 是什么？为什么 RPC 需要它？字段的 `required`、`optional` 和编号为什么重要？`kitex` 工具链怎么用？IDL 演进时如何保证兼容？Protobuf 分支和 Thrift 有什么不同？

## 一句话理解

- IDL: 接口描述语言; 用一份与语言无关的文件定义“有哪些方法、参数长什么样”，然后让工具生成各语言代码;
- 类比: IDL 像餐厅菜单; 顾客和服务员都按同一份菜单点菜，不会出现“我要 A 套餐，后厨却理解成 B 套餐”;
- 价值: 跨语言、跨团队对齐契约; 代码生成省去手写编解码和桩代码;

## Thrift IDL 基础

- field id: 字段在二进制协议里的身份; 一旦发布，不能修改含义或复用到其他字段;
- `required`: 语义上是“必须携带”; 但新增 required 字段会破坏旧调用方，维护成本高;
- `optional`: 未设置时不序列化; 是新增字段最常用的选择;
- 默认值: 接收方可能自动构造默认值; 想区分“没传”和“传了零值”时用 `optional`;
- service: 一组方法的集合; 生成代码时会变成接口、Client 和 Server 桩;

```thrift
namespace go api

struct GetUserRequest {
  1: required i64 id
}

struct GetUserResponse {
  1: optional string name
}

service UserService {
  GetUserResponse GetUser(1: GetUserRequest req)
}
```

## 工具链

- `-module`: 生成代码使用的 Go module path; 必须与 `go.mod` 一致;
- `-service`: 额外生成 Server scaffold; 不指定时只生成类型与 Client 桩;
- `-use`: 复用另一个 module 已生成的 `kitex_gen`，避免重复类型;
- `-I`: 增加被 `include` 的 IDL 搜索目录;
- 生成结果: `kitex_gen` 是派生产物; 不要手工修改，业务写在 Handler;

```powershell
go install github.com/cloudwego/kitex/tool/cmd/kitex@latest
go install github.com/cloudwego/thriftgo@latest
kitex --version
kitex -module example.com/user -service user api.thrift
```

## 演进流程

- 第一步: 用兼容方式修改 IDL（优先加 optional 字段，不改 field id）;
- 第二步: 重新运行相同的 `kitex` 命令;
- 第三步: 实现新增 Handler 方法;
- 第四步: 先发布兼容新旧契约的 Server，再发布使用新字段的 Client;
- 原则: 线上兼容性靠“字段编号不变 + 新字段 optional”来保证;

## Protobuf 分支

- Kitex 仅支持 proto3;
- `option go_package` 必须指向稳定导入路径;
- proto unary 默认使用 Kitex Protobuf（自定义信封，不是标准 gRPC wire）;
- IDL 包含 stream method 时自动切换到 gRPC;
- 没有 stream 但要求 gRPC 互通时，Client 显式配置 `client.WithTransportProtocol(transport.GRPC)`;

## 常见误区

- 误区: 修改字段编号或类型; 会导致线上新旧包互相读错;
- 误区: 手改 `kitex_gen`; 下次生成会覆盖，业务代码应依赖接口而非生成细节;
- 误区: 一上来就加 `required`; 新字段优先 `optional`，避免破坏老客户端;
