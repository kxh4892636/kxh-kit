# 错误处理与生命周期

## 错误分类

| 类别                  | 含义                   | 处理                     |
| --------------------- | ---------------------- | ------------------------ |
| BizStatusError        | 请求到达并完成业务判断 | 按业务码处理，不盲目重试 |
| timeout               | 超过连接或调用预算     | 判断阶段、幂等与剩余预算 |
| discovery/LB          | 无实例或选择失败       | 检查控制面与实例状态     |
| remote/network        | 对端或网络异常         | 保留错误链并结合链路定位 |
| circuit/overlimit/ACL | 治理主动拒绝           | 降载、退避或返回明确状态 |
| panic/internal        | Handler 或框架内部异常 | 报警并定位堆栈           |

## 业务异常

```go
func validateID(id int64) error {
	if id <= 0 {
		return kerrors.NewBizStatusError(400, "invalid user id")
	}
	return nil
}
```

- Server: `NewBizStatusError` / `NewBizStatusErrorWithExtra` 返回业务状态;
- Client: 将 error 转换为 `BizStatusErrorIface`，读取 code、message、extra;
- 原则: 业务错误表示 RPC 已成功执行; 不用 ErrorHandler 把它伪装成 transport error;

## RPCInfo 与 panic

- RPCInfo: 请求结束后进入 `sync.Pool`; 异步使用可能脏读或 panic;
- 异步需求: 先 `rpcinfo.FreezeRPCInfo` 复制;
- Handler panic: 框架恢复后返回带 `[happened in biz handler]` 的错误与堆栈;
- fatal error: 并发读写 map 等 runtime fatal 无法 recover;

## 优雅退出

- 第一步: readiness 先变为不可接收新流量;
- 第二步: Registry/编排平台完成摘流;
- 第三步: Server 等待在途请求与 stream;
- 第四步: 达到 `ExitWaitTime` 后强制结束;
- 第五步: 关闭 tracer/exporter、注册中心 Client 与其他资源;

- K8s: `preStop`、摘流传播时间、`ExitWaitTime` 必须小于 `terminationGracePeriodSeconds`;
- 上游: 不能假定下游 100% 优雅退出; 仍需处理换节点与短暂建连失败;
- 共享响应: 禁止多个请求并发修改同一 response; FastWrite panic 往往是业务数据竞争;
