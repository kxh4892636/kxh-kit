# 错误处理与生命周期

## 错误类型有哪些?

- RPC 异常: 请求没有按预期完成远程调用，例如超时、无实例、网络错误或治理拒绝;
- 业务异常: 请求已到达并完成业务判断，但结果不满足业务规则，例如用户不存在;

| 类别                  | 含义                   | 处理                     |
| --------------------- | ---------------------- | ------------------------ |
| BizStatusError        | 请求到达并完成业务判断 | 按业务码处理，不盲目重试 |
| timeout               | 超过连接或调用预算     | 判断阶段、幂等与剩余预算 |
| discovery/LB          | 无实例或选择失败       | 检查控制面与实例状态     |
| remote/network        | 对端或网络异常         | 保留错误链并结合链路定位 |
| circuit/overlimit/ACL | 治理主动拒绝           | 降载、退避或返回明确状态 |
| panic/internal        | Handler 或框架内部异常 | 报警并定位堆栈           |

## 业务异常如何进行处理?

- Server: `NewBizStatusError` / `NewBizStatusErrorWithExtra` 返回业务状态;
- Client: 将 error 转换为 `BizStatusErrorIface`，读取 code、message、extra;
- 原则: 业务错误表示 RPC 已成功执行; 不用 ErrorHandler 把它伪装成 transport error;

```go
func validateID(id int64) error {
	if id <= 0 {
		return kerrors.NewBizStatusError(400, "invalid user id")
	}
	return nil
}
```

## RPCInfo 与 panic

- RPCInfo: 保存一次 RPC 的服务、方法、地址、耗时和配置等上下文信息；请求结束后对象会进入 `sync.Pool` 复用;
- `sync.Pool`: 临时对象池；对象归还后可能被另一请求重新使用，因此原引用不再可靠, 有可能被其他请求使用了; 异步需求, 先 `rpcinfo.FreezeRPCInfo` 复制;

```go
info := rpcinfo.GetRPCInfo(ctx)
go func() {
    // 异步任务，可能在请求 A 结束之后才执行
    time.Sleep(time.Second)
    log.Println(info.To().Method())  // 危险！此时对象可能已被请求 B 复用
}()

ctx = rpcinfo.FreezeRPCInfo(ctx)   // 复制一份，脱离 Pool
go func() {
    ri := rpcinfo.GetRPCInfo(ctx)  // 用冻结后的副本，安全
    ...
}()
```

- Handler panic: Kitex 的 panic 携带 `[happened in biz handler]` 的错误与堆栈;

## 服务如何进行优雅的退出?

- 优雅退出: 服务停止接收新流量，但给正在处理的请求留出完成时间，再关闭进程和资源;
- 第一步: readiness 先变为不可接收新流量;
- 第二步: Registry/编排平台完成摘流;
- 第三步: Server 等待在途请求与 stream;
- 第四步: 达到 `ExitWaitTime` 后强制结束;
- 第五步: 关闭 tracer/exporter、注册中心 Client 与其他资源;
