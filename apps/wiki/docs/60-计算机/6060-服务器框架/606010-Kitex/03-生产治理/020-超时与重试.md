# 超时与重试

为什么超时是生产第一道防线？RPC timeout 默认是多少？重试有哪几种？重试为什么可能放大故障？什么时候该重试，什么时候该快速失败？

## 一句话理解

- 超时: 给一次调用设置“最多等多久”;
- 重试: 调用失败后“再试一次”;
- 类比: 超时是闹钟，重试是“没接电话再打一次”; 但对方可能只是忙，盲目重打会让情况更糟;

## 超时预算

| 超时               | 默认值      | 约束对象                   |
| ------------------ | ----------- | -------------------------- |
| Connect Timeout    | 50ms        | 建立连接                   |
| RPC Timeout        | 0，无限制   | 一次 unary RPC             |
| Read/Write Timeout | Server 配置 | 传输读写等待，不是 Handler |
| Exit Wait Timeout  | 5s          | Server 退出等待            |

- 生产基线: Client 必须显式设置 RPC timeout;
- deadline: 上游 ctx deadline、Kitex timeout 与下游预算取最早生效者;
- 判断: `kerrors.IsTimeoutError(err)` 识别 Kitex timeout 类别;
- 默认行为: RPC timeout 不会自动重试;

## 重试类型

- Failure Retry: 超时或指定错误/响应后再次调用;
- Backup Request: 超过延迟阈值并发发送备用请求，先成功者获胜;
- Mixed Retry: 组合 failure 与 backup 策略;
- 建连失败重试: 请求尚未发出时的框架机制;

```go
policy := retry.NewFailurePolicy()
policy.WithMaxRetryTimes(2)
policy.WithMaxDurationMS(800)

cli, err := userservice.NewClient(
	"user",
	client.WithRPCTimeout(300*time.Millisecond),
	client.WithFailureRetry(policy),
)
```

## 安全边界

- 幂等: 开启业务请求重试的首要前提;
- 总预算: 首次调用 + 退避 + 所有重试必须小于上游 deadline;
- 放大: 重试会增加下游流量; 故障时需要停止策略与熔断保护;
- 同节点: 默认优先换实例; 只有明确场景才启用 same-node retry;
- streaming: 不支持常规重试;
- backup: 延迟阈值参考 TP99; 过小会长期制造双倍请求;

## 决策

- 快速失败: 非幂等写、资源已耗尽、明确业务异常;
- Failure Retry: 幂等且瞬时网络/实例错误可恢复;
- Backup Request: 长尾延迟主导且下游容量充足;
- 不确定时: 先设置 timeout 与观测，不开启重试;

## 常见误区

- 误区: 不设 RPC timeout; 默认无限等待会让 goroutine 堆积;
- 误区: 对非幂等写开启自动重试; 可能重复下单或重复扣款;
- 误区: 重试次数大但总预算不设; 会拖垮上游调用;
