# 服务发现与负载均衡

## 什么是服务发现, 服务端如何注册实例, 客户端如何解析并选择实例

- Server: `server.WithRegistry` + `WithServerBasicInfo`;
- Client: `client.WithResolver`，service name 作为查询键;
- 直连: 已知地址时跳过发现; 适合本地开发、诊断与固定依赖;
- 实例元数据: zone、版本、权重、标签可参与路由与均衡;

```go
registry, err := etcd.NewEtcdRegistry([]string{"127.0.0.1:2379"})
if err != nil {
	return fmt.Errorf("create registry: %w", err)
}
svr := userservice.NewServer(
	new(UserServiceImpl),
	server.WithRegistry(registry),
	server.WithServerBasicInfo(&rpcinfo.EndpointBasicInfo{ServiceName: "user"}),
)
```

## 有哪些负载均衡策略

- WeightedRoundRobin: 默认策略; 按权重轮询;
- WeightedRandom: 按权重随机; 大样本下趋于均衡;
- ConsistentHash: 相同 key 尽量命中相同实例; 适合有状态或缓存亲和;
- Tagging Based: 根据标签筛选与路由多态实例;
- 自定义: 实现 LoadBalancer 接口，并通过 Client Option 注入;

## 服务发现和负载均衡的规则

- 服务名: 注册与发现两端必须一致;
- 更新: Resolver 必须处理新增、删除和权重变化;
- 空实例: 明确 fail-fast、缓存旧值或降级策略;
- 一致性哈希: key 不能为空，虚拟节点越多越均匀但构建成本越高;
- K8s DNS: ClusterIP 只暴露一个地址时，Client 无法感知 Pod 级实例并做严格负载均衡;

## 服务发现的第三方实现有哪些

- etcd、Consul、Nacos、Eureka、Polaris、ServiceComb、Zookeeper: 均由 kitex-contrib 适配;
- DNS: 适合由 DNS 提供实例记录的环境;
- RuleBasedResolver: 在现有 Resolver 上按元数据顺序执行过滤规则;
- 社区扩展: 不属于 Kitex 内核; 需要单独验证版本、故障语义与维护状态;
