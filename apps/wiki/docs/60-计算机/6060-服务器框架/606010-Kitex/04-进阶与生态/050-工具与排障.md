# 工具与排障

kitexcall 怎么用？RPC 调用出问题按什么顺序排查？常见错误码对应什么？Go 层面怎么诊断？如何构造最小复现并验证修复？

## 一句话理解

- kitexcall: 不写 Go 代码，直接用 IDL 和 JSON 发起 RPC 的工具;
- 排障顺序: 契约 → 寻址 → 建连 → 调用 → Server → 系统;
- 类比: 排障像查快递：先看地址对不对，再看车有没有发出，再看仓库是否签收;

## kitexcall

- kitexcall: 根据 Thrift/Protobuf IDL，用 JSON 从命令行发起 RPC;
- 用途: 本地联调、实例直连、协议验证与最小复现;
- 必需信息: IDL、目标地址、method、JSON request;
- transport: Buffered、Framed、TTHeader、TTHeaderFramed; 使用前确认服务端协议;
- Multi Service: method 使用 `ServiceName/MethodName`, 并选择能携带 service name 的 transport;

```powershell
kitexcall -idl-path api.thrift -m UserService/GetUser `
  -endpoint 127.0.0.1:8888 -d '{"id":1}'
```

## 排障顺序

- 契约: Client/Server 是否使用兼容 IDL 与生成版本;
- 寻址: service name、Resolver 结果、实例地址是否正确;
- 建连: 网络、TLS、协议、连接池与 connect timeout;
- 调用: RPC timeout、限流、熔断、重试与业务异常;
- Server: Handler 日志、panic stack、资源与下游依赖;
- 系统: goroutine、heap、CPU、文件描述符与连接数;

## 常见症状

- `ErrServiceDiscovery`: Resolver/Registry 或 service name 问题;
- `ErrGetConnection`: 地址、网络、协议或连接池问题;
- `ErrRPCTimeout`: 先分解 discovery/connect/write/server/read，不直接调大 timeout;
- `ErrCircuitBreak`: 下游错误率触发主动保护;
- `ErrOverlimit`: Server 容量保护触发;
- `[happened in biz handler]`: 业务 Handler panic;
- FastWrite/FastRead panic: 常见根因是请求/响应对象被并发修改;

## Go 诊断

- stack: 从 panic 起始位置定位首个业务 frame;
- race detector: 复现数据竞争; 生产启用有明显性能成本;
- pprof heap: 区分仍被引用、连接缓存、大包池化与真实泄漏;
- coredump + Delve: 无法从普通 stack 解释的 crash;
- 大对象: 持有 `[]byte`/`string` 子切片仍会保留完整底层内存;

## 测试与复现

- mock Client: 对 `kitex_gen/.../client.go` 的 Client interface 使用 `mockgen` 生成桩;
- middleware stub: 需要保留 Kitex 内置 middleware 行为时，在真实 Client 上注入自定义 middleware;
- 集成测试: 启动真实 Server/Client 验证协议、生成代码、治理和 tracing;
- race: 对共享 request/response 与异步 Handler 路径运行 Go race detector;
- 版本: 复现时记录 Kitex runtime、kitex tool、thriftgo/protoc 与生成文件版本;

## 验证闭环

- 用 kitexcall 构造最小请求;
- 同时记录 Client error chain、Server 日志和 trace;
- 每次只修改一个 timeout、协议或治理变量;
- 修复后重放原请求，并检查指标没有引入重试或连接放大;

## 常见误区

- 误区: 一看到 timeout 就调大; 应先定位耗时阶段;
- 误区: 不看协议直接 kitexcall; 服务端协议不匹配会得到难懂错误;
- 误区: 不复现就改配置; 要保留最小复现和修改前后证据;
