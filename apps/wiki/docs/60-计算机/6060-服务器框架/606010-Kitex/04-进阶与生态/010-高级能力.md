# 高级能力

## 能力地图

| 能力            | 解决的问题                        | 使用边界                     |
| --------------- | --------------------------------- | ---------------------------- |
| Generic Call    | 运行时才知道 IDL/service/method   | 网关、测试平台、流量代理     |
| Metainfo        | 跨 RPC 透传键值元信息             | 控制大小、敏感性与传播范围   |
| Multi Service   | 一个 Server 承载多个 service      | 路由必须携带 service name    |
| Server SDK Mode | 将 Kitex 嵌入已有 Server 生命周期 | 自行管理 listener 与启动退出 |
| gRPC Proxy      | 透明代理 gRPC 流量                | 不等于业务网关               |
| xDS             | 从控制面获取路由与治理配置        | 需要兼容的 xDS 环境          |

## 泛化调用

- Thrift binary: 直接转发编码后的 Args; 适合低开销流量中转;
- Map/JSON: 动态构造请求; 易用但分配与转换成本高;
- HTTP mapping: 根据 Thrift annotation 做 HTTP↔RPC 映射; 仅支持规定的注解与数据形态;
- DynamicGo: 减少动态转换开销; 受架构与协议支持范围约束;
- Client 复用: 按目标 service 建池; 禁止每请求创建泛化 Client;

## 数据与生命周期

- Payload Validator: 在 Handler 前校验生成类型; 适合契约级校验;
- FieldMask: 只序列化/反序列化选定字段; 默认是白名单语义;
- Frugal: JIT Thrift Codec; 首次编解码有 JIT 成本，slim 模板失去 fallback;
- RPCInfo/Metainfo: 异步持有前复制; 限制透传数据量;
- Start/Shutdown Hook: 注入业务初始化与清理; 失败策略必须明确;
- ErrorHandler: 自定义框架错误的编码或转换; 业务错误仍使用 BizStatusError;

## 特定架构

- Proxy Application: 拦截并转发原始请求; 需要处理协议、service/method 与错误映射;
- Multi Service: TTHeader/gRPC 等必须携带 service name; Pure Framed 无法可靠路由;
- GLS: goroutine-local 状态; 易被异步和 goroutine 切换破坏，优先使用 context;
- Request Profiler: 度量请求资源成本; 仅在需要精细成本归因时启用;
- Serialize On Demand: 大对象或代理按需字段处理; 先验证收益与兼容性;

## 选择原则

- 静态业务服务: 使用生成代码，避免 Generic Call;
- 元信息: 能放在显式请求字段就不依赖隐式透传;
- 高性能 Codec: 先用基准与 profile 证明瓶颈;
- 高级能力: 引入前明确 fallback、版本矩阵、监控与回滚路径;
