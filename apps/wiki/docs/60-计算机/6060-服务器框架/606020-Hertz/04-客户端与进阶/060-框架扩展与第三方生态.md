# 框架扩展与第三方生态

## 框架扩展点

- network: 默认 Netpoll 与 Go net 可按平台、协议和性能需求选择;
- protocol: 接入 HTTP/2 等协议实现;
- renderer/JSON: 替换响应渲染和 JSON 编码实现;
- tracer/instrumentation: 采集请求、网络和细粒度事件;
- logger: 将 Hertz 日志接口适配到 Zap、Slog 等实现;
- registry/discovery: Server 注册实例，Client 解析可用地址;
- response writer: 对写出行为进行受控扩展;

## 中间件速查

| 需求        | 代表扩展             | 使用边界                         |
| ----------- | -------------------- | -------------------------------- |
| 跨域        | CORS                 | 明确 origin、method、credentials |
| 身份        | JWT、KeyAuth、Paseto | 认证后仍需业务授权               |
| 会话与跨站  | Session、CSRF        | Cookie 场景配套使用              |
| 安全 Header | Secure               | 按 API/HTML 场景配置             |
| 压缩与缓存  | Gzip、ETag、Cache    | 避免压缩敏感响应与缓存私有数据   |
| 权限模型    | Casbin               | 策略存储、更新和审计需治理       |
| 接口文档    | Swagger              | 契约同步且管理入口受保护         |
| 诊断        | pprof、Sentry        | 不直接暴露公网或敏感上下文       |
| 国际化      | i18n                 | 稳定错误码与本地化消息分离       |

## 治理与观测

- logger: Zap、Logrus、Zerolog、Slog 选择一种主实现;
- telemetry: Prometheus 与 OpenTelemetry 组成指标和 Trace 主线;
- flow control: Sentinel 提供限流、熔断等治理能力;
- request metadata: Request ID 与 access log 串联一次调用;
- service registry: Nacos、Consul、etcd、Eureka、Polaris、ZooKeeper 等按现有基础设施选择;

## 选择标准

- maintenance: 活跃维护、发布节奏和安全响应能力;
- compatibility: 与当前 Hertz/Go 版本兼容，并有可重复测试;
- semantics: 明确 middleware 顺序、失败模式与默认值;
- observability: 扩展自身能暴露错误、耗时和容量指标;
- exit plan: 业务依赖接口，避免第三方类型扩散到领域层;

## 自定义扩展时机

- 已有扩展无法表达稳定需求，而不是只为减少几行胶水代码;
- 接口足够小，生命周期、并发安全和资源所有权清晰;
- 提供最小示例、单测、基准和失败注入;
- 协议与网络扩展风险最高，先用真实流量模型证明必要性;

## 排障顺序

```text
确认 Hertz 与扩展版本 → 缩小到最小 Engine → 检查中间件顺序
→ 检查 context/资源释放 → 开启指标与 Trace → 再做性能归因
```

- 不同时替换网络库、协议和 JSON 库后再比较性能;
- 区分框架默认行为、第三方扩展行为和应用配置;
- 生产升级先灰度，关注 panic、错误率、延迟和连接资源;
