# HTTP/2、H2C 与协议选择

## HTTP/1.1 默认线

- 成熟: 代理、调试和基础设施支持广泛;
- keep-alive: 连接可复用，但同一连接的并发能力受协议模型限制;
- 适用: 常规 JSON API、文件和多数公网服务;

## HTTP/2

- multiplexing: 同一连接并发多个 stream;
- header compression: 降低重复 Header 成本;
- flow control: 连接和 stream 都有流控，需要关注慢消费者;
- TLS: 浏览器和公网部署通常通过 TLS + ALPN 协商;
- Hertz 接入: 使用对应 HTTP/2 协议扩展，而不是仅改一个 Header;

## H2C

- H2C: 无 TLS 的 HTTP/2; 常用于受控内网;
- prior knowledge/upgrade: 客户端与代理必须支持相同协商方式;
- 安全: H2C 不提供机密性和身份校验，不能替代 TLS;
- 运维: 先验证负载均衡、服务网格和健康检查是否真正支持;

## 选型

| 场景                    | 建议                          |
| ----------------------- | ----------------------------- |
| 普通公网 REST           | HTTP/1.1 或网关协商 HTTP/2    |
| 大量并发小请求          | 压测 HTTP/2 multiplexing 收益 |
| 受控内网且已有 h2c 基建 | 可评估 H2C                    |
| 双向消息                | WebSocket，而非仅因 HTTP/2    |
| 服务端事件推送          | SSE 或流式响应                |

## 验证

- 功能: 客户端、入口代理和 Hertz 的协议协商一致;
- 性能: 对真实请求大小、并发和网络条件压测;
- 限制: 设置最大并发 stream、Header 与窗口边界;
- 降级: 明确 HTTP/2 不可用时是否回退 HTTP/1.1;
- 观测: 按协议版本记录连接、请求、重置和流控等待;
