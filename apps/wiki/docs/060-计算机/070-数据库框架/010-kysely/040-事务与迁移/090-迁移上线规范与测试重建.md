# 迁移上线规范与测试重建

## 迁移上线要遵守哪些规矩？

- 迁移是「一次性、不可回改」的脚本：合入主干后不要再改内容，只追加新迁移;
- 破坏性变更分两步：先加新列并双写，后续版本再删旧列;
- 部署顺序固定为「先跑迁移，再启动新代码」;
- 多实例同时启动是安全的，库级锁保证只执行一次，见 [编写迁移文件](./030-编写迁移文件.md)。

## 破坏性变更怎么分两步走？

| 阶段   | 动作                         | 老代码还能跑吗 |
| ------ | ---------------------------- | -------------- |
| 版本 A | 加新列（可空），新老代码双写 | 能             |
| 版本 B | 回填历史数据                 | 能             |
| 版本 C | 加约束、删旧列               | 只保留新代码   |

- 任何一步失败都能回退到上一版本，不会出现「库已改、代码没改」的死局;
- 大表回填要分批，见 [批量写入](../030-写入数据/060-批量写入.md)。

## 回滚策略该怎么定？

- `down` 只保证结构能还原，**不保证数据能还原**（删列的数据不会回来）;
- 生产回滚优先用「新迁移反向修」而不是 `migrateDown`;
- 危险迁移（删列、删表）先在备份上演练，见 [SQLite 并发与运维](../060-速查/040-SQLite并发与运维.md)。

## 测试环境怎么快速重建？

- 每个测试文件用 `:memory:` 库，跑一遍迁移即得到干净结构;
- 或直接 `db.schema.createTable(...)`，跳过迁移以减少测试耗时;

```ts
const db = new Kysely<Database>({
  dialect: new SqliteDialect({ database: new SQLite(":memory:") }),
});
await migrator.migrateToLatest();
```

- 每个用例结束后 `await db.destroy()`，否则内存库句柄不释放，测试进程可能挂住;
- 迁移本身也要有测试：至少验证 `up` → `down` → `up` 能跑通。

## 上线前核对清单是什么？

- [ ] 迁移文件已提交且文件名顺序正确;
- [ ] 本地与 CI 都能从空库跑到最新;
- [ ] `up` 与 `down` 成对，且 `down` 真的能跑;
- [ ] 破坏性变更按三步走;
- [ ] 备份已完成，且验证过可恢复。

- 脚本怎么写见 [在脚本与 CI 中运行迁移](./080-在脚本与CI中运行迁移.md)。
