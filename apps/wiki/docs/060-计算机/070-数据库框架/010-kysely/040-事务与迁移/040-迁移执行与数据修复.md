# 迁移执行与数据修复

## 迁移能保证只跑一次吗？

- 能。Kysely 会在库里建 `kysely_migration`、`kysely_migration_lock` 两张表，并加库级锁;
- 多个进程同时调 `migrateToLatest()` 也会串行，只成功一次；进程崩溃后锁自动释放;
- SQLite 上这两张表会出现在 `db.introspection.getTables()` 里，属正常现象。

## 迁移里能跑数据修复吗？

- 能，迁移文件里就是普通 `db`，可以查出来再改;
- 数据量大时用一条 `sql` 处理，别在迁移里写业务逻辑;

```ts
import { sql } from "kysely";

export async function up(db: Kysely<any>) {
  await sql`update person set last_name = '' where last_name is null`.execute(db);
}
```

- 需要分批时循环加 `limit`，或像 [批量写入](../030-写入数据/060-批量写入.md) 那样切块;
- 修复数据的迁移不要依赖当前业务代码，条件写死在当时的数据形态上。

## 迁移失败了怎么查？

| 现象                              | 原因                       | 处理                                      |
| --------------------------------- | -------------------------- | ----------------------------------------- |
| `error` 非空但 `results` 只有部分 | 中途某条失败并回滚         | 看 `results[].status == 'Error'` 定位文件 |
| 表已存在                          | 迁移被手工执行过           | 不要改历史迁移，追加新迁移或修复记录表    |
| 顺序冲突报错                      | 新迁移排到了已执行迁移之前 | 改名，或用 `allowUnorderedMigrations`     |
| `kysely_migration` 缺失           | 从未跑过迁移               | 直接 `migrateToLatest()` 即可             |

- 排查时先看 `kysely_migration` 表里记录到哪个版本;
- 需要人工干预时，先备份库，再改记录表。

## 迁移文件本身要注意什么？

- `up` 必需、`down` 可选；写 `down` 时考虑数据丢失（删列不可逆）;
- 迁移里写死表结构，不要引用业务类型别名;
- 上线规范与三步破坏性变更见 [迁移上线规范与测试重建](./090-迁移上线规范与测试重建.md)。
