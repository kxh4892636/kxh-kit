# 项目结构

## 小型项目如何组织？ 何时拆分 package？

- 小型项目: 优先保持结构简单;
- 拆包时机: 职责稳定后再拆分 package;

```text
hello/
├── go.mod      # module 配置文件
├── go.sum      # 依赖校验文件
├── main.go     # 可执行程序入口
└── calc/       # 普通业务包目录
    └── calc.go # calc 包源码
```

- 拆分依据: 职责形成稳定接口、被复用或需独立维护时才拆包;
- 反例: 文件变长不代表必须加包层级;
- 依赖方向: 新包要有清楚的调用方向, 避免互相引用成环;
- 经验: 接口放在需要该行为的一侧, 更容易缩小依赖;

## 常见分层包含哪些目录？ 各层职责是什么？

```text
project/
├── cmd/               # 可执行程序入口集合
│   └── server/        # server 程序入口目录
│       └── main.go    # server main 包入口文件
├── internal/          # 受父目录树导入边界约束的内部代码
│   ├── handler/       # 输入输出边界层
│   ├── service/       # 业务规则层
│   └── repository/    # 数据访问层
├── pkg/               # 可被外部 module 复用的公共包
└── go.mod             # module 配置文件
```

- `cmd`: 放程序入口;
- `pkg`: 可放公共包, 并非必需;
- `internal` 的强制规则: 见[可见性](../001-包与导入/040-可见性.md);
- handler: 处理输入输出;
- service: 表达业务规则;
- repository: 隔离存储操作;
- 前提: 职责未形成时不必先建空层;
