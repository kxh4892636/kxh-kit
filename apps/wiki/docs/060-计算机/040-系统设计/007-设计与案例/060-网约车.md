# 网约车系统设计

## 网约车案例需要支持哪些角色与操作？

- 乘客: 查看附近车辆、预计到达时间 ETA 与价格, 选择目的地叫车并查看司机实时位置;
- 司机: 接受或拒绝订单, 查看接客地点, 开始行程并在到达后结束;
- 质量目标: 高可靠、高可用、低延迟并可扩展, 派单正确性比地图位置绝对同步更重要;
- 扩展需求: 行程评价、支付及指标分析;
- 核心约束: 一个司机同一时刻不能接下冲突行程, 一个订单也不能被多个司机成功占有;

## 请求与定位上报的规模如何分别计算？

- 题设: 1 亿 DAU、100 万司机、每天 1000 万单;
- 动作量: 每用户每天 10 次业务动作;
- 口径: 每次记录按 400 B;

| 项目         | 计算            | 结果                 |
| ------------ | --------------- | -------------------- |
| 业务请求     | 1 亿 × 10       | 10 亿/日             |
| 平均业务 RPS | 10 亿 / 86400   | 11574/s, 约 12K/s    |
| 每日逻辑记录 | 10 亿 × 400 B   | 400 GB               |
| 十年逻辑记录 | 400 GB × 3650   | 1.46 PB              |
| 平均业务入口 | 400 GB / 86400  | 4.63 MB/s, 约 5 MB/s |
| 平均行程创建 | 1000 万 / 86400 | 115.74/s             |

- 假设边界: 请求不一定都永久保存, 若只存行程而非完整动作事件, 存储应按对应实体重算;

## 定位上报为什么要单列预算？

- 定位补充: 100 万在线司机每 5 秒上报一次即 20 万次/s;
- 结论: 已远大于业务请求基线;
- 位置带宽: 载荷、协议开销、乘客推送与轨迹保留要单列预算;
- 对照: 原文的 5 MB/s 覆盖不了全部系统;

## 定位带宽与地区峰值怎么算？

- 地区峰值: 请求集中在城市、上下班和活动区域, 全球平均值不能代表单个派单分区的容量;

## 行程和支付数据如何关联？

| 实体      | 关键字段                                                         | 主要约束           |
| --------- | ---------------------------------------------------------------- | ------------------ |
| customers | id、name、email、createdAt                                       | 乘客身份           |
| drivers   | id、name、email、dob、location、cabID                            | 司机资料与位置引用 |
| cabs      | id、driverID、type、regNo                                        | 车辆及司机关联     |
| trips     | id、customerID、driverID、status、source、destination、createdAt | 行程状态与双方归属 |
| ratings   | customerID、driverID、tripID、rating、feedback                   | 指定行程的评价     |
| payments  | id、tripID、method、amount、status                               | 行程支付结果       |

- 关系修正: 原图同时存 `trip.paymentID` 与 `payment.tripID`;
- 做法: 明确唯一权威关联或加事务约束, 避免两侧指向不同记录;
- 金额补充: 原图使用 float, 实际支付可采用最小货币单位整数或精确十进制, 并保存币种;

## 状态与存储怎么分层？

- 状态分离: 当前位置高频变化, 可保存在有过期规则的索引; 行程与支付状态需要可靠持久化;
- 行程约束: 适合事务模型;
- 空间查询: 可用专用索引;
- 反例: 不必让一个库承担全部高频职责;

## 接口如何防止操作到错误订单？

```text
requestRide(customerID, source, destination, cabType, paymentMethod, requestID) → ride
cancelRide(customerID, rideID, reason?) → result
acceptRide(driverID, rideID) → result
denyRide(driverID, rideID) → result
startTrip(driverID, tripID) → result
endTrip(driverID, tripID) → result
rateTrip(customerID, tripID, rating, feedback?) → result
```

- 原文修正: 取消接口只有 customerID 不足以唯一表达目标, 这里补充 rideID;
- 坐标: source 与 destination 是有序经纬度对;
- 需约定: 坐标系统、单位与合法范围;

## 身份与幂等怎么约束接口？

- 身份: `customerID` 与 `driverID` 必须对应认证主体;
- 还要: 行程操作时验证关联关系;
- 幂等: 叫车、取消、接单、结束行程都可能因重试重复;
- 做法: 按请求或状态版本保证只产生一次有效转换;

## 请求与行程是同一个东西吗？

- 请求与行程: 原文混用 ride 与 trip, 设计时区分等待匹配的叫车请求与已建立的行程;
- 还需: 明确 ID 映射;
