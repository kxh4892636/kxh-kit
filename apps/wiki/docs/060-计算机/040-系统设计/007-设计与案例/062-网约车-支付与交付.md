# 网约车支付与交付

## 支付完成如何可靠地反映到行程状态？

- 第三方支付: 原文采用 Stripe 或 PayPal 等处理器, 把支付渠道细节交给专门服务;
- 完成信号: 不以浏览器跳回成功页作为唯一证据, 应验证服务端事件并在必要时主动查询支付结果;

## Webhook 与状态边界怎么定？

- Webhook: 校验事件签名, 依据事件或支付 ID 幂等更新, 允许重复或乱序到达;
- 状态边界: 行程已完成而支付待处理是合理中间状态, 不能因网络超时再次扣费或把真实行程抹去;
- 参考: [Stripe Webhook 文档](https://docs.stripe.com/webhooks);
- 内容: 签名验证、重复事件与顺序处理要求;

## 地理分区与缓存怎样控制热点？

- 区域分区: 按城市或业务服务区域归属位置数据, 减少大多数附近查询的跨区请求;
- 边界查询: 用户靠近分区边缘时要查询相邻区域, 不能把邮编边界当作物理距离边界;

## 热点地区与缓存怎么处理？

- 热点地区: 分布不均时需细分热门区域;
- 边界: 单靠一致性哈希无法兼顾地理邻近与负载均匀;
- 缓存: 保存最近位置并附采样时间和 TTL, LRU 只能管理容量, 不能说明位置仍有效;
- 未命中: 可尝试读取可靠位置源, 但过旧位置只能作为历史信息, 不能直接用于实时派单;

## 行程通知怎样避免干扰派单？

- 通知: 接单、到达与支付事件进独立通知流程, 分发见 [即时通信](030-即时通信.md);
- 边界: 通知失败不改变已提交的司机归属;

## 行程统计应该记录到哪里？

- 统计: 收集等待时长、取消、匹配成功率与行程事件;
- 修正: 原文误用视频案例的 views 表, 这里应落进行程与业务事件模型;

## 节点故障时如何保持派单约束？

- 冗余: 服务、入口、缓存与持久存储都要有副本;
- 前提: 关键接单判断回权威状态, 不从延迟副本决定可用司机;
- 降级: 排名或分析故障可采用简化候选策略, 但不可牺牲重复接单约束;

## 需要验证哪些冲突场景？

- 验证场景: 两人抢一车、两车接一单、取消与接单同时发生;
- 还要覆盖: 位置过期、跨区查询、重复支付事件、连接中断;
