# 网约车匹配与位置

## 服务怎样分配实时与持久状态责任？

- 乘客服务: 管理乘客身份与资料;
- 司机服务: 管理司机、车辆与上报入口;
- 叫车服务: 接收请求、聚合附近司机并执行匹配, 管理匹配中的状态;
- 行程服务: 管理已接单后的开始、进行、完成和取消规则;
- 支付服务: 连接第三方支付并维护支付状态;

## 服务边界怎么划？

- 通知与分析: 通过事件独立工作, 分别负责用户触达与运营指标;
- 服务边界: HTTP、gRPC、服务发现或网格按通信需要选择, 先明确数据所有者再决定部署粒度;

## 从叫车到完成的主流程是什么？

```text
乘客提交起终点与车型 → 创建待匹配请求
→ 查询候选司机并估算 ETA → 邀约
→ 某司机原子接单 → 通知双方并持续显示司机位置
→ 接客后开始行程 → 到达后结束行程
→ 支付处理 → 允许评价
```

- 状态约束: 每一步只能由允许的前置状态进入, 拒绝订单不应意外结束其他司机的行程;

## 主流程的异常怎么处理？

- 不确定结果: 请求超时后应查询状态而非盲目创建第二个行程;
- 失败边界: 匹配超时、乘客取消、司机失联与支付失败各有不同处理, 不应统一回滚整个现实行程;

## 司机位置如何持续更新到乘客端？

- 上报: 按时间或移动距离上报 GPS 坐标与采样时间;
- 后台运行: 还要考虑系统权限与省电限制;
- 连接选择: WebSocket 可双向交换位置与状态, 周期 HTTP 上报同样可行;
- 澄清: 主动上报本身不是长轮询;

## 位置下行的边界是什么？

- 下行: 只有有权查看该司机的乘客接收相应更新, 不向所有用户广播完整轨迹;
- 新鲜度: 每个位置带时间戳并设置过期规则, 长期失联的司机不能继续作为可接单候选;
- 高频优化: 可合并更新并降低静止时采样频率, 精度与吞吐按 ETA 和用户体验要求权衡;

## 经纬度条件查询如何作为附近司机的基线？

```sql
SELECT driver_id, latitude, longitude
FROM driver_locations
WHERE latitude BETWEEN :min_lat AND :max_lat
  AND longitude BETWEEN :min_lon AND :max_lon;
```

- 初筛: 包围盒找出可能在附近的司机, 再用实际地理距离过滤, 不把矩形结果当精确半径结果;
- 单位修正: 原文用 `X±R` 混了经纬度与半径;
- 做法: 先把距离转成合法边界, 或用空间查询能力;
- 性能判断: 无合适索引的全表扫描可能昂贵, 但不能因此断言 SQL 本身无法支持大规模空间查询;

## Geohash 怎样用于司机候选查询？

- 路径: 给司机当前位置算 Geohash;
- 查询: 覆盖乘客周围区域的多个编码范围;
- 过滤: 再按坐标距离筛选;
- 索引位置: 热点位置数据可放内存索引, 以减少每次候选查询的访问成本;

## Geohash 的边界与取舍是什么？

- 边界条件: 跨网格司机不能因前缀不同而遗漏;
- 原理与精度表: 见 [空间索引](../006-可靠性与安全/010-Geohash.md);
- 使用判断: 实现简单且能复用字符串索引, 但需要处理覆盖范围、误差和高频更新;

## 四叉树怎样组织高密度地区的司机？

- 路径: 按区域保存司机, 密度超过阈值时继续细分, 查询只遍历与搜索范围相交的区域;
- 位置更新: 司机跨区域时移出旧节点并加入新节点, 查询应避免读到不一致的重复位置;
- 缓冲: 可以先记录最新位置并批量更新索引, 以吞吐换取明确可控的新鲜度延迟;

## 四叉树与 Hilbert 映射如何取舍？

- Hilbert 映射: 可辅助布局或范围访问, 但四叉树不依赖它;
- 机制: 见 [四叉树](../006-可靠性与安全/015-四叉树.md);
- 选择边界: 原文偏好四叉树, 但要结合更新频率、区域密度与现有空间数据库能力验证;
- 反例: 概念合适不等于最优;

## 多个司机同时接单时怎样避免重复匹配？

- 原子状态转换: 只有订单仍待匹配且司机仍可用时, 才能同时写入订单归属与司机占用状态;
- 竞争胜者: 使用条件写、版本号或事务决定唯一成功者, 失败者收到明确的已被接单结果;
- 原文修正: 单进程 Mutex 只保护进程内线程;
- 多实例竞争: 需要共享权威状态的原子保证;

## 跨存储的接单约束怎么保证？

- 跨边界: 订单与司机状态跨存储时要有协调、预占租约与补偿策略;
- 机制: 见 [分布式事务](../003-分布式数据/040-分布式事务.md);
- 租约过期: 旧接单请求不能在租约已失效后覆盖新归属, 应校验版本或隔离令牌;

## 如何从附近候选中选择合适司机？

- 候选过滤: 先排除位置过期、车型不符、不可接单或无权限服务该区域的司机;
- 排序: 综合到达时间、路网、评分和相关反馈, 而不只比较直线距离;
- 邀约: 可分批优先通知高排名司机, 设置响应期限, 避免同时向大量司机发出互相冲突的承诺;
- 高需求: 动态加价可反映供需紧张, 但价格必须在订单和支付中具有可解释、稳定的确认版本;
