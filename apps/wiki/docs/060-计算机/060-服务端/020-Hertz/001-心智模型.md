# Hertz 心智模型

## Hertz 在接入层负责哪一段？

- Hertz: CloudWeGo 的 HTTP 框架；接入层里 Engine 管寻址、中间件与生命周期;
- `hz`: 生成骨架;
- Handler: 只做 HTTP 到业务的适配;

## 一次 HTTP 请求在 Hertz 里怎么走？

- 顺序: 解析 → 全局中间件 → 路由匹配 → 组中间件 → Handler → 业务 → 编码写回;

```text
连接 → HTTP 解析 → 全局中间件 → 路由匹配 → 路由组中间件
    → Handler → Service → Repository → 响应编码 → 网络写回
```

## 一个 Handler 只该做哪三件事？

- 三件: 取 HTTP 输入、调 Service、把结果映射成响应;

```go
func (h *ArticleHandler) Get(ctx context.Context, c *app.RequestContext) {
	id, err := strconv.ParseInt(c.Param("id"), 10, 64)
	if err != nil {
		c.JSON(consts.StatusBadRequest, map[string]string{"code": "INVALID_ARGUMENT"})
		return
	}
	article, err := h.svc.Get(ctx, id)
	if err != nil {
		c.JSON(consts.StatusInternalServerError, map[string]string{"code": "INTERNAL"})
		return
	}
	c.JSON(consts.StatusOK, article)
}
```

- `ctx` 是取消与 deadline 的来源，一路传给 Service 和下游;
- Service 不接收 `*app.RequestContext`；分层边界见 [分层与依赖方向](../000-服务端知识/010-基础模型/020-依赖方向.md);
- Thrift IDL 在 Hertz 里只描述 HTTP 接口、驱动 `hz` 生成，不改变 HTTP 传输;

## 新增一个接口按什么顺序推进？

- 六步: 定契约 → 生成 → Handler → Service → 跑通 → 补中间件、退出、观测与发布;

1. 定 HTTP 方法、路径、请求字段、成功状态与错误响应;
2. 写 IDL，用 `hz` 生成模型、路由与 Handler 骨架;
3. Handler 绑定并校验输入，读身份，调 Service;
4. Service 做业务规则，Repository 隔离存储;
5. 用 curl 或 `ut.PerformRequest` 跑通成功与失败路径;
6. 补中间件、退出、观测和发布配置;

## Hertz 和 Kitex、长连接怎么分工？

- Hertz: HTTP 服务与网关；Kitex: 服务间 RPC；同一服务可以两者并存;
- 长连接: SSE、WebSocket、HTTP/2 按需接，普通 CRUD 不需要先开;
- 请求生命周期、超时预算、错误分类的原理见 [请求生命周期](../000-服务端知识/010-基础模型/010-请求生命周期.md)、[超时预算](../000-服务端知识/040-可靠性/010-预算模型.md)、[错误分类与响应](../000-服务端知识/020-契约与错误/030-错误分层与响应.md);
