# 扩展与排障

## 生成桩覆盖不到时有哪些扩展能力？

| 需求                    | 功能                 | 使用前确认                 |
| ----------------------- | -------------------- | -------------------------- |
| 运行时才知道 IDL 或方法 | Generic Call         | 是否真的无法用生成桩       |
| 向下游传业务元信息      | Metainfo             | 数据大小、敏感性与传播范围 |
| 同端口提供多个接口集合  | Multi Service        | 路由能携带 service name    |
| 接入已有监听与启停流程  | Server SDK / Invoker | 谁负责 listener 与退出     |
| 转发 gRPC 请求          | gRPC Proxy           | 是否需要透明转发           |
| 接入已有控制面          | xDS                  | 团队是否已有配套平台       |

- 落地顺序: 这些不是上线必修课，先让最小请求在目标环境成功，再补超时、错误与资源释放测试; 定位顺序本身是通用方法，见 [故障定位](../000-服务端知识/060-观测与交付/060-故障定位/010-排查顺序.md);

## 注册发现与配置中心怎么接？

- 注册: Server 用 `server.WithRegistry`，Client 用 `client.WithResolver`; service name 必须两端一致;
- 负载均衡: 算法默认 WeightedRoundRobin; 取舍见 [009-治理与观测接入](./009-治理与观测接入/010-超时重试与熔断限流.md);
- 适配器与配置中心: etcd、Consul、Zookeeper、Nacos、Polaris、Eureka、ServiceComb、DNS、RuleBasedResolver; 配置中心（etcd / Nacos / Zookeeper / Consul / Apollo / File）经 Suite 下发 timeout、retry、circuit breaker、fallback、limiting;
- ready 与版本: 注册成功不等于业务 ready，readiness 由业务依赖状态决定; `kitex-contrib` 由社区维护，不随内核保证兼容，固定 Kitex + 适配器 + 第三方 Client 的版本矩阵;

## kitexcall 怎么复现一次调用？

```powershell
kitexcall -idl-path api.thrift -m UserService/GetUser `
  -endpoint 127.0.0.1:8888 -d '{"id":1}'
```

- 必需信息: IDL、目标地址、method、JSON request; 适合实例直连与协议验证;
- transport: 可选 Buffered、Framed、TTHeader、TTHeaderFramed，用前确认服务端协议;
- Multi Service: method 写成 `ServiceName/MethodName`，并选能携带 service name 的 transport;

## 每个错误症状对应哪个入口？

| 症状                             | 入口                                                        |
| -------------------------------- | ----------------------------------------------------------- |
| 找不到实例或 service name 不匹配 | `ErrServiceDiscovery`                                       |
| 地址、网络、协议或连接池问题     | `ErrGetConnection`                                          |
| 超时                             | `ErrRPCTimeout`: 先分解 discovery/connect/write/server/read |
| 下游错误率触发保护               | `ErrCircuitBreak`                                           |
| Server 容量保护触发              | `ErrOverlimit`                                              |
| Handler panic                    | 文案含 `[happened in biz handler]` 与堆栈                   |
| FastWrite / FastRead panic       | 常见根因是请求/响应对象被并发修改                           |

- 错误透出: 不要用 ErrorHandler 把业务拒绝改成网络失败，业务码语义见 [003](./003-服务端开发.md);

## 异步任务和中间件里怎么读 RPCInfo？

```go
func logMethodAsync(ctx context.Context) {
	// 请求结束后 RPCInfo 会进 sync.Pool 被复用；异步读取前先冻结。
	frozen := rpcinfo.FreezeRPCInfo(ctx)
	go func() {
		log.Println(rpcinfo.GetRPCInfo(frozen).To().Method())
	}()
}
```

- 冻结: 只解决「读到别人的数据」，异步任务仍要自己管理 deadline 与退出; 中间件里 `next` 可能返回 nil，业务拒绝在 `rpcinfo.GetRPCInfo(ctx).Invocation().BizStatusErr()`，不在返回值里;
