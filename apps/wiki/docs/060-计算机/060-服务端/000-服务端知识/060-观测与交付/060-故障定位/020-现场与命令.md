# 现场与命令

## 故障排查时要保留哪些现场？

- 保留现场: 错误链、request_id、Trace、指标时间窗，比反复重试更有价值;
- 一次只改一个变量，改完用同一请求复现验证;
- 没有 request_id，跨服务只能靠时间对齐，容易误判；同时改多个配置，无法判断哪个生效。

## 故障排查用哪些命令抓运行态？

```bash
curl -i -H 'X-Request-ID: debug-1' http://localhost:8080/users/1
```

```bash
# Go 服务运行态
go tool pprof -http=:8080 http://localhost:6060/debug/pprof/goroutine
go tool pprof -http=:8080 http://localhost:6060/debug/pprof/heap
```

- 用同一个 request_id 串起网关、应用、下游日志;
- 对比故障时间窗内的指标（QPS、错误率、P99、连接数）;
- 混沌演练时保留「注入前/注入后」两组基线。

## 故障症状对应先查哪里？

| 症状           | 先查                             |
| -------------- | -------------------------------- |
| 401 / 403      | 认证中间件、token 过期、权限规则 |
| 404            | 路由注册顺序、路径参数、前缀     |
| 429            | 限流阈值、调用方维度             |
| 502 / 504      | 反向代理、上游超时、实例健康     |
| 超时但下游正常 | 连接池、队列、锁、GC             |
| 内存持续上涨   | goroutine/连接泄漏、缓存无上限   |

## 排查方式错了会看到什么症状？

| 症状             | 原因                        |
| ---------------- | --------------------------- |
| 反复重试掩盖问题 | 没有保留首次失败现场        |
| 调大超时后更慢   | 瓶颈是下游容量，不是超时值  |
| 本地复现不了     | 环境/协议/版本不一致        |
| 日志对不上       | 没有统一 request_id         |
| 只查应用不查系统 | 连接数、FD、GC 也可能是根因 |
