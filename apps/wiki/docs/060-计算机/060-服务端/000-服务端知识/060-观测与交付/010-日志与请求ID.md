# 日志与请求 ID

## 请求日志必须带哪些字段？

- 日志给机器查：一行一个 JSON，字段名固定，输出到 stdout;

```json
{
  "ts": "2026-10-27T12:00:00.123Z",
  "level": "info",
  "service": "article-api",
  "request_id": "9f2c1e7a5b",
  "trace_id": "4b8e...",
  "method": "GET",
  "path": "/articles/1",
  "status": 200,
  "duration_ms": 12,
  "error_code": "",
  "error_message": ""
}
```

- 每条请求日志至少带: 时间、级别、服务名、`request_id`、方法/路径、状态、耗时、错误;
- `error_message` 只放可公开的信息；堆栈单独字段，且只在内网日志;
- 采样: 正常请求按比例，错误请求全量保留;
- 字段名一旦确定就不要再改，采集端依赖它做索引。

## request_id 怎么贯穿一次请求？

```text
入口：读取或生成 request_id → 写入响应头与日志上下文
业务：日志自动带上 request_id；关键分支记录决策与输入摘要
出口：出站调用透传 request_id / trace 上下文
收尾：记录状态与耗时，错误额外记录堆栈
```

- `request_id` 在入口生成或透传，贯穿响应头、日志、Trace，出站调用继续带;
- 用随机值，不用自增；客户端传入时要校验格式与长度;
- 没有 request_id，跨服务排查只能靠时间猜。

## 访问日志与业务日志怎么分工？

- 访问日志记结果，业务日志记决策与上下文;
- 业务日志用结构化字段，不要把对象 `printf` 成一行;
- 日志级别: error 只给需要人处理的，warn 给可恢复异常，info 给状态变化;
- 不记录敏感字段: `Authorization`、`Cookie`、密码、token、DSN;
- 敏感字段一旦进日志，等于长期泄露，清理成本极高;
- 不在请求链路里同步写文件或远程日志服务，交给采集端;
- 多行日志与自由文本无法聚合，排障时要人工 grep。

## 日志写错会看到什么症状？

| 症状                   | 原因                                                 |
| ---------------------- | ---------------------------------------------------- |
| 跨服务查不到同一次请求 | 没有透传 request_id                                  |
| 日志无法聚合           | 多行输出或字段名不固定                               |
| 日志量暴涨             | 没有采样，或把整个请求体打出来                       |
| 凭证出现在日志平台     | 只过滤了 `password`，没过滤 `Authorization`/`Cookie` |
| 日志阻塞请求           | 同步写文件或远程服务                                 |
