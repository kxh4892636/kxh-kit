# 测试策略

## 测试按哪几层隔离边界划分？

- 分层依据是「隔离的边界」，不是代码行数;

| 层级         | 验证对象                       | 依赖                 |
| ------------ | ------------------------------ | -------------------- |
| Service 单测 | 业务规则、错误传播             | fake Repository      |
| Handler 单测 | 输入映射、状态码/业务码        | fake Service         |
| 集成测试     | 路由、序列化、中间件、RPC 接线 | 临时端口或进程内引擎 |
| 依赖集成     | SQL、索引、事务、缓存          | 真实依赖（容器）     |
| 运行态验收   | 配置、探针、观测、退出         | 接近生产的环境       |

- Service 用 fake Repository 测业务分支；Handler 用 fake Service 测映射与错误码;
- 集成测试只覆盖框架接线：路由、序列化、中间件、真实端口或进程内引擎;
- 只有依赖集成测试才连真实 MySQL/Redis，验证 SQL、索引、事务;
- 所有测试都连数据库，会慢、会互相污染、失败难定位。

## 每层要覆盖哪些失败路径？

- 参数错、未认证、无权限、不存在、冲突、下游超时，每层都要有;
- HTTP 接口用真实请求或进程内引擎覆盖状态码与响应体;
- 只测正常路径，线上第一批问题一定出在错误分支;
- 集成测试用随机端口，避免并行时冲突；依赖集成用一次性容器与独立库名。

## 一个失败路径单测长什么样？

```go
func TestCreateUser_InvalidEmail(t *testing.T) {
	svc := NewService(&fakeRepo{})
	_, err := svc.Create(context.Background(), CreateInput{Email: "bad"})
	if !errors.Is(err, ErrInvalidInput) {
		t.Fatalf("want ErrInvalidInput, got %v", err)
	}
}
```

## 交付前要跑哪些测试与检查命令？

```powershell
go test ./...
go test -race ./...
go vet ./...
```

- 交付前跑 race / vet / 静态检查；并发问题只能靠工具暴露，不跑 `-race` 时并发读写 map 会留到线上。

## 测试交付判定要拿哪四类证据？

- 契约兼容：新调用方 ↔ 旧服务、旧调用方 ↔ 新服务的关键调用通过;
- 故障路径：无实例、数据库失败、超时、限流、熔断、退出都有证据;
- 可观测：日志/指标/Trace 含 service 与 method，不泄露敏感数据;
- 运行态：readiness 摘流后无新请求，终止窗口内完成在途请求。

## 测试策略写错会看到什么症状？

| 症状                        | 原因                   |
| --------------------------- | ---------------------- |
| 测试慢且互相污染            | 单测连了真实数据库     |
| 线上错误码与测试不一致      | Handler 测试只断言 200 |
| 并发问题线上才出现          | 没跑 `-race`           |
| 集成测试偶发失败            | 共用固定端口或共享数据 |
| 交付后才发现探针/退出有问题 | 没有运行态验收         |
