# 性能与压测

## 压测前先定哪些目标和基线？

- 先测量再优化：没有基线的优化只是猜测;
- 先定目标: P99 延迟、吞吐、错误率、资源上限；目标不同，优化手段不同;
- 看分位不看平均，看饱和度（CPU、连接池、队列、GC）不看单点;
- 平均延迟会被大量快请求拉低，长尾才是用户体感;
- 优化顺序: 减少远程调用 → 减少数据量 → 加缓存 → 并发/批处理 → 换实现;
- 适用: 所有服务端服务。

## 压测按什么步骤找到拐点？

```text
定目标 → 建基线（单请求/混合场景）→ 逐步加压
→ 记录 P50/P95/P99、错误率、饱和度 → 找拐点
→ 定位瓶颈（CPU/DB/锁/GC/序列化）→ 优化 → 回归对比
```

- 逐步加压找拐点；拐点之后再加压，延迟与错误率会同时恶化;
- 压测环境要接近生产：同样的 CPU/内存、连接池、下游、数据量;
- 混合场景按线上比例构造读写比；数据量接近生产，避免全内存命中;
- 只压一个接口，会忽略共享资源（连接池、锁）的竞争；还要关注下游是否先被打满;
- 压测环境与生产不一致，结论不可迁移。

## 用什么命令压测和剖析？

```bash
# Go 基准与剖析
go test -bench=. -benchmem ./...
go tool pprof -http=:8080 http://localhost:6060/debug/pprof/profile?seconds=30

# HTTP 压测
npx autocannon -c 100 -d 30 http://localhost:3000/api/users
```

- 压测时打开性能剖析端口，但不要暴露到公网;
- 用 `Server-Timing` 或阶段打点定位耗时分布。

## 压测中的瓶颈常出现在哪些位置？

| 位置   | 症状                | 先看什么                |
| ------ | ------------------- | ----------------------- |
| 数据库 | 延迟随并发线性上升  | 慢查询、索引、连接池    |
| 连接池 | 等待时间高          | 池大小、实例数、DB 上限 |
| 序列化 | CPU 高、payload 大  | 字段裁剪、压缩          |
| 锁     | 并发上不去          | 临界区、全局锁          |
| GC     | 延迟毛刺            | 分配速率、对象生命周期  |
| 下游   | 本服务 CPU 不高但慢 | 下游分位与超时          |

## 压测结论失真会看到什么症状？

| 症状               | 原因                             |
| ------------------ | -------------------------------- |
| 压测很好，线上很慢 | 环境、数据量或下游不同           |
| 只优化平均延迟     | 长尾没有改善                     |
| 加压后错误率飙升   | 已过拐点，容量不足               |
| 数据库先挂         | 只压了应用，没算连接池与 DB 上限 |
| 优化后没有回归对比 | 没有保留基线                     |
