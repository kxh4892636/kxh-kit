# 依赖方向

## 分层模型把依赖指向哪边？

```text
传输层（HTTP / RPC）
   → Handler：解析、校验、身份、映射
      → Service：业务规则、事务边界、编排
         → Repository：存储接口
            → MySQL / Redis / 下游 RPC
```

- 所有服务端框架都只能向右依赖: Handler 可以依赖 Service，Service 不知道 Handler 的存在;
- Service 只依赖 Repository 接口，不依赖 ORM、HTTP、RPC 类型;
- Repository 返回领域对象，不返回数据库游标、ORM 查询对象。

## 怎么判断依赖方向做对了？

- 看「换传输协议或换数据库时，要改几层」: 只改一层才算对;

- Service 不导入框架包: Go 接收标准库 `context.Context`，Node 不接收请求上下文对象；业务才能在定时任务、CLI、其他入口复用;
- Repository 接口定义在消费方（Service）侧，实现放在基础设施层；测试用 fake 覆盖业务分支，不连数据库;
- 目录名不重要，依赖方向才重要；`main` / 组装函数是唯一组装点，不出包级全局单例。

## 依赖方向错了会有哪些症状？

| 症状                   | 原因                                               |
| ---------------------- | -------------------------------------------------- |
| 单元测试必须连数据库   | Service 直接依赖 ORM                               |
| 换 HTTP 框架要重写业务 | 业务写在 Handler 或请求上下文里                    |
| 循环依赖               | Repository 反向依赖 Service                        |
| 事务边界模糊           | 事务写在 Handler，或每个 Repository 方法各自开事务 |
| 业务层出现 HTTP 状态码 | 传输概念泄漏进领域层                               |
