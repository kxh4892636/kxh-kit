# 配置与启动顺序

## 配置的优先级顺序是什么？

- 所有服务端框架同一优先级: 代码默认值 < 配置文件 < 环境变量 < 启动参数; 后者覆盖前者;

```text
# 同一份配置的三个来源，后者覆盖前者
config/default.yaml
ENV=production
./server --listen=:8080
```

- 配置在启动时冻结: 运行中不改路由、中间件和监听地址;
- 运行中改配置要热加载、锁与回滚机制，成本远高于重启发布。

## 配置为什么必须在启动时校验？

- 带病启动会把「配置错误」变成线上 5xx，而且很难定位;

```go
type Config struct {
	Listen  string
	DSN     string
	Timeout time.Duration
}

func (c Config) Validate() error {
	if c.DSN == "" {
		return errors.New("DSN is required")
	}
	if c.Timeout <= 0 {
		return errors.New("timeout must be positive")
	}
	return nil
}
```

- 启动即校验: 缺必填项、超时为非正数、连接池上限冲突，直接失败;
- 依赖就绪才接流量: 数据库、缓存、注册中心连通后再打开 readiness;
- 先接流量再连数据库，会让一批请求必然失败;
- 校验失败时打印字段名，不打印值（可能是 Secret）。

## 配置里的 Secret 从哪里注入？

- 只来自环境变量或 Secret Manager，不进仓库、镜像、日志与错误响应;

- 密码、token、证书私钥用环境变量注入；配置文件只放可提交项;
- `.env` 只提交示例文件，真实值进 `.gitignore`；容器用 `--env-file` 或 Secret 挂载，不要把 `.env` 打进镜像。

## 服务启动顺序是什么？

```text
读取配置 → 校验 → 初始化日志/追踪 → 连接数据库/缓存/注册中心（带超时 Ping）
→ 创建 Repository → Service → Handler → 启动 Server → readiness 通过
```

- 退出按相反顺序执行，见 [优雅退出](../040-可靠性/040-优雅退出/010-退出顺序.md);
- 依赖连接失败要区分「重试可恢复」与「配置错误」：前者有限次重试，后者直接退出。

## 配置与启动做错有哪些症状？

| 症状                     | 原因                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------- |
| 改了环境变量不生效       | 代码里写死默认值，或读取顺序反了                                                                    |
| 启动成功但首批请求全 5xx | 依赖未连通就打开了 readiness                                                                        |
| 密钥进了镜像             | Secret 写进配置文件或构建参数                                                                       |
| 线上与本地行为不同       | 配置文件覆盖了环境变量，或本地缺省值不同                                                            |
| 启动迁移偶发失败         | 启动时执行 DDL，多实例并发（见 [GORM 与 MySQL](../050-数据访问/020-GORM与MySQL/010-建模与查询.md)） |
