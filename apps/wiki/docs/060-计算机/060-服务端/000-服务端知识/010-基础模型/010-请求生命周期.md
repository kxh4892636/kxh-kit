# 请求生命周期

## 一次请求在服务端经过哪些环节？

- 所有服务端框架共用一条链路，协议不同、阶段相同;

```text
客户端
  → 接入：建连、TLS、路由/方法匹配
  → 横切：认证、限流、日志、追踪、超时
  → 业务：参数校验 → 业务规则 → 事务边界
  → 依赖：数据库、缓存、其他服务
  → 响应：序列化、状态码/错误码
  → 横切收尾：耗时、指标、日志
```

## 请求的哪些逻辑必须收敛到边界？

- 认证、限流、日志、超时、错误响应只写一次；写进业务代码就会逐层重复，行为分叉;

- 中间件顺序决定行为: 先认证再限流，和先限流再认证，过载时表现完全不同;
- deadline 不向下传递: 下游一直占用连接，故障时形成雪崩;
- 错误只在边界写一次响应: 响应一旦写出，状态码不能再改。

## Handler 与 Service 的分界线在哪？

- Handler 是翻译层: 外部类型 → 领域调用 → 外部响应；它不该有业务规则;

- 业务写在 Handler: 换传输协议要重写一遍；放 Service，HTTP 与 RPC 可以共用;
- 业务层看到的是领域对象，不是 `Request`/`Response`/`RPCInfo`。

## HTTP 与 RPC 的同一环节如何对应？

| 环节     | HTTP                        | RPC                 |
| -------- | --------------------------- | ------------------- |
| 定位     | 方法 + 路径                 | 服务名 + 方法名     |
| 输入     | 路径、查询、Header、Body    | IDL 生成的结构体    |
| 输出     | 状态码 + Body               | 响应结构体 + 错误   |
| 业务失败 | 4xx/5xx + 业务码            | 业务错误码 + 消息   |
| 横切     | 中间件链                    | 中间件链            |
| 连接     | keep-alive / HTTP2 多路复用 | 长连接池 / 多路复用 |

- 传输层只负责「把请求送到、把响应带回」，不承载业务判断。

## 请求链路上线前要自查哪几项？

- 六项都在入口处一次确认:

- [ ] 入口有超时上限吗？
- [ ] 鉴权在业务之前吗？
- [ ] 参数在进入业务前校验了吗？
- [ ] 业务是否只依赖领域接口？
- [ ] 错误是否只写一次响应？
- [ ] 响应头 / Trace / 日志里有 request_id 吗？

## 请求生命周期错位有哪些症状？

| 症状                     | 原因                                                                   |
| ------------------------ | ---------------------------------------------------------------------- |
| 换协议要重写业务         | 业务规则写在 Handler 里                                                |
| 过载时先被打满再鉴权     | 限流中间件写在认证之前                                                 |
| 日志重复或缺失           | 每层都打日志，或中间件顺序颠倒                                         |
| 异步任务读到别的请求数据 | 直接持有会被复用的上下文（连接对象、请求对象、RPC 信息），异步前没复制 |
| 下游超时后连接堆满       | 没有把 deadline 继续传给下游                                           |
