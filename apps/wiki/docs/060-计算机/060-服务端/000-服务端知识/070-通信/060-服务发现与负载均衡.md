# 服务发现与负载均衡

## 服务发现与负载均衡各负责什么？

- 服务发现把「服务名」解析成「可用实例列表」；负载均衡从列表里选一个;
- 适用: 多实例部署、按服务名调用的内部服务;
- 注册与发现两端的服务名必须一致；名字是发现、观测、治理的共同键;
- 只按轮询选实例、忽略延迟与负载，会让慢实例持续接流量;
- K8s 的 ClusterIP 只暴露一个虚拟地址，客户端无法感知 Pod 级实例。

## 五种负载均衡算法怎么选？

| 算法                | 特点                    | 适用                 |
| ------------------- | ----------------------- | -------------------- |
| 轮询 / 加权轮询     | 简单、可预测            | 实例同构、请求均匀   |
| 随机 / 加权随机     | 大样本下趋均衡          | 实例多、无状态       |
| 最少连接 / 最少请求 | 跟随负载                | 请求耗时差异大       |
| 一致性哈希          | 相同 key 命中同一实例   | 缓存亲和、有状态分片 |
| 标签 / 区域路由     | 按 zone、版本、灰度分流 | 多活、灰度           |

## 服务实例列表变化时客户端要做什么？

```text
服务启动 → 注册实例（地址、权重、元数据）
客户端 → 解析服务名 → 订阅列表变化 → 过滤不健康实例
→ 按算法选实例 → 调用 → 失败时换实例重试
服务下线 → 先注销 → 等待摘流 → 停止进程
```

- 实例列表会变：新增、下线、权重变化、健康状态变化都要能处理;
- 列表陈旧会把请求打到已下线实例，表现为间歇性连接失败;
- 空实例要有明确策略：快速失败、短暂缓存旧列表，或降级；没有策略，注册中心抖动会直接放大成业务故障;
- 注册成功不等于业务就绪，readiness 由依赖状态决定;
- 列表更新要防抖，避免频繁重建连接池;
- 一致性哈希的 key 不能为空；虚拟节点越多越均匀，但构建成本越高;
- 观测每个实例的成功率、延迟与连接数，而不只是服务整体。

## 服务发现配错会看到什么症状？

| 症状                     | 原因                              |
| ------------------------ | --------------------------------- |
| 间歇性连接失败           | 实例列表陈旧，打到已下线实例      |
| 灰度流量不生效           | 元数据/标签没有参与路由           |
| 缓存命中率低             | 一致性哈希 key 为空或不稳定       |
| 注册中心抖动导致全站故障 | 空实例没有降级策略                |
| K8s 下负载不均           | 只配了 ClusterIP，没有 Pod 级发现 |
