# RPC 与 HTTP 的选择

## 对外接口和内网调用各该选什么协议？

- 对外、面向浏览器或第三方的接口用 HTTP：生态广、可调试、网关友好;
- 内部高频、强契约、需要超时/重试/熔断治理的调用用 RPC;
- 适用: 需要划分内部调用与对外接口的服务;
- RPC 需要 IDL、代码生成、版本管理，团队与工具链成本更高;
- HTTP JSON 可读、易调试，但契约约束弱，字段变更容易失控;
- RPC 的收益来自契约与治理，不是「看起来更快」；没有这些需求时，HTTP JSON 更简单。

## HTTP 与 RPC 的七个维度怎么对比？

| 维度     | HTTP + JSON              | RPC + IDL                |
| -------- | ------------------------ | ------------------------ |
| 契约     | OpenAPI / Schema，弱约束 | IDL，强约束              |
| 代码生成 | 可选                     | 必需                     |
| 调试     | curl 即可                | 需要专用工具             |
| 性能     | 文本序列化，开销较大     | 二进制，开销较小         |
| 治理     | 依赖网关/中间件          | 框架内置超时、重试、熔断 |
| 跨语言   | 天然支持                 | 依赖 IDL 与生成器        |
| 适用     | 对外、变化频繁、弱契约   | 内部、稳定、强契约       |

- 把内部 RPC 直接暴露到公网，会把内部拓扑、错误码与方法名一起暴露。

## 协议边界为什么放在网关？

- 外部 HTTP 进来，内部转 RPC；不要让外部直接依赖内部 RPC 契约;

```text
调用方在公网 / 浏览器 → HTTP
调用方是内部服务，且需要强契约与治理 → RPC
调用频率低、字段常变 → HTTP JSON
需要流式/双向 → 见 [流式与长连接](./020-流式与长连接/010-选型与边界.md)，不要只按 RPC/HTTP 二分
```

- 同一个业务能力不要同时暴露两套语义不同的接口;
- 网关做协议转换时，要保留 request_id、超时预算与错误码映射;
- 两种协议都要有超时、错误码、request_id 与可观测性，不能只给 RPC 配。

## 协议选错会看到什么症状？

| 症状                             | 原因                               |
| -------------------------------- | ---------------------------------- |
| 内部调用没有超时                 | 只给 RPC 配了治理，HTTP 客户端裸调 |
| 对外接口字段频繁破坏兼容         | 没有 Schema 与兼容性评审           |
| 网关转换后错误码丢失             | 只映射了 HTTP 状态，没映射业务码   |
| 内部方法名泄露到公网             | RPC 直接暴露，没有网关             |
| 为了「性能」上 RPC，维护成本更高 | 没有评估 IDL 与工具链成本          |
