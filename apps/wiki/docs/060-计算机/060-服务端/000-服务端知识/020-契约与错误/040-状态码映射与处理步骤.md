# 状态码映射与处理步骤

## HTTP 状态码与业务码怎么映射？

| 场景                 | HTTP | 业务码              |
| -------------------- | ---- | ------------------- |
| 参数缺失或格式错     | 400  | `INVALID_ARGUMENT`  |
| 未认证               | 401  | `UNAUTHENTICATED`   |
| 已认证但无权限       | 403  | `PERMISSION_DENIED` |
| 资源不存在           | 404  | `NOT_FOUND`         |
| 版本冲突、唯一键冲突 | 409  | `CONFLICT`          |
| 限流                 | 429  | `RATE_LIMITED`      |
| 未分类内部错误       | 500  | `INTERNAL`          |

- RPC 用对应的状态码表达同一套语义；业务码仍然保留;
- 429 要带 `Retry-After`；5xx 只对幂等请求考虑重试;
- 超时归为 504 或传输错误，不要伪装成业务失败。

## 一次错误从捕获到响应要经过哪些步骤？

```text
捕获错误 → 分类（传输/业务/系统）→ 映射状态与业务码
→ 生成/透传 request_id → 写响应（只写一次）→ 记录日志（含堆栈）
```

- 内部错误对外统一文案，细节留在日志;
- 同一请求不要返回两种错误（例如既写 400 又写 500）;
- 错误码要有清单和负责人，新增要评审。
