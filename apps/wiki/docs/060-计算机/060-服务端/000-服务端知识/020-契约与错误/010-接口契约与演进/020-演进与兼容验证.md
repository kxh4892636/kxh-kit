# 契约演进与兼容验证

## 接口字段怎么演进才不破坏兼容？

| 变更         | 兼容性 | 做法                   |
| ------------ | ------ | ---------------------- |
| 新增可选字段 | 兼容   | 直接发                 |
| 新增必填字段 | 不兼容 | 先给默认值，再逐步强制 |
| 改字段类型   | 不兼容 | 新增字段，双写过渡     |
| 复用字段编号 | 不兼容 | 禁止                   |
| 删除字段     | 需过渡 | 先停读写、观察，再删   |
| 改方法语义   | 不兼容 | 新增方法，旧方法保留   |

- 枚举新增值要确认旧调用方的默认分支;
- 契约变更与实现变更分开提交，方便回滚;
- 删除字段分两步: 先停止读写并观察，再删定义。

## 接口发布前怎么验证双向兼容？

```text
写契约 → 兼容性评审 → 生成代码 → 实现 → 双向兼容测试 → 发布 → 观察旧版本流量 → 下线旧字段
```

- 兼容性双向验证: 新调用方对旧服务、旧调用方对新服务;
- 二进制协议按字段编号解析: 编号复用会让旧数据被解释成新含义;
- 旧调用方不认识新字段，新增必填字段会让它直接失败;
- 生成代码也要 review，重点看 diff 是否只包含预期变更。

## 接口契约破坏后会看到哪些症状？

| 症状                   | 原因                               |
| ---------------------- | ---------------------------------- |
| 上线后旧调用方解析失败 | 新增了必填字段或改了类型           |
| 数据出现「脏读」       | 字段编号被复用                     |
| 生成代码与实现冲突     | 手改过生成文件                     |
| 本地能调、联调失败     | 只对了契约，传输协议或序列化不一致 |
| 删除字段后旧数据读不出 | 没有分两步下线                     |
