# 文件上传

## 文件上传为什么必须先限制再解析？

- 上传是「不可信输入 + 大 body」: 限制必须在解析之前生效；纯 RPC 用字节字段 + 长度校验;

- 三类上限都要设: 单文件大小、请求总大小、文件数量;
- 超大 body 会在解析阶段打满内存，属于低成本 DoS。

## 上传文件的类型怎么校验？

- 看文件内容（魔数）与允许列表，不看扩展名，也不只看 `Content-Type`;

- SVG、HTML 等类型被当页面打开时会执行脚本;
- 图片做二次转码，文档走扫描或沙箱预览。

## 上传文件的名称与存储路径怎么定？

- 服务端生成文件名，用户文件名只作展示；绝不直接拼路径;

- 用户文件名可含 `../` 或空字节，直接落盘会路径穿越;
- 上传目录与站点不同源，响应加 `Content-Disposition: attachment`;
- 下载走鉴权代理或签名 URL，不暴露真实存储路径。

## 文件上传的请求与处理流程长什么样？

```http
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----x

------x
Content-Disposition: form-data; name="file"; filename="a.png"
Content-Type: image/png

<binary>
------x--
```

```text
鉴权 → 大小限制（代理层 + 应用层）→ 解析 multipart → 校验数量/类型/大小
→ 生成内部文件名 → 落对象存储或沙箱目录 → 记录元数据 → 返回文件 ID
```

- 需要流式接收时，边读边写并累计字节数，超过上限立即中断;
- 失败要区分「太大」「类型不允许」「存储失败」，分别给 413、400、500;
- 大文件走对象存储直传，应用只发签名，避免穿过后端进程。

## 文件上传有哪些常见失败？

| 症状                 | 原因                                             |
| -------------------- | ------------------------------------------------ |
| 上传大文件后进程 OOM | 没有 body 限制，或限制挂在解析之后               |
| 文件被当页面执行     | 上传目录与站点同源，且没有 `Content-Disposition` |
| 任意路径写入         | 用用户文件名拼接存储路径                         |
| 传了可执行文件却通过 | 只校验扩展名或 `Content-Type`                    |
| 下载链接被猜中       | 用自增 ID 或真实路径直接暴露                     |
