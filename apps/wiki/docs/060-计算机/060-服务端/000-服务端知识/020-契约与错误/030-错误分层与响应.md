# 错误分层与响应

## 接口错误为什么先分三层？

- 三层: 传输错误（没到）、业务拒绝（到了但不满足规则）、系统故障（到了但处理失败）；HTTP 与 RPC 接口都按这三层分;

- 4xx 与 5xx 的调用方行为不同: 4xx 通常不重试，5xx 才可能重试;
- 业务拒绝不是故障: 不报 5xx、不触发告警、不盲目重试;
- 错误信息泄露内部结构，是最常见的低成本攻击入口。

## 错误响应对外说哪三样东西？

- 状态（HTTP 状态或 RPC 状态）、稳定业务码、安全 message；堆栈、SQL、DSN、内部主机名只进服务端日志;

```json
{
  "code": "ARTICLE_NOT_FOUND",
  "message": "article not found",
  "request_id": "9f2c1e7a5b",
  "details": { "field": "id" }
}
```

- HTTP 状态表达类别，`code` 表达具体业务原因;
- `message` 面向调用方，可公开；`details` 只放结构化校验信息，不做调试容器;
- 业务码稳定，前端才能做分支；message 会变，不能拿来判断;
- 每个响应都带 `request_id`，把响应、日志、Trace 串起来;
- 错误只在边界写一次响应，中间层只返回 error。

## 错误响应设计错了会有哪些症状？

| 症状                  | 原因                                 |
| --------------------- | ------------------------------------ |
| 所有错误都返回 200    | 用业务字段表达失败，网关与监控看不见 |
| 前端无法区分失败原因  | message 随版本变化，没有稳定业务码   |
| 业务拒绝触发大量告警  | 把业务错误记成 5xx                   |
| 日志里出现 DSN / 密码 | 错误对象直接序列化输出               |
| 重试把写请求执行两次  | 没区分 4xx/5xx，也没检查幂等         |
