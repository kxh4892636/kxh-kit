# 跨源访问

## CORS 与同源策略是什么关系？

- CORS 是浏览器在同源策略上的放行机制，不是服务端鉴权；绕过浏览器的请求不受它约束；纯 RPC 服务不适用;

- 同源 = 协议 + 主机 + 端口三者完全一致，任一不同就是跨源;
- 跨源请求分两类: 简单请求直接发出，其余先发 `OPTIONS` 预检;
- 浏览器默认禁止脚本读取跨源响应，防止恶意站点借用户 Cookie 读取数据。

## 预检请求长什么样？

```http
OPTIONS /api/articles HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization
```

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 600
Vary: Origin
```

```http
# 实际请求的响应
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Access-Control-Expose-Headers: X-Total-Count
Vary: Origin
```

- 预检让浏览器在发送有副作用的请求前，先确认服务端允许该来源、方法和请求头;
- 预检通常不带 Cookie，鉴权中间件必须放行 `OPTIONS`，否则预检永远失败;
- 预检结果可以缓存（`Access-Control-Max-Age`），来源或规则变化时要能失效。

## 带 Cookie 的跨源请求要满足什么？

- `Access-Control-Allow-Origin` 必须回显具体来源，不能是 `*`，同时带 `Access-Control-Allow-Credentials: true`。

## CORS 白名单怎么配才安全？

- 用白名单，不要反射任意 `Origin`；动态匹配时校验协议与结尾，防止 `evil-example.com` 通过后缀校验;

- 只开放实际需要的方法与请求头；`Expose-Headers` 只列前端要读的响应头;
- 错误响应也要带 CORS 头，否则前端只能看到网络错误;
- 需要缓存时加 `Vary: Origin`，避免 CDN 把 A 站点的响应发给 B 站点;
- 只在一层配置: 应用配了，反向代理就不要再加;
- 与 CSRF 分开: CORS 管「能不能读响应」，CSRF 管「能不能以用户身份写请求」。

## 跨源失败先查什么？

| 症状                         | 原因                                          |
| ---------------------------- | --------------------------------------------- |
| 预检返回 401 / 405           | 鉴权或路由拦截了 `OPTIONS`                    |
| 浏览器报 `Allow-Origin` 重复 | 应用与代理都加了 CORS 头                      |
| 带 Cookie 仍然失败           | `Allow-Origin: *`，或缺少 `Allow-Credentials` |
| 换域名后偶发跨域             | 命中了旧预检缓存，或缺少 `Vary: Origin`       |
| 前端读不到自定义响应头       | 没有在 `Expose-Headers` 中声明                |
