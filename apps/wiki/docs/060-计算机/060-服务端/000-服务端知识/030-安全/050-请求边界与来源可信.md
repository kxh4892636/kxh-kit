# 请求边界与来源可信

## 请求的哪些上限必须在解析之前生效？

- 所有服务端服务适用: body 大小、header 大小与数量、字段数量、文件数量，全部在解析之前生效;

| 资源          | 上限参考  | 超限响应       |
| ------------- | --------- | -------------- |
| JSON body     | 100KB–1MB | 413            |
| 上传单文件    | 5–50MB    | 413            |
| Header 总大小 | 8–32KB    | 431            |
| 单请求字段数  | 按业务    | 400            |
| 读请求        | 3–10s     | 408 / 关闭连接 |

- body 解析会把整个请求读进内存，上限放在解析后已经晚了。

## 请求边界按什么顺序生效？

```text
TLS/网关 → 连接数与速率限制 → header 大小 → body 大小 → 读超时
→ 解析 → 字段校验 → 业务超时 → 下游 deadline
```

- 反向代理层与应用层都设上限，取更小的那个。

## 请求超时为什么要分层设置？

- 连接、读请求、写响应、业务执行、下游调用各管一段，超时也要分层;

- 慢请求会占满连接与 goroutine，读超时是最便宜的防护;
- 没有读超时，少量慢连接就能耗尽 worker;
- 超时错误要能区分「读超时」和「业务超时」。

## X-Forwarded-For 什么时候可以信任？

- 只有请求来自可信代理时才解析；直连客户端可以伪造它;

```text
客户端 1.2.3.4
  → 可信代理 A（追加 1.2.3.4）
  → 可信代理 B（追加 A 的地址）
  → 应用
X-Forwarded-For: 1.2.3.4, 10.0.0.8
```

- 客户端 IP: 从可信代理那一侧往左数，跳过可信代理，取第一个不可信地址;
- 代理链可信跳数写死，不猜；代理要覆盖而不是追加不可信头，直连客户端伪造的 `X-Forwarded-For` 也在代理层被覆盖;
- 直接信任 `X-Forwarded-For` 的第一段，等于让攻击者自选 IP，绕过 IP 白名单与限流。

## 限流按 IP、用户还是接口？

- 按「谁」限: IP、用户、API Key、接口；只按 IP 会在 NAT 下误伤。

## 请求边界配错会有哪些症状？

| 症状                 | 原因                                       |
| -------------------- | ------------------------------------------ |
| OOM 但 QPS 不高      | 单个超大 body 没限制                       |
| IP 限流被绕过        | 信任了客户端可伪造的 `X-Forwarded-For`     |
| 少量慢连接拖垮服务   | 没有读超时或 idle 超时                     |
| 业务超时后请求还在跑 | 只设了读超时，没给业务 context 设 deadline |
| NAT 用户被集体限流   | 只按 IP 限流，没有用户维度                 |
