# 超时预算模型

## 超时为什么是预算而不是单个配置？

- 预算: 入口拿到 deadline，向下逐层分配，下游必须小于上游剩余;
- 适用: 所有跨进程调用;
- 传上下文不等于设超时：框架默认值通常很宽松甚至不限时;
- 每层都用默认值: 入口 1s、下游 10s，故障时下游还在跑，上游早已返回;
- 没有 deadline 的 goroutine 会一直等到对端关闭，连接池被占满;
- 超时不是越大越好：过大会让故障请求长期占用连接与 goroutine。

## 入口 deadline 怎么分给业务、下游和重试？

```text
入口 deadline（如 2s）
  ├─ 排队/解析：100ms
  ├─ 业务处理：剩余
  ├─ 下游调用：剩余 - 余量（如 300ms）
  └─ 重试退避：计入总预算
```

- 给响应写出和错误处理留 10–20% 余量;
- 重试消耗同一份预算，首次调用 + 退避 + 每次重试都算进去;
- 流式接口不能用短写超时；SSE/WebSocket 用心跳与业务层超时;
- 超时错误要能区分阶段：建连、写请求、等响应、读响应。

## 超时预算设错会看到什么症状？

| 症状                     | 原因                               |
| ------------------------ | ---------------------------------- |
| 下游一直跑，上游已返回   | 没有把 deadline 继续传下去         |
| 调大超时后故障更严重     | 超时掩盖了容量问题，连接被长期占用 |
| 重试把预算吃光           | 只算了单次调用时间                 |
| 流式接口频繁断开         | 套用了短的写超时                   |
| 服务端读超时被当成业务慢 | 混淆了读写超时与 Handler 执行时间  |
