# 退出顺序

## 优雅退出解决什么问题？

- 目标: 进程退出时已接收的请求仍能完成，新流量不再进来;
- 代价: 退出变慢，需要与平台终止窗口协调。

## 为什么退出顺序不能反？

- 先关数据库: 在途请求踩到已关闭的连接池，报 `database is closed`;
- 先关监听但没等摘流: 网关仍可能把新请求打进来，客户端看到连接重置;
- 提前关 exporter: 缓冲区里的 trace、指标丢失。

## 正确的退出顺序是什么？

```text
readiness 失败 / 注册中心注销
  → 等摘流传播（5–15s，按网关刷新周期）
  → 停止接收新请求（关闭监听 / 停止 accept）
  → 等在途请求完成（有上限）
  → flush 并关闭 exporter、DB、缓存、MQ
  → 退出进程
```

- 预算: 摘流 + 排空 + 清理 < 平台宽限期 `terminationGracePeriodSeconds`;
- 等待上限到期后强制退出，避免 SIGKILL 切断清理;
- readiness 失败只摘流量，liveness 不应因退出而重启。

## 摘流为什么要等传播窗口？

- 注册中心、网关、负载均衡感知状态有延迟，收到 SIGTERM 时它们可能还在转发;
- 窗口按网关刷新周期定，常见 5–15s；太短丢请求，太长浪费发布窗口。
