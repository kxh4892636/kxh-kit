# 熔断降级与限流

## 限流、熔断、降级各挡什么？

- 三种保护各挡不同的事：限流保护自己，熔断保护下游，降级保证有可接受的结果;
- 适用: 所有有下游依赖或容量上限的服务;
- 降级只在「存在业务可接受的替代结果」时使用；返回旧数据要标记新鲜度;
- 降级结果和正常结果混在一起统计，会让成功率失真;
- 下游已经故障时继续全量请求，会拖垮连接池与线程。

## 熔断状态机怎么在三种状态间转？

```text
CLOSED ──错误率超阈值且样本足够──→ OPEN
OPEN ──冷却时间到──→ HALF-OPEN
HALF-OPEN ──探测成功──→ CLOSED
HALF-OPEN ──探测失败──→ OPEN
```

- 熔断按 key 统计：服务 / 实例 / 方法；阈值同时看错误率与最小样本量，样本太少不熔断;
- 只按错误率熔断，低流量下 1 个错误就 100%，会误熔断;
- 常见默认：错误率 50%、最小样本 200、OPEN 冷却 10s;
- 实例级熔断放在负载均衡之后，只隔离单个实例;
- 服务级熔断按调用方/被调方/方法聚合;
- 冷却时间从秒级到分钟级，按恢复速度调。

## 一次请求里三种保护按什么顺序生效？

```text
入口：QPS / 并发连接限流
  → 下游调用：熔断（按服务/实例）
    → 瞬时失败：幂等且预算允许时重试
      → 仍失败：业务允许时降级，否则明确失败
```

- 组合顺序: 限流 → 熔断 → 重试 → 降级；重试放在熔断之后，避免放大故障;
- 限流要按维度：IP、用户、接口、租户;
- 降级要可观测：记录降级原因、比例、数据新鲜度。

## 限流、熔断、降级分别用在什么场景？

| 场景             | 选择                   |
| ---------------- | ---------------------- |
| 自身容量有限     | 限流（QPS + 并发）     |
| 下游持续错误     | 熔断，避免继续打       |
| 下游偶发超时     | 重试（幂等 + 预算）    |
| 有可接受替代结果 | 降级，并标记数据新鲜度 |
| 没有替代结果     | 明确失败，不假装成功   |

## 三种保护配错会看到什么症状？

| 症状                    | 原因                          |
| ----------------------- | ----------------------------- |
| 低流量服务频繁熔断      | 只看错误率，没有最小样本量    |
| 熔断后永远不恢复        | 没有 HALF-OPEN 探测或冷却过长 |
| 降级把过期数据当新数据  | 没有标记 freshness            |
| 限流按 IP 误伤 NAT 用户 | 维度单一                      |
| 故障时重试把下游打垮    | 重试在熔断之前，且没有总预算  |
