# 重试与幂等

## 什么条件下才允许自动重试？

- 三道门槛: 幂等、错误可恢复、总预算够；任一不满足就快速失败;
- 幂等是前提：写请求不能确认幂等，就不要自动重试，否则重复订单、重复扣款;
- 总预算 = 首次调用 + 退避 + 所有重试 + 余量，必须小于上游 deadline;
- 默认换实例重试，同一节点重试只在明确场景开启;
- 重试会放大流量：下游已经过载时，重试等于二次打击;
- 适用: 所有跨进程调用的失败处理。

## 哪些错误可以重试，哪些必须直接失败？

- 先分类再决定，不能按「失败」统一处理;

| 结果                  | 默认动作                         |
| --------------------- | -------------------------------- |
| 400 / 401 / 403 / 404 | 不重试                           |
| 409 冲突              | 不重试，交给业务处理             |
| 429                   | 按 `Retry-After` 退避后重试      |
| 500 / 502 / 503 / 504 | 幂等请求可重试                   |
| 连接失败 / 建连超时   | 可重试                           |
| 业务超时              | 看幂等与剩余预算                 |
| 流式中断              | 不自动重试，重连后按幂等语义续传 |

## 重试的决策流程是什么？

```text
失败 → 分类（可恢复？幂等？预算够？）→ 退避（指数 + jitter）→ 换实例 → 重试
      └─ 任一不满足 → 快速失败，返回明确错误
```

- 幂等键放在业务层：请求 ID、唯一键、状态机;
- 客户端重试与服务端限流、熔断配合，故障时先停重试;
- 观测重试次数与原因，重试率上升往往早于错误率上升;
- 流式调用不支持常规重试，只能重连并处理已发送的数据。

## 重试退避怎么算？

- 指数退避逐次翻倍，再加抖动打散同步到达;

```text
第 1 次失败：等 100ms + rand(0, 50ms)
第 2 次失败：等 200ms + rand(0, 50ms)
第 3 次失败：等 400ms + rand(0, 50ms)
超过预算或次数上限：返回最后一次错误
```

- 固定间隔退避会让重试请求同步到达，形成周期性尖峰。

## 重试写错会看到什么症状？

| 症状                | 原因                             |
| ------------------- | -------------------------------- |
| 重复下单 / 重复扣款 | 写请求被自动重试，且没有幂等键   |
| 故障时流量翻倍      | 重试没有总预算与熔断配合         |
| 重试把上游拖超时    | 只算了单次调用时间               |
| 4xx 也被重试        | 错误分类没做，按「失败」统一处理 |
| 流式重试后数据重复  | 重连后从头发送                   |
