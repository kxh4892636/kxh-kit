# 熔断降级与限流

## 限流、熔断、降级各挡什么？

- 限流: 保护自己; 熔断: 保护下游; 降级: 保证有可接受的结果;
- 降级前提: 存在业务可接受的替代结果;
- 返回旧数据: 要标记新鲜度;

## 如何保护一个请求? 限流, 熔断, 降级的要求有哪些？

- 组合顺序: 限流 → 熔断 → 重试 → 降级; 重试放在熔断之后, 避免放大故障;
- 统计粒度: 按服务、实例或方法;
- 阈值: 同时看错误率与最小样本量;
- 边界: 样本太少不熔断;
- 限流要按维度: IP、用户、接口、租户;
- 降级要可观测: 记录降级原因、比例、数据新鲜度;

```text
入口：QPS / 并发连接限流
  → 下游调用：熔断（按服务/实例）
    → 瞬时失败：幂等且预算允许时重试
      → 仍失败：业务允许时降级，否则明确失败
```

## 限流、熔断、降级分别用在什么场景？

| 场景             | 选择                   |
| ---------------- | ---------------------- |
| 自身容量有限     | 限流（QPS + 并发）     |
| 下游持续错误     | 熔断, 避免继续打       |
| 下游偶发超时     | 重试（幂等 + 预算）    |
| 有可接受替代结果 | 降级, 并标记数据新鲜度 |
| 没有替代结果     | 明确失败, 不假装成功   |
