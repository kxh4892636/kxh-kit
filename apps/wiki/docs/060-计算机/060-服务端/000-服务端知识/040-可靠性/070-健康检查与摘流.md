# 健康检查与摘流

## readiness 与 liveness 的分工是什么？

- liveness 回答「进程要不要重启」，readiness 回答「能不能接流量」;

| 端点            | 查什么            | 失败后果       |
| --------------- | ----------------- | -------------- |
| liveness        | 进程与事件循环    | 重启实例       |
| readiness       | 关键依赖 + 初始化 | 摘流量，不重启 |
| startup（可选） | 冷启动是否完成    | 延迟存活检查   |

- 适用: 所有被编排平台管理的服务;
- liveness 不查外部依赖：数据库抖动不应该导致所有实例被重启，否则「数据库抖动 → 全量重启 → 雪崩」;
- readiness 查关键依赖，失败只摘流量，不重启进程。

## 探针端点必须满足哪些约束？

- 探针要轻，且不能被业务中间件拦住;
- 不套鉴权、限流、body 限制，放在版本前缀之外;
- 不返回版本号、环境变量、内部地址;
- 探针被鉴权拦截时，平台永远认为实例未就绪，流量进不来;
- 依赖检查只做轻量 Ping，不做全量查询;
- 探针本身要有超时，不能因为检查依赖而挂住。

## 健康检查与就绪探针的响应长什么样？

```http
GET /healthz
200 OK
{"ok":true}
```

```http
GET /readyz
503 Service Unavailable
{"ok":false,"reason":"db"}
```

- 失败要能区分原因（db / cache / config），但不要暴露内部地址。

## 探针参数怎么定才能配合发布？

```text
liveness：进程存活即 200，无外部调用
readiness：检查数据库/缓存等强依赖，带 200ms 级超时
发布：readiness 失败 → 摘流 → 等在途请求 → 退出（见优雅退出）
```

- 间隔 5–10s，超时 1–3s，失败阈值 3 次;
- readiness 初始延迟要覆盖冷启动（连接池预热、配置加载）;
- readiness 太慢会让发布卡住，太快会在依赖未就绪时接流量;
- 摘流后要等一个传播窗口，再停止服务。

## 健康检查探针配错会看到什么症状？

| 症状                   | 原因                                 |
| ---------------------- | ------------------------------------ |
| 数据库抖动引发全量重启 | liveness 查了数据库                  |
| 实例一直不被摘流       | readiness 永远返回 200               |
| 发布卡住十分钟         | readiness 初始延迟过长或探针超时太短 |
| 探针 401               | 探针挂在鉴权中间件之后               |
| 新实例接流量后大量报错 | 依赖未就绪就打开 readiness           |
