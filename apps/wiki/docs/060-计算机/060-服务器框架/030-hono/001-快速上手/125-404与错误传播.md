# 404 与错误传播

## 404 应该用 `c.notFound()` 还是 `c.json(..., 404)`？

| 场景                    | 选择                                                          |
| ----------------------- | ------------------------------------------------------------- |
| 面向浏览器/普通调用     | `c.notFound()`，由 `app.notFound` 统一定制                    |
| 有类型安全客户端（RPC） | `c.json({ ok: false, ... }, 404)`，否则客户端推不出错误体类型 |

```ts
app.notFound((c) => c.json({ ok: false, error: "not_found" }, 404));
```

- `app.notFound` 只有顶层应用会被调用，子应用的 `notFound` 不生效;
- 路径存在但方法不对时默认也是 404，想要 405 就挂 `methodNotAllowed({ app })`;

## 一次请求的错误传播路径是怎样的？

```text
Handler 抛错
  → 调用它的那一层中间件捕获（c.error = err）
  → onError 生成响应（有就调，没有就 500）
  → 外层中间件的 await next() 正常返回，after 代码继续执行
```

- 关键: 每一层只捕获直接下层的异常，所以**抛错那一层自己的 after 代码不会执行**，外层中间件的 after 代码会执行;
- `next()` 永不抛错，这是不要在中间件里写 `try/catch` 的原因;
- 同一个 `next()` 调两次会抛 `next() called multiple times`;

## 为什么流式响应的错误不走 `onError`？

- 响应一旦开始写，状态码与头已经发出，无法替换;
- `onError` 的设计前提是「响应还没发出去」;
- 流内错误要用第三个参数的错误回调或事件形式告知客户端，见 [流式响应](../090-按需查阅/110-流式响应.md);

## 错误日志应该记什么？

| 字段               | 用途                     |
| ------------------ | ------------------------ |
| `requestId`        | 关联同一次请求的所有日志 |
| method + path      | 定位接口                 |
| 错误类型与 message | 聚合与告警               |
| 堆栈               | 排查根因                 |
| `cause`            | 第三方库的原始错误       |

- 日志记录完整，响应只回通用信息;
- `requestId` 的来源见 [请求 ID 与追踪](../003-上线/075-请求ID与追踪.md);
