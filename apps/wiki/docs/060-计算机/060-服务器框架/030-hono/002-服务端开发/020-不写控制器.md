# 不写控制器

## 为什么不建议写「控制器」？

```ts
// 🙁 路径参数推不出来
const bookPermalink = (c: Context) => c.json(`get ${c.req.param("id")}`);
app.get("/books/:id", bookPermalink);

// 😃 就地写，param('id') 有字面量类型
app.get("/books/:id", (c) => c.json(`get ${c.req.param("id")}`));
```

- 根因: Hono 的路由类型靠 `app.get(path, handler)` 的链式泛型推导，把 Handler 抽成独立函数就断了类型链;
- 代价: 丢了参数类型、丢了 RPC 的 `AppType` 推断;
- 对比: Express 的 Controller 模式之所以流行，是因为它本身没有类型推导可丢;

## 那 Handler 该怎么抽出去？

```ts
import { createFactory } from "hono/factory";
import { logger } from "hono/logger";

type Env = { Variables: { userId: string } };
const factory = createFactory<Env>();

const auth = factory.createMiddleware(async (c, next) => {
  c.set("userId", "1");
  await next();
});

const handlers = factory.createHandlers(logger(), auth, (c) => c.json({ userId: c.var.userId }));

app.get("/api", ...handlers); // 类型推断正常
```

- `factory.createHandlers(...)` 返回可展开的数组，把中间件与 Handler 打包到别处定义;
- `factory.createMiddleware()` 与 `createMiddleware()` 等价，但能继承 `Env` 泛型，避免 `Env` 写两遍;
- 展开时必须保持顺序：中间件在前，Handler 在最后;

## 什么时候仍然可以抽 Handler？

- 只有「同一段逻辑被多个路由复用」时才抽，且抽成 Service 而不是 Controller;
- 如果必须保留独立 Handler 函数，用 `factory.createHandlers()` 而不是裸函数，类型才不会丢;
- Service 的签名只收普通对象，不收 `Context`，见 [目录与分层](./010-目录与分层.md);

## 抽出去之后如何保证 RPC 类型不断？

- 用 `factory.createApp()` 创建的实例依旧链式注册，`AppType` 正常;
- 导出类型时导出「链式赋值后的变量」，不要导出裸 `app`;
- 详见 [RPC 服务端准备](../090-按需查阅/060-RPC服务端准备.md)。
