# 性能优化与压测

## Node 适配器有哪些性能开关？

```ts
serve({
  fetch: app.fetch,
  overrideGlobalObjects: true, // 默认: 用轻量 Request/Response 覆盖全局，更快
  autoCleanupIncoming: true, // 默认: 未读完请求体时主动销毁连接
});
```

| 选项                           | 关闭的代价                                                    |
| ------------------------------ | ------------------------------------------------------------- |
| `overrideGlobalObjects: false` | 保留原生全局对象，性能下降，但适合依赖原生实现的库            |
| `autoCleanupIncoming: false`   | 只在「请求方可信且一定读完 body」时开；否则可能被半开连接拖死 |

- 两个开关默认值已经是「兼顾正确性与性能」的选择，没有压测证据别改;

## 优化该从哪里下手？

| 顺序 | 动作                      | 依据                                 |
| ---- | ------------------------- | ------------------------------------ |
| 1    | 打开 `compress()`         | Node 不自动压缩，文本类响应能省 60%+ |
| 2    | 加 ETag / `Cache-Control` | 静态与幂等 GET 直接省掉传输          |
| 3    | 减少 N+1 与串行 await     | 路由不是瓶颈，IO 才是                |
| 4    | 大 JSON 分页或流式        | 避免一次性解析超大 body              |
| 5    | 换路由器                  | 只有压测证明路由匹配占比高时才考虑   |

- 反模式: 为了「快」提前上 `hono/tiny` 或关掉 `autoCleanupIncoming`，换来的是兼容性与稳定性风险;
- 每次只改一处并复测，否则无法归因;

## 压测怎么做才可信？

```sh
npx hono benchmark --plain     # Hono 官方 CLI，走 app.request()，不含网络开销
bombardier -d 10s http://localhost:3000/   # 含网络与 Node HTTP 栈的真实压测
```

- 先用 `hono benchmark` 定位应用内部耗时，再用真实 HTTP 压测看整体;
- 压测时关闭日志中间件，否则测的是 `console.log` 的速度;
- 观察指标不只看 RPS：还要看 P99 延迟、内存增长与事件循环延迟;

## 什么情况下该怀疑应用而不是框架？

| 现象            | 常见原因                             |
| --------------- | ------------------------------------ |
| CPU 高但 RPS 低 | 同步计算、正则回溯、大对象序列化     |
| 内存持续上涨    | 房间表/缓存无上限、闭包持有请求对象  |
| P99 抖动大      | GC、连接池不足、下游超时重试         |
| 首请求很慢      | 冷启动时初始化了连接池或加载了大文件 |
