# RPC 服务端准备

## RPC 模式解决什么问题？

- 痛点: 前后端各写一份接口类型，改字段靠人肉同步;
- 做法: 服务端把 `app` 的类型导出（通常叫 `AppType`），客户端 `hc<AppType>()` 直接获得路径、请求体、响应体的类型;
- 代价: 类型推导开销、目录耦合；跨语言调用不适用（那种场景用 OpenAPI/IDL）;

## 服务端要怎么准备？

```ts
import { Hono } from "hono";
import { zValidator } from "@hono/zod-validator";
import * as z from "zod";

const app = new Hono();

const route = app.post(
  "/posts",
  zValidator("form", z.object({ title: z.string(), body: z.string() })),
  (c) => {
    const data = c.req.valid("form");
    return c.json({ ok: true, data }, 201);
  },
);

export type AppType = typeof route;
```

- 三个前提:
  - 路由必须**链式**注册，并且类型从声明的变量推导（`const route = app.post(...)`）;
  - 请求类型来自校验器（`zValidator` / `sValidator`）;
  - 响应类型来自 `c.json(obj, status)` 的字面量;

## 大应用如何拼装而不破坏类型？

```ts
// app.ts
const routes = new Hono().route("/users", users).route("/posts", posts);

export const app = routes;
export type AppType = typeof routes;
```

- 顶层必须链式挂载并把类型导出，否则客户端推不出完整路径;
- 子路由内部也用链式，`const app = new Hono().get(...).post(...)`;
- 目录拆分建议见 [目录与分层](../002-服务端开发/010-目录与分层.md);

## 为什么不能在 RPC 里用 `c.notFound()`？

- `c.notFound()` 的返回体类型无法被推断，客户端 `res.json()` 退化为 `unknown`;
- 改用 `c.json({ ok: false, error: 'not_found' }, 404)`;
- 或给 `NotFoundResponse` 做模块增强后再用 `c.notFound()`：

```ts
declare module "hono" {
  interface NotFoundResponse extends Response, TypedResponse<{ error: string }, 404, "json"> {}
}
```

## 状态码怎么进入类型？

```ts
if (!post) return c.json({ error: "not found" }, 404);
return c.json({ post }, 200);
```

- 显式写出状态码，客户端才能按 `res.status` 收窄;
- 不写状态码时默认 200，客户端只能看到 200 分支;
- 客户端侧的用法见 [hc 类型安全客户端](./070-hc调用与传参.md);
