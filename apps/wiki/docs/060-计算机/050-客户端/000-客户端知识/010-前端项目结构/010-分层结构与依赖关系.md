# 分层结构与依赖关系

## 目录怎么分层？

划分依据是「变化原因」，不是「文件类型」：同一层里的代码应当因为同一类原因而修改。层内再按文件类型排（`component/`、`hook/`、`model/`），层与层之间只通过接口说话。

```text
src/
├── app/                        # 组合根
│   ├── bootstrap.ts            #   启动入口
│   ├── routes.tsx              #   路由表
│   └── container.ts            #   依赖装配
├── presentation/               # 表现层
│   ├── page/                   #   页面装配：只拼装模块，不写业务
│   ├── feature/                #   页面级业务模块，对外只暴露 index
│   │   └── <模块>/{index.tsx, component/, hook/, model/}
│   ├── component/{base,business}/   #   基础组件 / 跨模块业务组件
│   └── hook/                   #   通用 hook，不装业务数据逻辑
├── application/                # 应用层
│   ├── service/                #   用例：取数顺序、并发、失败回退
│   └── dto/                    #   读模型：已判定的结论
├── domain/                     # 领域层
│   ├── shared/                 #   跨子域基础类型（标识、无效值）
│   ├── <子域>/                 #   value-object/、specification/
│   └── gateway/                #   接口声明，只有类型
├── infrastructure/             # 基础设施层
│   ├── gateway/                #   接口实现，唯一碰外部系统的地方
│   ├── acl/                    #   外部字段 → 领域语言的翻译
│   ├── request/                #   请求实例、重试、环境参数
│   └── runtime/                #   平台识别、时钟、构建期配置
└── utils/                      # 语言级纯函数
```

各层的职责边界：

| 层         | 为什么需要它                 | 放什么                             | 不放什么                  |
| ---------- | ---------------------------- | ---------------------------------- | ------------------------- |
| 表现层     | 承载交互与视觉，变化最快     | 页面、组件、交互、文案             | 业务判定、外部字段名      |
| 应用层     | 决定「先做什么、失败怎么办」 | 取数顺序、并发、失败回退、埋点时机 | 精度与符号规则、HTTP 细节 |
| 领域层     | 规则唯一来源，可脱离环境执行 | 判定、计算、格式化口径、节点注册表 | 请求、框架、平台 SDK      |
| 基础设施层 | 隔离外部系统，可整体替换     | 请求、埋点、导航、翻译、环境参数   | 业务判定、用例签名        |
| 工具层     | 与业务无关的通用计算         | 日期、数字、字符串                 | 任何业务语义              |

判断一段代码属于哪层，按顺序问三个问题：

1. 有没有「如果 A 就 B」的业务判断？有 → 领域层。
2. 只是安排顺序、并发、失败回退？是 → 应用层。
3. 直接碰网络、SDK、全局对象？是 → 基础设施层。返回视图节点 → 表现层。

## 层与层之间是什么关系？

依赖是单向的：外层可以依赖内层，内层不能依赖外层。表格里是「行可以导入列」：

| 从 ↓ 可依赖 →  | utils | domain | application | infrastructure | presentation |
| -------------- | ----- | ------ | ----------- | -------------- | ------------ |
| domain         | ✔     | ✔      | ✘           | ✘              | ✘            |
| application    | ✔     | ✔      | ✔           | ✘              | ✘            |
| infrastructure | ✔     | ✔      | ✘           | ✔              | ✘            |
| presentation   | ✔     | ✔      | ✔           | ✘              | ✔            |

相邻层之间的关系，逐对说明：

- **表现层 → 应用层**：页面与模块只调用用例、消费读模型，不自己取数；表现层不导入基础设施层。
- **应用层 → 领域层**：用例按顺序调用值对象与规则，自己不写判定；领域层不知道用例存在。
- **应用层 ↔ 基础设施层**：两者互不依赖。用例声明需要什么能力（接口放在领域层），基础设施层实现它，装配发生在组合根。
- **领域层 ↔ 基础设施层**：只有一条边成立——基础设施层实现领域层的接口，并复用其值对象；反方向不成立。
- **组合根（`app/`）**：唯一同时依赖全部层的地方，只做挑选实现与注入，不写业务判断。

一句话概括：**依赖只向内，实现通过接口倒挂回来。**

## 数据在层间怎么流动？

| 形状     | 由谁生产   | 内容                           | 例子                                            |
| -------- | ---------- | ------------------------------ | ----------------------------------------------- |
| 事实快照 | 基础设施层 | 外部数据换成领域语言，保留原值 | `{ nodeId: '101', score: -9999, masked: true }` |
| 值对象   | 领域层     | 判定与格式化能力               | `formatSigned('plus')` → `+3`                   |
| 读模型   | 应用层     | 已判定的结论、默认值           | `{ visible: false, valid: false, score: null }` |

链路：

```text
接口响应 → acl 翻译 → 事实快照 → 用例调用值对象 → 读模型 → 视图
```

两条边界：

- 外部字段名只允许出现在 `acl/`；
- 文案与格式化后的字符串只允许出现在视图。
