# 进度估算与生产率数据

## 为什么不能把小项目的数据外推到系统产品？

- 编码占比: 编码大约只占整个问题的六分之一;
- 仅估计编码再套用比率, 无法得到整个任务的估计;
- 外推失真实例: Sackman、Erikson 和 Grant 报告平均 3200 指令的程序;
- 单人编码加调试约 178 小时, 外推得 35,800 语句/年;
- 规模减半的程序耗时约降为四分之一, 外推几乎达 80,000 代码行/年;
- 遗漏项: 计划、编制文档、测试、系统集成和培训的时间都必须考虑;
- 类比: 用 100 码短跑记录外推, 得出人类 3 分钟跑完 1 英里;
- 规律: 即使不考虑相互交流, 只回顾自己以前的工作也是幂函数;
- 数据: Nanus 和 Farr 在 System Development Corporation 研究;
- 结论: 指数为 1.5;
- Weinwurm 的 SDC 研究同样显示指数接近 1.5;

```text
工作量 = (常数) × (指令的数量) ^ 1.5
```

## 各家生产率数据分别说明了什么？

| 来源                          | 场景与口径                                                                                                     | 生产率                                                                 |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Portman (ICL)                 | 落后进度约 1/2; 每项工作耗时约是估计的两倍; 仅 50% 工作周用于编程与调试                                        | 其余时间: 机器当机、高优先级琐事、会议、文字工作、公司业务、疾病、事假 |
| Aron (IBM 盖兹堡系统技术主管) | 9 个大型项目; 程序员 > 25 人、近 30,000 指令; PERT 图按人小时估数百子任务; 仅设计加编程, 不含支持与系统测试    | 交互很少 10,000 指令/人年; 少量交互 5,000; 较多交互 1,500              |
| Harr (Bell Labs)              | 含编程、构件测试与系统测试; 不含计划、机器支持与文书工作 (1969 年春季联合计算机会议论文)                       | 控制程序约 600 指令/人年; 语言翻译约 2200 指令/人年                    |
| OS/360 (IBM)                  | 含小组计划、构件测试、系统测试与部分支持活动                                                                   | 控制程序组约 600~~800 经调试指令/人年; 语言翻译组 2000~~3000           |
| Corbato (MIT MAC)             | MULTICS 系统; 单位是"行"而非"指令"; 原文紧接"约 1 至 2 百万指令", 应指系统规模; 控制程序与语言翻译的良好平均值 | 平均 1200 行经调试的 PL/I 语句/人年 (约 1 至 2 百万指令/人年)          |

- Portman 的结论: 项目估算对每人年的技术工作时间数量做了不现实假设;
- 作者的个人经验也在相当程度上证实了他的结论;
- Aron 的口径修正: 数据除以 2 计入系统测试后, 与 Harr 数据接近;
- Harr 的注意点: 四个程序规模类似, 差异在组大小、时间长短、模块个数;
- 因果不明: 控制程序复杂导致人多, 还是人多导致模块多, 无人能确定;
- Morin: 编程生产率研究与估计技术已不少, 他调查了已发布数据;
- 共同结论: 生产率随任务复杂度与困难程度表现出显著差异;
- 作者的评价: Harr 数据是真正的贡献, 描述现有编程技术下大型系统开发状况;
- 图 8.3、8.4: 对比实际编程速度、调试速度与预期;
- 适用前提: Harr 和 OS/360 的数据都是关于汇编语言编程的;
- 使用高级语言进行系统编程的数据公布得很少;

## 高级语言能带来多少生产率提升？

- 单位陷阱: Corbato 用"行/人年", 其他项目大多是"指令/人年";
- 换算关系: 每个语句对应手写代码的 3 至 5 条指令;
- 结论一: 常用编程语句的生产率似乎是固定的;
- 该固定值已包含写注释和可能出错的情况;
- 结论二: 使用适当的高级语言, 生产率可以提高 5 倍;

## 怎样做估计才是可靠的？（笔记归纳）

- 复杂度法则: 编译器约为批处理程序的三倍, 操作系统约为编译器的三倍;
- 先验比率: 计划进度、编码、构件测试、系统测试各用比率, 不可互替;
- 数据适用边界: 构建独立小型程序的数据不适用于编程系统产品;
- 记录实际工时: 像 Portman 那样保存实际用时日志, 才能定位估算失误;
- 对齐口径: 比较生产率时必须对齐口径;
- 口径要素: 是否含测试、支持、计划、文书, 单位是行还是指令;

（source: 人月神话 · 第 8 章 胸有成竹）
