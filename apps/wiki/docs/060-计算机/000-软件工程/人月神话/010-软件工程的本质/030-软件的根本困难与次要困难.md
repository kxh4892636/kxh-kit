# 软件的根本困难与次要困难

## 为什么软件行业没有"银弹"？

- 人狼隐喻: 民间传说中最可怕的是人狼, 能从熟悉面孔出乎意料地变成怪物;
- 软件类比: 软件项目在非技术经理看来同样如此;
- 具体形态: 看似简单明了, 可能变成落后进度、超出预算、缺陷成堆的怪物;
- 银弹诉求: 由此出现近乎绝望的呼唤;
- 诉求内容: 寻找一种能让软件成本像硬件成本一样降低的"尚方宝剑";
- 核心命题（1986）: 没有任何技术或管理进展能独立许诺十年内生产率、可靠性或简洁性获数量级进步;
- 不是悲观: 怀疑论者并非悲观主义者——没有看到惊人突破;
- 但有可能: 现有方法的规范化、持续开拓、发展和传播, 仍可能在将来使生产率数量级提高;
- 原文: "虽然没有通天大道, 但是路就在脚下";
- 微生物理论: 消除管理灾难第一步是把"巨无霸理论"换成"微生物理论";
- 含义: 每一步"希望的诞生"本身就是对一蹴而就型方案的冲击;
  - 进步是逐步取得的, 伴随辛勤劳动; 软件工程由此诞生;
- 期望校准: 不能期望软件像硬件那样每两年翻一番;
- 矫正: 这种"畸形"不是软件发展太慢, 而是硬件发展太快;
- 硬件参照: 从人类文明开始, 没有其他产业能在 30 年内把性价比提高 6 个数量级;
- 原因: 这一进步来自计算机制造从装配工业转变成流水线工业;
- 分析路径: 先分析软件任务中固有的根本困难;
  - 再逐个检验候选银弹（见 [没有银弹与寻找方向](./040-没有银弹与寻找方向.md)）;

| 核心命题原文（1986）                                                                                                |
| ------------------------------------------------------------------------------------------------------------------- |
| There is no single development ... which by itself promises even one order-of-magnitude improvement within a decade |

## 根本困难与次要困难如何划分？

- 划分来源: 效仿亚里士多德, 把困难分成根本的与次要的;
- 根本的: 软件特性中固有的;
- 次要的: 出现在目前生产上、并非与生俱来的;
- 根本任务（essence）: 打造由抽象软件实体构成的复杂概念结构;
- 结构内容: 数据集合、数据条目之间的关系、算法、功能调用等;
- 该结构的特性: 要素本身抽象, 但内容丰富、高度精确;
- 特性: 同一概念构架可以有不同的表现形式;
- 次要任务（accident）: 使用编程语言表达这些抽象实体;
- 次要任务: 在空间和时间限制内把它们映射成机器语言;
- 困难的所在: 最困难的是规格化、设计和测试这些概念结构;
- 对比: 而不是表达概念和对实现逼真程度进行验证; 语法错误相对概念错误微不足道;
- 历史进步: 生产率上的巨大进步来自突破次要障碍;
- 障碍举例: 硬件限制、笨拙的编程语言、机器时间的缺乏等;
- 关键设问: 相对必要任务, 软件工程师在次要任务上花费了多少时间和精力?
- 9/10 推论: 除非次要任务占所有工作的 9/10, 否则把次要任务时间缩减到零也不会有数量级提高;
- 结论: 现在是关注软件任务中必要活动的时候了;
- 即: 构造异常复杂的抽象概念结构的那部分;
- 摘要建议一: 仔细进行市场调研、避免开发已上市产品;
- 建议二: 在获取和制订需求时把快速原型作为迭代计划的一部分;
- 建议三: 有机地更新软件、随运行使用测试逐渐添加功能;
- 建议四: 不断挑选和培养杰出的概念设计人员;

## 四类内在属性为什么会造成困难？

- 内在特性四类: 复杂性 complexity、一致性 conformity;
- 另两类: 可变性 changeability、不可见性 invisibility;
- 它们是必要属性、不是次要因素;
- 抽掉复杂度的软件实体描述, 常常也去掉了一些本质属性;

| 属性         | 含义                                                       |
| ------------ | ---------------------------------------------------------- |
| 复杂性       | 规模上可能比任何人类创造的其他实体都复杂                   |
| 复杂性       | 没有任何两个软件部分相同（至少在语句级别）                 |
| 复杂性扩展   | 不是相同元素重复添加, 而是不同元素的添加, 且元素非线性交互 |
| 复杂性→沟通  | 团队沟通困难→产品瑕疵/超支/延迟                            |
| 复杂性→状态  | 状态难以列举和理解→可靠性问题                              |
| 复杂性→调用  | 函数调用困难→易用性问题                                    |
| 复杂性→结构  | 结构复杂难以无副作用扩充                                   |
| 复杂性→出口  | 离散出口难以寻找和控制                                     |
| 复杂性→安全  | 安全机制状态不可见                                         |
| 复杂性→概念  | 妨碍概念完整性                                             |
| 复杂性→学习  | 学习负担使开发演变成灾难                                   |
| 一致性       | 很多复杂度随心所欲、毫无规则, 来自必须遵循的人为惯例和系统 |
| 一致性       | 随接口不同而改变、随时间变化                               |
| 一致性       | 变化不是必需的——只因它们由不同的人而非上帝设计             |
| 一致性后果   | 为保持与其它接口兼容、或为兼容性目标而增加的复杂性         |
| 一致性后果   | 对软件的任何再设计都无法简化这些特性                       |
| 可变性       | 软件持续遭受变更压力; 功能最容易感受这种压力               |
| 可变性       | 软件是纯思维活动的产物、可以无限扩展                       |
| 可变性后果   | 成功的软件必被越界使用并被要求扩展                         |
| 可变性后果   | 硬件平台/外设更换强迫软件保持一致                          |
| 可变性母体   | 软件扎根于应用、用户、自然及社会规律、硬件构成的文化母体   |
| 可变性母体   | 母体的持续变化无情地强迫软件随之变化                       |
| 不可见性     | 软件是不可见、无法可视化的; 客观存在不具有空间的形体特征   |
| 不可见性后果 | 没有现成表达方式（不像地图、膜片图、电路图）               |
| 不可见性手段 | 只能画控制流、数据流、依赖关系、时间序列、名字空间等多张图 |
| 不可见性手段 | 这些图相互关联重叠, 难以层次化                             |
| 不可见性后果 | 限制个人设计过程并严重阻碍交流                             |

- 复杂度对照: 建筑、汽车、计算机往往有大量重复的部分, 软件没有;
  - 软件若出现相同的情况, 会合并成供调用的子函数;
- 状态对照: 数字计算机本身已拥有大量状态, 软件系统的状态又比它多若干数量级;
- 建模方法失效: 数学和物理学三百年的成功依赖一条假设;
- 假设: "模型中忽略的复杂度不是被研究现象的必要属性";
- 失效: 当复杂度是本质特性时, 这条路径行不通;
- 一致性对照: 物理学家坚信必定存在某种通用原理;
- 爱因斯坦: 上帝不是专横武断或反复无常的; 软件工程师无法从类似信念中获得安慰;
- 可变性对照: 工业产品出厂后不会经常修改, 更改被整合进后续的产品系列;
  - 汽车更改罕见, 计算机现场调整时有发生, 但都远少于软件的现场修改;
- 建筑对照: 建筑修改成本很高, 从而打消了提出修改的念头;
- 不可见性对照: 建筑平面图能帮助评估空间布局、运输流量与视觉效果;
  - 机械制图、化学分子模型以几何抽象捕获物理存在的几何特性;
- 软件没有这种映射, 从而剥夺了一些强有力的概念工具的构造思路;

## 为什么根本困难不会因工具进步而消失？

- 属性归属: 四类困难属于概念结构本身, 不随表达它的语言、工具、环境而改变;
  - 工具进步只能压缩次要任务, 无法触及"构造概念结构"本身;
- 上限论证: 只要次要任务少于全部工作的 9/10, 把它清零也换不来 10 倍;
  - 生产率的上限由根本任务决定;
- 历史证据: 高级语言曾带来约 5 倍的提升（[48]）;
  - 统一编程环境同样约 5 倍（[55]）; 分时的进步不如高级语言那样显著;
- 历史结论: 它们都没有跨过数量级的门槛（评估见 [没有银弹与寻找方向](./040-没有银弹与寻找方向.md)）;
- 硬件对照不适用: 硬件的数量级增长来自产业形态转变（装配工业→流水线工业）;
  - 软件没有对应的"流水线"奇迹;
- 实践含义: 与其等待不存在的魔术, 不如把注意力放在根本任务上;
- 颇有前途的方向: 购买与自行开发、需求精炼与快速原型、增量开发;
- 另一条主线: 发现和培养杰出的设计人员;
- 见 [卓越的设计人员](../100-人与产品/020-卓越的设计人员.md);

（source: 人月神话 · 没有银弹－软件工程中的根本和次要问题）
