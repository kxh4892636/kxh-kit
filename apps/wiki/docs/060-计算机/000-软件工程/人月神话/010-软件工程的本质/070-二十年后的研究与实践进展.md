# 二十年后的研究与实践进展

## 为什么《人月神话》在 20 年后仍然相关？

- 缘起: 作者在飞往纽约拉瓜迪亚机场的航班上, 见邻座陌生人读《人月神话》;
- 对话: 他问"这本书如何", 对方答"这里面的东西我早就知道", 作者决定不自我介绍;
- 读者的困惑: 20 年前一本关于 30 年前开发经验的书, 为何仍与实践相关?
- 读者群: 还拥有律师、医生、社会学家、心理学家等软件业之外的读者;
- 解释一: 有人说软件开发学科没有正确发展, 常见论据是硬件制造生产率 20 年至少翻 1000 倍;
- 反驳: 反常的不是软件太慢, 而是硬件技术以不合人类历史节拍的方式爆发;
- 硬件爆发: 计算机制造从装配工业转向流水线工业、从劳动密集型转向资金密集型;
- 共性: 硬件与软件开发都保持固有的劳动密集特性;
- 解释二: 书只是顺便提及软件, 真正讲的是团队成员如何创建事物;
- 依据: 1975 年版前言已说软件项目管理更像其他类型的管理;
- 规律: 人类历史总在上演相同的故事, 剧本变化极慢而舞台布景随时改变;
- 类比: 二十世纪会反映在莎士比亚、荷马和圣经中, 以人与团队为主题的书淘汰得慢;
- 答复方式: 不按"错误、过时、新增"的顺序, 而按主题展开, 先讲写作时就正确的部分;

## 概念完整性在 20 年后被如何再确认？

| 主题           | 要点                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 结论           | 作者更确信: 概念完整性是产品质量的核心; 拥有一位结构师是最重要一步                                                     |
| 适用范围       | 不限软件: 计算机、飞机、防御系统、全球定位系统等复杂事物同样适用                                                       |
| 概念模型与判断 | 编程产品须交付条理分明的概念模型（应用、实现方法与界面策略）; 用户感受到的概念完整性是易用性中最重要的因素             |
| 例子           | Macintosh 全部应用界面统一是正例, MS-DOS 是粗糙但也可统一的接口                                                        |
| 单人设计       | 很多优秀软件由一两个人设计（书籍、音乐等纯智力作品亦然）; 很多产业无法负担: 竞争、复杂与多人月                         |
| 组织难题       | 大或紧急项目须多人设计且与单个使用人员概念一致; 大型项目管理与小型项目性质不同                                         |
| 管理必要       | 为获得一致性, 经过深思熟虑、有时甚至英勇的管理活动完全必要                                                             |
| 结构师         | 负责用户感受到的全部概念完整性; 开发并解释概念模型; 模型所有者兼用户代理, 在功能、性能、规模、成本、进度间体现用户利益 |
| 结构师全职     | 全职工作, 只有最小团队才可与经理合一; 类比电影导演与制片人                                                             |
| 体系结构分离   | 把用户感知的产品定义即体系结构与设计实现、物理实现分离, 划出清晰边界                                                   |
| 体系结构递归   | 主结构师分解子系统, 边界选在接口最小、最易严格定义处; 每部分有自己的结构师并汇报, 过程可重复                           |
| 教学证据       | 实验课讲授 20 次以上, 每 4 名学生左右小组分别选出经理与结构师                                                          |
| 教学效果       | 小队伍中角色分立显得极端, 但运作良好并促成设计成功                                                                     |
| 概念详情       | [概念完整性](./../030-概念完整性/010-概念完整性.md)                                                                    |
| 角色分工       | [产品负责人与技术主管](./../040-团队与组织/030-产品负责人与技术主管.md)                                                |

## 面向大型用户群的通用软件为什么会"盲目地增加功能"？

| 主题           | 要点                                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------------- |
| 背景           | 客户应用越来越多被商用软件包取代; 软件包成百上千甚至数百万拷贝出售; 结构师须为大型、不确定用户群设计 |
| 悖论           | 通用工具比专用工具更难设计, 必须给不同用户的各种需要分配权重                                         |
| 盲目的功能     | 结构师不断被诱惑以性能甚至可用性为代价添加边界实用功能                                               |
| 蔓延过程       | 吸引力初期明显, 性能代价到系统测试才出现, 手册增厚, 易用性损失蔓延                                   |
| 高危产品与调岗 | 幸存数代的大众软件; 数百万用户提成百上千需求, 都被当作"市场需要它"; 原结构师常调岗, 新结构师缺经验   |
| 反例           | Word 6.0 被评为"大型和慢速", 需 4MB 内存, 甚至 Macintosh IIfx 都不能胜任                             |
| 定义用户群     | 用户群越大越不确定, 就越需要明确共享同一幅用户图像                                                   |
| 四项属性       | 他们是谁、他们需要什么、他们认为自己需要什么、他们想要什么                                           |
| 频率猜测       | 属性本质是概率分布, 每个值有发生频率; 未清晰定义对象的调查既不确定又昂贵, 应直接猜测假设             |
| 猜测的好处     | 迫使结构师细致考虑对象用户群; 写下来引发讨论, 澄清设计人员的认识差异                                 |
| 敏感性分析     | 明确列频率帮助识别哪些决策依赖哪些属性; 关键决策值得为数值花费精力取得更好估计                       |
| 工具           | Jeff Conklin 的 gIBIS 能精确正式地跟踪设计决策并记录每个决策的原因                                   |
| 结论           | 为用户群属性明确记载各种猜测, 清晰和错误都比模糊不清好                                               |
| 第二系统       | 第 5 章指第二个实际系统, 第 11 章指开发第一个实际系统的第二次尝试                                    |

## Boehm 的模型如何量化"人月神话"？

| 主题            | 要点                                                                                             |
| --------------- | ------------------------------------------------------------------------------------------------ |
| 研究规模        | Barry Boehm 调查 63 个项目, 大多为航空项目加 25 个 TRW 公司项目                                  |
| 成果与评价      | 《软件工程经济学》与逐步推广的成本模型; 商业与政府软件系数不同, 数据充分, 作者认为将是一代经典   |
| 最优进度公式    | T = 2.5(MM)^(1/3): 月单位最优时间是估计工作量（人月）的立方根                                    |
| 推导            | 估计工作量由规模估计和模型其他因子导出; 最优人员配备曲线也由推导得出                             |
| 成本曲线        | 计划进度长于最优时成本缓慢攀升; 短于最优时成本急剧升高                                           |
| 硬下限          | 不管安排多少人手, 几乎没有项目能在少于 3/4 最优时间内成功, 是拒绝"不可能的进度担保"的依据        |
| Brooks 法则检验 | Abdel-Hamid 与 Madnick《软件项目动力学: 一条完整的路》(1991) 建立量化模型                        |
| 模型内容        | 含学习曲线、额外沟通与培训                                                                       |
| 检验结论        | 向落后项目加人总会增加成本, 但不一定使项目更落后; 新成员带来需数周弥补的负面效应, 早期加人更安全 |
| Stutzke 模型    | 更简单、结果类似; 详细分析加人过程与成本（含指导人员被调离原任务）                               |
| Stutzke 案例    | 真实项目中期偏移后成功翻倍人手并保住原进度; 还试验了加班等方法                                   |
| Stutzke 价值    | 最有价值的是如何加人、培训、用工具支持; 后期加入者须作为团队成员投入, 而非改变过程本身           |
| 模型局限        | 两模型都未考虑开发人员必须重新安排; Stutzke 未建模大型项目的沟通负担                             |
| 作者态度        | 细致研究使"异常简化"的 Brooks 法则更实用, 但仍坚持它作为最佳近似与警告                           |
| 详见            | [人月神话与 Brooks 法则](./../020-人月与进度/010-人月神话与-brooks法则.md)                       |

## 20 年后哪些进展是真的，哪些困难没有变？

| 主题           | 要点                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------ |
| 进展与现状     | 过去生产率提高大多来自消除非内在困难（笨拙语言、漫长批处理）; 这样的困难已经不多                 |
| 根本困难       | 彻底的进展将来自处理根本困难——打造和组装复杂概念性结构要素                                       |
| 方法           | 认为程序由比语句、函数、模块或类更大的概念结构要素组成; 参数化已建成要素并组装, 概念级别大幅提高 |
| 化学工程的镜子 | 1918 年 Arthur D. Little 在麻省理工学院建立第一个化学工程系                                      |
| 发展顺序       | 先经验法则, 再经验图表, 再零件设计公式, 最后是单个导管中热传导、质量转移与动量转移的模型         |
| 成熟标志       | 二次大战后化学工程师才提出闭环互联的连续流系统                                                   |
| 由此看软件     | Parnas 批评把软件称为"工程"很冒昧（以电气工程为对照）                                            |
| 年轻学科与处境 | 化学工程在同样年轻的阶段也远未成熟; 软件工程与工业化处理的非线性问题有关, 又被人性复杂性困扰     |
| 判断           | 27 岁的软件工程不是没有希望, 只是不够成熟                                                        |
| 未变问题一     | 如何把一系列程序设计和构建成系统                                                                 |
| 未变问题二     | 如何把程序或系统做成健壮的、经过测试的、文档化的、可支持的产品                                   |
| 未变问题三     | 如何维持对大量复杂性的控制                                                                       |
| 结论           | 焦油坑在将来很长一段时间内会继续使人们举步维艰                                                   |
| 探索范围       | 软件系统可能是人类创造中最错综复杂的事物, 只能在力所能及或刚超出的范围内探索                     |
| 行业要求       | 持续发展、用更大的要素开发、最佳使用新工具、最佳应用经论证的管理方法                             |
| 谦卑           | 自由发挥良好判断, 并认识到自己的不足与容易犯错                                                   |

## 《结束语》说了什么？

| 主题          | 要点                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------- |
| 起点          | 作者 13 岁的 1944 年 8 月 7 日读到哈佛 Mark I 型计算机研制成功的报道, 第一次感到向往与开心              |
| Mark I 设计师 | 构架设计师是哈佛的 Aiken; 实施设计师是 IBM 工程师 Clair Lake、Benjamin Durfee、Francis Hamilton         |
| 超文本先声    | 1945 年 4 月 Vannevar Bush 在亚特兰大月刊发表 "That We May Think"（原文如此）                           |
| 主张          | 把大量知识组织成超文本网络, 由机器沿已有链接并指明其他相关链接                                          |
| 入行          | 1952 年在 IBM 纽约恩迪科特暑期工获得 IBM 604 编程经验, 并了解 IBM 701（第一个存储程序计算机）的正式指令 |
| 毕业与感谢    | 从哈佛 Aiken 与 Iverson 名下毕业后梦想成真; 感谢上帝让他开心做喜欢的工作                                |
| 速度对照      | 第一台机器是哈佛刚出炉的 IBM 7030 Stretch, 1961 至 1964 年为世界最快, 共卖 9 台                         |
| 现在          | Macintosh Powerbook 更快、内存硬盘更大, 便宜 1000 倍, 按定值美元算便宜 5000 倍                          |
| 四次革命      | 计算机、电子计算机、小型计算机、微型计算机革命, 每次都带来计算机数量剧增                                |
| 知识爆炸      | 50 年代毕业时能读完所有期刊与会议报告、掌握全部潮流动向                                                 |
| 知识爆炸      | 现在只能对层出不穷的学科分支说"再见", 越来越难全部掌握                                                  |
| 态度          | 兴趣太多、学习研究思考的机会太多, 是不可思议的矛盾                                                      |
| 态度          | 这个时代远未结束, 仍在飞速发展, 更多乐趣尽在将来                                                        |

（source: 人月神话 · 20年后的人月神话、结束语）
