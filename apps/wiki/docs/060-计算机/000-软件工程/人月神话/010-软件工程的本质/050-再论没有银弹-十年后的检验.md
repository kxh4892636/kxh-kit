# 再论没有银弹：十年后的检验

## 为什么作者九年后仍要检验"没有银弹"的判断？

- 缘起: 文章最初是 IFIP'86 都柏林大会的约稿, 后在一系列刊物发表;
- 人狼风波: 《计算机》杂志翻印时配《伦敦人狼》式剧照, 并加补充报道《杀死人狼》;
- 作者不知情: 出版前未注意补充报道, 也没料到严肃技术文字被这样润色; 后另选古老素描;
- 反响对比: 《人月神话》被大量引用、很少异议; 《没有银弹》引发辩论、信件至今延续;
- 反弹模式: 多数人同意多数观点, 随后断定存在银弹——他们自己发明的银弹;
- 回读反馈: 1986~1987 年被强烈推崇的秘方没出现所声称的戏剧性效果;
- 检验标准: 爱听真正用过且满意的用户推荐; 中立客户若称"生产率提高十倍"即接受;
- 题记一: "生死有命, 富贵在天"（威廉三世, 奥伦治王子）;
- 题记二 波普: 想看到完美方案的人, 心底认为它们以前不存在、以后也不可能出现;

## "次要困难"为什么会被误读，复杂性为什么是层次化的？

| 主题                    | 要点                                                                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 词义澄清                | accident 来自亚里士多德的古老用法, 意为"附带的/从属的", 非"偶然发生"或"不幸的"                                                       |
| 立场                    | 作者并不贬低软件构建中的次要部分                                                                                                     |
| 三阶段（桃乐丝·赛尔丝） | 概念结构形式规格化 → 现实介质实现 → 与用户交互; 对应必要（essence）＝构思、次要（accident）＝实现                                    |
| 关键问题                | 哪些部分与概念结构的精确和有序表达相关? 哪些是创造结构的思维活动?                                                                    |
| 缺陷划分                | 概念性（未能识别异常）与表达性（指针错误、内存分配错误）; 表达部分已降到一半以下                                                     |
| 9/10 推论               | 无人公开发表说次要部分占 9/10, 因此推论成立——必须着手解决根本问题                                                                    |
| 动机研究                | Herzberg、Mausner 和 Sayderman 1959 年发现动机因素可提高生产率                                                                       |
| 环境与次要因素          | 再积极也不提高生产率, 产生负面影响时反而降低                                                                                         |
| 已消除的负面因素        | 笨拙的机器语言、漫长的批处理周转时间、无法忍受的内存限制                                                                             |
| 回应 Cox 一             | 困难并非来自"编程人员缺乏构建当今软件的技术"; 概念复杂性固有, 任何时间方法都存在                                                     |
| 回应 Cox 二             | 认定文章主张"没有任何处理根本困难的希望"不是本意; 四类属性产生的麻烦都可改善                                                         |
| 复杂性层次              | 复杂性是最严重的内在困难, 但并非所有复杂性都不可避免; 很多来自应用随意的复杂特性                                                     |
| Sodahl                  | 系统工作中的大多数困难是组织结构失误的征兆; 同等复杂的建模是隐藏而非解决问题                                                         |
| Lukasik                 | 组织复杂性也非任意, 可能受策略调整影响; 昨天的复杂性是今天的规律（分子无序性启迪气体动力学与热力学三大定律）                         |
| Lukasik                 | 相信软件复杂性终将以更高级的规律性概念（如物理学家的不变式）表达                                                                     |
| 作者回应                | 需要能量化静态结构信息内容的更广泛理论（如香农信息论之于交互流）; 复杂性是无数细节的函数, 必须精确说明; 仅靠不相干工作难以取得一致性 |
| 复杂性另一半            | 复杂性也因实现本身（数据结构、算法、互联性）; 更高层开发、用他人成果、重用自己的程序可避免整个层次                                   |
| 两条对策                | 层次化（分层的模块或者对象）; 增量化（系统可持续运行）                                                                               |

## 对《没有银弹》的批评为什么站不住？

| 主题            | 要点                                                                                                                                                     |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 悲观还是现实    | Harel（1992《批评银弹》）同读本文与 Parnas 1984《战略防卫系统的软件问题》                                                                                |
| Harel 评价      | 二者"太过黯淡"; 他写《走向系统开发的光明未来》; Cox 也认为过于悲观                                                                                       |
| 作者反驳        | 他犯乐观主义错误的几率远大于悲观主义; 乐观主义是程序员的职业病                                                                                           |
| 偏差方向        | 文中 1986 年"很多创新持续开拓发展将使生产率数量级提高"的预言, 十年后看过于乐观而非悲观; 爱因斯坦与哥德尔不因"黯淡"而错误                                 |
| Turski 的点金石 | 把一般金属变成金子; 统治者投钱、代代研究者追求, 是人类纯粹信仰的体现                                                                                     |
| 延续与后果      | 即使证明不存在, 寻找一劳永逸出路的愿望依然强烈; "化圆为方"论文、生发洗液、提高软件生产率的方法都被推销                                                   |
| 作者警戒        | 我们过于遵循乐观主义, 听从万灵药贩卖者; 他与 Turski 都认为白日梦限制发展、浪费精力                                                                       |
| 消极主题一、二  | Harel 归纳: 根本与次要问题的清晰划分; 独立评价每个候选银弹                                                                                               |
| 消极主题三      | 只预言十年而非足够长时间"出现任何重大进步"                                                                                                               |
| 回应主题一      | 划分是全文主要观点, 对理解软件为何难开发绝对关键, 也是改进指南                                                                                           |
| 回应主题二      | 技术各自过分宣扬效果, 独立评估公平; 反对的是魔术般作用的观点                                                                                             |
| 回应主题二      | Glass、Vessey 和 Conger 1992 论文提供证据: 对银弹的无谓研究仍未结束                                                                                      |
| 回应主题三      | 选十年是承认无法预见十年后; 谁能在 1975 年预见 80 年代微型计算机革命?                                                                                    |
| 回应主题三      | 银弹都宣称立刻见效; 硬件性能/价格比可能每十年成百倍增长, 以 40 年代价取得数量级进展不不可思议                                                            |
| 1952 年试验     | Harel 建议假设文章发表于 1952 年, 用反证法论证分开根本与次要问题不恰当                                                                                   |
| 反驳一          | 文章开头已称 50 年代占支配地位的次要困难已不存在, 消除它们带来若干数量级效果; 把辩论推回 40 年前不合理, 1952 年很难想象次要问题不占主要部分              |
| 反驳二          | Harel 设想的 50 年代状态不准确, 当时已不是只写 100~200 行小型个人程序的时代                                                                              |
| 1952            | Univac 用大约 8 人开发的复杂程序处理 1950 年人口普查; 其他机器用于化学动力学、中子漫射、导弹性能计算; 汇编语言、重定位链接与装载程序、浮点解释系统仍常用 |
| 1955            | 人们开发 50~100 人年的商用程序                                                                                                                           |
| 1956            | 通用电气路易斯维尔设备车间使用超过 80,000 条指令的薪资系统                                                                                               |
| 1957            | SAGE ANFSQ/7 防空系统已运转两年, 分布 30 个地点, 基于通讯、自消除故障、热备实时                                                                          |

## 哪些"银弹"被有条件地接受了？

| 主题                             | 要点                                                                                                             |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 重用与交互式构件开发             | Cox 1990《这就是银弹》; 作者由衷赞同它是解决根本困难的方法; 只反对 Cox 把困难归因于"缺乏技术"的前提              |
| Vanilla 框架（Harel）            | 建模技术; 论文细节不足但有资料可查; 针对概念要素设计与调试, 可能革命性                                           |
| Ken Brooks                       | 报告 Vanilla 在实际工作中应用时是颇有帮助的方法学                                                                |
| 可视化                           | Harel 论不可见性: 适当可视化图形带来可观成效, 不只限于次要问题; 思考与探索质量也改进                             |
| 未来系统                         | 围绕可视化表达开发: 用"合适的"实体与关系形成概念, 再用多种可视化语言组合成逐步完善的模型                         |
| Harel 的让步                     | 建模过程本身的某些方面不会立刻改观; 变量与数据结构的算法操作可能仍用文字描述                                     |
| 作者与 Harel 一致                | 软件要素不存在三维空间, 无概念设计到二维/三维图形的简单映射; 需多种图形各覆盖一方面                              |
| 提问与观察                       | 爱问"下个十一月在哪?"与"你自己关于时间历法的模型"; 优秀程序员空间想象强, 常有高度个性化时间几何模型              |
| O-O 发展缓慢                     | 九年间期望稳步增长、普及迟缓; 理论过多                                                                           |
| O-O 现状（Coggins）              | 应用错综复杂, 关注低层次抽象——链表/集合类, 非用户接口、射线束模型、有限元素模型                                  |
| O-O 现状                         | C++ 强类型检查帮助避免错误, 却使从小型事物构建大型物体非常困难                                                   |
| O-O 人为障碍（Parnas）           | O-O 与复杂语言联系过紧; 没讲设计方法与原理, 只当特殊工具; 不先教设计则语言作用小, 结果设计差、价值少、技术不流行 |
| O-O 经济学                       | 前期投入多（培训程序员用很新方法思考、把函数打造成通用类）, 真正获益在后续开发、扩展、维护中体现                 |
| O-O 经济学                       | Coggins: 不加快前两次开发, 产品族第五个项目才异常迅速                                                            |
| O-O 经济学                       | 为不确定收益冒险需要真正的管理勇气, 比技术竞争力更少有; C++ 仍取代 C                                             |
| 铜质子弹                         | "铜质子弹"（非银弹）; 很多特点无需整个 Smalltalk 或 C++ 软件包, 有些早于 O-O                                     |
| 铜质子弹                         | 吸引人之处类似复合维他命药丸——一次性得到所有好处（对程序员的培训）                                               |
| 重用的现状                       | 程序员常重用自己手头工作; Jones: 有经验者拥有私人开发库, 约 30% 重用代码                                         |
| 重用的现状                       | 公司级重用提供 70% 重用代码量, 需特殊开发库与管理支持, 并对变更统计度量以提高可信度                              |
| 重用的现状                       | W. Huang: 用责任专家的矩阵管理组织软件工厂, 培养重用自身代码的习惯                                               |
| 数学软件的传统（JPL Van Snyder） | 晦涩难懂, 每行需大量高智商输入, 重新开发成本高                                                                   |
| 数学软件的传统                   | 标准术语丰富、期刊与算法搜集、商业算法传统使查找成本低; 核反应、天气、海洋模型同样                               |
| 重用的障碍                       | 消费者"觉得"寻找验证构件比自写更贵时, 重复构件就产生, 与真正投入无关                                             |
| 重用数据（Jones）                | 5000 名以上程序员的机构都做正式重用研究; 500 名以下者不到 10% 着手                                               |
| 重用数据                         | 开放市场仅少量重用模块, 价格在常规开发成本的 1%~20%                                                              |
| 重用数据                         | Yourdon: 可重用构件工作量是一次性的两倍; 作者按产品化成本估计为三倍                                              |
| 重用难题                         | Parnas: 说起来容易做起来难, 需良好设计和文档; Ken Brooks 第五次用自己界面库仍在修改; DeMarco 对重用现象气馁      |
| 词汇问题                         | 思索层次越高要素越多; 由高于语句级别的大型要素构建系统, 编程词汇规模彻底扩大                                     |
| 词汇问题                         | 成员超过 3000 个的类库, 对象常需 10 到 20 个参数; 须学语法（外部接口）与语义（详细行为）                         |
| 词汇问题并不绝望                 | 日常词汇超过 10,000 个; 能区分巨大/大/辽阔/大量/庞大, 不会说"庞大的沙漠"或"辽阔的大象"                           |
| 词汇学习的启示                   | 要研究学问了解人如何拥有语言; 人在上下文中学习, 需出版复合产品例子而非零部件库                                   |
| 词汇学习的启示                   | 只记单词, 语法语义在上下文中逐渐学; 按语义分类分组组合规则, 而非比较对象子集                                     |

## 十年检验的结果是什么？

| 1986 年的预言或期望                        | 1995 年的检验                                                                                                                                                                      |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 十年内没有任何单独的进展能带来数量级提高   | 证实: 1986~1987 年被强烈推崇的秘方没有出现戏剧性效果; 没有中立客户以"生产率提高十倍"兑现银弹                                                                                       |
| 大众市场（成品软件）是意义最深远的开发方向 | 证实, 且作者被指出低估了它: 软件包客户化程度超出预期; Selin: 易定制是很大的卖点                                                                                                    |
| 面向对象技术会带来相当大的变化             | 期望稳步增长, 普及缓慢: 前期投入大、收益后移; Parnas 归因于没有讲授设计, Coggins 归因于抽象层次太低                                                                                |
| 重用和构件开发                             | 真正的重用才刚刚开始: 私人库约 30%、公司级约 70%（需专门库与管理支持）; 消费者侧存在心理障碍; 构件成本约为一次性的 2~3 倍                                                          |
| 方法、工具和工作站会稳步提高生产率         | Jones: 结构化与非结构化的等同 COBOL 程序相差 3 倍; Yourdon: 工作站和工具带来 5 倍提高; DeMarco: 没有看到数量级进步; Boehm: 一味追求完美质量, 生产率会像 IBM 的航天软件一样再次下降 |
| 复杂性是主要的限制                         | 未变: 软件仍然是棘手的, 前方没有魔术般的解决方案                                                                                                                                   |

- "进步"的性质（Coqui 的提醒）: 系统化方法的发展是为解决质量问题（特别是避免大型灾难）, 而不是出于生产率;
- Capers Jones 的处方: 先关注质量, 生产率自然会随之提高;
- Capers Jones: 很多代价高昂的后续项目投入大量时间和精力去修复规格说明、设计和实现上的错误;
  - 他提供的数据显示了缺乏系统化质量控制与进度灾难之间的密切关系;
- Boehm 提醒: 一味追求完美质量, 生产率会像 IBM 的航天软件一样再次下降;
- 70 年代的工程化目标: 在软件生产上应用工程原理;
- 目标: 提高软件产品的质量、可测试性、稳定性以及可预见性, 而不是开发效率;
- 驱动力: 担心拥有无法控制的"艺术家们"而可能导致巨大灾难;
- 软件工程作为工程的成长: 先建立规矩和可预见性, 再谈效率;
- 成品软件的竞争经济学: 大众市场软件与内部或外部客户软件开发相比几乎是崭新领域;
- 经济学: 当软件包的销量达到百万、即使只是几千, 关键支配性问题就变成质量、时机、产品性能和支撑成本;
  - 而不再是对客户系统异常关键的开发成本;
- 购买作为生产力工具: 提高信息管理系统（MIS）编程人员生产率最戏剧化的方法是购买商业成品;
- 购买: 薄膜包装软件像电锯、电转和砂磨机;
  - 组合成 Microsoft Works、Claris Works 那样兼容互补的集合能带来巨大灵活性;
  - 常用工具会熟能生巧, 因此必须注重常人使用的方便而不是专业;

## 为什么形势没有改变？

- 基本问题: 复杂性是这个行业的属性, 而且是主要的限制;
- Glass 的总结（1988）: "Parnas 和 Brooks 不是已经告诉我们了吗?";
- Glass: 软件开发是一件棘手的事情, 前方并不会有魔术般的解决方案;
  - 现在是从业者研究和分析革命性进展的时刻, 而不是等待或希望它的出现;
- 两种反应: 有人发现这是使人泄气的图画——他们依然认为突破近在眼前;
- 现实主义的结论: 那些非常固执、可以认为是现实主义者的人把它看成清新的空气;
- 结论: 把焦点集中在更可行的事情上, 取得逐步进展, 而不是等待不大可能到来的突破;

（source: 人月神话 · 再论《没有银弹》）
