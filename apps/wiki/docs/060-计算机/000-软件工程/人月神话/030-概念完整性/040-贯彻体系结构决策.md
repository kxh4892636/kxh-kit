# 贯彻执行：如何让所有人遵循结构师的决策

## 本章要解决什么问题？

- 题旨: 哈里·杜鲁门论总统权力, 光说不做是没有用的;
- 问题: 假设项目经理已有行事规范的结构师和许多编程实现人员;
- 问题: 如何确保每个人听从、理解并实现结构师的决策?
- 规模: 由 1000 人开发的系统, 一个 10 个结构师的小组如何保持概念完整性?
- 来源: 这套方法在 System/360 硬件设计工作中摸索出来;
- 适用: 对软件项目同样适用;

## 为什么手册是贯彻的主要工具？

- 定位: 手册（书面规格说明）是必要的工具, 尽管光有文档是不够的;
- 定义: 手册是产品的外部规格说明, 描述并规定用户所见的每一个细节;
- 角色: 它也是结构师主要的工作产物;
- 迭代: 随着用户和实现人员的反馈, 难用、难实现的地方不断被指出;
- 迭代: 规格说明不断被重复准备和修改;
- 版本化: 修改要阶段化, 进度表上应有带日期的版本信息;
- 边界: 手册描述包括所有界面在内的用户可见的一切;
- 边界: 同时避免描述用户看不见的事物;
- 边界: 看不见的部分是编程实现人员的工作范畴, 不应限制他们的设计和创造;
- 限度: 结构师必须为自己描述的任何特性准备一种实现方法;
- 限度: 但不应该试图支配具体的实现过程;
- 风格: 必须清晰、完整和准确;
- 风格: 用户常会单独提到某个定义, 每条说明必须重复所有基本要素;
- 风格: 所有文字相互一致;
- 代价: 这往往使手册枯燥乏味, 但精确比生动更加重要;
- 经验: System/360 Principles of Operation 的一致完整性来自仅有两名作者;
- 两名作者: Gerry Blaauw 和 Andris Padegs;
- 经验: 思路来自约十个人, 但转成书面规格说明必须由一两个人完成;
- 例: 书写定义必须对很多原先并不重要的问题作出判断;
- 例: 例如每次操作后如何设置返回的条件码;
- 分量: 保证这些看似琐碎的问题处理原则上的一致性, 决不是无关紧要的事情;
- 标杆: 作者见过最好的一份手册是该书的附录;
- 标杆: 它精确仔细地规定了 System/360 兼容性的限制;
- 标杆: 定义了兼容性、目标、变化与不变的部分;
- 标杆: 这正是规格说明作者应追求的精确程度;
- 要点: 在仔细定义规定什么的同时, 定义未规定什么;

## 形式化定义与记叙性文字如何配合？

| 方式       | 优点                                                                       | 缺点或局限                       |
| ---------- | -------------------------------------------------------------------------- | -------------------------------- |
| 形式化定义 | 精确; 倾向于更加完整; 差异更加明显; 可以更快地完成                         | 不易理解                         |
| 记叙性文字 | 显示结构性原则; 描述阶段或层次结构; 提供例子; 易表达异常与对比; 能解释原因 | 不适用于精确定义, 需与形式化并用 |

- 结论: 将来的规格说明应同时包括形式化和记叙性定义两种方式;
- 双时钟警告: "决不要携带两个时钟出海, 带一个或三个";
- 配套: 必须以一种作为标准、另一种作为辅助描述, 并明确划分;
- 先例: Algol 68 用形式化定义作标准, 记叙性文字作辅助;
- 先例: PL/I 用记叙性定义作主要方式, 形式化定义作辅助表述;
- 先例: System/360 用记叙性文字作标准, 形式化定义作派生论述;
- 工具: 巴科斯范式（语言定义常用）;
- 工具: PL/I 的抽象语法;
- 工具: Iverson 的 APL（曾用以描述 IBM 7090 与 System/360）;
- 工具: Bell 和 Newell 能同时描述配置与机器结构的标注方法;
- 工具示例: PDP-8、IBM 7090、System/360;

## 用实现来定义规格有什么风险？

| 维度   | 内容                                                                                                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 做法   | 几乎所有的形式化定义在描述系统外部功能时, 会用一段实现该功能的程序来定义特定的语义                                                                                                   |
| 约束   | 必须特别指出形式化定义仅仅用于外部功能, 说明它们是什么; 实现充当标准时, 还必须防止对实现的任何修改                                                                                   |
| 优点   | 所有问题可以通过试验清晰地得到答案, 从不需要争辩和商讨; 回答快捷迅速, 精确程度符合要求; 仿真装置同理; 制造第一批兼容性计算机时, 手册模糊之处就"问一问机器"; 新机器必须按上述结果运行 |
| 缺点   | 实现可能更加过度地规定外部功能; 无效语法通常会产生某些结果: 在拥有错误控制的系统中, 它通常仅仅导致某种"无效"的指示                                                                   |
| 案例   | 在 System/360 上模拟 IBM 1401 时, 有 30 个被认为是无效操作副作用的"古玩"得到广泛应用, 并被当作定义的一部分                                                                           |
| 后果   | 实现不但描述系统必须做什么, 还声明自己到底做了什么; 尖锐问题会得到未在计划中的意外答案; 真正的定义常常是粗糙的, 因为从未被仔细考虑过; 这些功能在其它实现中往往低效或代价高昂         |
| 例证   | 一些机器把乘法运算后的垃圾遗留在被乘数寄存器中; 该细节成为真正定义的一部分; 重复它可能会阻止某些快速乘法算法的使用                                                                   |
| 易混淆 | 实际使用标准是形式化描述还是叙述性文字, 这一点容易混淆; 使用实现作为形式化定义尤其如此, 特别是在程序化的仿真中                                                                       |

## 有哪些更直接的分发手段？

- 手段: 对软件系统结构师, 有一种更可爱的方法来分发和强制定义;
- 用途: 对建立模块间接口语法 (而非语义) 特别有用;
- 技术: 设计被传递参数和共享存储器的声明;
- 技术: 要求编程实现在编译时的一些操作 (PL/I 的宏或 %INCLUDE) 来包含这些声明;
- 好处: 接口仅通过符号名称引用时, 改声明只需增删变量并重编译受影响的程序;
- 好处: 不需要修改程序内容;

## 周例会与年度大会各自解决什么问题？

- 分级原因: 会议必要, 但数百人在场的大型磋商会议需要大规模正式召集;
- 分级: 因此分成周例会和年度大会两级;
- 年度大会目的: 解决周例会未重新考虑、慢慢堆积的小要求、公开问题和不愉快;
- 申诉: 对结果过于不满者可立刻诉诸项目经理, 但少见;

| 维度      | 周例会                                                                                                                                                                                                                                                                                                           | 年度大会                                                                                                                                                                        |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 频率/时长 | 每周半天                                                                                                                                                                                                                                                                                                         | 典型持续两周（作者会改为每六个月一次）                                                                                                                                          |
| 时机      | —                                                                                                                                                                                                                                                                                                                | 手册冻结的前夕                                                                                                                                                                  |
| 主持      | 首席系统结构师                                                                                                                                                                                                                                                                                                   | 项目经理                                                                                                                                                                        |
| 出席      | 所有结构师加硬件和软件实现人员代表与市场计划人员                                                                                                                                                                                                                                                                 | 体系结构小组、编程与实现人员代表、编程经理、市场和实现人员                                                                                                                      |
| 流程      | 任何人可提出问题和修改意见; 建议书通常以书面形式在会前分发; 新问题通常讨论一段时间, 重点是创新而不仅是结论; 少数解决方案传给一个或几个结构师, 记录到书面的变更建议说明书; 随后对变更建议做决策, 经历几个反复; 实现人员和用户仔细考虑, 正面和负面意见都被描述; 达成共识最好, 否则由首席结构师决定; 结论正式、果断 | 约 200 个条目, 大多规模很小, 列举在会议室周围的图表上; 每个不同的声音都有机会表达; 决策后配以出色的计算机化文本编辑工作; 每天早上参与者会在座位上发现记录了前一天决定的手册说明 |
| 有效原因  | 数月内相同小组每周交流一次, 彼此了解项目内容, 不需要额外培训时间; 小组成员睿智敏锐、与产品密切相关, 没有人是"顾问"角色, 每个人承担义务; 在界线的内部和外部同时寻求解决方案; 正式书面建议集中注意力、强制决策的制订、避免草稿纪要方式的不一致; 清晰授予首席结构师决策权力, 避免妥协和拖延                         | 不仅解决决策问题, 而且使决策更容易被接受; 作者称之为"收获的节日"; 每个人都在倾听和参与; 对复杂约束和决策之间的相互关系有更透彻的理解                                            |

## 为什么多重实现能保住手册的地位？

- 有利条件: System/360 的结构师有两个空前有利的条件;
- 条件: 充足的工作时间、与实现人员相同的策略影响力;
- 来源: 充足时间来自新技术的开发日程;
- 来源: 策略上的平等性来自多重实现的同时开发;
- 机制: 不同实现之间严格要求相互兼容;
- 机制: 这种必要性是强制规格说明的最佳代言人;
- 常规: 机器和手册会在某一天出现不一致, 人们通常会忽略手册;
- 原因: 与机器相比手册更容易改动且成本更低;
- 多重实现: 遵从手册更新机器所造成的延迟和成本消耗;
- 多重实现: 比根据机器调整手册要低;
- 推广: 在定义编程语言时可以卓有成效地应用;
- 推广: 迟早会有很多编译器或解释器;
- 推广: 如果起初至少有两种以上的实现, 定义会更加整洁和规范;

## 电话日志与产品测试分别起什么作用？

- 必要性: 实现推进中, 无论规格多精确, 仍会出现无数理解与解释问题;
- 规则: 鼓励有疑问的实现人员打电话询问相应结构师;
- 规则: 而不是一边自行猜测一边工作;
- 规则: 答案必须是可以告知每个人的权威性结论;
- 机制: 结构师保存电话日志, 记录每一个问题和相应回答;
- 机制: 每周合并若干结构师的日志, 重新整理并发布给用户和实现人员;
- 评价: 该机制很不正式, 但快捷且易于理解;
- 定位: 产品测试机构或小组是项目经理最好的朋友, 也是他每天要面对的敌人;
- 职责: 根据规格说明检查机器和程序, 充当麻烦的代言人;
- 职责: 查明每一个可能的缺陷和相互矛盾的地方;
- 缘由: 每个开发机构都需要独立的技术监督部门来保证公正性;
- 终极监督者: 用户是最终的独立监督人员;
- 终极监督者: 在残酷的现实使用环境中每个细微缺陷都将无从遁形;
- 代理: 产品-测试小组是顾客的代理人;
- 价值: 细心测试人员总会发现未贯彻、设计决策未正确理解或未准确实现之处;
- 结论: 测试小组是贯彻设计决策的必要手段, 应尽早着手、与设计同时实施;

（source: 人月神话 · 第 6 章 贯彻执行）
