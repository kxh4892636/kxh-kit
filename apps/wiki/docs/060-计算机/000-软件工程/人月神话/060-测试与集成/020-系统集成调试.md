# 系统集成调试

## 为什么系统集成是意料之外的难点？

- 判断: 软件系统开发过程中出乎意料的困难部分是系统集成测试;
- 需要再次确认两件事: 系统调试花费的时间会比预料的更长;
- 需要一种完备系统化和可计划的方法来降低它的困难程度;
- 常规看法（尽管并不是普遍的实际情况）: 系统集成调试要求在每个部分都能正常运行之后开始;

## "边合边试"为什么不划算？

- 反对常规的两种做法:
- 1. "合在一起尝试": 基于除构件单元上的 bug 之外还存在系统 bug（如接口）的观点;
- 越早将各个部分合拢, 系统 bug 出现得越早;
- 2. 使用系统的各个部分进行相互测试, 避免大量测试辅助平台的搭建工作;
- 评价: 这两种情况显然都是合理的, 但经验显示它们并不完全正确;
- 结论: 使用完好的、经过调试的构件, 能比搭建测试平台和全面构件单元测试节省更多时间;
- 总评: 所有这些良好的愿望只是试图为结果的偏离寻找一些合理理由;
- 更微妙的一种方法（第三种思路）"文档化的 bug": 申明构件单元所有的缺陷已经被发现;
- 这些缺陷还没有被修复, 但已经做好了系统调试的准备;
- 系统测试期间测试人员知道这些缺陷造成的后果, 从而可以忽略它们;
- 这样可以把注意力集中在新出现的问题上;
- 该方法的局限: 实际上调试人员并不了解 bug 引起的所有后果;
- 系统比较简单时问题不大;
- 对文档记录 bug 的修复工作本身会注入未知的问题;
- 接下来的系统测试会令人困惑;

## 测试平台需要哪些构件？

- 定义: 辅助测试平台指的是供调试使用的所有程序和数据;
- 它们不会整合到最终产品中;
- 合理成本: 测试平台可能会有相当于测试对象一半的代码量, 但这是合乎情理的;
- 伪构件 (dummy component): 仅仅由接口和可能的伪数据或者一些小的测试用例组成;
- 例: 系统包含某种排序程序但该程序还未完成;
- 其他部分的测试可以通过伪构件实现;
- 它读入输入数据、校验数据格式、输出格式良好但没有实际意义的有序数据;
- 微缩文件 (miniature file): 很常见的一类 bug 来自对磁带和磁盘文件格式的错误理解;
- 创建一个仅包含典型记录但涵盖全部描述的小型文件是非常值得的;
- 伪文件 (dummy file): 微缩文件的特例, 实际上并不常见;
  - OS/360 任务控制语言提供了这种功能, 对构件单元调试非常有用;
- 辅助程序 (auxiliary program): 用来测试的数据发生器、特殊的打印输出、交叉引用表分析等;
- 它们都是需要另外开发的专用辅助工具;

## 如何控制变更？

- 来源: 对测试期间进行严密控制是硬件调试中一项令人印象深刻的技术;
- 它同样适用于软件系统;
- 首先必须有人负责: 他必须控制各个构件单元的变更或者版本之间的替换;
- 受控拷贝的三种用途: 一是供构件单元测试使用的最终锁定版本;
- 二是测试版本的拷贝, 用来进行缺陷的修复;
- 三是安全版本, 其他人员可以在该拷贝上进行各自的程序开发工作;
- System/360 的"紫色线束": 发现 bug 后先设计快速修复电路并安装到系统;
- 这样不会妨碍测试继续进行;
- 更改过的接线使用紫色电线, 像伸着一个受了伤的大拇指;
- 完整的变更流程: 把更改记录到日志, 准备一份正式的变更文档, 启动设计自动化流程;
- 最后在电路图或者黄色线路中实现该设计的调整;
- 具体做法: 更新电路图和接线表, 开发新的电路板;
- 物理模型和电路图重新吻合后, 紫色线束不再需要;
- 软件里的对应手法: 关键在于对变更和差异的记载;
- 在一个日志中记录所有的变更;
- 在源代码中显著标记快速补丁和正式修改之间的区别;
- 正式修改是完备并经过测试的, 而且需要文档化;

## 为什么必须一次只添加一个构件？

- 规则: 一次添加一个构件;
- 诱惑: 乐观主义和惰性常常诱使我们破坏这个规则;
- 离散构件的添加需要调试伪程序和其他测试平台, 有很多工作要做;
- 人们会想"可能不需要这些额外工作? 可能不会出现什么 bug?";
- 回答: "不! 拒绝诱惑!", 这正是系统测试所关注的方面;
- 必须假设系统中存在着许多错误, 并需要计划一个有序的过程把它们找出来;
- 回归测试: 必须拥有完整的测试用例, 在添加了新构件之后用它们来测试子系统;
- 原来可以在子系统上成功运行的用例, 必须在现有系统上重新运行;
- 版本替换: 将使用中的构件替换成新版本, 仍然需要同样的系统化测试流程;
- 由于通常已具备更完整有效的测试用例, 测试时间往往会减少很多;

## 为什么变更必须阶段化？

- 平台效应: 项目中其他开发团队会使用经过测试的最新集成系统作为调试自己程序的平台;
- 测试平台的修改会阻碍他们的工作, 这是必须的;
- 阶段化要求: 变更必须被阶段化、定期发布;
- 这样每个用户拥有稳定的生产周期, 其中穿插着测试平台的改变;
- 这比持续波动所造成的混乱无序要好一些;
- 尺度证据: Lehman 和 Belady 出示了证据;
- 阶段要么很大、间隔很宽, 要么小而频繁;
- 根据他们的模型, 小而频繁的阶段很容易变得不稳定;
- 作者的经验也同样证实了这一点, 因此决不会在实践中冒险采用后一种策略;
- 与快速补丁的结合: 量子（阶段）化变更方法非常优美地容纳了紫色线束技术;
- 直到下一次系统构件的定期发布之前一直使用快速补丁;
- 而在当前的发布中把已经通过测试并进行了文档化的修补措施整合到系统平台;
