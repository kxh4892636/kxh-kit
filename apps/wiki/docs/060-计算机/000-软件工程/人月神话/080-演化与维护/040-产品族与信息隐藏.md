# 产品族与信息隐藏

## Parnas 的"产品族"思想是什么？

- 背景: 20 年时间里 David Parnas 一直是软件工程思潮的带头人;
- 人们熟悉他的信息隐藏概念;
- 对他把软件作为一系列相关产品族来设计的概念了解较少;
- 做法: 劝设计人员预测产品的后期扩展和后续版本;
- 定义它们在功能或者平台上的差异;
  - 搭建一棵相关产品的家族树;
- 核心技巧: 将变化可能性较小的设计决策放置在树的根部;
- 收益: 这样的设计使模块的重用最大化;
- 关键延伸: 相同策略可延伸到发布产品之外;
- 覆盖以增量开发策略创建的后续中间版本;
- 这样产品可以通过它的中间阶段, 以最低回溯代价增长;
- 家族树标签: 功能修改、移植到其他平台、第二代产品、内部版本、基产品;

## Microsoft 的"每晚重建"如何体现增量开发？

- 来源: Jim McCarthy 向作者描述了他所在队伍和微软其他团队的流程;
- 本质上是逻辑上的增量式开发;
- 引语: "在我们第一次产品发布之后, 我们会继续发布后续版本";
- "向已有的可运行系统添加更多的功能";
- "为什么最初的构建过程要不一样呢?";
- "从我们第一个里程碑开始(第一次发布有三个里程碑)";
- "我们每晚重建开发中的系统(以及运行测试用例)";
- "该构建周期成了项目的'心跳'";
- "每天, 一个或多个程序员-测试员队伍提交若干具有新功能的模块";
- "在每次重建之后, 我们会获得一个可运行的系统";
- "如果重建失败, 我们会停下整个过程, 直到找到问题并修复";
- "在任何时间, 团队中的每个人都了解项目的状态";
- 代价: 这很困难, 必须投入大量资源;
- 它是规范化、可跟踪、开诚布公的流程;
- 收益: 流程向团队提供自身的可信度;
- 而可信度决定士气和情绪状态;
- 对比: 其他组织的开发人员对此感到惊讶甚至震惊;
- 有人说"我们可以实现每周一次的重建, 但是每晚一次工作量太大";
- 这可能是对的;
  - Bell 北方研究所就是每周重建 1200 万行的系统;
- 与增量开发框架的关系见 [瀑布模型的谬误与增量开发](./030-瀑布模型的谬误与增量开发.md);

## 作者在信息隐藏上的错误是怎么被纠正的？

- 原著第 7 章的对比: OS/360 项目决定所有程序员应该了解所有的材料;
- 每个项目成员都拥有一份大约 10,000 页的项目工作手册拷贝;
- Mills 的立场: Harlan Mills 指出"编程是个开放性的公共过程";
- 把所有工作暴露在每个人的凝视之下能帮助质量控制;
- 既源于其他人优秀工作的压力;
  - 由于同伴能直接发现缺陷和 bug;
- Parnas 的立场: 代码模块应该采用定义良好的接口来封装;
- 模块的内部结构是程序员的私有财产, 外部不可见;
- 编程人员被屏蔽而不是暴露在他人模块内部结构面前时效率最高;
- 当年的判定: 作者在第 7 章把 Parnas 的概念称作"灾难的处方";
- 20 年后的纠正: Parnas 是正确的, 作者是错误的;
- 现在作者确信信息隐藏是唯一提高软件设计水平的途径;
- 信息隐藏常内建于面向对象编程中;
- 两种技术的适用性: 任何技术的使用都可能演变成灾难;
- Mills 的技术让编程人员理解所工作接口另一侧的详细语义;
  - 接口的隐藏会导致系统的 bug;
- Parnas 的技术在面对变更时是很健壮的;
- 更加适合"为变更设计"的理念;
- 组织含义见 [授权与准自治团队](./../040-团队与组织/050-授权与准自治团队.md);

## 面向对象与信息隐藏的三步演进是什么？

| 步骤   | 内容                                                                                          | 贡献                                                                                     |
| ------ | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 第一步 | Parnas 模块隐藏: 模块是拥有自身数据模型和自身操作集的软件实体, 数据仅能通过它自己的操作来访问 | Parnas 的模块信息隐藏定义是研究项目中的第一步, 是面向对象编程的鼻祖                      |
| 第二步 | 抽象数据类型: 把 Parnas 模块提升到可派生对象的抽象数据类型                                    | 若干思想家的贡献; 提供统一思考和指明模块接口的方式, 以及容易保证实施的类型规范化访问方法 |
| 第三步 | 继承: 类(数据)默认获得类继承层次中祖先的属性                                                  | 面向对象编程引入的强有力概念                                                             |

- 最大收获: 主要来自第一步模块隐藏;
- 以及预先建成的、为重用而设计和测试的模块或者类库;
- 重用的代价: 很多人忽视了模块不仅仅是程序;
- 某种意义上它是第 1 章讨论过的编程产品;
- 希望大规模重用却不付出构建产品级质量模块的初始代价;
- 产品级质量为通用、健壮、经过测试和文档化;
- 这种期望是徒劳的;

## 为什么说"更大的概念结构要素"是根本出路？

- 进展的来源: 过去软件生产率的进展大多来自消除非内在的困难;
- 如笨拙的编程语言、漫长的批处理周转时间等;
- 剩余的困难: 这些比较容易解决的困难已经不多了;
- 根本困难: 彻底的进展将来自对根本困难的处理;
  - 打造和组装复杂概念性结构要素;
- 实现路径: 认为程序由更大的概念结构要素组成;
- 比独立的高级语言语句、函数、模块或类等更大;
- 目标状态: 限制设计和开发, 只需参数化和组装已建成的要素;
- 就能大幅度提高概念的级别;
- 消除很多无谓的工作和大量语句级别的错误可能;
- 与产品族的关系: Parnas 产品族、模块隐藏与类库重用正是该手段的落地;

（source: 人月神话 · 20年后的人月神话）
