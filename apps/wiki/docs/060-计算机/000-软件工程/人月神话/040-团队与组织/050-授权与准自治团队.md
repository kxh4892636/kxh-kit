# 授权与准自治团队

## 为什么授权是软件管理的中心问题？

- 前提: 认同创造力来自个人, 而不是组织架构或者开发过程;
- 中心问题: 如何设计架构和流程, 来提高而不是压制主动性和创造力;
- 范围: 这个问题不是软件组织所特有的;
- 范围（续）: 一些杰出的思想家正努力致力于这项工作;
- 推论: 组织的价值在于放大个人的创造力, 而不是替个人决定如何工作;
- 推论（续）: 管理与技术角色、流程所有权、进度责任应尽量下沉到离工作最近的单元;

## "附属职能行使原理"讲了什么？

| 项       | 内容                                                                            |
| -------- | ------------------------------------------------------------------------------- |
| 出处     | E. F. Schumacher 的经典《小就是美: 人们关心的经济学》                           |
| 英文原名 | Small is Beautiful: Economics as if People Mattered                             |
| 原理来源 | 引自 Pope Pius XI 教皇通谕 Quadragesimo Anno 的"附属职能行使原理"(subsidiarity) |

- 原文要点: 向大型组织指派小型或者附属机构能够完成的职责是不公平的;
- 原文要点（续）: 同时也是正常次序的不幸和对它的干扰;
- 原文要点（续）: 每项社会活动就其本质而言, 应配备对社会个体成员的帮助;
- 原文要点（续）: 而不是去破坏和吸收它们;
- 原文要点（续）: 当权者遵守该原理, 能在各种组织中维持更加完美的次序;
- 原文要点（续）: 越强越有效的社会权威将是国家更加融洽和繁荣的条件;
- Schumacher 的解释: 如果较低级别组织的自由和责任得以保留, 中心权威实际上是得到了加强;
- Schumacher 的解释（续）: 其结果是, 从整体而言, 组织机构将"更加融洽和繁荣";
- 反直觉结论: 授权不是削弱中心, 而是强化中心;
- 反直觉结论（续）: 前提是把职责留在能完成它的最小单位, 而不是替它包办;

## 准公司是什么？

- 结构: 大型组织机构由很多准自治单元构成, 称为准公司;
- 特征: 每个准公司拥有大量自由, 为创造性和企业家职能提供最大的可能机会;
- 责任: 每个准公司同时具备盈亏帐目和资产负债表;
- 目的: 把"自由"与"对结果的问责"绑定, 让创造力有边界、可衡量;

## 20 年后哪些实践把这一理念落地？

- 新产业: 微型计算机革命创造了新型的软件工业, 出现成百上千家新兴公司;
- 新产业（续）: 它们热情、自由、富有创造性;
- 新产业（续）: 随着很多小公司被大公司收购, 大公司是否理解和保留小规模的创造性尚待分晓;
- 大公司内的下放: 一些大型公司的高层管理开始把权力下放到软件项目团队;
- 大公司内的下放（续）: 使其在结构和责任上接近 Schumacher 的准公司;
- 大公司内的下放（续）: 运作结果令人欣喜和吃惊;

| 来源                               | 经验                                                                                                                                                                                                                                                 |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Jim McCarthy(Microsoft)            | 每个队伍 30 至 40 人; 拥有自己的任务、进度, 甚至如何定义、构建、发布的过程; 团队由 4 或 5 个专家组成, 包括开发、测试和书写文档; 由团队而不是老板对争论进行仲裁; 授权和由团队自行负责项目的成功与否, 其重要性无法形容                                 |
| Earl Wheeler(IBM 软件业务退休主管) | 近年关键措施是将权力向下委派, "这就像是魔术"; 改进的质量、提高的生产率、高涨的士气; 小型团队没有中心控制; 团队是流程的所有者并且必须拥有一个流程（各有不同流程）; 团队是进度计划的所有者, 因此感受到市场的压力; 这种压力导致他们使用和利用自己的工具 |

- 边界与保守性: 和团队成员个人的谈话显示他们赞同被委派的权力和自由;
- 边界与保守性（续）: 同时反映出真正的下放显得多少有些保守;
- 结论: 授权是朝正确方向迈出的一大步;
- 结论（续）: 它产生了 Pius XI 所预言的好处——通过权力委派, 中心的权威实际上得到加强;
- 结论（续）: 从整体而言, 组织机构更加融洽和繁荣;

## 与 Mills 的"开放性公共过程"有什么关系？

- OS/360 的做法: 决定所有程序员了解所有材料;
- OS/360 的做法（续）: 每个项目成员拥有一份约 10,000 页的项目工作手册拷贝;
- Harlan Mills 的论据: "编程是个开放性的公共过程";
- Harlan Mills 的论据（续）: 把所有工作暴露在每个人的凝视之下能帮助质量控制;
- Harlan Mills 的论据（续）: 既源于其他人优秀工作的压力, 也由于同伴能直接发现缺陷和 bug;
- 授权视角: 开放过程把质量责任分散给全体成员, 而不是交给中心检查;
- 授权视角（续）: 属于典型的权力与责任下沉;
- 20 年后的裁决: 在公开与信息隐藏的争论中, Parnas 是正确的;
- 20 年后的裁决（续）: Mills 的技术让程序员理解所工作接口的详细语义, 但接口被隐藏会导致系统 bug;
- 20 年后的裁决（续）: Parnas 的技术在面对变更时更健壮;
- 20 年后的裁决（链）: [产品族与信息隐藏](./../080-演化与维护/040-产品族与信息隐藏.md);
- 与队伍模式的联系: 外科手术队伍式的团队组织同样是"把权力交给小单元"的体现;
- 与队伍模式的联系（链接）: 见 [外科手术队伍](./010-外科手术队伍.md);
- 与队伍模式的联系（链接续）: 见 [为变更组建团队](./040-为变更组建团队.md);
