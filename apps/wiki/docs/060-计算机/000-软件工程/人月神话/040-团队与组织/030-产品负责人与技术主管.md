# 产品负责人与技术主管

## 产品负责人和技术主管的职责分别是什么？

- 前提: 树状组织架构是权力和责任的结构, 其基本原理是管理角色的非重复性;
- 每个子项目需要的要素: 任务、产品负责人、技术主管（结构师）、进度、人力划分、各部分之间的接口定义;
- 产品负责人: 组建团队, 划分工作, 制订进度表, 要求必要资源, 建立团队内部的沟通和报告方式, 确保进度目标, 根据环境调整资源和团队构架;
- 产品负责人的沟通方向: 主要与团队外部, 向上和水平地沟通;
- 技术主管: 构思设计, 识别系统的子部分, 指明从外部看上去的样子, 勾画内部结构;
- 技术主管的核心产出: 整个设计的一致性和概念完整性, 控制系统复杂程度, 在技术问题出现时提供解决方案或调整系统设计;
- 技术主管的沟通方向: 在团队中是首要的, 工作几乎完全是技术性的;
- 关键判断: 两种角色所需技能非常不同, 很难由一个人同时具备;

## 为什么树状结构不足以描述交流？

- 事实: 树状结构几乎不能用来描述交流沟通, 因为交流是通过网状结构进行的;
- 推论: 树状模拟结构不能精确描述一般团队、特别工作组、委员会甚至矩阵结构组织;
- 工程含义: 组织图中那些"虚线部分"的特殊机制, 都是为了克服树状结构在交流上的缺乏;

## 两种角色有哪三种组合方式？

| 组合                                 | 适用与代价                                                                                                                         |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 同一人兼任                           | 适合 3-6 人的小队伍; 大型项目不适用, 因为同时具备管理技能和技术技能的人太少, 且两个角色都需要全职甚至加班                          |
| 产品负责人为总指挥, 技术主管为左右手 | 需要产品负责人预先声明技术主管的技术权威, 并在绝大部分争议中支持其技术决定; 实践有效但很少被应用; 好处是可以用不擅长管理的技术天才 |
| 技术主管为总指挥, 产品负责人为左右手 | 为技术天才搭建免于杂事干扰的环境（Heinlein《出售月球的人》的场景）; 同样能使工作非常有效                                           |

- 作者倾向: 对小型团队, 第三种安排最好, 与外科手术队伍一致; 对真正大型项目中的开发队伍, 产品负责人作为管理者更合适;

## 团队组织的第一目标是什么？

- 计算规模: 若项目有 n 个工作人员, 则有 `(n²-n)/2` 个相互交流的接口, 有将近 `2n` 个必须合作的潜在团队;
- 目标: 团队组织的目的是减少不必要交流和合作的数量;
- 手段: 人力划分（division of labor）和限定职责范围（specialization of function）;
- 效果: 树状管理结构使详细交流的需要相应减少;

## 搭建团队时应以什么为准？

- 原则: 团队的搭建必须根据参与的人员来组织, 而不是将人员纯粹地按照理论进行安排;
- 原因: 两种角色所需技能的组合方式控制和支配了两人之间的关系;
- 组合的前提条件: 产品负责人与技术主管必须在基本技术理论上观点相似, 必须在主要技术问题出现之前私下讨论, 且产品负责人必须表现出对技术主管技术才能的尊重;
- 威信手段: 产品负责人可用办公室大小、地毯、装修、复印机等微妙状态特征暗示技术主管的威信;
