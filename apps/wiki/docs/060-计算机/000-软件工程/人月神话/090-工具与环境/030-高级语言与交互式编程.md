# 高级语言与交互式编程

## 为什么高级语言势不可挡？

- 两大收益: 使用高级语言的主要原因是生产率和调试速度;
- 性质: 所体现出来的是整体提升, 而不仅仅是部分增加;
- 生产率数据见下;
- [进度估算与生产率数据](./../020-人月与进度/020-进度估算与生产率数据.md);
- 调试改进: 来自 bug 更少、而且更容易查找;
- bug 更少的原因: 避免在错误面前暴露所有级别的工作;
- 后果: 否则不但会造成语法错误, 还会产生语义问题, 如不当使用寄存器;
- 辅助机制: 编译器诊断机制可以帮助找出类似错误;
- 更重要: 容易插入调试的快照;
- 作者立场: 这些生产率和调试方面的优势是势不可挡的;
- 判断: 无法想象使用汇编语言能方便地开发出系统软件;

## 对高级语言的三条传统反对意见怎样回应？

| 反对意见             | 回应                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| 无法完成我想做的事情 | 所有证据显示人们可以完成想做的事情, 只是需要花费时间和精力找出如何做, 可能需要一些讨人嫌的技巧 |
| 目标代码过于庞大     | 新的优化编译器已非常令人满意, 并且将持续改进                                                   |
| 目标代码运行速度过慢 | 经优化编译器生成的代码, 比绝大多数程序员手写代码的效率要高                                     |

- 补充手段: 在优化编译器代码被全面测试之后, 可以将其中的 1%~5% 替换成手写代码;
- 效果: 这往往能解决速度方面的问题;
- 语言选择: 现在可供合理选择的系统编程语言是 PL/I;
- PL/I 的优点: 提供完整的功能集;
- 与操作系统环境相吻合;
- 编译器多样: 一些交互式、一些速度很快、一些诊断性很好;
- 另一些能产生优化程度很高的代码;
- 作者的个人做法: 用 APL 解决算法更快;
- 再把这些算法翻译成某个系统环境下的 PL/I 语言;

## 交互式编程的证据是什么？

- 来源: MIT 的 Multics 项目成果之一, 是它对软件编程系统开发的贡献;
- 概念差异: 在系统编程所关注的方面;
- 对比: Multics（以及后续系统 IBM 的 TSS）和其他交互式系统概念上很不同;
- 差异点: 多个级别上数据和程序的共享与保护、可延伸的库管理、协助终端用户共同开发的设施;
- 作者的判断: 确信在某些应用上批处理系统决不会被交互式系统取代;
- 但: 认为 Multics 小组是交互式系统开发上最具有说服力的成功案例;
- 证据状况: 目前还没有明显的证据证明这些强大工具的效力;
- 但: 调试是系统编程中很慢和较困难的部分;
- 关键: 漫长的调试周转时间是调试的祸根;
- 结论: 交互式编程的逻辑合理性勿庸置疑;
- 小规模证据: 很多用这种方式开发小型系统和部分系统的人给出好的证据;
- 大规模证据: 作者唯一见到的关于大型编程系统开发方面的数字;
- 论文: 来自 Bell 实验室 John Harr 的论文（图 12.2）;
- Harr 数据的覆盖: 分别反映代码编写、汇编装配和程序调试的情况;
- 样本: 第一个大部分是控制程序, 其他三个是语言解释、编辑等程序;
- Harr 数据的结论: 系统软件开发中, 交互式编程的生产率至少是原来的两倍;
- 时代背景: 十年前的 OS/360 开发中并没有使用现在最重要的两种系统编程工具;
- 现状: 目前它们也没有得到广泛应用;
- 作者判断: 只有懒散和惰性会妨碍它们的广泛应用, 技术上的困难很快就不再成为借口;

## 高级语言与交互式编程在多数情况下为什么必须成对使用？

- 工具依赖: 远程键盘终端无法用于内存转储的调试;
- 结论: 大多数交互式工具的有效使用需要采用高级语言来进行开发;
- 正向循环: 有了高级语言, 可以很容易地修改代码和选择性地打印结果;
- 总评: 它们组成了一对强大的工具;

（source: 人月神话 · 第 12 章 干将莫邪）
