# 流程图与自文档化程序

## 流程图为什么被过誉了？

- 判断: 流程图是被吹捧得最过分的一种程序文档;
- 事实: 很多程序甚至不需要流程图, 很少有程序需要一页纸以上的流程图;
- 它显示了什么: 流程图只显示程序的流程判断结构, 是程序结构的一个方面;
- 单页有效: 绘制在一张图上时, 它能优雅地显示程序的判断流向;
- 多页失效: 分成几张时（需用编号的出口和连接符拼装）, 整体结构的概观被严重破坏;
- 定位: 一页纸的流程图是表达程序结构、阶段或步骤的基本图示, 也容易绘制;
- 图 15.1: 一个子程序流程图的图样, 由 W. V. Wright 提供;
- 不必正式: 既没有、也不需要遵循精心制订的 ANSI 流程图标准;
- 要求: 所有图形元素（方框、连线、编号等）只需能使这张详细流程图可以理解就行了;

## 详细流程图为什么被淘汰？

- 判断: 逐一记录的详细流程图过时而且令人生厌, 只适合启蒙初学者的算法思维;
- 历史来源: Goldstine 和 Neumann 引入这种方法;
- 做法: 框图和框图中的内容作为一种高级别语言;
- 作用: 将难以理解的机器语言组合成一连串可理解的步骤;
- 消解的推演: 早期 Iverson 认识到, 系统化的高级语言中分组已经完成;
- 结果一: 每一个方框相应地只包含一条语句, 方框本身变成单调乏味的重复练习, 可以去掉;
- 结果二: 剩下的只有箭头, 连接相邻后续语句的箭头也是冗余的;
- 图 15.2: 流程图与对应程序的对比;
- 出处: Cashman 与 Keys 1971 年的教材;
- 最后剩下的: 只有 GO TO 跳转;
- 推演: 遵守良好规则、使用块结构消除 GO TO 语句, 那么所有的箭头都消失了;
- 结论: 箭头能在很大程度上帮助理解, 大家完全可以丢掉流程图, 使用文字列表来表达;
- 现实观察: 作者从未见有经验的编程人员在写程序前例行绘制详尽流程图;
- 现象一: 在一些要求流程图的组织中, 流程图总是事后才补上;
- 现象二: 一些公司很自豪地使用工具软件, 从代码中生成这个"不可缺少的设计工具";
- 解读: 这种普遍经验不是对良好实践的偏离, 而是对技术的良好评判;
- 收获: 它向我们传授了一些流程图用途方面的知识;
- 引文支持: 作者引用《使徒行传》15:10;
- 引文: "为什么让他们背负我们的祖先和我们自己都不能承担的重负呢?";
- 立场: 对新的编程人员和陈旧的流程图方法持相同态度;

## 为什么要把文档并入源代码？

- 数据处理的基本原理: 试图把信息放在不同的文件中并维持它们之间的同步, 费力不讨好;
- 更合理的方法: 每个数据项包含两个文件都需要的所有信息;
- 做法: 采用指定的键值区别, 并把它们组合到一个文件中;
- 程序文档的违反: 典型做法是维护一份机器可读的程序, 以及一系列记叙性文字和流程图的文档;
- 判断: 这恰好违反了上述原则;
- 后果: 不同文件的数据保存带来了不良的后果;
- 后果一: 程序文档质量声名狼藉, 文档的维护更是低劣;
- 后果二: 程序变动总是不能及时精确地反映在文档中;
- 解决方案: "合并文件", 即把文档整合到源代码;
- 好处一: 对正确维护是直接有力的推动;
- 好处二: 保证编程用户方便、即时地得到文档资料;
- 名称: 这种程序被称为自文档化 (self-documenting) 程序;
- 时代判断: 现在看来, 在程序中包括流程图显然是一种笨拙的做法（但不是不可以）;
- 理由: 流程图方法落后、高级语言的使用占统治地位, 把程序和文档放在一起很合理;
- 收益: 把源程序作为文档介质强制推行了一些约束;
- 对读者: 一行一行的源程序本身就可以再次利用, 使新技术的使用成为可能;
- 任务: 现在, 已经到了为程序文档设计一套彻底的新方法的时候了;
- 目标: 文档是作者以及前人都不曾成功背负的重担, 必须把它的负担降到最小;

## 自文档化有哪三个基本方法？

- 方法一 用语言强制的语句作载体: 借助语言要求必须存在的语句;
- 作用: 附加尽可能多的"文档"信息;
- 工具: 标签、声明语句、符号名称均可用来向读者表达尽可能多的意思;
- 方法二 格式: 尽量使用空格和一致的格式提高程序的可读性, 表现从属和嵌套关系;
- 方法三 段落注释: 以段落注释的形式, 向程序中插入必要的记叙性文字;
- 现状: 大多数文档一般都包括足够多的逐行注释;
- 极端: 即使是满足公司呆板"良好文档"规范的程序也包含了很多注释;
- 但: 即使这些程序, 在段落注释方面也常常是不够的;
- 价值: 段落注释能提供总体把握, 真正加深读者对整件事情的理解;
- 时机约束: 文档通过程序结构、命名和格式来实现, 所有这些必须在书写代码时完成;
- 可行性: 自文档化的方法减少了很多附加工作, 使这件工作遇到的障碍会更少;

## 自文档化有哪些具体技巧？（例子见图 15.3: 一段自文档化的 PL/I 程序）

| 技巧 | 做法                                                                                                                                                                                                           |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 为每次运算使用单独的任务名称; 维护一份日志记录程序运行的目的、时间和结果; 名称由助记符（如 QLT）加数字后缀构成, 后缀作为运算编号, 把列表和日志联系在一起; 可用"重复进行公共信息的批处理"准备每次运算的新任务卡 |
| 2    | 使用包含版本号和能帮助记忆的程序名称; 假设程序将会有很多版本（例子中使用的是 1967 年的最低一位数字）                                                                                                           |
| 3    | 在过程 (PROCEDURE) 的注释中包含记叙性的描述文字                                                                                                                                                                |
| 4    | 尽可能为基本算法提供参考引用, 通常它会指向更完备的处理方法; 既节省空间, 又允许有经验的读者自信地略过这一段                                                                                                     |
| 5    | 显示和算法书籍中传统算法的关系: 更改、定制细化、重新表达                                                                                                                                                       |
| 6    | 声明所有的变量; 采用助记符, 并使用注释把 DECLARE 转化成完整的说明; 声明已包含名称和结构性描述, 需要增加的仅仅是对目的的解释                                                                                    |
| 7    | 用标签标记出初始化的位置                                                                                                                                                                                       |
| 8    | 对程序语句进行分组和标记, 以显示与设计文档中语句单元的一致性                                                                                                                                                   |
| 9    | 利用缩进表现结构和分组                                                                                                                                                                                         |
| 10   | 在程序列表中手工添加逻辑箭头, 它们对调试和变更非常有帮助; 补充在页面右边的空白处, 成为机器可读文字的一部分                                                                                                     |
| 11   | 使用行注释来解释任何不很清楚的事情; 若已采用上述技术, 注释的长度和数量都将小于传统惯例                                                                                                                         |
| 12   | 把多条语句放置在一行, 或者把一条语句拆放在若干行, 以吻合逻辑思维, 表示和其他算法描述一致                                                                                                                       |

## 自文档化的反对意见如何回应？

- 最强反对: 必须存储的源代码规模增加;
- 背景: 编程技术越来越向在线源代码存储的方向发展, 这成为一个主要考虑因素;
- 作者的亲身体验: 他发现自己编写的 APL 程序注释比 PL/I 程序要少;
- 原因: APL 程序保存在磁盘上, 而 PL/I 则以卡片的形式存储;
- 回应一: 文本编辑的访问和修改也在朝在线存储的方向前进;
- 效果: 程序和文字的混合使用减少了需要存储的字符总数;
- 回应二（击键）: 采用打字方式时每份草稿、每个字符需要至少一次击键;
- 对比: 自文档化程序的字符总数更少, 每个字符需要的击键次数也更少;
- 另: 电子草稿不需要重复打印;
- 流程图与结构图: 只用最高级别的结构图时, 另用一份文档可能更安全;
- 理由: 结构通常不会频繁变化;
- 补充: 它理所当然也可以作为注释合并到文档中;
- 适用范围: "自文档化"方法的基本思想可以得到大规模的应用;
- 受限: 对空间和格式要求更为严格的部分应用可能受限;
- 可用: 命名和结构化声明显然可以利用起来, 宏可以起到很大的帮助;
- 段落注释: 它的广泛使用在任何语言中都是很棒的实践;
- 与高级语言的关系: 自文档化方法激发了高级语言的使用, 特别是用于在线系统的高级语言;
- 表现: 无论对批处理还是交互式, 它都表现出最强的功效和应用的理由;
- 收束: 这些语言和系统强有力地帮助了编程人员;
- 理由: 因为是机器为人服务, 而不是人为机器服务;
- 结论: 无论从经济上还是从以人为本的角度来说, 它们的应用都是合情合理的;

（source: 人月神话 · 第 15 章 另外一面）
