# 关键文档与文档结构

## 本篇的范围是什么？

- 范围: 第 10 章"少数关键文档是项目的枢纽";
- 内容: 它们的种类、作用与启动方式;
- 提示: 文档的可检索结构（项目工作手册）见下;
- [交流与项目工作手册](../040-团队与组织/020-交流与项目工作手册.md);

## 为什么少数文档是项目的枢纽？

- 文档假设 (Documentary Hypothesis): 少数文档是枢纽;
- 场景: 在一片文件的汪洋中, 每件项目管理工作围绕它们运转;
- 地位: 它们是经理们的主要个人工具;
- 初始感受: 文书工作令人生厌、毫无必要、令人分心, 有被吞没的威胁;
- 作用一: 写文档是集中考虑、使各种讨论意见明朗化的主要时刻;
- 反例: 否则项目往往处于无休止的混乱状态;
- 作用二: 文档的跟踪维护是项目监督和预警的机制;
- 作用三: 文档本身可作检查列表、状态控制, 也可作汇报的数据基础;

## 其他行业的关键文档有哪些？

| 文档             | 内容                                                       |
| ---------------- | ---------------------------------------------------------- |
| 目标             | 待满足的目标和需要, 迫切需要的资源、约束和优先级           |
| 技术说明         | 计算机手册与性能规格说明; 计划新产品时第一个产生, 最后完成 |
| 进度、时间表     | 时间安排                                                   |
| 预算             | 不只是约束; 会迫使技术决策的制订, 促使并澄清策略上的决定   |
| 组织机构图       | 人员划分                                                   |
| 工作空间分配     | 地点安排                                                   |
| 报价、预测、价格 | 三个因素互相牵制, 决定项目成败                             |

| 环节   | 内容                                                                     |
| ------ | ------------------------------------------------------------------------ |
| 循环名 | 报价-预测-价格循环                                                       |
| 第一步 | 先定产品性能说明和假设价格, 才能做市场预测                               |
| 第二步 | 预测值加设计得出的组件数量决定生产成本, 进而得出单元开发工作量与固定成本 |
| 第三步 | 固定成本决定价格                                                         |

- 良性循环: 价格低于假设值 → 预测值较高、单元成本较低 → 价格能继续降低;
- 灾难循环: 价格高于预测值;
- 后果: 必须提高性能与支持更高的市场预测, 同时降低成本以产出更低报价;
- 结果: 所有人努力打破这个循环;
- 循环的双面性: 压力常是激励市场人员和工程师工作的最佳动力, 也会带来可笑的踌躇和摇摆;
- 案例: 某项目三年开发周期中, 机器指令计数器的设计每六个月变化一次;
- 表现: 要性能时用触发器实现, 要降成本时改用内存实现;
- 对策: 一位最好的项目经理充当大型调速轮, 用惯性降低来自市场和管理人员的起伏波动;
- 大学科系对照项: 目标、课程描述、学位要求、研究报告（申请基金还要计划）、课程表与安排;
- 对照项续: 预算、教室分配、教师和研究生助手分配;
- 相似点: 与计算机项目相似, 只缺价格文档; 学校的决策机构完成了这项任务;
- 决策记录: 校长、教师会议或系主任的决定几乎都是技术说明或其变更;
- 相似性的根源: 任何管理任务的关注焦点都是时间、地点、人物、做什么、资金;

## 软件项目需要哪些关键文档？

| 管理问题 | 文档         | 要点                                                             |
| -------- | ------------ | ---------------------------------------------------------------- |
| 做什么   | 目标         | 定义待完成的目标、迫切需要的资源、约束和优先级                   |
| 做什么   | 产品技术说明 | 以建议书开始, 以用户手册和内部文档结束; 速度和空间说明是关键部分 |
| 时间     | 进度表       | —                                                                |
| 资金     | 预算         | —                                                                |
| 地点     | 工作空间分配 | —                                                                |
| 人员     | 组织图       | 与接口说明相互依存                                               |

- 现象: 许多软件项目从商讨结构的会议开始, 然后开始书写代码;
- 建议: 项目规模再小, 项目经理也应立刻正式生成若干文档作为数据基础;
- 限度: 哪怕这些迷你文档非常简单;
- 文书工作的来源: 技术、周边组织机构、行业传统等因素定义项目必须准备的文书工作;
- 启动方式: 接着他会和其他管理人员一样要求各种文档;
- Conway 规律: "设计系统的组织架构受到产品的约束限制";
- Conway 映射: 生产出的系统是这些组织机构沟通结构的映射;
- Conway 补充: 一开始反映系统设计的组织架构图肯定不会是正确的;
- 变化准备: 如果系统设计能自由地变化, 项目组织架构必须为变化做准备;
- [组织结构与交流](../040-团队与组织/020-交流与项目工作手册.md);

## 为什么需要正式的文档？

- 记录决策: 只有记录下来, 分歧才会明朗、矛盾才会突出;
- 书写: 这项活动需要上百次的细小决定;
- 作用: 让人们在令人迷惑的现象中得到清晰、确定的策略;
- 沟通渠道: 项目经理常发现理应被普遍认同的策略不为团队一些成员所知;
- 分工: 他的主要工作是沟通而不是做出决定, 文档能极大减轻负担;
- 数据基础与检查列表: 周期性回顾能清楚项目所处的状态, 以及哪些需要重点更改和调整;
- 对"完备信息管理系统"的保留: 管理人员可能只有 20% 的时间从自己头脑外部获取信息;
- 其余工作: 沟通, 即倾听、报告、讲授、规劝、讨论、鼓励;
- 但对基于数据的部分: 少数关键文档可以满足绝大多数需要;
- 结论: 只有书面计划是精确和可以沟通的;
- 计划包括: 时间、地点、人物、做什么、资金;
- 少数关键文档封装了项目经理的工作;
- 心态: 一开始就认识它们的普遍性和重要性;
- 结果: 把文档作为工具友好地利用, 而不是令人厌烦的繁重任务;
- 收益: 遵循文档开展工作, 项目经理能更清晰和快速地设定自己的方向;

（source: 人月神话 · 第 10 章 提纲挈领）
