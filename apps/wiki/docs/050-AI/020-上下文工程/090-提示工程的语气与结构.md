# 提示工程的语气与结构

## 系统提示词的设计检验标准是什么？

- 对象: API 消息列表中 `role: "system"` 的那条消息，是 Agent 的“员工手册”;
- 内容: 定义 Agent 的身份、行为规则、约束条件与工作流程;
- 检验标准: **如果一个聪明的新员工读完系统提示词还不知道该怎么做，Agent 也一样不知道**;
- 目标: 让模型在具体任务中充分发挥其通用能力，而不是靠模型自己猜;

## 语气与风格如何影响 Agent 行为？

- 简洁约束: 可以要求 “You MUST answer concisely with fewer than 4 lines”;
- 失败场景: 要求“keep your response to 1-2 sentences”且不解释为什么不能做某事，避免冗长的自我辩护;
- 强度标定: 大写字母（如 “NEVER do X”）比 “Please avoid doing X” 更能引起模型注意;
- 稀释效应: 过度使用大写强调会导致效果被稀释，应保留给真正关键的约束;
- 实验结论: 风格（专业中立 / 夸张自信 / 轻松带表情）显著改变表达方式，但对任务完成率的影响相对有限——模型有很强的风格适应能力;

## 为什么结构化提示比纯文本更有效？

- 敏感性: 现代大语言模型对结构化输入展现出显著的敏感性，源于训练数据中包含大量结构化内容;
- XML 的语义: 标签名称本身携带语义，`<working_directory>` 立即告诉模型这是工作目录信息;
- 纯文本的代价: “当前目录：/Users/project/src” 需要模型额外思考冒号前后的关系;
- Markdown 的作用: 在保持可读性的同时提供轻量级结构，适合组织层次化的指令;
- 双层配合: XML 负责机器可解析的精确语义，Markdown 负责人机共读的组织逻辑;

```text
# 工具使用规范

## 文件操作
<file_operation>
- 读取文件前必须先检查路径是否存在
- 写入文件前必须先备份
</file_operation>
```

## 流程驱动与规则堆砌有何差别？

- 规则堆砌的困境: 上百条零散规则、没有流程图和优先级说明，多条规则同时适用时无法选择，未覆盖情况无法处理;
- 流程驱动的形态: 提供标准操作流程（SOP），让模型随时知道自己在哪个阶段、当前目标是什么、完成后进入哪一步;
- 异常处理: 遇到异常时可根据所处阶段确定处理方式，而不是遍历所有规则找匹配项;

```text
Step 1: Validation → 文件不存在则记录错误并停止
Step 2: Classification → 按扩展名与内容判定类型
Step 3: Preprocessing → 配置文件备份；大文件流式处理
Step 4: Execution
Step 5: Verification
```

- 原理: 针对人类降低认知负担的方法对模型同样有效，因为模型在训练中学习了人类的语言和思维模式;
- 消融证据: 保留全部规则内容但打乱组织结构，任务成功率下降超过 30%，Agent 经常跳过身份验证等关键步骤;
- 原因: 规则以无序方式呈现时，模型难以识别其中的优先级与依赖关系;
