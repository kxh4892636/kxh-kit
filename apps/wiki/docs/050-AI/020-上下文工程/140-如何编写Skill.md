# 如何编写 Skill

## 一份可用的 Skill 应回答哪些问题？

- 反面: 不应只是背景知识或一次成功对话的摘要;
- 正面标准: 让一个刚加入团队的员工知道——遇到什么任务时使用它、按什么顺序行动、哪些情况需停下来确认、什么结果才算完成;
- 来源: 需要有人把经验写成模型能执行的指令;
- 参考文献: 提示工程师宝玉的《图解 Skill》;

## Skill 的内容应包含哪四个部分？

- 服务对象与角色: 说明这份 Skill 服务谁、面向什么任务、输出应达到什么标准;
- 核心原则: 只保留三到五条最重要的判断，并为关键原则配正例与反例;
- 禁止清单: 记录高频错误、越权动作和容易误解的表达，同时写清合法例外;
- 参考资料: 放术语表、模板、范文和更详细的子文档;
- 规则写法: 尽量写成 “作用域 + 动作 + 例外 + 验证方式”，避免堆成越来越长的禁用词表;
- 打包能力: Skill 不仅包含指导性文档，还可捆绑可执行代码工具与模板文件，例如 PPT Skill 可带 PPT 模板和解析脚本;

## 写作型 Skill 应该怎样起步？

- 材料: 从三到五篇自己最满意的原创文章开始;
- 初版: 让 Agent 归纳用词、句式、段落结构和语气，生成一份二十行左右的初版;
- 检验: 用它处理一项真实的写作任务，由作者逐句改稿;
- 关键信号: 原文与修改稿的差异比抽象地说“更自然一点”更有信息量——它告诉 Agent 哪些词被删、哪些长句被拆、哪些地方需要补事实;
- 迭代: 把反复出现的改动整理回 Skill，并为每条规则保留正例、反例和适用范围;
- 验收: 只要求具备清晰触发条件、三到五条带示例的原则、作用域与例外，不把一次主观判断当作普遍规则;
- 启示: 短小、可读、能通过真实任务检验的初版，比一开始罗列几十条规则更适合作为迭代起点;

## Skill 生态的工程价值是什么？

- 模块化: 每个 Skill 是自包含的知识模块，可独立开发、测试与版本控制，便于分享;
- 生态类比: 与开源包管理系统（pip、npm）有深刻相似性，每个 Skill 封装某个领域的最佳实践;
- 意义: 能力扩展从集中式系统提示词编辑，转变为分布式、社区驱动的 Skill 生态构建;
- 现状: Anthropic 官方 Skills 仓库已涵盖文档处理（PPTX、PDF、DOCX）、数据分析、代码生成等领域;
- 设计原则: **选择 Agent 交互模式时应与模型厂商的训练方法保持一致**——基础模型公司推行的 Agent 用法本质上是它们专门训练过的模式;
- 推论: 同一生态内的模型在这些模式下天然具有最佳表现;

## 使用 Skill 完成复杂任务的实验观察到什么？

- 任务: 从一篇学术论文 PDF 生成 10-15 页演示文稿，使用 Claude Code 或支持 `SKILL.md` 渐进式披露的等价运行时;
- 流程: 在元数据目录看到 PPTX Skill 描述 → 识别任务需要 → 调用 Skill 加载完整指令 → 选择性加载 `html2pptx.md` → 使用捆绑脚本生成预览、模板作为设计起点;
- 观察: 渐进式加载在全过程中自然发生，Agent 只为真正需要的内容付出上下文成本;
- 验收: 覆盖标题页、问题背景、方法概述、关键结果、结论，至少 3 张与文字一致的图表，格式正确可打开;
- 对照: Skill 是实验对象，运行时可以替换；只要具备「元数据目录 + 按需加载」机制即可;
