# 模型与 Agent 的共同演进

## Harness 里的兜底逻辑记录了什么？

- 典型形态: 多级上下文压缩、失败数千次才熔断的重试、悲观地默认“不安全”的权限判断;
- 共同含义: 每一段看似丑陋的“屎山”，记录的都是模型此刻还做不稳的地方;
- 结局: 当下一代模型把这些约束内化，对应的代码就可以删掉;
- 边界与要素: 这类逻辑属于 Harness 的约束、验证与纠正部分，见[Harness 工程](../010-Agent基础/060-Harness工程.md);

## 模型与 Agent 为什么构成一个飞轮？

- 因果链: 模型之所以能内化某种能力，正是因为 Agent 早已在真实业务里替它把这些坑趟了一遍，并沉淀成下一轮训练的信号;
- 循环: 用户提出真实难题 → 应用层用 Harness 把模型暂时做不好的事补上 → 这些补救反过来变成模型下一次迭代的训练信号;
- 性质: 这是一个自我强化的飞轮;
- 前提: 模型和 Agent 从来不是上下游，而是一起往前走的，见[两朵乌云](./040-两朵乌云.md);

## 模型会不会最终吃掉 Harness？

- 结论: 会，但不是一次性吃掉，而是一层一层地吃，并且没有吃完的那一天;
- 已发生的例子: 打断、插话这些曾经要靠外挂 Harness 才能拼出的行为，如今被直接做进了模型内部;
- 理由一（时间差）: 训练以月计，模型等得起，业务等不起;
- 理由二（不可内化）: 模型无法内化真实业务中所有的约束与偏好，总有一层最新的边界需要外部逻辑兜底;
- 理由三（前沿迁移）: 每一代模型都会打开新的能力前沿，而前沿处恰恰是模型最做不稳的地方;
- 推论: Harness 不会消失，它只是随着模型不断向新的前沿迁移;
- 《苦涩的教训》在 Agent 时代的读法: 通用方法终将胜出，但“终将”二字里的每一段路，都是 Harness 铺出来的;
- 与术语节奏的关系: 这类 Harness 实践总在实践中先出现、后获得命名，见[实践在前，命名在后](./020-实践在前命名在后.md);

## 只改 Harness 的杠杆有多大？

- 实验结论: 不换模型、只改 Harness，任务准确率从 52.8% 跳到 66.5%;
- 双重含义: 这既说明 Harness 今天的杠杆有多大，也说明它之所以有这么大杠杆，恰恰是因为模型还没走到那一步;
- 两端咬合: 飞轮转得最快的地方，是同时握住两端的人;
- 实例: Anthropic 用 Claude Code 让自家模型与自家 Harness 互相喂养、共同进化;
- 咬合机制: 模型知道 Harness 会怎样调用它，Harness 也清楚模型的边界在哪，两端的每一次改动都能立刻反馈给对方;

## 为什么这条飞轮是最深的护城河？

- 判断: 真实业务、反馈数据与模型迭代咬合得越紧，别人越难从外部追上;
- 对造模型者: 护城河就是把这条飞轮转起来，让真实场景的反馈尽快回流到训练里;
- 对应用开发者: Harness 是短期最锋利的技术杠杆，但模型每内化一层约束，就会顺手抹平一批只靠 Harness 建立的优势;
- 应用层的长期壁垒: 往往在技术之外——独占的数据、稳固的渠道、用户的信任、网络效应，以及必须由人与 Agent 协作的物理世界场景;
- 稳妥打法: 把 Harness 用来争取时间，把这段时间用来构筑技术之外的壁垒;
- 对读者的意义: 站在飞轮哪一端决定了该投入什么，也决定了焦虑的重点;

## 什么不会随模型迭代而过时？

- 事实: 模型每几个月迭代一次，具体的 API、产品和榜单都会翻篇;
- 不变的部分: “看到什么、能做什么、如何验证做得对不对”三问，完整解释见[实践在前，命名在后](./020-实践在前命名在后.md);
- 实用收益一: 无论下一代模型带来什么新能力，都知道该把它放进[核心公式](../010-Agent基础/010-Agent公式与边界.md)的哪个位置;
- 实用收益二: 也能一眼看出，它离吹散[那两朵乌云](./040-两朵乌云.md)还有多远;
