# 虚拟身份与隔离执行环境

## Agent 应该复用用户账号还是拥有虚拟身份？

- 直接管理用户账号: 看似便捷，但一旦 Agent 出错或被攻破，用户的全部数字身份都会暴露;
- 虚拟身份方案: 赋予 Agent 一套独立身份，如同秘书拥有自己的办公电话与邮箱;
- 身份三件套: 专属的通讯账号、存储空间、计算环境;
- 效果: Agent 以透明身份代表用户工作，身份的明确性不削弱信任，反而增强沟通的真实性;

## 虚拟身份为什么需要隔离的执行环境？

- 载体: 虚拟电脑（VM/容器）与虚拟手机（Android 模拟器），提供操作系统级隔离和完整的桌面/移动操作能力;
- 理由一: 虚拟电脑可全天候运行，不受用户设备联网状态影响，也不干扰用户正在操作的应用;
- 理由二: Agent 执行错误操作最多导致虚拟环境崩溃，不影响用户的真实设备;
- 理由三: 隔离环境阻止 Agent 随意访问用户本地文件，提高安全性;
- 概念边界: 环境侧的资源与状态属于 Environment，隔离与权限机制属于 Harness，见 [Harness 工程](../010-Agent基础/060-Harness工程.md);

## 独立身份会带来哪些现实挑战？

- 挑战一 反机器人机制: 许多网站用 CAPTCHA 与 IP 信誉检测拦截自动化访问，数据中心 IP 的虚拟环境很容易被识别;
- 应对: 实践中往往需要配置住宅代理网络（使用真实家庭 IP）才能正常访问;
- 挑战二 必须以用户本人身份登录的任务: 采用 Human-in-the-Loop 认证，通过 VNC/RDP 远程桌面让用户在可视化环境中亲自完成登录;
- 收益: 用户能看到 Agent 正在操作的完整界面，理解为什么需要认证;
- 令牌复用: 认证后的会话令牌在有效期内复用，避免频繁打断用户，在自主性与安全性之间取得平衡;

## 共享文件系统如何避免上下文膨胀？

- 机制: 以卷挂载方式（如 `/workspace/shared`）连接 Agent、虚拟电脑与虚拟手机;
- 传递方式: 数据以文件路径引用传递，而非内容拷贝，因此不占用上下文窗口;
- 任务示例: 用户把 CSV 上传到共享目录 → 虚拟电脑中的 Agent 读取、分析、生成图表并保存回共享目录 → Agent 只把图表文件路径返回给用户;
- 结果: 各方之间传递的始终只是轻量级路径字符串;
- 衔接: 身份与环境就位后，剩下的是多个事件同时涌向同一 Agent 实例时的处理问题，见 [结构化事件建模与处理策略](./050-结构化事件建模与处理策略.md);
