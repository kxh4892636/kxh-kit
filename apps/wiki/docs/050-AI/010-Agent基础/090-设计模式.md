# 贯穿全书的设计模式

## 为什么要在第一章一次性命名设计模式？

- 原因: 后续章节反复用到同一批模式，先给出规范定义可避免重复命名与理解漂移;
- 数量: 五个——提议者—审核者、渐进式披露、只增不改、边界集 + 保留集、最小 diff + 可回滚;

## 提议者—审核者解决什么问题？

- 定义: 产出与评判由两个**不共享上下文**的角色分别承担;
- 关键约束: 评判方看到的是产物本身——渲染结果、测试输出、结构化的调用参数——而不是产出方的推理过程;
- 前提: **自审不可靠**——同一上下文中的模型难以发现自己的认知盲区，也很难判断自己是否已被注入;
- 应用: 第三章更新知识；第四章工具调用的事前审批与事后验证（Sidecar 是只读变体）；第五章 PPT、视频、日志实验；第七章评估 UI；第九章审核更新提案；第十章对等协作;

## 渐进式披露优化了什么？

- 定义: 不把全部信息一次性放进上下文，而是先给一份可检索的目录，再按需加载细节;
- 优化对象: 同时优化**上下文预算**与**选择精度**;
- 典型形态: 第二章的 Agent Skills——元数据常驻、正文按需加载;
- 变体: 第三章的分层检索、第四章的主动工具发现与分页截断、第十章的 Agent 发现;

## 只增不改带来什么性质？

- 定义: 状态以追加的方式演进，已写下的内容不再回头修改;
- 换来: 可缓存、可重放、可审计;
- 性能形态: 第二章的 KV Cache 前缀稳定性——改动越靠前，作废的缓存越多;
- 其他实例: 第三章的事件式记忆；第四章把新工具的 schema 追加到轨迹末尾而非插回前缀;

## 边界集 + 保留集为什么必须成对使用？

- 定义: 任何一次修改都要同时在“它应当改变的那批样本”和“它不应当影响的那批样本”上验证;
- 只测边界集: 会把过拟合当成进步;
- 只测保留集: 会把无效修改当成安全;
- 应用: 第七章的回归任务、第八章的训练与评估隔离、第九章的更新提案验证;

## 最小 diff + 可回滚的意义是什么？

- 定义: 每次修改尽量小、带来源、可单独回滚，而不是整体重写;
- 核心收益: 让归因成为可能——出了问题能定位到具体哪一次改动;
- 应用: 第三章的知识更新、第五章的代码补丁、第九章的 Prompt 与程序更新;
- 呼应: 第一章开头的三条更新路径（上下文内适应、外部产物更新、参数更新）正是按可回滚程度从高到低排列;
