# 跨组织协作的 A2A 协议

## 为什么跨组织协作需要新协议？

- 前提: 前面的系统都假设所有 Agent 由同一个团队开发、运行在同一个系统内，此时参数传递、共享文件、消息总线三种机制足够用;
- 新问题: 当协作跨越组织边界——你的 Agent 需要调用另一家公司的 Agent——就需要标准化的互操作协议;
- 类比: A2A 之于 Agent，就是网络协议之于进程;
- 来源: 2025 年 Google 发布的 **A2A**（Agent2Agent）协议，后捐赠给 Linux 基金会托管;

## Agent Card 解决什么问题？

- 定义: 一份描述 Agent 能力的元数据文档，发布在约定的公开地址下;
- 声明内容: 这个 Agent 能做什么、支持哪些输入输出模态、如何认证;
- 类比: 相当于 Agent 的"名片";
- 解决的问题: 跨组织的能力发现问题——调用方在互不可见的前提下知道对方是否胜任;

## 任务生命周期如何标准化？

- 建模: A2A 把协作单元建模为任务（Task）;
- 状态机: 已提交、进行中、需要输入、已完成、失败;
- 原生支持: 长时间运行的任务与流式进度更新;
- 与状态获取的呼应: 统一的状态机词汇让状态查询与汇报可路由、可追溯，见 [Agent 间的消息与状态](./070-Agent间的消息与状态.md);

## 不透明协作为什么是必需的？

- 定义: Agent 之间只交换任务与产物（Artifact），不暴露内部的提示词、思考过程与工具实现;
- 一致性: 这与"不共享上下文"原则一致，见 [不共享上下文的多 Agent 协作](./050-不共享上下文的多Agent协作.md);
- 必要性: 它是跨组织协作中必要的安全属性——协作方互不信任、实现互不可见;
- 产物传递: 交换的是任务与产物引用，而不是完整轨迹或内部推理;

## A2A 与 MCP 各自覆盖哪一段？

| 协议 | 解决的关系                  | 层次                  |
| ---- | --------------------------- | --------------------- |
| MCP  | Agent 与工具之间的互操作    | 单 Agent 的能力边界内 |
| A2A  | Agent 与 Agent 之间的互操作 | 跨信任边界的标准化层  |

- 关系: A2A 并不取代三种通信机制，而是在它们之上、跨信任边界的标准化层;
- 使用门槛: 同一团队内部的多 Agent 系统直接用消息总线即可；只有当协作方互不信任、实现互不可见时，才需要 A2A 这样的公开协议;
