# 终止级联与资源调度

## 执行终止为什么有两种强度？

- 触发场景: 并行协作中常出现"一个任务成功，其余任务便无需继续"——多个 Agent 分头搜索，一个命中目标后其余应立即停止;
- 优雅终止（首选）: 主 Agent 发出 `terminate` 信号，子 Agent 在当前步骤的安全点响应，先清理资源（关闭浏览器会话、写入未完成文件、释放锁），返回确认（ack）后退出;
- 强制终止（兜底）: 直接终止进程，仅在子 Agent 对优雅信号无响应时使用，代价是可能遗留悬挂资源与未完成写入;
- 对应关系: 两者正是 Unix 的 `SIGTERM` 与 `SIGKILL` 的区别;

## 主 Agent 终止后，仍在运行的子 Agent 怎么办？

- 级联终止: 借鉴 Go 的 context，终止沿创建关系向下级联——取消一个 Agent，它派生的所有子 Agent 随之取消，从根上杜绝无人认领的孤儿 Agent;
- 实现对应: 子 Agent 在安全点检查终止信号，对应 Go 中对 `ctx.Done()` 的轮询;
- 例外: 若确实需要脱离主 Agent、长期运行的后台 Agent（类似 Unix 的 `nohup`），就让它从一棵新的生命周期树起步（对应 `context.Background()`），显式声明不随父级终止;
- 相关观察: 并行搜集实验中的级联终止与竞态处理见 [并行协作与级联终止](./140-并行协作与级联终止.md);

## 资源与调度要管住哪些稀缺项？

- 稀缺资源: 进程世界稀缺的是 CPU 时间与内存，Agent 世界稀缺的是 **token** 与**并发额度**;
- 职能归属: 这项职能通常落在管理者 Agent 或运行时身上;
- 预算: 启动子 Agent 时设定步数或 token 预算，超限即止，机制细节见 [步骤预算与预算感知](./030-步骤预算与预算感知.md);
- 模型分级: 困难任务交给强模型，机械任务交给低成本模型;
- 并发上限: 避免几十个 Agent 同时耗尽 API 配额;
- 抢占: 并发数达到上限而更紧急的任务到来时，打断执行中的子 Agent;

## 管理者 Agent 的调度为什么优于传统调度器？

- 关键差异: 管理者 Agent 具备推理能力，可以启动多个子 Agent 并行探索一个问题;
- 动态调整: 根据它们的进展决定给哪些 Agent 分配更多资源，或终止看起来误入歧途的 Agent——像公司内部赛马一样;
- 成熟度: 资源与调度领域的实践远不如操作系统调度成熟，但它决定了多 Agent 系统的成本上限，应在架构设计阶段就予以考虑;
