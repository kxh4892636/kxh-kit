# 代码搜索工具

## 在庞大代码库中定位代码有哪几类互补工具？

| 工具                         | 匹配对象             | 优势                                   | 根本局限                                       |
| ---------------------------- | -------------------- | -------------------------------------- | ---------------------------------------------- |
| 正则内容匹配（grep/ripgrep） | 文件内容逐行扫描     | 知道具体文本时快速准确，可表达复杂结构 | 只找字面匹配，无“用户认证”字样就找不到登录逻辑 |
| 文件名模式匹配（glob）       | 路径结构             | 不打开文件，速度最快                   | 不涉及内容语义                                 |
| 语义代码搜索                 | 代码与查询的“意义”   | 找语义相似但用词不同的代码             | 需建索引，维护成本                             |
| 符号级定义与引用查找         | 符号的定义点与调用点 | 区分同名符号的定义与调用               | 主流 coding agent 尚未采用                     |

- 定位: 定位相关代码是 Coding Agent 工作的起点，四类工具构成互补工具箱;

## 正则内容匹配的实用要点是什么？

- 适用: Agent 已知具体文本（函数名、变量名、错误消息）时，快速定位所有出现位置;
- 表达能力: 正则不仅能搜字面文本，还能搜符合特定结构的代码片段，例如 `def handle.*`;
- 减噪: 应支持文件类型过滤（只搜 Python）与路径模式过滤（排除测试目录）;

## 文件名模式匹配为什么常是探索第一步？

- 示例: `**/*.test.ts` 递归找所有 TypeScript 测试文件；`src/components/**/Button.tsx` 在 components 下任意深度找 Button.tsx;
- 用途: 通过快速扫描整个文件系统建立项目的组织框架;
- 理由: 不需要打开和读取文件，速度比内容搜索快得多;

## 语义代码搜索要解决哪两个问题？

- 问题一——结构感知的分块: 代码有严格语法结构，应按函数、类、方法等完整语义单元切分，而非按固定字符数盲目切割;
- 问题二——混合检索: 稠密向量嵌入擅长找到语义相似但用词不同的代码（搜“验证用户身份”能找到 `check_credentials`），关键词匹配擅长精确命中函数名与变量名；两者并行执行后由重排序模型合并排序;
- 适用: 探索性任务，如在不熟悉的代码库中寻找“与数据库交互”或“处理用户输入验证”的代码;

## 要不要为语义搜索建嵌入索引？

- 分歧: 业界存在明显的路线之争;
- 终端型路线: 以 Claude Code 为代表，刻意不建嵌入索引，纯靠 agentic 的 grep + glob 现场检索;
- 理由: 不必维护随代码演化而陈旧的索引，也省掉一整套索引基础设施;
- IDE 型路线: Cursor 这类工具早期愿意为跨文件语义召回付出建索引成本，以便在大库中快速找到语义相关但用词不同的片段;
- 现状: Cursor 等 IDE 目前也改用 grep + glob 现场检索了;

## 符号级查找与文本搜索差在哪？

- 例证: 符号查找知道 `authenticate` 在第 42 行是函数定义、在第 189 行是调用；文本搜索只能找到所有包含该字符串的行;
- 类比: IDE 的“跳转到定义”“查找所有引用”;

## 四类工具如何组合？

- 策略: 先用语义搜索找到相关模块，再用正则匹配精确定位具体代码行，最后通过符号搜索追踪调用链;
- 概括: 从粗到细、从语义到语法的渐进式策略;
