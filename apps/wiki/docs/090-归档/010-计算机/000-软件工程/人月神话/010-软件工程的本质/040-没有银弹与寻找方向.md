# 没有银弹与寻找方向

## 以往的突破为什么没有带来数量级提升？

- 评估方法: 回顾最富成效的进步, 外推其固有限制, 看解决根本还是次要困难;
- 高级语言: 生产率、可靠性和简洁性上最有力的突破;
- 高级语言效果: 大多数观察者相信生产率至少提高 5 倍;
  - 可靠性、简洁性和理解程度也大为提高;
- 机理: 抽象程序关心操作、数据类型、流程和通讯;
- 对照: 机器语言关心位、寄存器、条件、分支、通道、磁盘;
  - 高级语言消除了并非程序固有的整个级别的复杂度;
- 局限一: 思考数据结构、类型和操作的速度只是非常缓慢地提高;
- 局限二: 对较少使用复杂语义要素的用户甚至增加了脑力负担;
- 局限三: 它能提供的是所有编程人员在抽象程序中能想到的要素;
- 分时: 保证及时性, 使程序员维持对复杂程度的总体把握;
- 批处理代价: 长周转时间意味着遗忘细节, 重思代价高昂;
  - 最严重后果是失去对复杂系统的掌握;
- 分时局限: 主要效果就是缩短响应时间;
  - 响应时间接近人类可辨识的 100 毫秒时, 收益趋近于零;
- 统一编程环境: Unix 和 Interlisp 是第一批集成开发环境, 生产率提高 5 倍;
- 机制: 集成库、统一文件格式、管道和过滤器, 解决共用程序的次要困难;
- 放大效应: 新工具能通过标准格式用于任何程序, 激发工具库开发;
- 结果: 环境开发成为当时软件工程研究的主要题目;

## 银弹候选清单上都有什么？

- 评估框架: 逐个追问——它针对什么问题? 必要问题还是剩余的次要困难? 是创新还是增量改进?
- 共同判据: 若低层次类型说明等非本质内容不占据设计工作的 90%, 消除它们就不会带来数量级提高;

| 候选银弹               | 它想解决的问题                                   |
| ---------------------- | ------------------------------------------------ |
| Ada 和其他高级编程语言 | 用更抽象的语句表达设计, 降低机器的次要复杂度     |
| 面向对象编程           | 抽象数据类型与层次化类型, 摆脱表达设计的句法负担 |
| 人工智能               | 用曾属人类智慧的方法解决开发问题                 |
| 专家系统               | 用归纳推论引擎加规则基础提供建议                 |
| "自动"编程             | 从问题的一段陈述自动产生程序                     |
| 图形化编程             | 用图形和可视化表达软件结构                       |
| 程序验证               | 在设计级别、源代码级别消除缺陷                   |
| 环境和工具             | 集成库、统一格式、智能编辑器、开发数据库         |
| 工作站                 | 更强的运算能力与内存加速开发                     |

## 为什么每一种候选都不是银弹？

| 候选       | 要点                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------ |
| Ada        | 本质只是另一种高级语言                                                                           |
| Ada        | 抽象数据类型和层次化模块化理念可能比语言本身更先进; 用设计承载需求也可能过于丰富                 |
| Ada        | 障碍已解: 词汇子集和硬件的 MIPS 进步足以解决学习与编译成本                                       |
| Ada        | 最大贡献不在语言特性或环境, 而是推动培训方式转变: 对开发人员进行现代软件设计技术培训             |
| Ada        | 十年内被评估认可后会有相当大的变化; 仍不是消灭生产率怪兽的银弹                                   |
| 面向对象   | Mark Sherman 指出必须区分两个互不相干的概念                                                      |
| 面向对象   | 概念一 抽象数据类型: 用名称、值集合和操作定义类型, 隐藏存储结构; 如 Ada 包、Modula 模块          |
| 面向对象   | 概念二 层次化类型: 类; 如 Simula-67 的类, 允许定义可被后续子类型精化的通用接口                   |
| 面向对象   | 作用: 两者消除设计表达上的次要困难, 允许直接表达设计的内在特性                                   |
| 面向对象   | 局限: 内在问题是设计的复杂度, 它们毫无触及                                                       |
| 面向对象   | 判据: 除非低层次类型说明占软件产品设计的 90%, 否则不会数量级提高; 作者深表怀疑                   |
| 人工智能   | Parnas 澄清术语混乱; AI-1 解决以前只能靠人类智慧的问题, 标签易变、理解运行方式后就不算 AI        |
| 人工智能   | AI-2 启发式和基于规则的特定技术才可讨论; 语音识别与图象识别、专家系统技术都不同                  |
| 人工智能   | 局限: 软件开发的困难是决定说什么而不是如何说, 表达简化只能提供少量促进                           |
| 专家系统   | 构成: 归纳推论引擎和规则基础; 引擎独立于应用、可服务多用户, 值得大力投入                         |
| 专家系统   | 优势二: 应用相关部分在规则库中统一编码, 为规则的开发、更改、测试和文档化提供工具                 |
| 专家系统   | Feigenbaum: 能力不来自前所未有的推导机制, 而来自丰富的知识积累, 因此更精确地反映现实世界         |
| 专家系统   | 作者评价: 最重要的进步是"具体应用的复杂性与程序本身相分离"                                       |
| 专家系统   | 用途: 建议接口规则、制订测试策略、记录 bug 频率、提供优化建议                                    |
| 专家系统   | 比喻: 像飞行员的检查列表, 规则库纳入越多系统结构信息越准确                                       |
| 专家系统   | 机制: 诊断规则与编制测试用例集同源, 能减少测试设计总量; 规则库可随产品模块化修改                 |
| 专家系统   | 瓶颈: 难从技术说明自动/半自动产生诊断规则; 难找能说清"为什么"的分析专家                          |
| 专家系统   | 代价: 知识获取本身已很昂贵; 抽取专家知识并精炼成基础规则的工作量是其两倍; 前提是拥有专家         |
| 专家系统   | 最强贡献: 给缺乏经验的开发者提供最优秀开发者的经验; 这一差距可能比其他工程领域都大               |
| "自动"编程 | 近四十年不断被预言, 一再沦为"用当时尚不可用的更高级语言编程"的热情                               |
| "自动"编程 | Parnas: 这是"魔咒"式、语义不完整的术语——多数技术说明本质上是问题的解决方法                       |
| "自动"编程 | 成功例外: 数据发生器类工具（如排序程序）: 问题能用较少参数迅速描述                               |
| "自动"编程 | 例外条件: 存在大量已知解决方案组成的库, 参数与方案间有清晰选择规则                               |
| "自动"编程 | 这种简洁属性是例外, 无法想象它如何普及到寻常软件系统                                             |
| 图形化编程 | 至今没有令人信服的进步, 作者确信将来也不会出现                                                   |
| 图形化编程 | 流程图是很差劲的软件结构表达方法                                                                 |
| 图形化编程 | 流程图是冯·诺依曼、戈尔德斯廷、勃克斯提供的高级控制语言, 如今变成事后描述、多页连接令人同情      |
| 图形化编程 | 屏幕太小: "类似桌面"的工作站像"飞机坐舱座椅", 无法同显所有范围与细节, 硬件须再发展               |
| 图形化编程 | 更基本: 软件难以可视化——图形只表达一个方面, 如同盲人摸象, 多视图叠加难抽全局                     |
| 图形化编程 | VLSI 类比误导: 芯片是两维对象的层次设计, 几何特性即本质特性, 软件不是                            |
| 程序验证   | 概念很先进, 对安全操作系统内核等应用非常重要                                                     |
| 程序验证   | 不能保证节约劳动力: 验证工作量太大, 只有少量程序能得到验证                                       |
| 程序验证   | 不意味着零缺陷: 数学验证仍可能出错, 所以不能省略程序测试                                         |
| 程序验证   | 完美验证只能建立"满足技术说明"的程序, 而此时最困难的部分已接近完成; 部分工作变成对规格说明的测试 |
| 环境和工具 | 高回报的本能选择: 层次化文件系统、统一文件格式, 获得一致接口和通用工具                           |
| 环境和工具 | 智能化编辑器: 特定语言的编辑器最有希望消除语法错误和简单语义错误                                 |
| 环境和工具 | 集成数据库: 可能是已实现的最大成果, 跟踪大量开发细节、供精确查阅并保持团队最新                   |
| 环境和工具 | 评价: 有价值、能带来一些提高, 但回报有限                                                         |
| 工作站     | 现有运算速度已满足编制与文档需要, 编译还需提高; 欢迎更强工作站, 但不期望魔术般提高               |
| 工作站     | 运算速度提高十倍后, 思考活动将成为日常主要活动——实际上已是现在的情况                             |
| 关键人物   | MYSIGMA（日本）、Northrop 的 Steve Lukasik、达特茅斯的 Mark Sherman                              |
| 关键人物   | 美国管理系统公司主席 Ivan Selin（1987 年信）、《C++ Report》专栏作者 Coggins                     |

## 针对根本困难的三条可行方向是什么？

- 生产率公式: 针对次要困难的工作可表达为 任务时间 = Σ(频率)i×(时间)i;
- 含义: 若创造性部分占大部分时间, 仅表达概念无法显著影响生产率;
- 方向一 购买和自行开发: 最彻底的方案是不开发任何软件;
- 经济性: 购买总比重新开发低廉——100,000 美元仅相当于一个人年, 且立即可用、文档良好;
- 市场逻辑: 软件成本一直是开发成本而非复制成本;
  - n 个拷贝使开发人员的生产率有效提高 n 倍, 是行业范围的提高;
- 历史转折: 1950~1960 年代用户不在工资、物流、帐务系统中用商用软件包;
- 原因: 需求过于专业;
  - 80 年代需求大增, 重大变化在硬件/软件成本比率;
- 数据对照: 1960 年 200 万美元机器的买主愿为定制薪资系统支付 250,000 美元;
  - 如今 50,000 美元办公机器的买主不愿再付, 转而调整软件包;
- 戏剧性例外: 电子表格和简单数据库系统取代大量原先用 Cobol 或报表生成程序编写的应用;
- 部署策略: 生产一线配很多个人计算机, 装通用书写、作图、文件管理和电子表格程序;
  - 配熟练使用人员并散布到各岗位; 实验室可配数学和统计软件包;
- 作者判断: 这个大众市场是软件工程领域意义最深远的开发方向;
- 方向二 需求精炼和快速原型: 最困难的是确切决定搭建什么系统;
- 为什么难: 需求失误影响最大, 纠正需求的困难也最大;
  - 客户不知道需要什么, 连必须确定的细节也常被忽略;
  - 复杂软件系统往往是活动的、变化的系统, 动态部分很难想象;
- 定论: 在尝试和开发客户定制系统之前, 完整、精确、正确地抽取需求不可能, 即使客户与工程师一起工作;
- 用户的现实: 很多用户天天操作计算机却不写代码, 不少人不会编程也能解决新问题;
- 可操作建议: 把与客户的多次广泛沟通作为系统定义的一部分, 而不只是一次需求评审;
- 快速原型: 对重要系统界面进行模拟, 演示待开发系统的主要功能;
  - 不必受相同硬件速度、规模或成本约束, 通常只展示功能主线、不处理异常输入和退出清除;
- 原型目的: 明确实际的概念结构, 让客户测试一致性和可用性;
- 流程批判: 现有"先明确阐述系统→竞标→开发→安装"的假设根本上不正确;
  - 很多软件问题正来自这一谬误;
- 改进方向: 对产品和原型不断往复地开发和规格化;
- 方向三 增量开发: 借鉴生物的复杂性, 秘密是逐步发育成长, 而非一次性搭建;
- 隐喻来源: 1958 年听到朋友说"搭建"而非"编写"系统, 视野豁然开朗;
- 隐喻失效: "搭建"的隐喻已超出有效期限;
- 隐喻转向: 作者主张转向生物"成长"的隐喻, 而非规格说明、构件装配或脚手架等建造类表达;
- Harlan Mills 的建议: 所有软件系统都应增量开发;
- 做法: 先让系统能运行, 即使只能正确调用一系列伪子系统;
  - 然后一点一点充实, 子系统轮流被开发或以占位符代替;
- 方法要求: 自顶向下设计, 因为它本身就是自顶向下增长, 便于逆向跟踪和原型开发;
  - 每项新功能、每个新模块都从已规划的系统中有机增长;
- 实践效果: 可运行系统一出现, 开发人员热情迸发;
- 例证: 图形系统屏幕上出现第一个长方形时, 工作动力成倍增长;
- 实践数据: 团队可在四个月内"培育"出比"搭建"复杂得多的系统, 大型项目同样受益;
- 作者自述: 没有任何方法和技术能如此彻底地改变他自己的实践;
- 可检查的判据: 开发过程中的每个阶段总有可运行的系统;

（source: 人月神话 · 没有银弹－软件工程中的根本和次要问题）
