# 剔除 bug 的设计

## 本章要解决什么问题？

- 章首的诘问（莎士比亚《亨利四世》）: "我能召唤遥远的精灵。那又怎么样, 我也可以, 谁都可以。";
- 关键反问: "问题是你真的召唤的时候, 它们会来吗?";
- 现代对应: 有人说"我可以编写控制航空货运、拦截弹道导弹、管理银行账户、控制生产线的系统";
- 回答很简单: "我也可以, 任何人都可以, 但是其他人成功了吗?";
- 三个问题: 如何开发一个可以运行的系统? 如何测试系统?
- 如何将经过测试的一系列构件集成到已测试过、可以依赖的系统?

## bug 的主要来源是什么？

- 定义: 系统各个组成部分的开发者都会做出一些假设;
- 这些假设之间的不匹配, 是大多数致命和难以察觉的 bug 的主要来源;
- 关联途径: 获取概念完整性的途径直接面对这些问题;
- 概念完整性使产品易于使用, 也使开发更容易进行、bug 更不容易产生;
- 详见 [概念完整性](../030-概念完整性/010-概念完整性.md);
- Vyssotsky（Bell 实验室安全监控系统项目）: "关键的工作是产品定义。";
- V. A. Vyssotsky: "许许多多的失败完全源于那些产品未精确定义的地方。";
- 效果: 细致的功能定义、详细的规格说明、规范化的功能描述说明及其实施;
- 这些做法大大减少了系统中必须查找的 bug 数量;
- 具体措施: 在编写任何代码之前, 规格说明必须提交给测试小组;
- 由测试小组详细检查说明的完整性和明确性;
- 为什么需要测试小组: Vyssotsky 称开发人员自己不会完成这项工作;
- "他们不会告诉你他们不懂。相反, 他们乐于自己摸索出解决问题和澄清疑惑的办法。";

## 自顶向下设计如何减少 bug？

- 来源: 1971 年 Niklaus Wirth 形式化了一种优秀编程人员常用的设计流程;
- 适用性: 理念虽为程序设计提出, 同样适用于复杂系统的软件开发设计;
- 程序开发可划分成体系结构设计、设计实现和物理编码实现;
- 每个步骤都可以用自顶向下的方法很好地实现;
- Wirth 的精化流程: 设计被看成一系列精化步骤;
- 开始勾画出能得到主要结果但比较粗略的任务定义和大概的解决方案;
  - 对定义和方案进行细致检查, 判断结果与期望之间的差距;
  - 把解决方案在更细的步骤中分解;
- 双向精化: 任务定义的精化变成解决方案中算法的精化;
  - 还可能伴随数据表达方式的精化;
- 模块化: 识别出解决方案或数据的模块后, 其细化可以和其他工作独立;
- 模块的大小程度决定了程序的适用性和可变化的程度;
- 表达层级: Wirth 主张每步尽量用级别较高的表达方法表现概念、隐藏细节;
  - 有必要进行进一步的细化;
- 避免 bug 的四个方面:

| 方面                         | 作用                                     |
| ---------------------------- | ---------------------------------------- |
| 1 清晰的结构和表达方式       | 更容易对需求和模块功能进行精确描述       |
| 2 模块分割和模块独立性       | 避免系统级的 bug                         |
| 3 细节的隐藏                 | 结构上的缺陷更加容易识别                 |
| 4 每个精化步骤的层次上可测试 | 测试可以尽早开始, 每步重点放在合适的级别 |

- 允许回退: 按部就班的流程并不意味着步骤不能反过来;
- 甚至可以推翻顶层设计、重新开始整个过程, 这种情况经常发生;
- 好处: 更清楚在什么时候和为什么抛弃某个臃肿的设计并重新开始;
- 对比: 一些糟糕的系统往往试图挽救一个基础很差的设计, 加表面装饰般的补丁;
- 自顶向下的方法减少了这样的企图;
- 作者的预言: "我确信在十年内, 自顶向下进行设计将会是最重要的新型形式化软件开发方法。";

## 结构化编程的核心主张是什么？

- 来源: 另外一系列减少 bug 数量的新方法很大程度上来自 Dijkstra;
- Bohm 和 Jacopini 为其提供了理论证明;
- 受限的控制结构: 仅包含语句形式的循环结构（例如 DO WHILE）;
- 以及 IF...THEN...ELSE 的条件判断结构;
- 理论证明: Bohm 和 Jacopini 展示这些结构在理论上是可以证明的;
- Dijkstra 的论断: GO TO 不加限制的分支跳转会产生导致自身逻辑错误的结构;
- 反面意见: 附加的控制结构非常有效, 例如多路分支（CASE、SWITCH 语句）;
- 又如异常跳转（GO TO ABNORMAL END）;
- 完全避免 GO TO 语句的说法有些教条主义, 而且似乎有些吹毛求疵;
- 关键之处: 构建无 bug 程序的核心是把系统的结构作为控制结构来考虑;
- 而不是独立的跳转语句;
- 这种思考方法是程序设计发展史上向前迈出的一大步;

（source: 人月神话 · 第 13 章 整体部分）
