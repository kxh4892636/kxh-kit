# 程序维护与软件熵

## 软件维护和硬件维护有什么不同？

| 维度     | 硬件维护                             | 软件维护                               |
| -------- | ------------------------------------ | -------------------------------------- |
| 主要活动 | 替换损坏器件、清洁润滑、修复设计缺陷 | 不含清洁润滑和器件修复; 主要修设计缺陷 |
| 缺陷性质 | 多数变更修复实现缺陷, 而非结构缺陷   | 变更包含更多新增功能                   |
| 用户感知 | 常常是不可见的                       | 通常是用户能察觉的                     |

- 定义: 程序发布给顾客使用后不会停止变化;
- 发布后的变更被称为"程序维护";
  - 软件的维护过程不同于硬件维护;
- 成本数据: 广泛使用的程序, 维护总成本常是开发成本的 40% 或更多;
- 该成本受用户数目严重影响: 用户越多, 发现的错误越多;

## 发布后的错误率为什么会循环攀升？

- 案例（麻省理工学院核科学实验室 Betty Campbell）: 特定版本的软件在发布生命期中有一个循环;
- 循环: 起初上一个版本中被发现和修复的 bug 在新版本中仍会出现;
- 新版本中的新功能会产生新的 bug;
- 解决这些问题后程序正常运行几个月;
  - 错误率重新攀升;
- 解释: 用户的使用到达新的熟练水平, 开始运用新的功能;
- 高强度考验查出了新功能中很多不易察觉的问题;
- 图示: 出现的 bug 数量是发布时间的函数（图 11.2）;

## 为什么缺陷修复总在引入新 bug？

- 基本数字: 缺陷修复总会以 20%~50% 的机率引入新的 bug;
  - 整个过程是前进两步、后退一步;
- 原因一 问题级别误判: 看似轻微、仅局部操作失败的错误, 实为系统级问题;
- 这类问题通常并不明显;
- 修复局部问题的工作量很清晰且往往不大;
  - 更大范围的修复工作常常被忽视;
  - 软件结构很简单, 或者文档书写得很详细;
- 原因二 维护者不是作者: 维护人员常是初级程序员或新手, 非原开发者;
- 代价: 程序每条语句的维护需要的系统测试比其他编程要多;
- 理论要求: 每次修复之后必须重新运行先前所有的测试用例;
  - 确保系统不会以更隐蔽的方式被破坏;
- 实际情况: 回归测试必须接近上述理想状况, 成本很高;
- 对策一: 用能消除或指明副作用的程序设计方法, 维护成本回报大;
- 对策二: 设计实现的人员越少、接口越少, 产生的错误也越少;

## 为什么系统会越维护越混乱？

- 研究: Lehman 和 Belady 研究大型操作系统一系列发布版本的历史;
- 发现一: 模块数量随版本号线性增长;
- 受影响的模块以版本号指数的级别增长;
- 发现二: 所有修改都倾向破坏系统的架构, 增加混乱程度;
- 发现三: 修复原有设计瑕疵的工作量越来越少;
- 早期维护活动本身漏洞引起的修复工作越来越多;
- 结论: 系统随时间越来越无序, 修复工作迟早失去根基;
- 每一步前进都伴随一步后退;
- 现实状态: 理论上系统一直可用, 实际已面目全非;
- 无法再成为下一步进展的基础;
- 机器、配置、用户的需求都在变化;
  - 现实系统不可能永远可用;
- 崭新的、对原有系统的重新设计完全必要;
- 引语（原文归为 Pascal. C. S. Lewis 所敏锐指出; 原文如此, 人名疑为笔误）:
- "使用卓越的能源构建文明、成立杰出的机构, 但每次总会出现问题;
- 一些致命的缺陷会将自私和残酷的人带到塔尖, 接着一切开始滑落……";
- "看上去, 就好像是机器正常启动, 跑了几步, 然后垮掉了。";
- 结论的来源: Belady 和 Lehman 通过统计模型研究软件系统;
- 得到了更具普遍意义、为所有经验支持的结论;

## 熵的比喻如何解释维护？

- 系统软件开发: 减少混乱度（减少熵）, 本身处于亚稳态;
- 软件维护: 提高混乱度（增加熵）;
- 最熟练的软件维护也只是放缓系统退化到非稳态的进程;
- 含义（笔记引申）: 维护不是"恢复原状";
- 而是对抗不可逆的退化;
- 这为"为舍弃而计划"提供了物理直觉（见 [为舍弃而计划](./010-为舍弃而计划.md)）;

（source: 人月神话 · 第 11 章 未雨绸缪）
