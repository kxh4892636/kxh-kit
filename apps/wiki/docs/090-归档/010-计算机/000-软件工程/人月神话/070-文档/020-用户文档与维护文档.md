# 用户文档与维护文档

## 程序为什么有两种"面貌"？

- 程序的本质: 计算机程序是从人传递到机器的一些信息;
- 要求: 为把人的意图清晰地传达给不会说话的机器, 程序采用严格的语法和严谨的定义;
- 另一种面貌: 书面的计算机程序还要向用户诉说自己的"故事";
- 私有程序也需要: 即使是完全开发给自己使用的程序, 这种沟通仍然必要;
- 原因: 记忆衰退的规律会让作者失去对程序的了解, 不得不重拾劳动的各个细节;
- 公共程序更甚: 用户在时间和空间上都远离作者, 文档的重要性不言而喻;
- 结论: 程序向用户呈现的面貌和提供给机器识别的内容同样重要;
- 普遍现象: 面对文档"简约"的程序, 大多数人都不免暗骂远方的匿名作者;
- 说教为什么失败: 向新人灌输文档重要性的很多次尝试都失败了;
- 说教目的: 延长软件的生命期、克服惰性和进度的压力;
- 失败之因: 很可能由于使用了错误的方法;
- Watson 的经历: Thomas J. Watson 年轻时做收银机推销员;
- 表现: 工作勤奋却连一台也卖不出去;
- 销售经理: 听完汇报后说"帮我抬一些机器到马车上, 收紧缰绳, 出发!";
- 做法: 在接下来的客户拜访中身体力行演示如何出售, 事实证明可行;
- 作者的结论: 多年讲座、讲述甚至热诚劝诫都不管用;
- 现状: 工程师们知道如何正确地编写文档, 却缺乏工作的热情;
- 有效做法: 演示"如何完成这项工作"的效果要好得多;
- 重点: 应放在"如何做才能产生一篇优秀的文档"上;

## 使用者需要什么样的文档？

- 用户分级: 仅仅偶尔使用的用户、必须依赖程序的用户、必须修改程序的用户;
- 最低要求: 每个用户都需要一段对程序进行描述的文字;
- 常见缺陷: 大多数文档只提供很少总结性内容, 描绘了树木、形容了树叶, 却没有森林的图案;
- 做法: 为了得到一份有用的文字描述, 必须放慢脚步, 稳妥地进行;

程序的使用文档应包含九项:

| 项  | 内容                                                    |
| --- | ------------------------------------------------------- |
| 1   | 目的: 主要的功能是什么? 开发程序的原因是什么?           |
| 2   | 环境: 程序运行在什么样的机器、硬件配置和操作系统上?     |
| 3   | 范围: 输入的有效范围是什么? 允许显示的合法范围是什么?   |
| 4   | 实现功能和使用的算法: 精确地阐述它做了什么              |
| 5   | 输入-输出格式: 必须是确切和完整的                       |
| 6   | 操作指令: 包括控制台及输出内容中正常和异常结束的行为    |
| 7   | 选项: 用户的功能选项有哪些? 如何在选项之间进行挑选?     |
| 8   | 运行时间: 在指定的配置下, 解决特定规模问题所需要的时间? |
| 9   | 精度和校验: 期望结果的精确程度? 如何进行精度的检测?     |

- 篇幅与时机: 三、四页纸常常就可以容纳以上所有的信息;
- 要求: 特别注意表达的简洁和精确;
- 时机: 它包含和软件相关的基本决策, 绝大部分需要在程序编制之前书写;

## 验证程序需要哪些测试用例？

- 附带证明: 除程序的使用方法外, 还必须附带程序正确运行的证明;
- 名称: 即测试用例 (test case);
- 例行小用例: 每一份发布的程序拷贝应该包括一些可以例行运行的小测试用例;
- 作用: 给用户信心, 他拥有了一份可信赖的拷贝, 并且正确地安装到了机器上;
- 全面用例的用途: 在程序修改之后进行常规运行;
- 划分: 这些用例可以根据输入数据的范围划分成三个部分;

| 类别         | 数量     | 检查目标                                                                             |
| ------------ | -------- | ------------------------------------------------------------------------------------ |
| 常规数据用例 | 主要部分 | 针对遇到的大多数常规数据和程序主要功能进行测试                                       |
| 合法边界用例 | 相对较少 | 对输入数据范围边界进行检查, 确保最大可能值、最小可能值和其他有效特殊数据可以正常工作 |
| 非法数据用例 | 相对较少 | 在边界外检查数据范围边界, 确保无效的输入能有正确的数据诊断提示                       |

## 修改程序需要哪些内部文档？

- 前提: 调整程序或者修复程序需要更多的信息;
- 要求: 了解全部的细节, 且这些细节已记录在注释良好的列表中;
- 与一般用户的差别: 修改者迫切需要一份清晰明了的概述, 这次是关于系统的内部结构;

修改文档应包含五项:

| 项  | 内容                                                                                                                   |
| --- | ---------------------------------------------------------------------------------------------------------------------- |
| 1   | 流程图 (flow chart) 或子系统的结构图                                                                                   |
| 2   | 对所用算法的完整描述, 或者是对文档中类似描述的引用                                                                     |
| 3   | 对所有文件规划的解释                                                                                                   |
| 4   | 数据流的概要描述: 从磁盘或者磁带中获取数据或程序处理的序列, 以及在每个处理过程完成的操作                               |
| 5   | 初始设计中对已预见修改的讨论; 特性、功能回调的位置以及出口; 原作者对可能扩充之处及可能处理方案的意见; 对隐藏缺陷的观察 |
