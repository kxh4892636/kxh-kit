# 依赖方向

## 分层模型把依赖指向哪边？

```text
传输层（HTTP / RPC）
   → Handler：解析、校验、身份、映射
      → Service：业务规则、事务边界、编排
         → Repository：存储接口
            → MySQL / Redis / 下游 RPC
```

- 依赖方向: 只能向右, Handler 可以依赖 Service;
- 反向禁止: Service 不知道 Handler 存在;
- Service 只依赖 Repository 接口, 不依赖 ORM、HTTP、RPC 类型;
- Repository 返回领域对象, 不返回数据库游标、ORM 查询对象;

## 怎么判断依赖方向做对了？

- 看「换传输协议或换数据库时, 要改几层」: 只改一层才算对;
- Service 不导入框架包: Go 只收标准库 `context.Context`;
- Node: 不收请求上下文对象;
- 目的: 业务能在定时任务、CLI、其他入口复用;
- Repository 接口: 定义在消费方 Service 侧, 实现放基础设施层;
- 测试: 用 fake 覆盖业务分支, 不连数据库;
- 目录名不重要, 依赖方向才重要; `main` / 组装函数是唯一组装点, 不出包级全局单例;

## 分层目录和接口示例长什么样？

```text
# Go
cmd/server/main.go          # 读取配置、创建依赖、启动、退出
internal/user/
  handler.go                # 传输适配：请求 → 领域调用 → 响应
  service.go                # 业务规则与事务
  repository.go             # 存储接口
  repository_sql.go         # SQL / ORM 实现
```

```go
// Service 定义自己需要的存储接口，实现放在外层。
type UserRepository interface {
	FindByID(ctx context.Context, id int64) (*User, error)
}

type UserService struct{ repo UserRepository }

func (s *UserService) Get(ctx context.Context, id int64) (*User, error) {
	if id <= 0 {
		return nil, ErrInvalidID
	}
	return s.repo.FindByID(ctx, id)
}
```
