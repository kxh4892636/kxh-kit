# 查询与访问路径

## 一次查询的代价由什么决定？

- 由「访问路径」决定: 命中索引还是全表扫描、读多少行、返回多少列;
- 同一句 SQL 换执行计划就差几个数量级; 结果对不代表能上生产;
- 判断顺序: 先看扫描行数, 再看回表与排序, 最后看返回体积;

```text
全表扫描 → 命中索引 → 覆盖索引
行数依次减少，磁盘与 CPU 依次减少
```

## 索引为什么会让写变慢？

- 索引是额外的有序结构, 每次写都要同步维护;
- 读多写少的表加索引收益大; 高频写入的表, 索引是写放大;
- 复合索引按「最左前缀」生效: 把等值条件放前面, 范围条件放后面;
- 关联列（外键）没有索引时, 每条主表行都触发一次子表全表扫描;

## 怎么确认查询走了索引？

- 看执行计划: 出现「全表扫描 / SCAN」就说明索引没用上;
- 常见失效原因: 列上套了函数或类型转换、前导通配的模糊匹配、隐式类型不匹配;
- 凭直觉加索引不如先测: 数据量小的时候扫描更快, 计划会随数据量变;

## 为什么必须参数化查询？

- 拼字符串等于把用户输入当代码执行, 注入无法在业务层补救;
- 参数化同时让数据库复用执行计划, 减少解析开销;
- 标识符（表名、列名）不能参数化, 只能用白名单校验后拼接;
- 参数个数有上限（SQLite 32766）: 批量写要按「列数 × 行数」切批;

## 主子表一起读，什么时候该拆成两次查询？

| 做法         | 查询次数 | 适用                           |
| ------------ | -------- | ------------------------------ |
| 嵌套聚合     | 1        | 主表行数少、子表窄             |
| 两次查询拼接 | 2        | 主表要分页、子表宽或行数不可控 |

- 一次查回嵌套结构省往返, 但结果集体积是「主表行 × 子表行」, 容易把响应撑大;
- 主表分页时, 嵌套聚合会对整表算一次, 再用两次查询更可控;
- 任一种都要保证关联列有索引, 否则退化成 N 次全表扫描;

## 查询结果「查不到」有哪些非数据原因？

- 读写不在同一个连接或事务: 写入未提交, 读方看不到;
- 显式事务忘了提交: 连接释放时回滚, 症状是「写成功了但查不到」;
- 隔离级别与快照: 读事务开始得早, 看不到之后提交的行;
- 读走了从库、写走了主库, 复制延迟;
- 连错了库或 schema: 表名对但库不对;
