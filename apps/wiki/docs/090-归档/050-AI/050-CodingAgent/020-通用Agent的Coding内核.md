# 通用 Agent 的 Coding 内核

## 通用 Agent 为什么以 Coding 而不是 Deep Research、Computer Use 为核心？

- 形态: Manus、OpenClaw 这类产品把 Deep Research、Computer Use、Coding 三大能力融在一个系统中;
- 关键判断: 通用 Agent 的核心是 Coding Agent 加文件系统;
- 理由一: 几乎一切高效内容生成最终都落到代码上——PPT、Word 本质是 OOXML，PDF 报告可由 Markdown/HTML/LaTeX 生成，数据分析与可视化由 Python 脚本完成;
- 理由二: Deep Research 的搜索与信息综合可由代码驱动的 Web 请求与解析实现;
- 理由三: Computer Use 通用性更强，但成本、延迟、稳定性都不如直接用代码或 API 完成同一操作;
- 理由四: GUI 中成功的浏览器操作序列可固化为可复用代码;
- 结论: 代码生成是效率最高、成本最低、可复用性最强的能力基座;

## 一次通用 Agent 任务中信息如何流转？

```text
用户：分析上季度销售数据并生成总结报告
1 读记忆：MEMORY.md 记录偏好 PDF 报告、数据源为 Google Sheets
2 调工具：搜索 Sheets API 用法，用代码执行下载数据
3 写代码：Python 生成分析脚本（pandas 聚合 + matplotlib 可视化）
4 生成产物：report.pdf 与 charts/ 目录
5 更新记忆：MEMORY.md 记下数据源与 ID，下次不再询问
```

- 枢纽: 文件系统贯穿全程——记忆从文件读取、产物写入文件、经验保存为文件;

## 文件系统为什么是 Agent 的中枢？

- 定位: 文件系统不只是数据存储，而是 Agent 记忆、知识和能力的中枢;
- 记忆结构: 长期事实与用户偏好存 `MEMORY.md`，按日期归档的 Markdown 日志承载过程记录;
- 反直觉选择: 用 Markdown 而非向量数据库;
- 理由一: 用户可直接打开文件阅读和修改记忆，记错一行删掉即可;
- 理由二: Markdown 天然保留时间顺序，避免语义检索中的时间混淆;
- 理由三: 可通过 Git 版本控制与回滚;

## Agent 修改自身外部产物的前提与边界是什么？

- 前提: Agent 拥有写文件能力，因此具备修改自身外部产物的技术条件;
- 行为: 首次执行任务发现关键信息（如银行验证身份需要开户行地址）时，可先写入记录;
- 边界: 记录何时足以成为可靠知识、指令或程序，仍需结合更多轨迹与结果验证;
- 关联: 这属于持续进化问题，见持续进化章节;

## 什么样的 Agent 才以 Coding 为核心架构？

| Agent 类型               | 任务空间                 | 核心架构                         | Coding 的位置                  |
| ------------------------ | ------------------------ | -------------------------------- | ------------------------------ |
| 开放任务型通用 Agent     | 边界不确定、产物形态多样 | Coding Agent + 文件系统          | 元能力，动态扩展能力边界       |
| 垂直领域 Agent（如客服） | 相对封闭                 | 固定业务流程、领域工具、对话策略 | 工具箱里的一件工具，非架构中枢 |

- 结论: “Coding 是核心”只适用于以开放任务为目标的通用 Agent;
- 保留: 即使在垂直 Agent 中，精确计算、数据处理、规则校验仍离不开 coding;
