## 决策与证据

- **音频走自写的 Range 处理器**（`server/media.ts`）：`/media/*` 不用 `serveStatic`，因为它对开放式 `Range: bytes=N-` 会一次回整段剩余字节；自写处理器把每次响应封顶 512 KB（`CHUNK_BYTES`），并给出正确的 `audio/flac` 类型与 `ETag`/`Last-Modified`，返回 206 + `Content-Range`，越界回 416。
- **预加载交给浏览器**（2026-11-01 用户定调）：不再自建预取。实测 Chrome 在播放 3 秒内就按 512 KB 分片连取 7 片（约 3.5 MB、≈25 秒音频），自带 read-ahead 已覆盖需求；自建预取只会与它重复下载。
- **索引由后端持有**（2026-11-01 用户指定）：`tracks.json` 放 `server/data/tracks.json`（`TRACKS_FILE` 可覆盖），进程启动时读入内存并计算 ETag；`GET /api/tracks` 返回，命中 `If-None-Match` 时 304。前端不进构建产物、换曲库不必重新 build 前端。
- **后端职责**：托管 `dist/client`、托管 `/media/*`、`GET /api/tracks`（含 ETag/304）、`/api/health`；历史与洗牌不经过网络。
- **首屏自动播放**：`<audio autoPlay>` 在现代浏览器可能被拦截，实现上先尝试 `play()`，失败则显示「点击开始」按钮，不做静默失败。
- **无数据库**（用户 2026-11-01 定稿）：历史在 `localStorage`，服务端无状态，重启服务不影响历史。
- **洗牌袋**：`client/app/store/bag.ts` 的纯函数 `shuffleBag(ids, lastId)`——Fisher–Yates 洗副本；`next()` 弹栈，空了重洗，重洗后首项若等于刚播曲目则与次项交换，避免「刚听完又听到」。
- **历史**：`pushHistory(list, id, now)` 纯函数——先剔除同 id 旧记录再 `unshift`，`slice(0, 13)`；`zustand/persist` 的 `partialize` 只持久化 `history`，`bag`/`current` 为会话态。
- **写入时机**：`<audio>` 的 `playing` 事件触发，避免「点了下一首但没播出来」污染历史。
