# 播放历史与洗牌袋

## 交付

服务端记录播放历史（SQLite，保留最近 13 条）与可解释的随机策略：`POST /api/plays` 写一条、`GET /api/plays?limit=13` 读回、`GET /api/queue/next` 按洗牌袋给出下一首。关联 [US-004](../story.md#us-004-回看最近听过的十三首)。

## 范围

- 做：历史表与接口、洗牌袋状态、重播去抖（同曲只留最新一条）、13 条修剪。
- 不做：跨设备同步、收藏、统计报表、推荐。

## 直接依赖

- **03**：需要 `tracks` 表与稳定的曲目 id，才能写历史与出队列。

## 验收

- [ ] 播放一首后 `GET /api/plays?limit=13` 首条为该曲目，且带 `played_at`
- [ ] 连续播放 20 首后，历史恰好 13 条，最旧被裁掉
- [ ] 同一曲目连续播放 3 次，历史只增加 1 条（更新时间戳）
- [ ] `GET /api/queue/next` 连取 20 次（曲目数 145），无重复；取空后重新洗牌
- [ ] 服务与浏览器重启后历史仍可读

## 上下文

- [spec](../spec.md)、[02](02-站点形态与技术选型.md)、[03](03-曲目索引生成.md)
- 表结构草案：`play_history(id integer pk, track_id text not null, played_at text not null)`；索引 `idx_play_history_played_at`

## 决策与证据

- **历史放服务端而非 localStorage**：用户已定「数据库使用 sqlite」，且重启浏览器不该丢历史；服务端写入一次即完成。
- **13 条用修剪而非视图截断**：写入后 `DELETE FROM play_history WHERE id NOT IN (SELECT id FROM play_history ORDER BY played_at DESC, id DESC LIMIT 13)`，保证表不会无限增长。
- **重播去抖**：同 `track_id` 已有记录时更新 `played_at` 而不插入，避免单曲循环把 13 条全占满。
- **洗牌袋状态放内存**：本机单用户，进程重启重洗即可，不必持久化；`Math.random()` 直抽会频繁重复，已被排除。
