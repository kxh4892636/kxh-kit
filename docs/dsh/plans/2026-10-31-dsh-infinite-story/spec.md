# dsh-infinite-story — spec

> 状态：设计已收敛（2026-10-31）
> 归属域：`docs/dsh`
> 原型：`.tmp/mama-story`（手工 + PowerShell 的 v0，将作为迁移样本）

## 一句话

把「无限故事」从一套靠自觉的 Markdown 约定，变成**插件托管的可运行状态机**：规则进上下文，状态由工具落盘，漂移由 guard 拦截。

## 背景：v0 暴露了什么

| 问题       | 现象                                | 根因                                 |
| ---------- | ----------------------------------- | ------------------------------------ |
| 正文不落盘 | 08–17 章只存在于对话里，靠事后补账  | 「写正文」与「写文件」是两个动作     |
| 节点被漏   | 家长会差点整场丢掉                  | 没有强制收账点                       |
| 规则会忘   | R1–R24 十余条，写起来只记得住三五条 | 规则是文档，不在上下文里，也不是约束 |
| 校验靠手   | check 只验解析，audit 后补          | 没有写入时闸门                       |
| 规模到顶   | 分片预案写了，代码没写              | 没有工程化                           |

结论：**规则不进上下文就会漂；状态不经过工具就会漏。**

## 目标 / 非目标

**目标**

1. 同一套结构承载任意体裁、任意长度的故事。
2. 规则分「通用」与「故事特有」，**两者都必须进入 agent 上下文**。
3. 写一次正文，结构必然自洽；不自洽拒写。
4. 规模随故事生长而扩展，靠**语义分片 + 按需引用**，不靠单文件堆。
5. 工具面交付，不做 CLI / HTTP（ADR-0002）。

**非目标**：不生成正文、不做 GUI、不做协作/云同步、不训练模型。

## 一、规则进上下文（核心，不是附属）

**这是插件存在的第一理由。** 规则不写进上下文，模型必然漂。

### 规则分两类

| 类               | 内容                                                                   | 存哪                                | 何时进上下文                                                         |
| ---------------- | ---------------------------------------------------------------------- | ----------------------------------- | -------------------------------------------------------------------- |
| **通用规则**     | 推进权、篇幅、节奏、衔接、视角、禁忌边界、存档义务、节点/伏笔/收账机制 | 插件内建（随插件升级，用户不用管）  | 每次 `story_open` / 每次 `story_brief`                               |
| **故事特有规则** | 本故事的体裁约定、禁忌线、人设锚点、结局约束、节奏开关、量表定义       | `stories/<id>/RULES.md`（用户可写） | 每次 `story_open` / 每次 `story_brief` / `story_append` 的返回值尾部 |

### Brief：上下文的唯一入口

`story_open` 返回一份 **Brief**，结构固定：

```
【故事】名字 · 体裁 · 第 N 章
【立场】当前时间 / 地点 / 在场焦点人物 / 她的状态
【上一拍】一句话
【近期节点】未来 48 小时内会开窗/会过期的
【悬置】openThreads
【通用规则】← 十条以内，压缩成可执行句
【本故事规则】← RULES.md 的要点
【禁忌】← taboos + ending.forbidden
【人称与称呼】← persona 锚点
```

**Brief 不是摘要，是操作手册。** 目标：模型读完这一段就知道该怎么写，不用回去翻文件。

### 规则如何常驻

- `story_append` 成功时，返回值尾部附一段**精简规则回声**（3–5 条当次最相关的），防止长对话里规则被稀释。
- 规则变更时用户直接改 `RULES.md`，下次 brief 自动生效——**始终使用最新原则**（用户指定，不做版本化）。

## 一·B、故事模式开关

### 为什么要有开关

这是个**重插件**：装系统提示、起文件监听、注册四个工具。绝大多数会话不写故事，不该承担这些成本，也不该被"故事规则"污染。

所以做**会话级开关，默认关**。

### 开关状态

- 作用域：**单个会话**。
- 持久化：随会话保存，重开页面能恢复。
- 默认：关。

### 会话固定绑定一个故事

**一个会话 ↔ 一个故事，一对一，绑定后不再切换。**

```
sessionA  →  妈妈的夏天
sessionB  →  （未绑定，开关关着）
sessionC  →  另一个故事
```

规则：

1. **打开开关时绑定**。没绑定时，开关打开会先问：新建 / 选一个已有的 / 迁移旧目录。选定即写死。
2. **绑定后不换**。想换故事，只能**新建会话**。理由：故事的上下文（Brief、文件监听、pending）全都挂在会话上，换故事等于把整条上下文换掉，技术上可行但语义混乱，不如开新会话干净。
3. **关掉再开，还是同一个故事**。开关只管启停，不管指向。
4. **解绑**只在「故事被删除」时发生；解绑后开关自动关闭。删除手动操作，不自动触发。

### 同一故事被多个会话打开

会话锁：`.story/<id>/LOCK`（内容记 sessionId）。

- 第一个打开的会话 = **可写**。
- 第二个打开同一故事 → **只读**，Brief 顶部标明「另一会话正在写，本会话只读」。
- `story_write` 在只读会话里调用 → 拒绝。
- 第一个会话关闭开关或退出 → 释放锁，第二个会话下次 `story_open` 时升级为可写。

### 关闭时

| 项           | 行为                                                       |
| ------------ | ---------------------------------------------------------- |
| 系统提示段   | **不注入**（会话的 token 前缀保持干净）                    |
| 四个工具     | 仍可见，但调用即返回「故事模式未开启，请在会话页打开开关」 |
| 文件监听     | 不启动（不占 inotify / 不轮询）                            |
| Brief / 校验 | 一律不跑                                                   |

工具"可见但拒绝"而不是"不注册"，理由是：模型看到工具存在却调不动，会明确知道有这个东西并提示用户开；而工具凭空消失，模型会以为能力不存在，转而自己手搓一套。

### 打开时

1. 注入系统提示段（见下节），从下一次请求生效。
2. 启动该故事目录的文件监听。
3. 第一次 `story_open` 返回绑定故事的 Brief。
4. 关闭 → 撤销系统提示段、停监听、清 pending、释放锁。**不删任何文件。**

### 界面

会话页面顶部（或输入区上方）一个 toggle：

```
[ 故事模式 ]  ●——○
```

- 关闭态：灰。
- 开启态：高亮，旁边显示 `妈妈的夏天 · 第 17 章`。
- 未绑定故事时点亮开关 → 弹出选择（新建 / 已有 / 迁移）。
- 点击关闭前若还有未清的 pending，提示：「有 3 条待修，仍然关闭？」

## 一·C、系统提示注入（铁律层）

### 分层

规则的稳定性不一样，放的位置也不该一样。

| 层         | 位置                                               | 内容                               | 变动频率     | 是否受压缩影响   |
| ---------- | -------------------------------------------------- | ---------------------------------- | ------------ | ---------------- |
| **铁律层** | 会话系统提示段（`agent.ctx.systemPrompt.section`） | 十条以内的硬规则                   | 仅随插件升级 | **不受影响**     |
| **运作层** | `story_open` 返回的 Brief                          | 当前状态、节点、悬置、本故事 RULES | 每章变       | 会，但每次都重发 |
| **软提示** | `story_write` 返回值                               | 伏笔提示、下一拍                   | 每次         | 一次性           |

**铁律层放系统提示，是为了解决你提的那个问题：上下文被压缩时，规则不能失真。**

系统提示段是会话作用域的前缀，压缩不会动它（ADR-0004：段内容稳定时保持 KV 缓存前缀稳定）。所以只要把最要紧的规则塞进去，压多少次都在。

### 铁律层写什么（目标 ≤ 300 字）

只放"忘了就会毁掉整个故事"的规则，不放细节：

```
【故事模式 · 铁律】
1. 正文写成后必须调用 story_write 落盘；只留在对话里的内容视为不存在。
2. 改动 state/clock/beats 后必须调用 story_check；pending 未清空前不得写正文。
3. 时间只进不退。节点被越过即作废，不补写、不复活。
4. 秘密只在 knows 里的人之间流动；旁人不得有任何"意味深长"的反应。
5. 推进权归你，但用户指定情节时用户优先。
6. 该慢则慢（亲密、对峙、关键对话），该跳则跳（通勤、上课、等待）。
7. 一条正文一次落盘；不许把多章攒起来再写。
8. 关闭故事模式即停用以上全部。
```

八条，短句，正向陈述。**每条都是"忘了就会出事"的，没有一条是风格建议。**

风格类的东西（篇幅、人称、露骨度、称呼）放 Brief 与 `RULES.md`——它们需要随场景变，塞进系统提示反而僵。

### 为什么铁律层不能太长

它在**每个请求**里都要带一遍。300 字是上限，超了就该拆：能进 `RULES.md` 的都进，只留跨故事通用的。

### 注入时机

- 开关打开时注册，关闭时撤销。
- 内容只随插件版本变，**不随故事变**——这样多会话、多故事共享同一段前缀，缓存命中率最高。
- 故事特有的禁忌（taboos）不放这里，放 Brief：它每条故事都不一样，一放就破坏前缀稳定性。

### 缓存稳定性（硬约束）

系统提示段是 KV 缓存的前缀。**前缀里动一个字，后面全部重算。** 所以铁律层必须逐字节固定。

| #   | 约束                                                                               | 反例（禁止）                  |
| --- | ---------------------------------------------------------------------------------- | ----------------------------- |
| C1  | **编译期常量**：`src/prompt/iron-rules.md` 打包进 dist，运行时读一次，不做任何拼接 | 读 `RULES.md` 拼进提示        |
| C2  | **零变量**：不含故事名、章节号、时间、会话 ID、用户名、pending 数量                | `【故事】妈妈的夏天 第 17 章` |
| C3  | **整段注册、整段撤销**：不允许增量更新或分段替换                                   | 每章重新注册一次 section      |
| C4  | **`name` 与 `order` 固定**                                                         | 按故事动态改 order            |
| C5  | **只随插件版本变**：升级插件导致内容变＝缓存失效一次，可接受（发布频率低）         | 为了"动态"而每次请求重算提示  |
| C6  | **故事相关的一切禁止进系统提示**，包括"只注入一次"                                 | 开局注入当前进度快照          |

**C2 是重点**：只要允许一个变量进去，前缀就变成"每会话一份、每章一份"，缓存收益归零，而收益正是这套设计存在的理由。

**C6 的反例要特别小心**：很多方案会"开局把当前状态注入系统提示，图省事"。这看起来只写一次，但不同故事的前缀完全不同，多故事场景下缓存彻底失效；同一故事重开开关时前缀又要重算。所以状态一律走 Brief。

### 哪些内容必须进 Brief 而不能进系统提示

| 内容                      | 为什么       |
| ------------------------- | ------------ |
| 当前章节 / 时间 / 地点    | 每次都变     |
| 在场人物与状态            | 每次都变     |
| 未来 48h 节点             | 每次都变     |
| 本故事 RULES 要点         | 每条故事不同 |
| taboos / persona / ending | 每条故事不同 |
| pending 问题              | 每次检查后变 |
| 上一拍摘要                | 每次都变     |

反过来，铁律层里只留**跨故事、跨时间都不变的八条**。

### 指针而非内容：`.story/ACTIVE.md`

故事特有的东西不能进系统提示，但**"去哪儿读"是固定的**。

所以系统提示里只写一个**指针**，形同 skill 的 description——只说有这么个东西、在哪儿、什么时候读，不说内容。

固定路径：`.story/ACTIVE.md`

```markdown
# 当前故事

- 入口：./mama-story/STORY.md
- 规则：./mama-story/RULES.md
- 分片：./mama-story/shards/
```

- 路径**永远不变**，所以系统提示里的那句"读 `.story/ACTIVE.md`"也永远不变，缓存稳。
- 内容随会话绑定的故事变，由插件在开关打开时写入。
- 模型读它 → 拿到真实路径 → 再读 `STORY.md` / `RULES.md` → 需要谁再读哪个分片。

**这三跳就是渐进披露**：系统提示（1 行指针）→ ACTIVE（3 行路径）→ STORY（索引）→ 分片（内容）。每跳只带下一跳需要的最小信息。

### 指针与 Brief 的分工

|        | `.story/ACTIVE.md`          | `story_open` 的 Brief                         |
| ------ | --------------------------- | --------------------------------------------- |
| 谁生成 | 插件在开关打开时写一次      | 插件每次算                                    |
| 内容   | 路径（静态）                | 状态（动态：章节、时间、节点、悬置、pending） |
| 谁读   | 模型自己 `read`，零调用成本 | 模型调工具拿，插件已经算好                    |
| 用途   | 找到档案                    | 知道现在该写什么                              |

两者不重复：**ACTIVE 解决"去哪儿找"，Brief 解决"现在到哪了"。**

### 铁律层最终文本

```
【故事模式 · 铁律】
本会话绑定了一个故事。开工前先读 `.story/ACTIVE.md`，按它指的路读入口与规则。
1. 正文写成后必须调用 story_write 落盘；只留在对话里的内容视为不存在。
2. 改动 state/clock/beats 后必须调用 story_check；pending 未清空前不得写正文。
3. 时间只进不退。节点被越过即作废，不补写、不复活。
4. 秘密只在 knows 里的人之间流动；旁人不得有任何"意味深长"的反应。
5. 推进权归你，但用户指定情节时用户优先。
6. 该慢则慢（亲密、对峙、关键对话），该跳则跳（通勤、上课、等待）。
7. 一条正文一次落盘；不许把多章攒起来再写。
8. 关闭故事模式即停用以上全部。
```

**依然是零变量**：没有故事名、没有章节号、没有时间。唯一的外部引用是一个固定路径。

## 二、独有机制：五类声明

插件不理解语义，只机械执行五类。语义留给人。

### 1. meters — 量表

**是什么**：一条可增可减的数值刻度，0–10 或 0–100，记录"看不见但会变的东西"。

**为什么有用**：故事里真正推动情节的不是事件，是**积累到临界点的状态**。老师的怀疑、她的羞耻、钱的窟窿、身体的状况——这些平时没有台词，却在某一天忽然爆发。量表把这种"积累"变成可追的数。

**例子**：

```jsonc
{
  "id": "suspicion-teacher",
  "label": "班主任的怀疑",
  "range": [0, 10],
  "start": 2,
  "up": ["请假对不上", "成绩下滑", "家长会说漏"],
  "down": ["主动交出满意的解释"],
}
```

- 2 → 老师只是多看了一眼
- 5 → 开始打电话
- 8 → 家访
- 10 → 摊牌

**不设它会怎样**：写到某天老师忽然发难，读者觉得突兀；或者反过来，铺垫了一堆却永远不发作。

---

### 2. taboos — 禁用项

**是什么**：硬红线。不是"建议避免"，是**一旦出现就算错**。

**为什么有用**：故事的"味道"是靠**不做某些事**维持的。一旦破例一次，整条线就塌了。

**例子**（本故事）：

- `第三方识破关系` —— 破了，禁忌感立刻消失，变成普通的出轨故事
- `道德说教` —— 破了，变成说教文
- `元叙事出戏` —— 破了，读者被踢出来

**不设它会怎样**：模型会不自觉地"合理化"——让同学猜到了、让老师说了句意味深长的话、让主角自我反省。每一次都合理，加起来就毁了。

---

### 3. persona — 人设锚点

**是什么**：称呼、自称、口癖、说话长短的硬约束。

**为什么有用**：**语气漂移是最难察觉的漂移。** 写二十章之后，她会不知不觉从"嘴硬心软"变成"温柔体贴"，从"妈妈"变成"宝贝"。读者说不清哪里不对，但会觉得"不像她了"。

**例子**：

```jsonc
{
  "白洁": {
    "address": ["妈妈", "宝宝"], // 必须出现
    "mustNot": ["对白里出现全名"], // 绝不能出现
    "voice": ["嘴上拒绝，身体先动", "话讲一半就停"], // 语气锚点
    "samples": ["哎哟，眼睛往哪儿瞅呢", "别老这么叫，叫得妈妈心里发慌"],
  },
}
```

**不设它会怎样**：二十章后她变成了另一个人，而且没人发现是第几章变的。

---

### 4. ending — 结局约束

**是什么**：故事最终必须落在哪，以及什么绝对不能发生。

**为什么有用**：长故事最大的漂移是**方向漂移**——写偏了，最后收不回来。提前钉死终点，模型才不会为了眼前的戏剧性把路走死。

**例子**：

```jsonc
{
  "type": "happy",
  "must": ["两人最终在一起，身体健康"],
  "forbidden": ["一方病重身亡", "彻底决裂", "被迫永别"],
}
```

**不设它会怎样**：写到一半为了让读者揪心，把她的病写重了，收不回来了。

---

### 5. cadence — 节奏开关

**是什么**：什么场景该慢写，什么该跳过。

**为什么有用**：这次真实发生的问题——该细的地方一笔带过，该跳的地方啰嗦半天。节奏是"读者的体感"，必须有硬规则。

**例子**：

```jsonc
{ "slowOn": ["亲密", "对峙", "她说起以前"], "skipOn": ["通勤", "上课", "写作业", "等结果"] }
```

**不设它会怎样**：一个上午写三千字，一场关键对峙两句话带过。

---

### 五类之外

暂不需要第六类。若将来出现，优先判断能否归入这五类；实在不行再加，加之前先问"这能不能用现有五类表达"。

## 三、防漂移（Drift Guard）

| 档          | 查什么                                                                               | 何时                  | 成本                         |
| ----------- | ------------------------------------------------------------------------------------ | --------------------- | ---------------------------- |
| **L0 结构** | schema、章节连续、cursor 有效、links/relations/threads 引用存在、配额、时间不倒流    | 每次 append，失败拒写 | 本地                         |
| **L1 一致** | 章节标注 == 时钟、出场人物 ∈ focus、`knows` 未被越权、md↔json 双向对齐、量表在范围内 | append + 收账         | 本地                         |
| **L2 语义** | taboos 是否出现、persona 语气是否漂、ending 是否偏、外人是否越权知情                 | 章末 / 手动 `--deep`  | **独立模型裁判**（用户指定） |

### L2 的规矩

- **用独立模型**，不用写正文的那个（避免自利倾向）。
- 判词必须结构化：`{pass, violations:[{rule, evidence, location}], suggestion}`
- `evidence` 必须是正文原文片段，裁判不得臆造。
- 只抽样，不逐段。
- 判过一次就记 `drift-log.jsonl`，同类问题下次 brief 里点出来。

## 四、存储：按 skill 的组织方式写（to-skill 约束）

故事存档和 skill 是同一种东西：**给 agent 读的文本集合**。所以直接借用 skill 的四条组织约束。

| skill 约束                 | 在故事里的落法                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **Progressive disclosure** | `STORY.md` 只放索引与最小上下文；人物、地点、线索各成分片，模型按需 `read`                                                      |
| **Co-location**            | 同语义的内容放在一起：一个人物的全部信息在 `chars-*.md` 的一节里，不散落                                                        |
| **Single source of truth** | 每条事实只有一个权威位置：规则只在 `RULES.md`（故事特有）+ 插件内建（通用）；时间只在 `clock.json`；伏笔只在 `foreshadows.json` |
| **Pruning**                | 分片里不写"说明性废话"：不解释机制、不重复规则、不留已废弃的设定                                                                |

### 目录

├─ WORLD.md            # 世界索引：链接到各分片

- `她怎么说话`（而不是"人设一致性规范"）
- `谁知道了什么`（而不是"信息扩散矩阵"）

## 六、工具面：只留四个

### 原则

**工具只做两件事：插件必须强制的，和模型做不到的。**

- 模型能做到的（读一个 md、改一个字段、算个加法）→ 让它自己做，插件不包。
- 必须强制的（写正文要落盘、写坏了要拦）→ 工具。
- **新增机制不新增工具。** 机制扩张只允许扩张两处：schema 字段 + 校验规则。工具数量恒定。

这条是硬约束。一个机制一个工具，迟早有三十个工具、模型记不住、也选不对。

### 四个工具

| 工具             | 干什么                                                           | 为什么必须是工具                                 |
| ---------------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| `story_open`     | 打开故事，返回 **Brief**（规则 + 状态 + 节点 + 悬置 + 下一步）   | 规则必须进上下文，模型自己读不全也记不住         |
| `story_write`    | 写正文 → 落盘 → 回写 cursor → 跑 L0/L1 → 不过就拒写              | 「写正文」和「记状态」必须合成一个不可跳过的动作 |
| `story_check`    | 全量校验（`deep:true` 时走 L2 独立模型），返回问题清单与修复建议 | 校验逻辑是确定性的，不能交给模型自评             |
| `story_scaffold` | 新建故事，生成骨架与默认 RULES.md                                | 骨架路径与 schema 一次性写对，比让模型照模板搭稳 |

就这四个。不做 `advance` / `tick` / `agenda` / `seed` / `affinity` / `reveal` / `meter`。

### 各机制怎么在只有四个工具的情况下运转

| 机制           | 谁写 | 写到哪                                                 | `story_check` 查什么                                                      |
| -------------- | ---- | ------------------------------------------------------ | ------------------------------------------------------------------------- |
| 时钟推进       | 模型 | `clock.json` 的 `now` + `advances[]` 追加              | `now` 单调不减；每次推进有对应 `advances` 记录；章节标注时间与 `now` 相容 |
| 节点开窗/过期  | 模型 | `beats.json` 的 `status`                               | `status` 必须与 `now` 按时间窗推导出的结果一致，不一致即报错              |
| 伏笔埋/提/触发 | 模型 | `foreshadows.json`                                     | `status ∈ {未触发,已触发,失效}`；未触发 ≤ 上限；`id` 唯一                 |
| 好感度         | 模型 | `state.json` 的 `affinity` + `log/affinity.jsonl` 追加 | 每条变动必须有对应流水；`level` 与 `value` 区间匹配                       |
| 量表           | 模型 | `state.json` 的 `meters`                               | 值在 `range` 内；变动有流水                                               |
| 人设揭示       | 模型 | `shards/chars-*.md` + `state.json`                     | `hidden` 与 `revealed` 不重复；揭示内容出现在人设册里                     |
| 每日收账       | 模型 | 自己核对，把结论写进 `state.json.openThreads`          | `openThreads` 非空时，`STORY.md` 的「悬置」段必须同步                     |
| 分片引用       | 模型 | 自己 `read` `shards/*.md`                              | `WORLD.md` 的链接必须都指向存在的文件                                     |

**这就是"让模型自己去做"的具体形态**：它改 JSON、写 MD、追加 JSONL，`story_check` 事后验算。插件不替它做，只保证它做对了。

### 校验什么时候跑（触发模型）

**这是整套设计里最容易翻车的地方。** 模型直接改 JSON 时，没有任何工具被调用——如果不解决，校验就永远只在"模型想起来的时候"跑。

所以设三层触发，前一层兜不住就用后一层接住。

#### 触发层 1：写入口强制（同步，硬）

`story_write` 被调用时，**先跑全量 L0/L1，再决定写不写**。

```ts
story_write:
  1. loadState → guard.structural + guard.consistency
  2. 有 error → 拒绝写入，返回问题清单（模型必须先修）
  3. 无 error → 写文件、回写 cursor、追加流水
  4. 写后再跑一次（因为 cursor 变了）
  5. 通过 → 返回正文结果 + 下一拍提示 +（按概率）伏笔提示
```

写正文是最高频的动作，把闸门装在最高频的路径上，覆盖率最高。

#### 触发层 2：文件变更监听（异步，兜底）

插件用 `chokidar` 监听 `.story/**` 下的 `*.json` 与 `shards/*.md`，并在 `ctx.on("fs/observed")` 上挂钩（`dsh-nested-skill` 已证明这条路可行）。

文件被改 → 立即跑一致性校验（纯计算，几十毫秒）→ 不通过则把问题写进 `pending-issues.json`。

_\*pending 不清空，任何 story_* 工具都不放行。_* 具体：

- `story_open` 返回 Brief 时，pending 非空则置顶显示：「先修这些」。
- `story_write` 入口发现 pending 非空 → 直接拒绝。
- `story_check` 是唯一允许带着 pending 调用的工具（它就是用来修的）。

这样即使模型绕过工具直接改文件，下一次开口就被拦住。

#### 触发层 3：Brief 回显（软，防遗忘）

每次 Brief 末尾固定一段：

```
【上次检查】第 N 章，通过 / 未通过（3 条）
【过期节点】T05 已在 次日 17:00 作废，未补写
```

不是新机制，只是把 pending 与 drift-log 的摘要塞进上下文。

#### 各机制的具体挂点

| 机制               | 挂在哪                                                                         | 谁触发                     |
| ------------------ | ------------------------------------------------------------------------------ | -------------------------- |
| 时间推进校验       | 层 2 监听 `clock.json` → 用 `now` 推导每个节点的应有状态，与 `beats.json` 比对 | 文件变更，立即             |
| 节点过期           | 同上（`beats.json` 由模型改，校验器只验）                                      | 文件变更，立即             |
| 伏笔提示           | **`story_write` 成功返回值**（每次写完按熵给一次，约 1/3）                     | 写正文这个动作本身         |
| 伏笔优先级         | Brief 里列出「未触发的 12 条」按与当前场景的相关度排序                         | 每次 open                  |
| 章节时间自洽       | 层 1 + 层 2                                                                    | 写正文 / 改 clock          |
| 人设语气漂移（L2） | 章末抽样，一次性开销                                                           | `story_write` 检测到新章时 |

#### 为什么伏笔提示不需要独立触发点

它是**软机制**，忘了不致命。而它天然寄生在 `story_write` 上——写正文是必然发生的动作，把提示挂在它的返回值里，就等于零成本获得了触发点。

硬机制（时间、节点、引用完整性）不能寄生，所以需要层 2 的监听兜底。

#### 状态机

```
        ┌──── pending 为空 ────┐
        │                      │
  [模型改文件] ──▶ [watcher] ──▶ [有违规] ──▶ pending-issues.json
        │                                      │
        └──▶ [story_write] ──▶ 入口再查一遍 ────┘
                                   │
                           pending 非空 → 拒绝
```

**结论**：触发不靠"模型记得住"，靠三点——高频路径设闸门、旁路动作装监听、软提示寄生在必然动作上。

### 为什么校验比工具更重要

模型改文件会改错——漏字段、写错状态、时间倒退。这没关系，**check 会抓出来，模型再改一次**。

这比"每个机制一个专用工具"更耐扩张：

- 加一个新机制 → 加一个 schema 字段 + 一条校验规则，工具数不变。
- 校验规则可以版本化、可以单测、可以离线跑。
- 模型有自由度，插件有底线。

### Brief 里的「下一步」

`story_open` 的返回值末尾固定一段：

```
【下一步】写完正文调用 story_write；改过 state/clock/beats 后调用 story_check。
【别做】不要只把正文留在对话里；不要通过改 check 规则来绕过 check。
```

规则里最容易被忘的两条，放在每次 brief 的最后。
