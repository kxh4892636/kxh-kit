### 新阻断点：0.2.x 插件兼容性校验

`dsh plugin` 的 `add` 走 `runPluginCommand`：pnpm 安装后读装好的 manifest 做兼容性评估（`dsh-app-boot/lib/index.js`）：

- `unmetRequirements`（279–299 行）：有 `engines.dsh` 时只按它判定，否则逐个校验 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*` 的 peer 范围是否 `satisfies(runtimeVersion, range)`；
- `evaluatePluginCompatibility`（311–326 行）返回 `requirements`，CLI 打印 `dsh: to accept the risk, run: dsh plugin --profile web allow-version …`；
- 运行版本来自 `getDshRuntimeVersion()`，即本机 `dsh` 安装锚点的 `0.2.1-rc.2`。

本包 peer `^0.1.5-rc.1` 按 semver 预发布可比性不满足 `0.2.1-rc.2`（只比同 `major.minor.patch` 元组），因此**当前状态下安装必然被拒**；这是「必须更新声明」的硬证据，而不是风格问题。

### 上游行为变化（影响语义而非接口）

- 来源 rank：`dsh-skill-filesystem` 现为 project-dsh 100 / project-agents 200 / custom 300 / user-dsh 400 / user-agents 500 / bundled 600（`BUNDLED_SKILL_RANK`）；`0.1.5-rc.1` 没有 bundled 根也没有 `.dsh/skills` 项目根。本包统一 250 → 只在 project-agents 上成立「声明优先」。
- home 解析：`0.1.5-rc.1` 用 `resolve(config.agentsHome ?? $DSH_AGENTS_HOME ?? ~/.agents)`；`0.2.1-rc.2` 改用 `resolveAgentsHome(config.agentsHome)`（`@deepseek-ai/dsh-home-paths`），会展开 `~` 并把空白 env 视为未设置。
- 不完整发现：watcher 启动失败时返回 `{ candidates, complete: false }`（`lib/index.js` 的 `list`），而不是抛出或静默。
- `path`：`readSkillText` 现在返回 `{ path: realpath/fs.processPath, content }`，候选与定义的 `path` 用该值。
- 发现深度未变：`discoverRoot` 仍只读 `<root>` 的直接子项（目录 → `<dir>/SKILL.md`，文件 → `*.md`），本插件仍是必要的补充。

### 安装链路事实

- `dsh plugin --profile web add <spec>` → `runPluginCommand`：支持 `file:`/绝对路径目录/`.tgz`/git/npm；相对路径被拒。
- 安装后 `reconcile()` 把声明了 `dsh.bundle` 的新依赖追加进 `package.json` 的 `dsh.profile.bundles`；`cordis.patch.yml` 作为 bundle 层在组合时读入。
- 组合顺序：各 bundle 层 → profile 用户层（`~/.dsh/profiles/web/cordis.patch.yml`）→ home 用户层 → `--patch`。只有 profile 用户层被热重载；bundle 列表变化需要重启（0.2.1 的 `dsh` 树中已无 `patchReload` 字样）。

### 单测基线红项

`vp test src` 33/37：四项失败（`finds nested skills…`、`tags candidates…`、`loads full definitions through get()`、`honors extraRoots as custom source`）。根因：fixture 用 `C:/project`，`provider.roots()` 里 `resolve(cwd)` 在 POSIX 上把相对形态拼到 cwd，`memoryFs` 的键永远不匹配 → 候选为空。与上游版本无关，是「Windows 上写成、Linux 上首跑」的平台假设。

## 拷问记录

### 第 1 轮

#### Q1 — 声明对齐用哪种机制

- 问题：peer 抬到 `^0.2.1-rc.2`、还是加 `engines.dsh: ^0.2.1-rc.2`、还是保留旧 peer 走 `allow-version` 豁免？
- 前置问题：无。
- 下游边界：决定 package.json 形状与是否需要 profile 豁免记录。
- 推荐答案及理由：抬 peer。`unmetRequirements` 优先读 `engines.dsh`，没有才校验 `@deepseek-ai/dsh*` peer；peer 已覆盖同一语义，二者并存会出现两个真相。豁免会掩盖声明漂移，与 ADR-0003「声明等于已在本机验证的通道版本」冲突。
- 修改意见：（auto 模式，agent 依证据推进；用户可在 dev gate 推翻）
- 处理结论：已确认（本轮）。实施时改为**精确钉版** `0.2.1-rc.2`（不带 caret）：`^0.2.1-rc.2` 会解析到同元组的 `0.2.1-rc.3`，而 `rc.3` 的传递依赖（如 `@deepseek-ai/dsh-util-values@0.2.1-rc.3`）在当前 npm 镜像尚未收录，`pnpm install` 直接失败；且范围混装正是 ADR-0003 已排除的情形。写入 spec「实施决策」。

#### Q2 — rank 模型是否修正

- 问题：保持单一 250，还是按来源派生（201/301/501）？
- 前置问题：无。
- 下游边界：改变 user/custom 根下同名冲突的胜出者，属可观察行为变化，决定版本号是否按 minor 走。
- 推荐答案及理由：按来源派生。CONTEXT 的「声明优先」与 ADR-0001 都承诺一层形态胜出，而 250 只在 project-agents（200）成立；0.2.1 又引入 project-dsh（100）与 bundled（600）两个来源根，flat 250 与来源序自相矛盾。
- 修改意见：（auto 模式）
- 处理结论：已确认（本轮）。ADR-0001 的 rank 表述同步修订，决策本身不变。

#### Q3 — 交付形态

- 问题：`.tgz` tarball、`file:` 目录，还是 `link:` 工作区链接？
- 前置问题：无。
- 下游边界：决定重建 dist 后是否需要手工同步 profile 快照，以及 profile 清单里依赖的形态。
- 推荐答案及理由：tarball。`file:` 在 profile 侧表现为链接投影（`linkedRoots`），`vp pack` 重建后 inode/内容需要重新同步；tarball 与工作区解耦，前序 Plan 已用同一结论交付。
- 修改意见：（auto 模式）
- 处理结论：已确认（本轮）。

#### Q4 — 验证层级与 3080 重启

- 问题：只用 `--dump-config` 证明组合、还是另起独立 dsh 进程证明运行时发现、还是重启 3080 宿主？
- 前置问题：Q3（安装形态决定验证对象）。
- 下游边界：决定验收证据强度与会话中断风险。
- 推荐答案及理由：`--dump-config` + 独立进程（`headless` + `--patch` 挂载本插件）。前两者可复核且不动宿主；重启会中断本会话，且 bundle 层生效时机只影响「何时可见」，不影响正确性判断。重启留给用户。
- 修改意见：（auto 模式）
- 处理结论：已确认（本轮）。注意：独立进程验证的是「插件在 0.2.1-rc.2 上能发现嵌套 skill」，与「web profile 装好后能否发现」是两个证据，都要取。

#### Q5 — 单测 fixture 怎么修

- 问题：把 fixture 改成 POSIX 绝对路径、改成运行时 `mkdtemp` 真实目录、还是给 `memoryFs` 加平台无关的虚拟根？
- 前置问题：无。
- 下游边界：决定测试在 Windows/Linux 双平台的可维护性。
- 推荐答案及理由：用 `resolve("/project")` 派生虚拟根。POSIX 下得到 `/project`，Windows 下得到 `C:\project`；`FILES` 的键与断言都用同一 `join` 派生并归一为 `/`，与 `memoryFs` 的 `toPosix` 一致。`mkdtemp` 会让纯逻辑测试依赖真实 IO，抵消 `memoryFs` 的意义。
- 修改意见：（auto 模式）
- 处理结论：已确认（本轮）。
