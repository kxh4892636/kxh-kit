# Flow 以证据与文档推导当前位置

原运行协议同时维护 phase、cursor、Issue 运行状态与文档状态，并按日期切断存储；调用方还需区分进入、领取、恢复、续租与同步。决定以破坏性 schema 7 收敛为 status、acquire、report，让调用方重复「取得当前位置与执行权 → 执行 skill → 报告证据」。

固定 `.flow/state.json` 只保存 Plan 的 mode、receipts、leases。Plan 的 `/questing → /to-issues` 短证据链决定直接交付或 Issue 图；Issue frontmatter 是执行状态事实源，spec 是派生视图。删除 phase、cursor 与重复 Issue 状态，跨日复用同一记录；旧日文件保留但不读取，不提供迁移或完成后隐式重置。

status 只读，acquire 统一创建、领取、恢复与续租，report 统一完成、暂停与阻塞。模式创建后固定，避免并行交付期间更换确认约定。所有操作返回统一快照与全 Plan 证据链；只有 owned 允许执行 next，status 的 session 只识别已有有效持有人。每个真实目标最多一个有效租约，同一 session 在每个 Plan 内最多持有一个 Issue。Issue 必须满足直接依赖，blocked 恢复须有解除证据；Issue 选择仍由调用方按用户优先级决定。

`/code-delivery` 拥有准入至提交的完整交付，成功提交后报告 completed，证据引用提交和交付验证。删除 started 和独立 commit action，避免暴露 skill 内部时点。脚本保证顺序与证据登记，不验证声明真实性；文档完成状态也不生成虚构 receipt。

所有预检先于写入，相关写命令自动刷新 spec。多文件更新用 pending journal 完成中断恢复；status 遇 pending 提示先 acquire，恢复在预检与各次写入前检查外部冲突并保留现场。外部编辑器不参与 Flow 锁，检查与替换无法保证原子性，恢复期间须暂停编辑同批文件。这比仅依赖单文件原子写增加少量持久化复杂性，但将恢复规则集中在脚本内。

验收基线：直接交付与 Issue 图按顺序推进；完整交付仅登记一次；查询与恢复一致；跨日不重开；竞争领取只有一个有效持有人；阻塞恢复需要证据；无效输入不改文件；中断恢复保留 receipt 与文档一致性且不覆盖外部冲突；旧命令与旧 schema 明确不受支持。
