- RPC 大型应用组织：`server/app.ts` 用单一链式 `routes` 组合 `CORS → 健康检查 → .route("/api", createMarketHandler(service)) → onError → notFound`，导出 `AppType = ApplyGlobalResponse<typeof routes, GlobalErrorResponses>`；移除原先逐请求 try/catch 中间件，只保留 `app.onError()`；404 使用 `c.json(..., 404)`。
- 统一响应结构：`shared/api.ts` 新增 `ApiResponse<T> { code: number; message: string; extra: Record<string, any>; data: T }`、`apiCode`（0 成功，1001–1007 错误，1007 为未匹配路由）、`apiOk`、`apiFail`。成功 handler 用 `apiOk(data)` 包装；错误映射用 `apiFail(code, message, extra = {})`，失败时 `data = null`；HTTP 状态由 Hono 按语义单独返回（200/400/404/408/500/502/504），与业务码分离。`ApplyGlobalResponse` 的全局错误类型使用 `ApiResponse<null>`。

## 决策与证据

计划阶段已核实的迁移约束（2026-10-17，main `17d76733`）：

- 服务端编译：`tsconfig.server.json` 必须 `rootDir: "."`、`outDir: "dist"` 才能同时编译 `server` 与 `shared`；`rootDir: server` 即使只做 type-only 引用也会报 TS6059（tsc 实测）。产物为 `dist/server/*` 与 `dist/shared/*`，`start` 为 `node dist/server/main.js`。
- 迁移目录：产物比源码多一层 `dist/`，同一相对路径无法同时命中；改为 `path.resolve("migrations")`。dev、`start`、E2E 的 cwd 均为应用根（README 已有工作目录约定），因此三种入口一致。
- Hono RPC 子应用：已验证 `new Hono().route("/api", subApp)` 后 `AppType` 仍能推导 `/api/securities` 的响应类型；handler 拆分不会破坏 `hc<AppType>`。
- Hono 大型应用优化依据官方 RPC 指南「Using RPC with larger applications」：链式定义子应用与顶层 `routes`、从链式 routes 导出 `AppType`、全局错误用 `ApplyGlobalResponse`、成功响应用带状态码的 `InferResponseType`；已核对 Hono 4.13.7 导出 `ApplyGlobalResponse` 并用 tsc 验证该组合可编译。
- 类型性能取舍：本次引入 `hcWithType` 作为唯一实例化点（已用 tsc 验证 `Parameters<typeof hc>` + type-only `AppType` 可编译）；TypeScript project references/声明缓存/按子应用拆客户端仍不引入，后续 route 数或 tsserver 延迟明显增长时再按指南升级。
- 框架边界：service/repository 不导入 Hono；`MarketError` 去掉 HTTP 状态，由 `market/handler/errors.ts` 映射。以此作为三层边界的验收依据。
- 依赖方向：handler → service（业务用例与错误类型）→ repository 接口（`market/repository/market-repository.ts`）；SQLite 实现与 `libs` 由 `server.ts` 组合根注入；service 不导入 `repository/sqlite`、`libs` 实现或 Hono。
- SQLite 接入库：保持 `better-sqlite3` 13.0.3 + `drizzle-orm` 0.45.2 + `drizzle-kit` 0.31.10（已在 catalog/锁文件固定，Node 24/Windows 实测）。已核对 drizzle-orm 0.45.2 驱动目录：有 `better-sqlite3`、`libsql`、`mysql2`、`node-postgres` 等，无 `node:sqlite`；better-sqlite3 13 要求 Node >=22 且提供 Win/Linux/macOS 预编译。
- 前端层级：`client` 作为源码根时，`features/market-dashboard/chart/` 是 level-4 文件目录，`libs`/`utils` 在 level-2，均符合 code-spec，无需拆分 chart 或页面。
- `tsconfig.json` 会因类型导入把 `server/app.ts` 纳入程序；其依赖图不引入 Node 内置模块，现有前端 `types: ["vite/client"]` 已验证可编译。统一检查配置加入 `node` 类型只为服务端源码。
- `vitest` 的 unit include 需覆盖 `client/**/*.test.ts`、`server/**/*.test.ts`、`shared/**/*.test.ts`；browser 为 `client/**/*.test.tsx`；覆盖率 include 三个源码根并排除测试与 `client/test-support`。
- Vite `root: "client"` 时，`index.html` 内脚本改为 `/app/main.tsx`；`outDir` 相对 root 解析，需 `emptyOutDir: true` 清理 `dist/client`，不影响 `dist/server`、`dist/shared`。
- 现有测试拆分依据：`service.test.ts` 混合配置/入口（→ `server.test.ts`）、HTTP 错误（→ `handler/routes.test.ts`）、SQLite 初始化与事务（→ `repository/sqlite/sqlite-market-repository.test.ts`）；`daily-bars.test.ts` 的用例策略与取消不写入（→ `service/market-service.test.ts`）；触发回滚属存储行为（→ repository 测试）。
- `market-number-format` 移到 `client/utils` 后，chart 与看板统一以 `@/utils/market-number-format` 引用；`cn` 无调用点，移到 `client/utils/cn.ts` 保留现有依赖。
- Playwright webServer 命令改为 `pnpm run dev:web -- --host ... --port ... --strictPort`，否则参数会传给编排工具而非 Vite。
- E2E 编译产物必须在启动前端前完成；`global-setup` 继续承担编译与后端拉起，`start`/`kill` 的身份校验与 UUID 状态目录逻辑保留；fixture 的 import 路径改为 `dist/server/...`。
- 开发服务端用 `node --watch --experimental-strip-types server/main.ts`；Node 不走 tsconfig paths，因此服务端与 shared 之间使用相对导入。生产为 `node dist/server/main.js`。
- 统一响应：`ApiResponse<T>` 由 `shared/api.ts` 定义；成功用 `apiOk(data)`（`code=0`、`extra={}`），失败用 `apiFail(code, message, extra={})`；`data` 成功时为业务载荷、失败时为 `null`；`extra` 为 `Record<string, any>` 结构化细节。
- 错误分层：service 的 `MarketError` 只含业务码与消息，handler 映射 404/504/502 并用 `apiFail` 包装；Zod → 400 `invalid_argument`，取消 → 408 `canceled`，未知 → 500 `internal`；当前 `MarketError` 的 status 字段在重构中移除，相关测试同步调整。
- 删除旧应用目录前确认无未纳入迁移的工作区文件；`data/`、`e2e/.backend/`、`e2e/test-results/` 等运行产物不进入版本控制。
