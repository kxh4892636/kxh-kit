# 体验分 E2E 测试执行

本 reference 负责按体验分功能模块验收文档执行真实浏览器 E2E。一次 E2E 路径同时证明页面交互、UI 状态、相关接口响应和页面消费结果。

执行前必须定位对应功能模块的验收文档；文档缺失、过期或不覆盖当前需求时，先按 [documentation.md](documentation.md) 创建或更新文档，再执行 E2E。体验分 H5/PC 路由和文档位置也从 [documentation.md](documentation.md) 读取。

## 执行顺序

1. 根据需求、修改文件或用户指定内容定位受影响的体验分端型、功能模块、目标 app 与目标页面。完成标准：得到一个或多个 `apps/experience-score-*/src/v10/features/<feature>/test/` 目录，目标 URL 来源有明确记录。
2. 读取对应功能模块的验收文档：优先读取用户指定的 `test/yyyy-mm-dd-xxx.md`；未指定时读取与本次需求匹配的需求文档和 `test/index.md`。完成标准：待执行场景全部来自模块验收文档。
3. 检查文档中的 ready 场景、agent 浏览器步骤、入口 URL、前置数据、等待条件、UI 断言、接口断言和证据要求。完成标准：每条待执行路径都有可操作步骤和可观察断言。
4. 确认目标页面、路由、商家态、业务完成标准、可访问 URL、账号、权限和测试数据。完成标准：agent 能拼出目标 URL 并进入目标页面，或明确缺少哪个输入。
5. 使用当前可用的浏览器控制能力操作承载用户登录态的浏览器，执行文档中的用户动作。完成标准：页面进入目标状态，关键交互已触发。
6. 命中 H5/PC 多端或抖店/罗盘多平台时，只执行文档声明的受影响路径；文档要求 PC 双平台覆盖时同时覆盖抖店和罗盘，H5 只覆盖抖店。
7. 沿同一条用户路径验证页面交互、UI 状态、网络请求、响应数据和异常信息。完成标准：每个关键动作都有用户可见断言和相关接口断言。
8. 记录结果和证据；如果来自 E2E 文档，回写执行记录。完成标准：结论包含 passed / failed / blocked、环境、浏览器、时间、证据和未完成原因。
9. 如有失败，修复后只重验失败的路径、步骤、UI 断言或接口断言。

## 前置条件

- agent 可使用当前可用的浏览器控制能力操作承载用户登录态的浏览器，并能打开页面、等待加载、读取页面信息、在页面上下文执行 JavaScript；本 skill 不限制具体框架。
- 已识别目标 app、workspace、路由、页面 URL 和 URL 来源。
- 目标 URL 可访问，并且账号、权限、商家态、测试数据和外部依赖已满足当前场景。
- 如果目标环境需要发布或流水线部署，调用方先完成环境准备；本 reference 只消费可验收 URL，不定义发布完成口径。

## Dev Server 与页面定位

本地验收或 HMR 检查时使用本节。

1. 检查是否已有目标 app 的 dev server：

   ```bash
   ps aux | grep -E "emo start|edenx|webpack" | grep -v grep
   ```

2. 有进程时等待 HMR 编译最新代码后继续；无进程且用户要求本地验收时启动目标 workspace 的 `emo start <workspace-name>`。
3. 从修改文件定位页面目录，例如 `src/pages/<module>/...`。
4. 读取路由配置，找到页面 `path`。
5. 结合 app `AGENTS.md` 的访问域名和路由前缀拼接 URL。
6. 打开或切到目标页面并等待页面加载；未找到目标页面时新开标签页访问目标 URL，或请用户打开页面。完成后记录成功、待确认或阻塞结论。

## 验证方法

根据改动类型组合使用当前可用的浏览器控制能力：

- 页面信息：读取当前 URL、标题、页面主体和可见页面状态。
- 截图：验证布局、样式、遮挡、响应式状态。
- DOM/脚本检查：检查普通 DOM、localStorage、页面文本和页面可读状态。
- 页面主执行上下文：读取全局变量，例如 ECOP 的 `window.__PRELOAD_CONTEXT__`；当前 JavaScript 执行方式看不到页面全局变量时，先切到页面主执行上下文读取，再判断页面状态。
- 用户操作：通过点击、输入、键盘、触摸或明确 DOM 行为触发表单、弹窗、抽屉、筛选和提交。
- 控制台检查：检查运行时错误。
- 网络检查：检查接口调用和响应。

文案、数据和状态类改动优先用脚本或快照验证；视觉样式类改动需要截图。

## E2E 内的接口检查

页面验收时同步检查本次改动相关接口。接口检查是每个关键页面动作的内置断言：

1. 找到与页面加载、查询、提交、保存、导出等动作相关的请求。
2. 检查 HTTP 状态码、请求取消、超时、CORS 和重定向。
3. 检查业务响应 `code`、`message` 和核心 `data` 字段。
4. 确认页面展示与接口数据一致。
5. 若发现错误，提取响应 header 中的 `logId`、`x-tt-logid`、`x-tt-trace-id`、`x-request-id` 等追踪字段，并记录失败请求、响应摘要和触发步骤。

## 失败重验

E2E 失败后先把失败拆成最小可验证单元，再按影响范围重验：

- UI 断言失败：修复前端后，回到失败页面和失败交互步骤，重验该 UI 断言及其直接依赖的接口。
- 接口断言失败：修复前端请求/消费逻辑或后端接口后，回到触发该接口的用户动作，重验接口响应和页面展示。
- 控制台错误：修复后重验触发该错误的页面动作，并确认错误不再出现。
- 商家态或权限失败：只重做商家态准备和后续受影响步骤，已通过的静态检查不重复。
- 代码修复后：确认目标环境已经承载最新代码，再回到失败页面路径重验；目标环境不可确认时，标为 blocked 并记录缺失的环境事实。

## 注意事项

- 等待 HMR 完成后再验收修改结果。
- 抽屉、弹窗、二级菜单内的改动必须先触发对应交互再验证。
- 只有发现 HMR 未生效或页面状态异常时才刷新页面，并记录刷新原因。
- 验证阶段不运行 `pnpm biome check --write` 这类自动格式修复命令。
- 目标环境部署状态不明时，先补齐环境事实再给出 E2E 结论。
- 截图前先处理会遮挡目标区域的活动弹窗、权限弹窗或登录弹窗，并记录处理动作。
- 动态订单号、商品 ID、客服 ID、分数值等历史样例只作为本次执行事实，不写成长期稳定断言。
