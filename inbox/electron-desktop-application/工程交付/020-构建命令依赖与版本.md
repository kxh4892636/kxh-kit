# Electron 构建命令、依赖与版本兼容

## 脚本分层

| script         | 目的                       |
| -------------- | -------------------------- |
| `dev`          | 开发态运行                 |
| `build`        | typecheck + 三 target 构建 |
| `start`        | 预览现有生产 build         |
| `build:unpack` | 构建并生成解压目录         |
| `build:win`    | 构建 Windows NSIS          |
| `build:linux`  | 构建 Linux AppImage        |
| `build:mac`    | 构建 macOS DMG             |

- 命令边界: `build` 不生成安装器，平台脚本会先 build 再调用 electron-builder;
- 调试顺序: 先让 build 通过，再排查平台打包问题;
- CI 顺序: frozen install 后依次执行格式、lint、类型、测试、build 和 package;

## electron-vite 依赖处理

- main/preload: `dependencies` 默认 externalize，运行时由打包器收集;
- renderer: 依赖默认 bundle 进 Web 资产;
- Node built-in 与 Electron: 默认保持 external;
- devDependencies: electron-builder 默认不把它们作为生产依赖收集;
- native addon: 不能假设能完整 bundle，通常需要保持 external 并处理 ABI;

## 版本兼容思维

- “全部最新”: 应解释为满足 peer range 的最新兼容组合;
- electron-vite 5: Vite peer range 为 5、6、7;
- Lithe 选择: Vite 7 + React plugin 5，而不是强行使用 Vite 8;
- Electron 43: 内置 Node 24，因此类型和 CI 对齐 Node 24;
- 升级验证: main、preload、renderer、E2E 和 package 必须一起验证;

## 为什么不使用最新 Node 类型

- 类型应描述目标 runtime，而不是开发机上能安装的最高版本;
- 使用 Node 26 类型可能允许调用 Electron 内置 Node 24 不存在的 API;
- `@types/node` 对齐 24 能更早发现 runtime 漂移;
- Node major 升级通常由 Electron 升级带入，不应独立假设;

## pnpm 约束

- `packageManager`: 固定 pnpm 11 的精确版本与 integrity;
- frozen lockfile: CI 不允许安装时改写依赖解析;
- `pnpm peers check`: 检查 peer dependency 一致性;
- overrides: 只用于已确认的传递依赖兼容问题，并限制作用范围;
- supply-chain policy: install 时检查 lockfile 的发布时间策略和 build script 许可;

## 判断清单

- 当前工具是否支持目标 Node、Vite 和 TypeScript major;
- 依赖在 main/preload 是 bundle 还是 external;
- renderer-only 依赖是否误进入生产 node_modules;
- native addon 是否需要 Electron rebuild;
- lockfile、peer check 和实际 package 是否同时通过;
