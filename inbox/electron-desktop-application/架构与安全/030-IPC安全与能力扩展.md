# Electron IPC 安全与能力扩展

## main 的运行时校验

- sender 校验: `event.sender` 必须等于主窗口 `webContents`;
- frame 校验: `event.senderFrame` 必须等于主窗口 main frame;
- 参数校验: theme 必须属于 `light | dark | system`;
- 数据访问: handler 调用数据库 repository，不向 renderer 暴露 SQL;
- handler 清理: 重建窗口前和退出时调用 `removeIpcHandlers()`;
- 基本原则: TypeScript 只约束编译期，来自 renderer 的数据始终按不可信输入处理;

## 新增本地能力的步骤

1. 在 shared contract 中定义最小输入和输出;
2. 在 channel 常量中增加领域化名称;
3. 在 preload 中只暴露具体函数;
4. 在 main 中验证 sender、参数、路径和权限;
5. 将实际能力封装在 main 侧模块中;
6. 为 main 模块写测试，为 IPC 真实路径写 E2E;

## 文件读取示例

```ts
// 推荐：main 根据已验证的业务标识解析路径
window.lithe.documents.read({ documentId });

// 不推荐：renderer 获得通用文件系统能力
window.lithe.fs.readFile(arbitraryPath);
```

- 路径边界: 不能只检查字符串前缀，应解析绝对路径并确认位于允许根目录;
- 返回边界: 大文件不应一次复制到 renderer，可采用分页、流或受控临时文件;
- 错误边界: main 错误经过 IPC 会被序列化，renderer 不应依赖完整 Error 原型和 stack;

## 命令能力示例

```ts
// 推荐：固定动作与结构化参数
window.lithe.workspace.runCheck({ workspaceId });

// 不推荐：允许页面执行任意 shell 字符串
window.lithe.shell.exec(command);
```

- executable 与 args: 分开传递，避免 shell 拼接与注入;
- cwd: 必须解析并限制在授权 workspace;
- env: 只传入任务需要的环境变量，避免泄漏 secret;
- timeout/cancel: 长时间任务必须支持中止和退出清理;

## 常见反模式

- 直接暴露 `ipcRenderer.send`、`invoke` 或 `on`;
- 接收 renderer 提供的 SQL、shell command 或绝对路径后直接执行;
- 只依赖 TypeScript 联合类型而没有运行时校验;
- 未校验 sender，导致其他窗口或 frame 调用高权限 handler;
- 使用一个 `execute-anything` channel 承载所有能力;
- 把错误 stack、内部绝对路径或 secret 原样返回页面;

## 审查清单

- API 名是否表达领域意图而不是底层工具;
- 参数能否缩窄为 ID、枚举或结构化对象;
- sender 和 frame 是否验证;
- 路径、命令和输出是否有明确上限;
- handler 是否在窗口重建和应用退出时清理;
- 正向、非法参数和非法来源路径是否均有测试;

## 官方资料

- [Electron Security Checklist](https://www.electronjs.org/docs/latest/tutorial/security): sender 校验与最小权限;
- [Context Isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation): 不应直接暴露通用 IPC;
