# Electron 代码路由与导航模式

## Lithe 的代码路由

- router: TanStack Router;
- root route: `AppShell`，所有页面共享侧栏和窗口标题区;
- home route: `/`，展示 Electron 运行环境;
- settings route: `/settings`，管理主题;
- route tree: 在 TypeScript 中组合，路由参数和 Link 获得类型推导;
- active state: `useRouterState()` 读取 pathname，驱动侧栏选中态;

```ts
const rootRoute = createRootRoute({ component: AppShell });
const homeRoute = createRoute({
  component: HomePage,
  getParentRoute: () => rootRoute,
  path: "/",
});
```

- “代码路由”: 路由树由 TypeScript 声明，而不是通过文件目录自动生成;
- “history 模式”: 导航状态如何映射到地址，两者属于不同维度;

## 三种 history 模式

| 模式            | 优点                                 | 缺点                     | Electron 适用性           |
| --------------- | ------------------------------------ | ------------------------ | ------------------------- |
| hash history    | 本地文件刷新稳定，无需服务器 rewrite | URL 带 `#`               | Lithe 首版最稳妥          |
| browser history | URL 干净，符合普通 Web 心智模型      | 本地深路径刷新可能失败   | 有 custom protocol 时可选 |
| memory history  | 不依赖地址栏，状态完全由内存控制     | 不可复制深链接，恢复较弱 | 固定流程或测试            |

## 为什么选择 hash history

- 生产 renderer 从本地 `index.html` 加载;
- browser history 的 `/settings` 可能被解释为文件系统路径;
- hash 后内容不参与底层文件定位，始终先加载同一个 HTML;
- 设置页地址形如 `index.html#/settings`;
- 不需要额外本地 Web server 或 rewrite 规则;

## 何时考虑 browser history

- 应用已注册 custom protocol，并能把任意 route 回退到入口 HTML;
- 需要更干净的可复制地址;
- 已为冷启动、刷新和外部 deep link 建立解析逻辑;
- 已在开发 URL 与打包协议两种环境验证;

## 何时考虑 memory history

- UI 是短流程、向导或固定单页，不需要地址语义;
- 不希望导航状态出现在 URL;
- 测试需要完全控制 history;
- 能接受关闭后导航位置不自然恢复;

## Electron 导航安全

- 应用内路由: 由 TanStack Router 在已加载页面内部处理;
- 顶层导航: Lithe 的 `will-navigate` handler 直接阻止;
- 新窗口: `setWindowOpenHandler` 返回 `deny`;
- 外部链接: 若未来允许，应在 main 校验协议和目标后调用受控 API;
- 验证: 路由必须在打包后的实际加载协议下执行 E2E;
