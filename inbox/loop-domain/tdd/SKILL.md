# 测试驱动开发

TDD 是 red → green 循环。本 skill 用来让这个循环产出值得保留的测试：什么是好测试、测试应该写在哪里、常见反模式，以及循环规则。每一轮都要应用这些规则；在循环开始前和进行中查看，而不是结束后再补看。

探索代码库时，只使用能从当前对话和已读文件中验证的术语与决策。

## 什么是好测试

测试通过公共接口验证行为，而不是验证实现细节。代码可以彻底重写，测试不应该随之失效。好测试读起来像规格说明：“用户可以用有效购物车结账”会明确告诉你系统具备什么能力；它能经受重构，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 接缝：测试写在哪里

**接缝**是你进行测试的公共边界：能观察行为、但不需要探入内部的接口。测试写在接缝上，不写在内部实现上。

**只测试预先确认过的接缝。** 写任何测试前，先写下本次要测试的接缝并与用户确认。未经确认的接缝不写测试。你不可能测试所有东西；提前确认接缝，是为了让测试投入落在关键路径和复杂逻辑上，而不是铺满每个边角。

问：“公共接口是什么？我们要测试哪些接缝？”

## 反模式

- **耦合实现**：mock 内部协作者、测试私有方法，或通过旁路验证（例如绕过接口直接查数据库）。识别信号是：行为没有变，只是重构后测试就坏了。
- **同义反复**：断言用和代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、用同样逻辑手写出来的快照、常量断言等于自身），因此测试天然会通过，永远无法与代码产生分歧。期望值必须来自独立的真相来源：已知正确的字面量、推导好的示例、规格。
- **水平切片**：先写完所有测试，再写完所有实现。批量测试验证的是_想象中_的行为：你测试的是事物的形状，而不是面向用户的行为；测试对真实变化不敏感，并且在理解实现前就锁定了测试结构。改用**纵向切片**：一个测试 → 一个实现 → 重复；每个测试都是一发 **tracer bullet**，会响应上一轮循环教给你的东西。

## 循环规则

- **先 red，再 green。** 先写失败测试，再只写刚好让它通过的代码。不要预判未来测试，也不要添加猜测性功能。
- **一次一个切片。** 每轮只处理一个接缝、一个测试、一个最小实现。
- **重构不属于循环本身。** 重构属于审查阶段（见 `code-review` skill），不属于 red → green 实现循环。
