# 行为驱动开发

BDD 是场景 -> 实现循环。本 skill 用来让这个循环锚定在可观察行为上：如何编写场景、自动化应该落在哪里、常见反模式，以及循环规则。每一轮都要应用这些规则；在循环开始前和进行中查看，而不是结束后再补看。

探索代码库时，只使用能从当前对话和已读文件中验证的领域语言与决策。

## 什么是好场景

场景通过示例描述业务行为，而不是描述 UI 操作或实现细节。代码可以彻底重写，场景不应该随之失效。好场景读起来像共享示例：“已批准客户可以在信用额度内下单”会明确告诉你系统具备什么能力；它能经受重构，因为它描述的是领域关心的结果。

示例见 [scenarios.md](scenarios.md)，自动化指南见 [automation.md](automation.md)。

## 示例：行为在哪里被规格化

**示例**是你规格化并自动化的具体行为切片：一条规则、一个触发、一个可观察结果。场景写在公共行为边界上，不写在内部实现上。

**只规格化已确认的行为示例。** 写任何场景前，先写下正在讨论的示例并与用户确认。未经确认的规则不写场景。你不可能规格化所有东西；提前确认示例，是为了让 BDD 投入落在业务关键行为上，而不是偶然流程上。

问：“哪些行为示例应该变成可执行场景？”

## 反模式

- **步骤脚本化**：描述点击、选择器、API 调用或数据库设置，而不是领域行为。识别信号是：规则没有变，只是界面变化后场景就坏了。
- **耦合实现**：命名内部服务、存储表、任务队列、功能开关或私有方法。场景应该向业务解释行为，并且只通过可观察结果约束实现。
- **示例含糊**：使用“有效数据”“正确结果”这类宽泛占位，而没有具体值。期望结果必须来自真实示例：推导好的值、业务规则或验收决策。
- **场景大纲膨胀**：把一个场景变成一组松散相关的行矩阵。当不同行解释的是不同行为时，按规则拆分；场景大纲只用于同一规则下的不同具体示例。
- **水平切片**：先写完所有场景，再写完所有自动化，再写完所有实现。批量场景验证的是想象中的行为，并会偏离代码教给你的东西。改用**纵向切片**：一个场景 -> 一个实现 -> 重复；每个场景都是一发 **tracer bullet**，会响应上一轮循环教给你的东西。

## 循环规则

- **先场景，再代码。** 先写可执行场景，再只写刚好满足它的实现。
- **一次一个示例。** 每轮只处理一个行为示例、一个场景、一个最小实现。
- **统一语言保持稳定。** 步骤名和场景文本使用用户与代码库都能支撑的领域语言。
- **重构不属于循环本身。** 重构属于审查阶段（见 `code-review` skill），不属于场景 -> 实现循环。
