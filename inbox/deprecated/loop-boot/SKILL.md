# Loop Boot

本 skill 是“需求 → 讨论 → 计划/测试 → 开发 → 验收 → 交付”的薄路由。它只规定主流程、分支条件和阶段门禁；具体操作细节交给对应 skill。

## 主流程

1. **理解输入**：接收 PRD、Figma、口头需求、问题背景或已有代码上下文。
2. **需求讨论**：先识别业务域；命中业务专属 skill 时先读取它，了解业务链路、页面入口、关键角色、核心规则和验收关注点。再使用 `grilling` 逐个澄清目标、验收标准、业务规则、入口、设计状态、权限和不做范围。一次只问一个问题；能从代码、文件或业务 skill 确认的问题先自行探索。
3. **计划分支**：
   - 小需求：影响面单一、验收路径明确、能在当前会话内完成时，可以直接进入测试用例和开发。
   - 大需求：跨页面/跨模块、多轮沟通、多会话开发、验收链路复杂或存在未决业务规则时，建议使用 `to-plan`。
   - 必须 `to-plan`：用户明确要求计划、任务可能跨会话继续、或已经出现多轮状态需要沉淀。
4. **测试用例/验证方式**：生成与任务对应的测试用例或验证方式。使用 `to-plan` 时，测试用例必须对应 TaskList 的验证方式；未使用 `to-plan` 时，也要在当前对话中维护轻量任务清单和对应验证方式。
5. **开发**：先使用 `code-spec`，由它按任务类型读取最小必要规范。再按 BDD/TDD 纵向切片开发。
6. **验收**：使用 `verify` 进入静态检查、构建、浏览器 E2E、接口断言、失败修复和最小重验闭环。需要商家登录、测试 `shopId` 或线上附身时，使用 `merchant-auth`。
7. **交付**：输出轻量阶段化结论，说明需求结论、计划选择、测试/验证、实现范围、验收结果和剩余风险。

## 停止门槛

如果目标、验收标准、核心业务规则、入口页面/接口、设计稿关键状态、权限或商家态任一项不清楚，且无法从代码、PRD、Figma 或业务 skill 中确认，不要进入开发。继续使用 `grilling` 单问题澄清。

需求、计划、测试用例或实现过程中发现的新代码事实发生冲突时，先回到需求/计划校准：更新事实、调整测试和任务，再继续开发。

## Figma 路由

用户提供 Figma 或设计稿时，只把设计能力作为阶段路由：

- 需求讨论阶段：只获取设计稿数据，读取 XML 文件和预览图，用于理解页面结构、关键状态、文案、布局和交互问题；不要下载图标、生成代码或做代码审查。
- 开发阶段：需求和测试用例确认后，再按需要下载图标、生成代码和做代码审查。

## 测试与开发规则

- 使用纵向切片：一个测试用例/验证方式 → 一个最小实现任务 → 验证通过 → 下一个切片。不要先批量写完所有测试再批量开发。
- 前端开发优先使用 `bdd`。页面、组件、交互、表单、路由、接口消费、权限态、空态和错误态都先用用户可观察行为描述；纯函数、格式化、权限判断、query 解析等局部逻辑可补充 `tdd`。
- 后端开发只能使用 `tdd`，以公开接口、handler、service/use case 或其他可执行边界为验证入口。
- 测试期望必须来自 PRD、设计稿、接口契约、业务规则、固定样例或已验证事实，不要从实现反推期望。
- 开发前明确不做范围：不实现未确认的设计稿状态，不补齐 PRD 未定义的业务规则，不顺手重构无关模块。

## 业务与验收路由

- 需求讨论、测试用例生成或验收方案制定前，都要先识别业务域。命中业务专属 skill 时优先读取它，例如体验分使用 `experience-score`，再结合业务链路、`bdd`/`tdd`/`verify` 生成测试和验收路径。
- 验收细节交给 `verify`。`loop-boot` 只要求进入验收闭环，不复制静态检查、PPE、E2E、接口排障等细节。
- 商家态准备交给 `merchant-auth`。只有需要测试商家、fake login、指定 `shopId`、线上真实商家或附身时触发。

## 上下文管理

大需求、多轮或多会话开发必须依赖 `to-plan` 持续校准目标、事实、TaskList、验证结果和风险。发生 compact/resume 或上下文接近失真时，先恢复并更新 plan，再继续开发。

## 轻量交付

最终回复保持简短，但覆盖闭环：

- 需求结论：完成了什么；不包含什么。
- 计划选择：是否使用 `to-plan`，以及原因。
- 测试/验证：BDD/TDD 场景或验证方式，以及执行结果。
- 实现范围：关键文件或模块。
- 验收结果：通过、失败、未验证及原因。
- 剩余风险：只写仍影响交付判断的风险。

小需求每项一句即可；大需求的详细状态写入 plan，最终回复只摘要关键结论。
