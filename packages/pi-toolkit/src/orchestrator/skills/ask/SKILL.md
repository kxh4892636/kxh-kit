# Ask

目标, 边界或方案未定, 或需向用户取证时按本循环推进; 结论写回 Plan 才算完成一轮, 用户答复前的推理不算结论.

## 概念

**Design tree** 按决策依赖展开, 答案决定下游问题; **frontier** 是前置已有答案,当前可回答的全部问题.

## 步骤

1. **取证**: 需要工作区事实时派该 Plan 的 worker(`orchestrator_command` 的 `dispatch`), 事实以 `orchestrator_state` 摘要或 note 正文回读; 编排方在会话内不读源码, 不跑命令(见 `../../prompt.md` 的「职责边界」);
2. **提问**: 每轮覆盖整个 frontier; 有可回读证据且无互斥选项的问题直接回答, 其余用 `ask_questions` 询问用户;
3. **修订**: 使用 `orchestrator_write` 把结论就地写入 Plan; 更新选择,被排除路径与假设, 重算 frontier; 上游改变时复核并修订失效的下游结论.
4. **收敛**: 可达问题均已处理,frontier 为空,无静默假设,用户反馈有结论后结束;

## 每轮记录

在相关 note 中增加"拷问记录"; 按轮保留仍影响当前决策的问答, 已不影响决策的轮次压成一句结论后删除细节; 合并重复问答时保留来源与结论.

```markdown
### 第 {round} 轮

#### Q{question} - {标题}

- 问题: {问题及必要的互斥选择}
- 前置问题: {Q 编号或无}
- 下游边界: {该答案会改变什么}
- 推荐答案及理由: {选择与证据}
- 处理结论: {用户反馈,确认状态与受影响的文档位置}

### 补充说明

{尚未被问题覆盖的用户输入及处理结论; 没有则写无}
```

每题重复以上结构, 编号递增, 按轮追加; 补充说明始终位于末尾.

<reminder>
处理用户输入时:
1. 明确指令照做; 事实性断言与前提需核查, 不可默认成立.
2. 出现以下任一情形, 先向用户指出, 不要静默修正,也不要直接照做:
   - 输入与可验证的事实或数据冲突
   - 前提或方案存在会导致返工,结论错误的漏洞
   - 有显著更优的做法, 且用户似乎并不知情
3. 上述分歧若经一轮澄清仍未收敛, 或若反复讨论后仍有用户未提及的关键问题, 调用 `ask_questions`: 说明问题,给出 2-3 个选项,标明你的建议.
4. 无需打断的, 正常执行, 并在回答中注明你据以判断的假设.
</reminder>
