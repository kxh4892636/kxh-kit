# Ask

使用同一循环逐轮拷问，复用仍成立的结论和确认；领域文档更新遵循 `prompts/system.md` 的维护循环。

## 逐轮拷问

**Design tree** 按决策依赖展开，答案决定下游问题。**Frontier** 是前置已有答案、当前可回答的全部问题。

1. **取证**：事实从工作区与工具查明并保留来源；需进一步探索时用只读工具在当前 agent 内取证，把未决项作为前置，仅暂停下游，其余 frontier 继续。
2. **拷问**：每轮覆盖整个 frontier，问题按本 quest 唯一递增编号，附推荐与理由；用 `ask_questions` 直接向用户提问，不在回复正文罗列问题；每题给 2–3 个互斥选项并把推荐项放首位；依赖本轮未决答案的问题留到下一轮。
3. **修订**：处理用户回答与评价，把结论写进权威文档（spec、note、CONTEXT、ADR、question），保留用户反馈及处理结论；按固定提示词的节奏合并进本轮批量写，不逐条实时落盘。更新选择、被排除路径与假设，重算 frontier；上游改变时复核并修订失效的下游结论。
4. **收敛**：可达问题均已处理、frontier 为空、无静默假设，用户反馈有结论；同步进度与恢复入口并跑 `nano_flow_check`。

## 每轮记录

在相关 note 的正文中记录拷问，按轮保留仍影响当前决策的问答；提问一律通过 `ask_questions` 发起，回答后把问题、选项、用户选择与处理结论写入正文。下方模板只用于落盘记录，不是提问渠道；合并重复问答时保留来源、反馈与结论。正文不强制固定章节，能支撑当前决策即可。

```markdown
### 第 {round} 轮

#### Q{question} — {标题}

- 问题：{问题及必要的互斥选择}
- 前置问题：{Q 编号或无}
- 下游边界：{该答案会改变什么}
- 推荐答案及理由：{选择与证据}
- 修改意见：{用户反馈或待评价}
- 处理结论：{已确认/暂定/待取证，以及受影响的文档位置}

每题重复以上结构，编号递增，按轮追加，补充说明始终位于末尾。

### 补充说明

{尚未被问题覆盖的用户输入及处理结论；没有则写无}
```

## 按交付单元聚合

方案收敛后，按 **可独立验收的交付单元** 划分 note，不按子任务逐条拆。同一交付单元内的返工、补测、修正与验证并入原 note，不新开；只有验收条件或状态需要分别表达（会单独 `blocked` 或单独完成验收）时才拆成两条。降低后续交付难度的前置准备排最前。唯一例外是大范围机械重构：expand → 按影响面分批 migrate（每批一个 note）→ contract 删除旧形态。

结果写进 Plan 的 note 文件，复用已有稳定 name 与有效证据；`related_noted` 只表达关联，不构成 DAG。
