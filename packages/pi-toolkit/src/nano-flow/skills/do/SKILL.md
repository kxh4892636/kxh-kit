# Do

用户已放行且有可推进的 note 时按本循环推进; 门禁, 验证与 evidence 是完成条件, 不是收尾时才补的步骤.

## 步骤

1. **选 note**: 用 `ready` 看依赖分组; 从组内从上到下取前置已完成的 pending note; 前置已完成的 note 可并行, 没有可执行的先报告队列与阻塞项.
2. **门禁**: 确认工作环境,执行契约与质量门禁.
3. **执行**: 按交付物适用的规范完成全部产出;
4. **验证**: 进行最小集合验收.
5. **收尾**: 置 `awaiting_verification` 并写"待验证"小节; 验证通过后写 evidence 并 `complete`, 同步 spec 与相关领域文档, 然后回到 ready 看下一组.

## 并行执行

`ready` 按依赖关系分组: 有依赖关系的 note 在同一组, 组内从上到下是依赖顺序. DAG 里前置已完成的 note 可以并行, 用 `subagent` 一条 note 一个任务, 任务里带上 Plan 路径, note id, 正文要点, 验收与停止点. 前置未完成的 note 等前置.

`nano_flow_write` 的写入由主会话串行: subagent 只产出工作与证据, `status` / `update` / `complete` 统一由主会话执行, 避免并发覆盖 `notes.json`. 子任务全部回收后, 主会话写回证据再选下一组.

## 门禁

先按 `../../prompt.md` 的「定位」读取领域知识.

以 spec 或 note 作为权威来源; 会话中确认的设计先写进 spec, 再作为输入.根据工作区事实和用户输入明确三项交付基线:

- **工作环境**: 执行,运行与验证所需的环境,服务和入口.
- **执行契约**: 范围,验收基线,步骤,停止点,交付物和状态变更授权.
- **质量门禁**: 该交付物适用的验证门禁与 verifying 的最小集合.

复用用户已确认的基线与授权; 未确认的项等待用户手动确认并记为未验证, 不得当作已完成.执行,取证,验证与验收后实时更新 story,spec,notes 的受影响内容与检查点; 基线实质漂移时, 更新受影响的权威输入并重新执行本 gate.

## 执行

- 交付中遇到阻塞时, 优先查阅 `common` 与该域的领域知识; 仍无解时把 note 置 `blocked` 并写清障碍与解除条件.

## verifying

1. **选择门禁**: 从工作区声明的规范,格式与静态检查,测试,构建,评审,运行态和消费者路径中, 选取验收门禁的最小集合; 选中评审时执行下方 review.
2. **执行门禁**: 按依赖顺序依次执行最小集合中的门禁.
3. **最小循环**: 从最早失败门禁取证, 做最小修复, 再从最早受影响门禁重验.

基线内所有适用门禁通过且审查发现已处理时完成验收; 未执行或未通过项明确记录, 保持待验收.

## review

交付物触及代码,行为或用户可见输出时, 启动两个 subagent(若可用), 并行审查; 纯文档改动可只做 Spec 审查.

- **Spec**: 读取交付产物对应的 story,spec,notes,adr,context 和其他来源, 验证是否符合工作需求.
- **Standards**: 基于已有知识, 额外遵循 `AGENTS.md` 和适用的规范 skill, 判断交付产物是否符合工作规范.

汇总去重后逐项修复或说明不采纳的依据; 修复后复验受影响门禁并复查原发现, 所有项均有结论且无未解决的阻断项时结束审查.

## 完成与登记

- 交付物可用且证据可回读后, 置 `awaiting_verification`, 把交付物与验证证据写进 evidence(命令与输出,文件,commit), 验证通过再 `complete`.
- 完成后同步受影响的 spec 章节与领域文档.
