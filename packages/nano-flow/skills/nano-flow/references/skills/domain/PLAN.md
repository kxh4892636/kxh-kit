# Plan

## 生命周期

- `planning`：新 Plan 的起点，讨论需求、调查和制定方案；这些 notes 可在此推进和完成。
- `implementing`：开始实际实现前迁入整个 Plan；继续开发、测试与验收。
- `reference`：全部 notes 已完成且仍有参考价值，经用户确认后迁入；仅讨论或计划的任务可从 planning 直接迁入。
- `archived`：废弃、过时或不再有用时迁入，内容冻结并退出当前权威来源；恢复工作时先迁回 planning 或 implementing，再依据现场修订。

生命周期表达工作阶段，notes 状态表达子任务进度；迁移 Plan 时同步相对链接。

## story.md

使用稳定的 `US-NNN` 标识。story 是用户故事的 card，逐轮拷问形成 conversation，可判定验收形成 confirmation。epic 内故事使用四级标题，独立故事使用三级标题，不创建空壳 epic。

```markdown
# {工作名}

## 原始想法

{用户的最初表述，保留原话}

## 角色

- **{角色名}**：{是谁、处境与工作方式}

## 故事

### {Epic 标题}

{这组故事共同完成什么}

#### US-001 {故事标题}

作为 {角色}，我 {想要}，以便 {收益}。

- [ ] {可判定的验收结果}

### US-002 {独立故事标题}

作为 {角色}，我 {想要}，以便 {收益}。

- [ ] {可判定的验收结果}

## 约束与澄清

{用户修正、不可丢失的边界与确认来源；区分原始要求、已确认变更和待确认假设，标明日期}

## 迷雾

{尚未澄清的空白、对验收的影响及取证入口；澄清后迁入对应章节}

## 上下文

{相关产物的路径或 URL，链接到 spec 与相关 notes；标明来源和适用范围}
```

## spec.md

- spec 状态从**全部 notes** 派生：全部 pending 为 pending，全部 completed 为 completed，其余为 in_progress。
- spec 的 `## Notes` 索引保持 1–21 项，选择对当前工作最有用的 notes; 索引不是全量清单；移出索引不等于删除文档或完成工作。
- 索引优先当前工作、阻塞、下一步与关键决策；索引中的链接、状态、直接依赖和下一步与 note 同步。未索引的剩余工作在「当前进度」保留定位入口。

```markdown
---
status: pending
---

# {工作名}

## 问题

{用户要得到的结果、已知约束，关联 story 的 US-NNN}

## 方案

{当前有效方案，保持在设计层级}

## 已排除的备选

- {方案}：{拒绝理由与依据，避免新上下文重复探索}

## 实施决策

{模块、接口、schema、契约；关键 state machine、schema、type shape 可内联并注明来源；区分已确认决策与假设}

## 工作环境

{执行该工作所需的环境信息: 例如项目管理工具, 本地开发环境, CI/CD 流水线, 运行时环境, 三方服务等；记录凭据获取方式，不写秘密值}

## 范围

{做什么}

## 非范围

{不做什么}

## 执行约束

{已有用户授权、模式、固定比较点、停止点、质量门禁与完成标准}

## 待定

{未决问题、选项或证据、影响与恢复条件；澄清后纳入方案或 notes}

## 上下文

{相对路径或 URL 引用 story、ADR、workflow、commit、diff 等；保留当前约束的证据来源}

## 当前进度

{截至日期与已核对的代码基线；已完成、进行中、未开始、阻塞与未验证事项，关联 notes；概括未索引的剩余工作及其定位入口}

## 恢复入口

{新上下文的阅读顺序、先核对哪些现场事实、下一项具体行动及命令、前置条件、预期结果与停止条件；链接到承载细节的 notes}

## Notes

| #   | Notes                  | 状态    | 阻塞于 | 下一步                 |
| --- | ---------------------- | ------- | ------ | ---------------------- |
| 01  | [{标题}](01-{标题}.md) | pending | —      | {当前具体动作或 skill} |
```

## notes：NN-中文标题.md

一份 note 只跟进一个原子化、独立的子任务, 例如讨论、调查、计划与实现等, 不同子任务使用同一模板。按工作性质填写交付和验收，例如「形成有依据的选择及理由」「制定可执行计划」「完成可验证的用户能力」，不将整段工作流水账塞入一个 note。

notes 状态流转如下:

```text
pending → in_progress → completed
              ↕
           blocked
```

- **标识与依赖**：文件 ID 为唯一、稳定的两位数字，新增使用未用 ID；删除或合并后允许断号，不重排幸存 ID。`blocked_by` 是两位字符串的 JSON 数组，如 `["01"]`，无依赖为 `[]`；依赖必须存在、ID 在当前 note 之前且无环。
- **推进**：直接依赖 completed 后开始工作，标记 in_progress；受阻标记 blocked 并记录障碍与解除条件，解除后回到 in_progress。
- **完成**：满足本 note 的验收条件，填入交付物与验证证据后标记 completed；讨论或计划以可检查的结论、方案作为交付物。
- **修订**：重新推进时据事实更新状态和检查点；删除或合并有依赖的 note 前，将消费关系改指实际承接产物或契约的 note。

```markdown
---
status: pending
blocked_by: []
---

# {标题}

## 交付

{用户可感知的结果或该项工作可检查的产物，关联 story 的 US-NNN 和 spec 方案}

## 范围

{做什么、不做什么}

## 直接依赖

- {NN 或无}：{原因；消费的产物或契约}

## 验收

- [ ] {可独立判定的最小结果}

## 上下文

- {相关 story、spec、ADR、workflow、代码路径、commit、diff 或 URL，以及适用的基线}

## 决策与证据

{调查所得事实及其来源、选定方案与理由、失败尝试及结果、已排除路径、待确认假设；使后续 agent 能复核而不重复试错}

## 执行检查点

{更新时间；已完成步骤、当前代码/文件/分支/commit 与未提交改动、已执行命令和结果、未执行或未验证项；必要的运行中任务与产物定位}

## 下一步

{具体动作、入口命令和工作目录、前置条件、预期结果、停止条件；决策需澄清时 /questing，代码交付时 /code-delivery}

## 阻塞记录

{仅 status 为 blocked 时保留：障碍与解除条件}

## 交付记录

{完成登记前填入并保留：交付物、验证命令/结果、证据链接与遗留限制}
```

## 模板扩展

保留固定章节，未知或不适用内容写明原因。内容无法归入现有章节（**独特**），且缺少它会损失执行或验收信息（**必要**）时，新增扩展章节。
