# 原型

原型是 **回答一个问题的一次性代码**. 问题决定形态.

## 选择分支

根据用户的输入和周围代码, 判断正在回答哪一类问题; 用户在场且问题含糊时直接询问:

- **"这套逻辑 / 状态模型顺手吗?"** → [LOGIC.md](LOGIC.md). 构建一个可分享的单文件 HTML (自由摸索按钮 + 分页签的引导式走查), 把状态机推过纸面上难以推理的用例, 非开发者也能亲手驱动.
- **"这东西应该长什么样?"** → [UI.md](UI.md). 在同一条路由上生成数个截然不同的 UI 变体, 通过 URL search param 和底部浮动栏切换; 每个变体按其中的设计流程做出独特而刻意的视觉方向.

两个分支产出的工件完全不同, 选错分支就浪费整个原型. 问题确实含糊且联系不上用户时, 按周围代码默认匹配 (后端模块 → 逻辑; 页面或组件 → UI), 并在原型顶部声明该假设.

## 两个分支共用的规则

1. **从第一天起就是一次性的, 并明确标记.** 原型代码放在它真正服务的位置旁边 (被原型的模块或页面附近), 让上下文显而易见; 命名上要让随手翻阅的人一眼看出这是原型而非生产代码. 一次性 UI 路由遵循项目已有的路由约定, 不要发明新的顶层结构.
2. **运行零门槛.** UI 原型从项目任务 runner 的一条命令启动: `pnpm <name>`, `python <path>`, `bun <path>` 等. 逻辑 demo 是用户双击即开的单个 HTML 文件. 无论哪种, 启动都不需要动脑.
3. **默认不持久化.** 状态住在内存里. 持久化正是原型要 _检验_ 的东西, 而不是原型应该依赖的东西. 问题明确涉及数据库时, 使用 scratch DB 或命名清晰为 "PROTOTYPE, 随手可删" 的本地文件.
4. **快速取证.** 原型阶段用手工走查验证问题, 不写测试; 错误处理以 _能跑_ 为限, 不做抽象.
5. **暴露状态.** 每个动作之后 (逻辑) 或每次变体切换时 (UI), 打印或渲染出全部相关状态, 让用户看到什么变了.
6. **按证据收口.** 动手前写明问题及判断答案的依据. 原型可运行、约定场景或全部变体已走查、观察与访问入口已提供时, 原型交付完成; 尚需用户判断时标记「待反馈」. 结论有观察支撑且所需用户判断已确认时, 问题才算回答.
7. **捕获与交付.** 原型作为 **primary source** 提交到一次性分支, 不进 main; 在 issue 或 commit 记录问题、观察、结论或待反馈状态及原型指针. 确认后的决策在正式实现时吸收: 逻辑模块可作为候选代码复用, UI 按选定设计正式实现, 均须遵循项目规范并完成适用的审查与测试; 手工走查只证明实验结果.
