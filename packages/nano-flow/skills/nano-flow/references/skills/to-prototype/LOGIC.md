# 逻辑原型

一个自包含的单文件 HTML (**可分享 demo**), 让任何人通过点按钮驱动一个状态模型. 当问题关乎 **业务逻辑, 状态转换或数据形状** 时使用: 这类东西纸面上看着合理, 只有推过真实用例才摸得到不对劲的地方.

因为只是一个文件, 无需安装任何东西, 你可以把它递给非开发者 (设计师, PM, 领域专家), 让他们亲手感受这个模型. 所以它说他们的语言, 不说代码的语言.

## 什么时候是这个形态

- "我不确定这个状态机能不能处理先 X 后 Y 的边界情况."
- "这个数据模型真的能表达 …… 这种情况吗?"
- "写 API 之前, 我想先摸一摸它应该长什么样."
- 任何有人想 **按按钮, 看状态变** 的场合.

如果问题是 "这应该长什么样", 走错分支了, 使用 [UI.md](UI.md).

## 流程

### 1. 写下问题

写代码之前, 先写下你在为哪个状态模型, 回答什么问题做原型. 一段话, 放在 demo 顶部 (放在可见的介绍区里, 而不只是注释). 回答了错误问题的逻辑原型是纯粹的浪费, 所以把问题写明, 之后才能核对 — 无论用户是现在看着, 还是离开后再回来 (AFK).

### 2. 把逻辑隔离进可移植模块

把真正的逻辑 (回答问题的那部分) 放在单个 `<script>` 块里, 写成一个小而纯的候选模块; 复用与正式交付遵循 [SKILL](SKILL.md) 的「捕获与交付」规则.

正确的形状取决于问题:

- **纯 reducer**: `(state, action) => state`. 动作是离散事件, 状态是单个值时合适.
- **状态机**: 显式的状态与转换. "此刻哪些动作甚至合法" 本身是问题的一部分时合适.
- **一组纯函数**, 作用于普通数据类型. 没有隐式的当前状态, 只有转换时合适.
- **一个有清晰方法面的 class 或模块**, 当逻辑确实拥有持续的内部状态时.

选 _最适合所问问题_ 的形状, 而不是最容易接到页面上的形状. 保持纯粹: 不碰 DOM, 不碰 `document`, 按钮 handler 不伸进它内部. 页面调用它; 反方向没有任何流动.

### 3. 构建可分享的 HTML 文件

一个文件, 纯 HTML/CSS/JS: 无框架, 无打包器, 无服务器, 全部内联, 双击即开, 经得起邮件转来转去. 任何人打开它就能跑.

为非开发者而写. 每个标签都用 **领域语言**, 不用代码语言: 按钮和状态读起来像业务, 不像 reducer. 文案写法遵循 [UI.md 的「设计中的写作」](UI.md#设计中的写作).

自上而下, 层次清晰地布局:

1. **标题和一句话说明** 这个 demo 让你探索什么 (第 1 步的问题).
2. **当前状态**: 全部相关状态渲染成可读的面板 (带标签的字段, 不是裸 JSON dump), 每次点击后重新渲染, 让变化可见. 有助于非开发者跟随时, 点出刚刚变了什么.
3. **自由摸索按钮**: 每个动作一个按钮, 始终可用, 任何人可以按任意顺序戳这个模型. 每次点击 dispatch 对应动作并重新渲染状态.
4. **引导式走查**: 一组 **场景**, 每个页签一个. 每个页签放一段平实语言的场景描述 (它设定的处境, 要留意什么), 下面是这个场景 **要按的按钮**, 按序排列. 每一步都是真按钮: 点击即执行该动作并前进到下一步. 开始一个走查会重置到已知的初始状态, 让场景每次都以同样方式运行.

选那些展示别扭用例的场景 — 纸面上难以推理的那些: 快乐路径, 刁钻的边界情况, 一次理应非法的尝试.

保持美观但克制: 干净的字体排印, 大方的间距, 一个点缀色. 不要动画, 不要噱头: 任何东西都不得与状态和按钮争夺注意力.

### 4. 交出去

把文件发给他们, 或当面打开. 他们得空会自己点完走查和自由摸索; 最有意思的时刻是他们说 "等等, 这不应该是可能的" 或 "咦, 我以为 X 会不一样" — 那些是 _想法_ 里的 bug, 而这正是全部意义. 他们想加新动作或新场景, 就加. 原型会演化.

### 5. 捕获答案和原型

按 [SKILL](SKILL.md) 的「按证据收口」与「捕获与交付」规则记录结果并归档完整 HTML, 保留可重跑的实验依据.
