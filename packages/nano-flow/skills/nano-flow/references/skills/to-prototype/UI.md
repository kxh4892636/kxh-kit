# UI 原型

在同一条路由上生成 **数个截然不同的 UI 变体**, 通过底部浮动栏切换. 用户在浏览器里来回翻看, 选定一个 (或从每个变体里各取一部分), 然后把其余的扔掉.

如果问题关乎逻辑/状态而非外观, 走错分支了, 使用 [LOGIC.md](LOGIC.md).

## 什么时候是这个形态

- "这个页面应该长什么样?"
- "定下来之前, 我想先看几个 dashboard 方案."
- "给设置页试一种不同的布局."
- 任何用户原本要在脑子里对着三个模糊 mockup 纠结一天的场合.

## 两种子形态: 强烈偏好子形态 A

UI 原型 **贴着应用其余部分** 时才容易判断: 真实的 header, 真实的 sidebar, 真实的数据, 真实的密度. 孤立的一次性路由是真空环境: 每个变体单独看都挺好. 只要存在可以承载变体的现成页面, 默认子形态 A; 确实没有邻近的归宿时才用子形态 B.

### 子形态 A: 挂在既有页面上 (首选)

路由已存在. 变体渲染在 **同一条路由** 上, 由 `?variant=` URL search param 门控. 既有的数据获取, params 和鉴权全部保留, 只替换渲染. 这是默认选项; 除非有具体理由, 都选它.

如果原型对应的东西还没有页面, 但 _自然会长在某页面内部_ (dashboard 的新区块, 设置页的新卡片, 既有流程的新步骤), 仍然是子形态 A: 把变体挂载进宿主页面.

### 子形态 B: 新建页面 (最后手段)

仅当被原型化的东西确实没有可栖身的现成页面时使用 (例如全新的顶层界面, 或无法合理嵌入任何地方的流程).

遵循项目已有的路由约定创建 **一次性路由**, 不要发明新的顶层结构. 命名上要一眼看出是原型 (例如在路径或文件名中包含 `prototype`). 同样使用 `?variant=` 模式.

采用子形态 B 之前先 sanity check: 真的没有任何现成页面可以嵌入吗? 空路由会隐藏设计问题, 而填充了真实内容的页面会暴露它们.

两种子形态的底部浮动栏完全相同.

## 设计原则

以小型工作室设计负责人的心态对待每个变体: 这家工作室以给客户做出绝不会与任何人混淆的视觉识别而闻名. 客户已经否掉过模板感的提案, 花钱买的是独特的观点: 针对这个简报, 在配色, 字体和布局上做出深思熟虑, 有主张的选择, 并承担一处能自圆其说的真实美学冒险.

### 立足于主题

简报没有钉死产品或主题时, 动手设计前自己先钉死: 说出一个具体的主题, 它的受众, 以及这个页面唯一的职责, 并说明你的选择. 记忆中关于用户偏好的任何信息, 他们正在构建的东西的上下文, 或你以前做过的设计, 都可以用作提示. 独特选择来自主题自己的世界: 它的材料, 工具, 造物与行话. 全程用简报的真实内容和主题素材来构建.

### 设计准则

Web 设计的 hero 是一个论点. 用主题世界里最有特征的事物开场, 形式不限: 一句标题, 一张图, 一段动画, 一个 live demo, 一个互动瞬间. 选择要刻意: 大数字配小标签, 辅助统计加渐变点缀是模板答案, 只有确实最优时才用.

字体承载页面的个性. display 与 body 字体的搭配要刻意, 而不是任何项目都会伸手用的那几套; 设定清晰的字阶 (type scale), 字重, 字宽和间距都要有意图. 让字体处理本身成为设计中令人记住的部分, 而不是内容的中性运输工具.

结构即信息. 结构性手段 — 编号, eyebrow, 分隔线, 标签 — 应编码内容里真实存在的东西, 而不是装饰. 许多泛泛的设计使用编号标记 (01 / 02 / 03), 但只有内容确实是序列时才合适, 例如真实的流程, 或顺序承载着读者所需信息的时间线. 采用编号标记这类选择之前, 先质疑它是否真的成立.

刻意地使用动效. 想清楚动效在哪里, 以及是否服务于主题: 页面加载序列, 滚动触发的揭示, 悬停微交互, 环境氛围. 一个编排过的瞬间通常比散落的特效更有力; 按方向所需选择. 但有时少即是多, 过多的动画会贡献 "这设计是 AI 生成的" 的感觉.

让复杂度匹配愿景. 极繁方向需要繁复的执行; 极简方向需要在间距, 字体和细节上的精确. 优雅就是把选定的愿景执行好.

认真对待文案. 设计简报常常不包含真实内容, 文案要你来写. 文案可以让设计感觉和设计本身一样模板化. 详见下文 "设计中的写作".

## 流程

### 1. 写下问题, 定下 N

默认 **3 个变体**. 超过 5 个就不再截然不同, 开始变成噪音, 以此为上限.

在原型所在位置或文件顶部注释里, 用一行写下计划:

> "设置页的三个变体, 在既有 `/settings` 路由上通过 `?variant=` 切换."

无论用户是否在场, 这行计划都能让他随时反驳.

### 2. 为每个变体构思设计计划

先校准: 当前 AI 生成的设计聚集在三种长相上 — (1) 暖奶油色背景 (接近 #F4F1EA) 配高对比衬线 display 字体和赤陶色点缀; (2) 近黑背景配单一的酸性绿或朱红亮色点缀; (3) 大报 (broadsheet) 风格版式, 发丝级细分隔线, 零圆角, 报纸般的密集多栏. 三者对某些简报都合法, 但它们是默认值而非选择, 而且不分主题地出现. 简报钉死了视觉方向时, 严格照做 — 简报自己的话永远优先, 包括它点名要这三种长相之一时. 简报留白的轴, 不要花在默认值上. 就像被雇佣的人类设计师, 做擅长的事和把每个项目当作实验与学习的机会之间, 常常需要仔细平衡.

分两步走. 第一步, 基于简报为每个变体构思一份简短的设计计划 — 一套紧凑的 token 系统, 含色彩, 字体, 布局和签名元素:

- **色彩**: 4–6 个命名 hex 值描述的调色板.
- **字体**: 2 个以上角色的字体 (有性格的 display 字体, 克制地使用; 互补的 body 字体; 需要时再为 caption 或数据配一个 utility 字体).
- **布局**: 一个布局概念, 用一句话的散文描述和 ASCII 线框图来构思和比较.
- **签名元素**: 这个页面将被记住的唯一独特元素, 以恰当的方式体现简报.

构建之前, 把计划对照简报再审一遍: 任何部分读起来像你为任何类似页面都会产出的通用默认值时 (可以拿一个类似 prompt 走一遍, 看是否殊途同归), 而不是为这个具体简报做的选择 — 修订它, 并说明改了什么, 为什么. 确认设计计划的相对独特性之后, 才开始写代码.

尽量把构思和迭代放在思考里完成, 只在有较高把握能取悦用户时才把想法亮出来.

### 3. 生成截然不同的变体

严格按修订后的设计计划实现每个变体, 每个颜色和字体决策都从计划中推导. 每个变体要对得起:

- 页面的目的和它能访问的数据;
- 项目的组件库 / 样式体系 (TailwindCSS, shadcn, MUI, 纯 CSS, 无论什么);
- 清晰的导出组件名, 例如 `VariantA`, `VariantB`, `VariantC`.

变体之间必须 **结构上不同**: 不同的布局, 不同的信息层级, 不同的主要可供性 (affordance), 而不只是颜色不同. 三个微调的卡片网格不是 UI 原型, 是壁纸. 两个草稿太像时, 带着明确的 "不许用卡片网格" 式约束重做一个.

写代码时注意 CSS selector 的优先级 (specificity) 结构. 很容易生成互相抵消的 CSS class (尤其是 `.section` 这类按类型命中的选择器和 `.cta` 这类按元素命中的选择器叠加时), 在 section 之间的 padding/margin 上经常发生.

### 4. 接在一起

在路由上创建一个切换组件:

```tsx
// 伪代码, 按项目框架适配
const variant = searchParams.get("variant") ?? "A";
return (
  <>
    {variant === "A" && <VariantA {...data} />}
    {variant === "B" && <VariantB {...data} />}
    {variant === "C" && <VariantC {...data} />}
    <PrototypeSwitcher variants={["A", "B", "C"]} current={variant} />
  </>
);
```

子形态 A (既有页面): 把既有的数据获取全部保留在切换逻辑之上, 只有渲染的子树随变体变化.

子形态 B (新建页面): `/prototype/<name>` 下的一次性路由挂载同一个切换器.

### 5. 构建浮动切换栏

固定在屏幕底部中央的小条, 由三部分组成:

- **左箭头**: 循环到上一个变体 (回绕).
- **变体标签**: 显示当前变体 key; 变体导出了名字时也显示名字, 例如 `B (Sidebar 布局)`.
- **右箭头**: 循环到下一个变体 (回绕).

行为:

- 点击箭头更新 URL search param (使用框架的 router, 例如 Next 的 `router.replace`, React Router 的 `navigate` 等), 让变体可分享, 刷新后稳定.
- 键盘: `←` 和 `→` 方向键同样切换. 焦点在 `<input>`, `<textarea>` 或 `[contenteditable]` 上时不要拦截方向键.
- 视觉上与页面区分开 (例如高对比度的胶囊形加柔和阴影), 让人一眼看出它不属于正在被评估的设计.
- 在生产构建中隐藏: 用 `process.env.NODE_ENV !== 'production'` 或等价检查门控, 防止误并原型把切换栏发给用户.

切换栏做成单一共享组件, 让两种子形态复用; 放在项目里共享 UI 所在的位置.

### 6. 交出去

把 URL (以及 `?variant=` 的各个 key) 亮出来. 用户得空就会翻看. 最有意思的反馈通常是 **"我想要 B 的 header 配 C 的 sidebar"**, 那才是他们真正想要的设计.

### 7. 捕获答案并清理

某个变体胜出后, 捕获答案 (哪个变体, 为什么), 然后按 [SKILL](SKILL.md) 所述捕获原型. 把胜者折入真实代码, 其余的移到一次性分支, 不进 main:

- **子形态 A**: 胜者折入既有页面; 落选变体和切换栏从 main 移除.
- **子形态 B**: 胜出变体提升为正式路由; 一次性路由和切换栏从 main 移除.

整套变体是 primary source, 所以它落在一次性分支而不是垃圾桶: 留在 main 分支里的变体组件和切换栏腐烂得很快, 还会迷惑下一个读者.

## 克制与自我批判

把大胆花在一个地方. 让签名元素成为唯一令人记住的东西, 它周围的一切保持安静和克制, 砍掉不服务于简报的装饰. 不冒险本身也是一种风险. 默默达到质量下限而不声张: 响应式直到移动端, 可见的键盘焦点, 尊重 reduced motion. 构建过程中持续批判自己的作品, 环境支持就截图 — 一图抵千 token. 想想 Chanel 的建议: 出门前照照镜子, 摘掉一件配饰. 人类创作者有记忆, 总是尝试新东西; 如果有可以快速记下尝试过什么的地方, 它会在后面的迭代里帮到你.

## 设计中的写作

文字出现在设计里只为一个原因: 让它更容易被理解, 因而更容易被使用. 文字是设计材料, 不是装饰. 对文案投入与间距和色彩同等的刻意. 动笔之前先问: 这个设计需要说什么, 怎样说才最有助于使用者 navigate 整个体验.

从终端用户的屏幕一侧来写. 用人们控制和认知的名字称呼事物, 绝不用系统的构建方式. 人管理的是通知, 不是 webhook 配置. 用平实的话说清某件事做什么, 而不是推销它. 具体永远好过抖机灵.

默认使用主动语态. 一个控件要确切说出使用后会发生什么: "保存更改", 而不是 "提交". 一个动作在整条流程里保持同一个名字, 写着 "发布" 的按钮, 产出的 toast 就写 "已发布". 界面的词汇表是人们在产品里认路的路标, 连贯与一致是人们学会认路的方式.

把失败和空态当作给出方向的时刻, 而非渲染情绪. 用界面自己的声音解释出了什么错, 怎么修. 报错不道歉, 也绝不含糊发生了什么. 空屏是一份行动邀请.

保持对话式的语域并调好音: 平实的动词, sentence case, 无填充词, 语气匹配品牌与受众. 让每个元素只做一件事: 标签负责标注, 示例负责演示, 没有任何东西悄悄身兼二职.

## 反模式

- **变体只在颜色或文案上有差异.** 那是微调, 不是原型. 真正的变体在结构上有分歧.
- **变体之间共享太多代码.** 共享一个 `<Header>` 没问题; 共享 `<Layout>` 就违背了初衷. 每个变体都应该有扔掉整个布局的自由.
- **把变体接到真实 mutation 上.** 只读原型就够了. 变体确实需要变更数据时, 指向 stub: 问题是 "这应该长什么样", 不是 "后端能不能工作".
- **把原型直接提拔进生产.** 变体代码是在原型约束下写的 (无测试, 错误处理从简). 折入时正式重写.
